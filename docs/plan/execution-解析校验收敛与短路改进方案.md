# Execution 解析小改进方案：双向校验收敛与解析短路

## 一、背景

统一寻址整改（见 checkpoint-execution-id-统一寻址整改方案.md）落地后，代码审查发现两个非阻塞的实现问题：

1. wf-server 的 agent 侧与 workflow 侧各持有一份镜像的"按 checkpoint entity_type 拒绝跨域 checkpoint"逻辑，仅分支方向相反，属重复代码；
2. 解析函数对每次解析固定执行 agent 侧与 workflow 侧各最多三次查询（活跃注册表、持久化记录、checkpoint 分区），共最多六次，且无法短路——server 热路径上的 chain 查询每次都要付出全部成本。

本方案只做结构性收敛与查询短路，不改变任何对外语义。

## 二、改进任务

### 任务一 双向校验收敛至 wf-api

将 agent 侧与 workflow 侧的 checkpoint 归属拒绝逻辑合并为 wf-api checkpoint 记录层的一个校验函数：入参为 checkpoint id 与期望域，内部读取 checkpoint 记录，归属域与期望域一致时放行，不一致时返回携带实际归属域的 Validation 错误（提示使用对应域的端点），记录不存在时返回 NotFound。

两侧 server handler 改为调用该函数，删除本地镜像实现。错误消息文案保持现状不变，前端与测试无感。

### 任务二 解析查询短路

当前实现先查完 agent 侧三处、再查 workflow 侧三处，两侧独立判断后再合成结论，因此任一侧命中都无法跳过另一侧——这是双命中歧义检测的必要代价，不能简单删除。

改进方式是重排查询顺序、按代价递增并在命中低成本来源时先记录：

- 第一层：agent loop 活跃注册表与 workflow execution 活跃注册表各查一次（内存操作，代价最低）；
- 第二层：两侧持久化记录各查一次（存储查询）；
- 第三层：两侧 checkpoint 分区各查一次（仅在前两层均未命中时执行，因为 id 若在注册表或持久化记录中已出现，checkpoint 分区的信息不改变结论——结论是"该域存在"，双命中与否只取决于另一域）。

短路规则：当两侧在第一、二层内已得出"恰好一侧存在"的结论时，跳过第三层直接返回；仅当第一、二层均未命中或双命中时，才需要第三层参与区分（双命中时第三层结果已不影响裁决，可直接以第一、二层结论返回歧义错误，即双命中情形也短路）。

预期效果：常规路径（id 存在于持久化记录）由六次查询降为四次；id 存在于活跃注册表时降为四次；只有"幽灵 id"（仅存在于 checkpoint 分区，实体记录已清理）才走满六次，且这类情形本身罕见。

### 任务三 行为差异说明落文档

audit 的歧义回落策略（静默 agent 优先）与 checkpoint 命令的显式覆盖要求是有意为之的差异：前者是只读聚合视图，后者是变更操作。在 docs/api 相应文档中补充一段说明，写明两者的歧义处理策略及理由，避免后续维护者误认为不一致是缺陷。

## 三、验证与收尾

- 为解析顺序补充单元测试：仅活跃注册表命中、仅持久化命中、仅 checkpoint 分区命中三种来源各自正确解析；
- 为双向校验函数补充单元测试：一致放行、不一致拒绝并携带实际域、不存在返回 NotFound；
- 两侧 server handler 的既有行为由现有集成语义覆盖，错误文案不变；
- `cargo clippy --all-targets --all-features` 全量编译检查。

## 四、明确不做的事项

- 不改变 resolve 系列函数的签名与返回类型。
- 不引入解析结果缓存——歧义窗口与生命周期管理带来的复杂度超过收益。
- 不调整 audit 的回落策略。
