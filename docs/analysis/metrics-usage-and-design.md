# Metrics 使用情况与设计分析

## 使用现状

指标系统以 `wf-metrics` 为中心，向上游执行引擎提供统一埋点，向下游运行时提供持久化与导出。

核心结构分为四层：基础采集层负责计数器、仪表、直方图与摘要的内存记录与查询；领域采集层为工作流、节点、智能体、工具、令牌、错误、事件、资源、子图、模板、重试与超时等场景提供类型化记录接口；注册表层统一持有全部领域采集器并提供刷新、清理、恢复与报告订阅；持久化抽象层通过接收器接口与存储解耦，由运行时注入具体实现。

执行链路采用可选注入方式传递注册表。工作流与智能体执行上下文携带可选的共享注册表，工作流侧记录执行启停与节点执行，智能体侧记录执行启停、迭代与工具调用，语言模型网关记录令牌用量，事件总线通过桥接任务记录通用事件计数。运行时是唯一的装配点，负责按配置创建注册表、挂载存储接收器、恢复直方图状态、启动刷新与清理任务、采样进程资源与存储操作计数、按需生成报告。接口层提供统计查询与历史合并查询，服务层提供指标抓取与查询接口。配置分为全局开关、保留窗口、报告开关、异常阈值与各采集器参数，由配置模块合并默认值后下发。

## 设计评价

优点在于写入路径针对高并发优化，百分位计算延迟到读取时，持久化可恢复分布状态，重试队列有界且可观测，全局禁用时无额外开销，存储解耦保持依赖方向正确。

不足在于五个方面。基础库反向依赖基础设施层，事件桥接放在基础库导致分层倒置。注册表一次性创建全部采集器，分采集器缺少启用开关与保留窗口配置，空闲采集器仍占用内存结构。注册表与运行时各持一套后台刷新清理任务，职责重复且易误用。令牌采集器以值传递而非共享引用传递，与其他路径不一致；检查点指标自成体系未纳入统一语义；资源采样存在占位零值序列。标签校验失败与未知指标类型静默丢弃，仅靠日志难以在监控中发现。

## 整改方向

首先纠正分层，将事件桥接从基础库迁移至已同时依赖事件总线与指标库的执行共享层，基础库移除对指标库的依赖，运行时与接口层更新引用路径。

其次补齐采集器配置语义，为分采集器补充启用开关与保留窗口，禁用状态下记录路径直接返回而不产生序列与持久化开销，保留窗口未配置时沿用全局保留窗口。

然后消除重复后台任务，注册表仅保留同步刷新清理能力，后台周期任务收归运行时统一拥有，避免双重刷新与双重清理。

再统一指标接入语义，令牌采集器改为共享引用传递以保证与注册表同一状态，资源采样取消占位零值序列以避免污染存储，检查点指标保持独立但明确其操作级定位而不混入执行语义。

最后消除静默丢数，对标签拒绝与空指标名计入自监控计数并保留日志，对未知持久化类型在查询转换时告警并跳过，保证问题可在内部指标与日志中被发现。
