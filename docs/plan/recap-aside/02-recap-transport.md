# 阶段 2 与阶段 3：传输与前端

## 阶段 2：服务端路由与 `web-app`

### 服务端路由

在 `wf-server` 为阶段 1 的读取面加薄传输：路由、鉴权、envelope 全部沿用同域既有写法。
约定三条：响应恒为成功 envelope，用「文本有无」区分「无可回顾内容」与「失败」（失败也只是无文本，
不回错误气泡）；不另加比旁路超时更短的 HTTP 超时；回合进行中也可请求（只读快照），
节流由前端「每回合最多一次」承担，服务端不做拒绝。

### `web-app` 接入

- 请求：与现有执行类请求同形的 POST 调用，返回可空文本；非成功、空文本一律视为无 recap。
- 触发判定：与快照三信号同构，只用浏览器可得信号——本回合耗时超阈（120 秒量级）、
  本回合内页面隐藏过、最后一条回答溢出一屏。判定抽为纯函数并单测（短且盯着则否，其余三信号各为是，
  开关关闭则否）。仅在正常自结束的回合后触发；目标/循环自主回合不触发。
- 竞态：每回合自增 ticket，在途请求可被新回合、切会话、重载 abort，结果回来时 ticket 已变则丢弃。
- 渲染：临时注记项，只存在于前端 state，不进历史来源、不持久化、不参与滚动锚点历史计算，
  切会话、重载、fork 后消失，前缀与弱化样式与设计语言一致。
- 手动命令：composer 加 `recap` 命令，调用同一请求面；手动路径不受自动开关约束，无结果时静默。

### 验收

请求面三种响应（有文本、无文本、失败）都收敛为「显示或不显示」；判定纯函数用例与快照对齐；
竞态用例（在途切会话、旧文本不得插入）；recap 项不进入历史数组；手动命令有无文本两条分支。
门：前端类型检查与构建、`cargo nextest run -p wf-server`。

## 阶段 3：`wf-tui` / `wf-mini` 与显示开关

- 触发判定：把终端可得信号（回合时长、焦点离开、回复折行超一屏）抽为与阶段 2 同形的纯函数，
  门槛语义对齐。只在正常自结束终态触发；目标/循环自主运行与非 root 会话不触发。
- 竞态：沿用 ticket + 中止在途任务的做法，新回合、新提交、切会话、切屏幕都使旧结果作废。
- 渲染：回答下方一行弱化注记，续行与前缀对齐；resume 重放不出现。
- 手动命令：会话命令加 `recap`，走同一读取面，有文本则同一样式落屏，无文本则静默。
- 显示开关：`wf-config` 显示旋钮只读接入（`web-app` 缺省按 true 处理以兼容旧服务端）；
  写入口（若需要）另立评审，不在本阶段做。

### 验收

判定纯函数用例与阶段 2 对齐；迟到结果不贴到新回合；在途任务可被丢弃；
开关关闭时自动注记消失但手动命令仍可用。门：相关 TUI crate 的 nextest 与全仓 clippy / fmt。
