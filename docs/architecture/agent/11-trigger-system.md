# 三系统模型：同步钩子、审批门禁、异步触发

本文描述 Rust 实现现状，是钩子与触发器章节的权威说明。类型在 `wf-types/trigger` 与
`wf-types/hook`，监听核心在 `wf-workflow/trigger`，动作执行器在
`wf-runtime/trigger_listener`，钩子同步发射管线在 `wf-execution-shared/hooks`。

三系统各有唯一职责：同步钩子做观察与执行前的同步门禁（处理器 `Veto`）、审批门禁做工具调用的人工把关与改写、异步触发做事后副作用。

## 1. 三系统总览

* 同步钩子（sync hook）：引擎在钩子点同步通知已注册的处理器（毫秒预算，引擎等待全部处理结果）。
  处理器默认只做观察；在门禁点（`BEFORE_EXECUTE` / `BEFORE_TOOL_CALL`）可返回 `Veto` 拒绝被守护
  的节点/调用（fail-open：超时与未注册按继续处理），改写入参仍不属钩子能力。每次发射另行发布一条
  `HOOK_TRIGGERED` 审计事件，该事件是持久化与可观测副本，不承载功能投递。
* 审批门禁（approval）：工具调用的人工把关与参数改写。需要向用户征求同意或改写入参时走审批；
  纯程序化的执行前拒绝也可由钩子处理器的 `Veto` 承担。
* 异步触发（async trigger）：监听器消费事件总线上的事件，按模板条件匹配后异步执行副作用
  （重试、跨执行访问、延迟容忍的动作）。触发动作永远在事件之后运行，不能阻断或门禁当次执行。

钩子配置有四种形态（工作流侧 `HookPointConfig`、代理侧 `AgentHookConfig`、静态序列化侧
`HookPointStaticConfig`、工具回调侧 `HookConfig`），全部收敛到 `wf-types/hook.rs` 的权威模型
`CanonicalHookSpec`：其余形态只做薄转换，校验只有 `validate_canonical_hook` 一个入口。
工具侧独有的 `parallel` / `continue_on_error` 不进入权威模型。

## 2. 五条加载期规则

以下规则在加载期即有确定结论，违反即拒绝或告警，不延迟到运行时：

1. 默认唯一订阅：同一竞争域（事件类型 + 二级事件名 + 可重叠的执行前缀）默认只允许一个订阅者，
   第二个订阅者是加载期配置错误。
2. 竞胜显式优先级：同一竞争域需要多个订阅者时，必须显式声明 `best_win` 派发模式，
   且域内每个订阅者都要声明互不相同的显式优先级，胜者为优先级最高者。不存在隐式排序：
   注册顺序、条件特异性都不参与胜负判定。
3. 前置订阅拒绝：触发模板订阅 `BEFORE_*` 钩子点（经 `HOOK_TRIGGERED` 审计事件）在加载期被拒绝，
   监听器运行时同样跳过。触发动作永远在钩子点之后异步执行，不能做前置门禁；执行前的同步拒绝请用
   钩子处理器的 `Veto`（`BEFORE_EXECUTE` / `BEFORE_TOOL_CALL` 门禁点），事后副作用请订阅对应的
   `AFTER_*` 点或对等领域事件。钩子名直接作 `event_type` 也是类别错误
   （钩子发射只发布 `HOOK_TRIGGERED`，钩子名事件永不存在），同样在加载期拒绝。
4. 压缩信号拒绝：内部压缩信号（`CONTEXT_COMPRESSION_REQUESTED` 直接订阅或经审计副本间接订阅）
   在加载期被拒绝。压缩路径由内置压缩服务同步接管，事件副本只是审计拷贝，不得驱动功能动作。
5. 启动有序、完成无序：同一钩子点的同步处理器先全部落定，再发布 `HOOK_TRIGGERED`
   审计事件，匹配该事件的触发模板总是在处理器之后启动；但引擎不等待触发动作完成，
   触发完成相对引擎下一步无序。两条路径都配置时只适用于两者效应可交换的场景，
   否则只保留一条；有对等领域事件时触发器优先订阅领域事件。

## 3. 选型对照

| 需求 | 用哪个系统 | 说明 |
|---|---|---|
| 观察一次调用 / 记录指标（不拦截） | 同步钩子处理器 | 毫秒预算，只读观察 |
| 执行前程序化检查、不通过即拒绝节点/调用 | 同步钩子处理器的 `Veto` | 仅 `BEFORE_EXECUTE` / `BEFORE_TOOL_CALL` 门禁点 |
| 工具调用的人工审批与改写入参 | 审批门禁 | 需征求用户或改写参数时走审批 |
| 事件发生后的副作用（通知、变量、子工作流、脚本） | 异步触发器 | 延迟容忍，失败只记日志 |
| 模型调用失败想介入重试 | 重试三件套（见第 7 节） | 观察走钩子、门禁走审批、事后走触发，不另设机制 |
| 压缩、子代理生命周期等内部信号 | 内置服务 + 同步钩子 | 不得用触发模板订阅 |

## 4. 条件语义与竞争域

条件字段包括事件类型、事件名、表达式、元数据相等组、元数据存在组与执行前缀，全部满足才算命中。

* 事件类型必须等于事件的标准名。
* 事件名仅 `NODE_CUSTOM_EVENT` 要求填写，其余按需作为二级区分。
* 元数据按与语义匹配：数值比较、前缀、数组包含（钩子审计事件的钩子类型数组命中其一即算命中，
  因此订阅单个钩子类型用纯字符串条件即可）。
* 表达式在事件字段加元数据合并后的上下文中求值，求值失败视为不命中。
* 执行前缀匹配事件的执行标识或回路标识之一。

竞争域键 = 事件类型 + 二级事件名，再按执行前缀是否可重叠划分。
元数据与表达式条件不进入域键：证明两个条件互斥一般不可判定，因此正交订阅也必须走显式
`best_win` + 互异优先级，而不是依赖推断的不相交。

## 5. 动作支持矩阵

权威矩阵见 `TriggerAction::supported_in`，两执行上下文对照如下。
校验入口为 `validate_trigger_action_for_context`，模板上下文固定为事件监听器；
节点内不支持的动作保持拒绝，报错文案统一并给出替代路径。

| 动作 | 事件监听器 | 消息节点（同步执行） |
|---|---|---|
| 停止、暂停、恢复执行 | 支持 | 支持 |
| 跳过节点 | 支持 | 支持 |
| 设置变量、发送通知 | 支持 | 支持 |
| 执行被触发子工作流 | 支持 | 支持（同步或派生） |
| 执行脚本 | 支持 | 支持 |
| 设置、追加消息上下文 | 支持 | 支持 |
| 执行被触发 Agent | 支持 | 拒绝（子执行需要触发事件携带的会话锚点，请改用执行被触发子工作流） |

被触发 Agent 为异步注入语义：子回路基于父会话在触发锚点处的快照运行，结果经版本校验写回，
父回路在下一次大模型请求时可见，父回路永不阻塞等待子回路。

同一事件的多副作用默认不开启：保持单胜者单执行。未来多执行必须是显式声明
（`allow_multi_effect`）加显式顺序（`effect_order`），且被声明的效应必须可交换；
声明只做校验，运行时仍单执行，直到有序多执行设计落地。

## 6. 触发源

仅事件驱动已实现。定时与 Webhook 为类型占位，使用时在加载期给出明确未实现提示，不做静默丢弃。

未来生产者接入契约：调度器与外部事件网关只负责把外部信号翻译为已有事件类型，
翻译入口为 `TriggerSource::translate_schedule_to_condition` /
`translate_webhook_to_condition`（统一译为 `NODE_CUSTOM_EVENT` 加二级判别名），
复用现有竞争域键与集合校验，不新增竞争维度。

职责边界（生产者只管信号，不管匹配与执行）：

* 调度器拥有时间：cron 解析、tick 循环、misfire/追赶策略、随监听器关闭；
* 网关拥有进入：HTTP 路由、鉴权、执行路由（定位已有执行或拒绝无归属进入）；
* 双方都必须发布携带 `execution_id` 的执行域事件——监听器丢弃无执行标识的事件，
  且每个触发动作都定位到 emitting execution。

更深一层缺口：执行创建式调度（“每晚全新跑一次 W”）今天表达不了——它需要先新增
创建式触发动作，现有动作全是“定位到 emitting execution”。可先装运的一步是
执行域定时/进入（挂在某执行上的 timer 与 ingress），翻译契约已就绪，缺的只是生产者。

## 7. 重试介入点

模型调用失败重试不设第四种机制，复用三系统，顺序固定为
预算 → 钩子观察 → 审批门禁 → 尝试 → 异步触发（见 `RETRY_INTERCEPTION_ORDER`）：

1. 预算：`RetryBudget` / 重试策略先判定容量；
2. 钩子观察：`on_retry` 回调同步发射 `RetryAttemptDescriptor`
  （`attempt` / `max_retries` / `delay_ms` / `reason`）；
3. 审批门禁：需要拦停重试时由审批机制做门禁；
4. 尝试：退避延迟后执行下一次调用；
5. 异步触发：`LLM_RETRY_SCHEDULED` 事件（与描述子相同的元数据键）供触发模板做事后处理，
   预算消耗经共享预算的事件回调上报。

订阅 `LLM_RETRY_SCHEDULED` 的模板按普通事件模板校验（该事件不是 `BEFORE_*`，不受前置订阅拒绝影响）。

## 8. 并发门限与熔断

`TriggerRuntimeLimits`（缺省为无界，保持历史行为）：

* `max_concurrent_actions`：并发执行的触发动作上限，按副作用占用的工作槽位数调优
 （IO 型动作一般取 8~32；下游是共享数据库或限流 API 时调低）。
* `dispatch_burst_limit`：单个事件执行的胜者上限；缺省保持单胜者语义，
  显式配置后才允许多胜者扇出。

超限一律告警加丢弃，不静默排队。

## 9. 可观测性

* 空发射分级日志（`empty_fire_log_level`，只读）：可观察钩子空发射打 DEBUG（零订阅者合法，
  不发布审计事件）；请求 / 变更型钩子空发射打 WARN（缺处理器必须可见）。
* 订阅清单查询（`summarize_subscriptions` / `query_subscriptions`，只读）：
  支持按事件类型与二级判别名检索模板订阅关系。
* 审计查询（`AuditEventFilter`，只读）：至少支持按执行标识（同时覆盖执行标识与回路标识）
  与事件类型过滤审计事件。

以上均为只读视图，不改变执行语义。

## 10. 配额与作用域

触发次数上限按执行标识与模板名组合计数，并发执行互不挤占；同对重入由在途守卫防止重复进入。
压缩类内部在途子工作流随监听器关闭而中止，不做恢复。
