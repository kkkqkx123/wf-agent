# 备份链路的错误处理

## 一、总体原则

备份链路遵循“失败大声、成功可校验、状态可观测”：

* 远端返回错误或数据不完整时不落盘、不登记索引、不推进到期时间、不触发裁剪。
* 单个执行失败只影响自身；同批次其他执行和其他后端继续。
* 状态按后端加执行记录，失败保留上次成功时间，下一周期自然重试。
* 关键失败同时进入日志和后端状态，查询接口能看到最后一次错误。

## 二、分阶段处理

| 阶段 | 失败情形 | 当前处理 |
|---|---|---|
| 配置加载 | `backends.toml` 存在但非法 | 启动失败，不用默认值静默覆盖 |
| 配置加载 | 未配置 `backup_dir` | 不启动备份循环；手动触发返回“backup directory is not configured” |
| 存储打开 | `backends.db` 或指定库打不开、损坏 | 后端域启用时启动失败并给出路径；不再静默降级为内存索引，避免写盘无索引的无管理备份 |
| 注册表读取 | 备份轮读取条目失败 | 记告警，设置顶层 `backup_round_error`，跳过本轮；不当作空注册表 |
| 隧道 | 本地端口被占用、ssh 启动失败或早期退出 | 启动接口直接报错；异常退出只标记中断原因，不自动重启 |
| 探测 | 端口不通、健康失败、`apiVersion` 不一致 | 该条目记为不可达，单项失败不影响其他条目 |
| 拉取 | 连接失败或超过配置超时（默认 15 秒） | 返回传输错误，记入该执行的 `backup_error` |
| 拉取 | 响应体超过配置字节上限（默认 64 MiB） | 在读回阶段拒绝，返回失败；不进入 JSON 解析 |
| 拉取 | 非 2xx、错误信封、`success=false` | 解析错误信封消息并返回失败，不写任何文件 |
| 拉取 | `data` 缺失、`bundle` 或 `checkpoints` 不是对象 | 按响应结构不完整处理，返回失败 |
| 拉取 | 执行 id 与请求不一致 | 按数据串扰处理，返回失败 |
| 落盘 | 建目录、创建临时文件、写入、文件同步、改名、目录同步失败 | 清理临时文件，返回失败；不写索引；目录同步失败只记告警 |
| 索引 | 索引写入失败 | 删除已发布文件，返回失败；避免未登记备份 |
| 裁剪 | 索引删除失败 | 记告警，保留文件，不返回失败 |
| 裁剪 | 文件删除失败 | 索引已先删除，只记告警，不留下指向缺失文件的记录 |

## 三、状态与可见性

管理端在内存中维护每个“后端 + 执行”的最后成功时间、最后一次错误与连续失败次数：

* 成功时更新成功时间、清空错误并把失败次数归零。
* 失败时保留原成功时间、已确认修订号和备份 id，写入错误并累加失败次数；不会把失败伪装成成功，也不会把未知基线误判为远端版本变化。
* 后端视图按后端聚合：成功时间取该后端所有执行中的最大值，错误去重后合并展示。
* 服务重启后内存中的运行状态清空，但持久同步状态与索引中该目标的最大创建时间会兜底到期判定和版本比对，因此不会全量并发拉取。

可见入口：

* `GET /api/v1/system/backends` 的每行 `last_backup_ms`、`backup_error`，以及顶层 `backup_round_error`。
* `GET /api/v1/system/backends/{name}/backups` 与 `GET /api/v1/system/backups` 的索引记录。
* 日志中的备份失败、裁剪失败、注册表读取失败与隧道退出告警。
* `wf remote status` 展示每行的备份时间和错误，以及顶层 `backup_round_error`；`wf remote backups` 展示索引与校验值，`wf remote sync-state` 展示每目标持久位点、远端状态与最近错误。
* `/metrics` 导出备份成功/失败、耗时、字节数、校验失败、裁剪与对账（缺失、孤儿、摘要不一致）指标，供抓取与告警使用。

手动触发 `wf remote backup-now` 的错误会经管理端接口返回：后端不存在是 404，执行失败按服务端执行错误返回，CLI 直接呈现客户端错误。手动拉取 `wf remote pull` 中，bundle、检查点链和写文件任一步失败都会终止，不再把检查点缺失静默写成空值。

## 四、重试与恢复

* 计划备份没有独立重试队列；失败任务等待下个调度周期再次到期，并按连续失败次数指数退避，上限为四个翻倍周期。
* 手动触发可立即重试，且复用同一套校验与落盘逻辑；与定时任务按目标串行化。
* 隧道异常退出后需要人工执行 `remote up` 重建；备份不会自动拉起 ssh。
* 备份的完整性可通过 `wf remote backup-verify ID` 复算摘要核查；结果区分文件缺失与内容变更。启动对账还会重算全部索引文件的摘要，新备份首次读回失败时其索引行和文件会被回滚。
* 读回路径为 `wf remote backup-export ID DEST` 加 `wf remote backup-check FILE [--expect-sha256 SHA]`：导出前服务端复验摘要与大小，客户端按原始字节落盘并再次复验，不符则拒绝写出。
* 恢复路径为 `wf remote backup-restore ID [--apply] [--replace]`：先由管理端复验本地快照，再由远端校验格式、归属、全部 checkpoint blob 可解码，然后判定目标状态。`absent` 新建，`identical` 直接返回 `noop` 且不写数据，`divergent` 需要 `--replace` 才覆盖；运行中的目标与归属其他目录的目标一律拒绝。默认 dry-run。远端恢复开关未开启时请求直接失败。应用成功后管理端采纳远端写入的序号与摘要，目标状态回到正常，不再在下一轮被判为内容损坏。
* `wf remote recover` 在上述单目标路径上做批量编排：只处理 `remote_missing` / `remote_corrupt`，按创建时间从新到旧遍历候选，取第一份复验与 dry-run 都通过的快照，默认 dry-run，单项失败只记录原因并继续；`--apply` 后重读 sync state 复核。恢复模式按状态选择：`remote_missing` 以新建方式恢复，`remote_corrupt` 以替换方式恢复；若目标实际已被重建，新建方式的 dry-run 会失败并按替换方式重试一次。它不拉起隧道，也不启动远端进程。
* `wf remote sync-reset --backend NAME --execution ID` 把单个目标标记为重新基线：清空持久序号与摘要并丢弃内存到期状态，下一轮忽略持久位点与本地快照序号，拉取一次新快照并采纳其位点；失败重试期间标记保持。不删备份、不动远端数据，也不触发裁剪。
* 存储打不开时启动失败，修复路径或权限后重启管理端；不再有静默内存模式。

## 五、已知边界

* 恢复快照的各部分来自一次导出流程。远端恢复把执行记录、检查点元数据与修订行放在同一个事务里，事务之外只有按 id 覆盖写的检查点 blob 与整体替换的文件归档；归档失败时目标行已是新值而归档仍是旧值，下一次比对会报告该差异，重放同一份快照即可收敛，不需要手工清理目标。
* 恢复快照包含完整检查点 blob 与执行上下文归档文件，但不含运行时会话、锁、凭据，也不重建工作区文件历史的全部引用状态。bundle 中的派生视图既不参与摘要，也不写回远端存储。
* 远端 API key 是管理端全局配置，不按后端条目区分。
* 多个管理进程共享同一备份目录时仍需外部保证唯一管理者，服务端不引入分布式锁。
* 备份文件读写放在阻塞任务池中执行，不会占用 tokio worker；响应体大小有可配置硬上限，超限快照直接失败，不包含裁剪后的部分检查点。
* 换 `backup_dir` 后新记录跟随新根目录；存量绝对路径索引仍可读，但要重写为相对路径需显式执行 `wf remote backup-relink --apply`。
* 错误通过日志、状态、接口和指标暴露，没有独立的告警推送通道。
* 管理端数据库与备份目录同时丢失时没有本地连接引用，无法自动从远端恢复；注册表配置需由外部保存。
