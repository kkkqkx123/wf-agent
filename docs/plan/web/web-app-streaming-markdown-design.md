# Web App 流式 Markdown 渲染设计方案（重写版）

> 范围：`apps/web-app`。目标：为 Agent 回路、工作流执行、LLM 生成三类场景引入流式 Markdown 渲染。状态：未开工。本文只描述选型、架构、映射与任务，不粘贴代码实现。

## 1. 背景与目标

三类输出均以增量 Markdown 文本为主：Agent 每轮的回复与工具结果与推理过程，工作流执行的节点日志与增量文本与错误分析，用户直调生成通道的流式生成。

三个要求：未闭合的代码块、表格、列表在流式中不闪烁不错位；高频增量不压垮主线程；支持代码高亮、图表、公式、推理折叠块。

## 2. 技术选型

渲染库选用 Svelte 5 原生的流式 Markdown 包（与 `markstream-svelte` 同类定位），理由：框架匹配，内部维护已提交与流式中双缓冲，未闭合结构保留在流式区；支持内容字符串直传与预解析节点两种输入；公式与图表能力可放入 Web Worker；自定义标签可注册为折叠组件。静态渲染库与手写拼接不满足中间态稳定要求，不采用。

已决策事项：渲染库选型即第 11 节旧开放点 O4 的结论，不再重议。

## 3. 后端通道（已核验）

`wf-server` 五个 SSE 端点均存在，与旧版描述一致：

| 端点 | 内容 |
|---|---|
| 生成流式通道 | 纯模型增量文本 |
| 回路流式通道 | 执行流事件，含模型增量、推理增量、工具起止、迭代起止 |
| 工作流执行流式通道 | 同回路，按类型路由到不同界面区域 |
| 事件流 | 基础事件，只做时间线元数据展示 |
| 错误分析流式通道 | 单段分析文本流 |

前端现有 `lib/api/sse.ts` 只覆盖事件流 get 通道；三个 POST 流式通道与错误分析通道均未接入，属剩余任务。

## 4. 架构分层

自下而上四层，职责划分：

- 传输层：POST 流式走可取消的流读取器封装（原生事件源只支持 GET），处理鉴权、限流、重连与断点续拉；GET 事件流沿用现有客户端。
- 解析层：帧解析与业务事件分类。兼容两种帧类型来源：协议层事件前缀与负载内事件名字段。
- 状态层：按会话维护消息列表，每条消息独立维护内容缓冲与待合并增量；模型回复与推理块分开维护，分区渲染。
- 渲染层：流式 Markdown 组件封装第三方包，对外只暴露内容文本、结束信号、主题三项；推理块与工具调用为独立业务组件，不经过 Markdown 语法。

限速策略：帧到达只写待合并增量，零解析开销；固定节拍批量合并进内容缓冲后触发一次重解析。节拍可调，默认取视觉流畅与主线程负载的折中值。

## 5. 帧到界面的映射

### 5.1 生成流

模型增量追加到当前助手消息缓冲；推理增量追加到推理块缓冲并渲染为折叠面板；用量帧更新计数；结束帧收敛未闭合结构并置结束态；错误帧写入错误态。

### 5.2 回路与工作流执行流

在生成流基础上加：工具起止帧新增与更新工具调用卡（待定、运行中、完成、失败四态）；迭代起止帧更新计数与折叠本轮内容；子代理起止帧做嵌套会话展示。

服务端最终文本到达时，可用其覆盖本地缓冲做确定性收敛。

## 6. 后端协议注意

生成流式通道的帧不带协议层事件前缀，类型在负载内字段承载；只有执行流首帧显式使用协议层事件。前端按兼容两种来源处理，不阻塞后端后续统一。

## 7. 与 TUI 端的关系

TUI 端已有成熟的流式解析器，采用同构的双缓冲加增量边界策略。两端不共享代码，但 Web 端可用 TUI 的保留规则（引用定义后置、表格不闭合、代码围栏检测）验证渲染正确性。

## 8. 剩余任务

按依赖顺序推进，每步都是可独立验证的增量：

- 传输与状态：POST 流式客户端、流存储、合并节流、取消与重连。
- 渲染组件：流式 Markdown 封装、推理折叠块、工具调用卡、迭代折叠容器。
- 通道对接：先调通生成流式通道，再对接回路与工作流执行流，最后接错误分析流。
- 增强（可选）：图表与公式 Worker 化、代码差异增强、断点续拉、多执行并行订阅。
