# code-context 集成现状与 cce-client 接入方案

本文说明 wf-agent 目前如何对接 CCE（code-context-engine），以及在 CCE 提供官方客户端 crate 之后如何改为
依赖该 crate（最终形式是通过 crates.io 依赖）。上游客户端的定位与边界见 CCE 仓库的
`docs/plan/client-crate-design.md`；本文只讨论 wf-agent 这一侧的现状、取舍与迁移动作。

## 一、现状：集成分层

`crates/infra/wf-integration/src/` 下的 `code_context` 子系统是唯一的对接点，其余 crate 只消费它的类型。

| 模块 | 职责 | 与 CCE 的关系 |
|---|---|---|
| `code_context.rs` | 配置与策略（`CodeContextConfig`：开关、传输、折叠、检索、项目供给）、托管组装（数据目录 + 服务端 TOML + 启动行） | 手写服务端配置格式与启动方式 |
| `code_context/project.rs` | 项目解析（列项目 → 规范化根路径匹配 → 缺失则创建）、首次全量索引、watch 启停 | 手写路径、请求体与响应解码 |
| `code_context/retrieval.rs` | 混合检索与 BM25 关键词检索的请求构造 + 结果归约 | 手写请求体；响应用"归约式消费"（从原始 JSON 取字段），字段缺失静默 |
| `code_context/navigation.rs` | 符号、引用、定义三个导航端点 | 同上 |
| `code_context/fold.rs` | 文件折叠批量请求与结果回写、候选选择、压缩边界提示 | 响应形状在本模块内自定义并按结构体严格解码（`FoldBatchResponse` 等） |
| `code_context/dead_letters.rs` | 死信列表、重试、确认 | 手写路径、请求体与响应解码 |
| `code_context/service.rs` | 活状态：端点、凭据、健康缓存、能力握手、项目状态机、维护入口 | 手写健康载荷解析与能力判据 |
| `transport.rs` | 打字化错误、按 origin 的断路器、请求标识、共享 HTTP 客户端与凭据、托管进程监督 | 手写 `/api/health` 解码；其余为本地策略 |

上游调用目前涉及 14 个端点：健康、项目列表/创建、项目索引、watch 启动、死信三件套、混合检索、关键词检索、
符号/引用/定义、折叠批量。CCE 的 graph / entity / storage / metrics / config 系列本集成不使用。

## 二、现状中的两类内容：有意设计 vs 被迫重复

**有意保留的本地能力**（不属于客户端职责，迁移后原样留下）：

1. 断路器与健康结论缓存：可用性是传输层属性，按 origin 维护，探测绕过断路器。
2. 能力握手：一次性判定"健康载荷可解码 + 项目端点存在"，不兼容不逐调用失败。
3. 项目与索引生命周期状态机：未解析 / 解析中 / 索引中 / 已就绪 / 失败，失败态保留项目 id；供给模式显式枚举。
4. 维护面语义分层：本地前置条件拒绝 vs 服务不可用。
5. 托管进程监督：单实例锁、重试相位、日志落盘与尾部告警、优雅停机。
6. 模型安全归约：检索/导航结果只暴露路径、行区间、片段等字段，内部 id 不越服务边界。
7. 折叠策略：候选筛选、token 门槛、批量上限、总预算、压缩边界提示。

**被迫重复的内容**（应由 client crate 承担，迁移后删除）：

1. 路径字面量与拼接（含项目作用域路径）。
2. 请求体字段名与结构（创建项目、索引、watch、死信、检索、关键词、导航、折叠）。
3. 响应字段名与解码严格性规则（缺字段算协议错误、未知字段忽略、数字 id 兼容十进制字符串）。
4. 凭据读取位置与认证头挂载。
5. 请求标识头与错误信息里的关联标识。
6. 各类调用的超时默认值（当前除索引与死信重试外共用单次调用超时）。

## 三、现状风险

1. **解码强度不一致，弱的那一半没有守卫。** 项目列表/创建、死信、折叠是严格解码（字段缺失即报协议错误）；
   项目索引与 watch 启动只判 HTTP 成功、不消费响应体；健康要求 `healthy` 存在、子系统缺省继承总体结论；
   检索、关键词检索与三个导航端点是"归约式消费"——从原始 JSON 里只取用到的字段，字段改名不会报错，
   只会让结果悄悄变空或丢字段。
2. **路径正确性靠人工比对。** 前缀常量与项目作用域拼接目前与上游一致，但没有任何自动化对抗日后的重命名。
3. **错误分类靠状态码 + 文本表达。** 上游的 `{success:false,error:{code,message}}` 在本地被压成字符串，
   维护面只能区分"本地拒绝/服务不可用"；更细的业务码目前不参与判定。
4. **服务端配置格式手抄。** 托管模式写出的 TOML 依赖上游配置节名（`database.sqlite` / `vector_local` / `bm25`
   / `logger`），上游改名只会在启动失败时才暴露。

## 四、目标形态

```
wf-agent
  ├─ code_context/service.rs      活状态 + 编排（保留）
  ├─ transport.rs                 断路器 + 托管进程监督（保留，去掉协议部分）
  └─ cce-client（crates.io）
        └─ cce-api               契约模型 / 路径 / 错误码
```

| 内容 | 迁移后 |
|---|---|
| 路径、请求体、响应类型、解码 | 来自 `cce-client`；本仓库不再出现端点字面量 |
| 错误分类 | 来自 `cce-client` 的分类（不可达 / 被拒绝 / 协议 / 凭据 + 状态码 + 业务码 + 请求标识），本地映射成现有 `ServiceError` / `OperationError` |
| 超时 | 由调用点显式给出（查询、索引、死信重试、watch 各自预算），客户端提供每调用覆盖 |
| 凭据 | 客户端按"环境变量名"解析，值不进日志与状态；本地不再维护认证头 |
| 请求标识 | 客户端生成；本地只把它带进日志与错误信息 |
| 断路器、健康缓存、能力握手、项目状态、监督、归约、提示 | 保留在本地 |
| 服务端配置格式 | 待定：若上游提供可复用的最小配置类型则替换手写 TOML，否则保留现状并接受该漂移面 |

## 五、逐模块迁移方案

| 文件 | 动作 | 迁移后职责 |
|---|---|---|
| `code_context/project.rs` | 删除列表/创建/索引/watch 的请求与解码 | 只保留根路径规范化与匹配（"workspace 归属"是本地语义）、索引是否已完成的判定 |
| `code_context/retrieval.rs` | 删除请求体构造与端点常量；归约函数入参从原始 JSON 改为客户端的 typed 响应 | 保留 `clamp_limit` 等预算策略与模型安全归约；字段改名会在编译期失败 |
| `code_context/navigation.rs` | 同上（三个端点的请求体与端点常量删除） | 保留参数校验与结果归约 |
| `code_context/fold.rs` | 删除自定义响应结构与 `FoldClient` 的 HTTP 部分，改用客户端折叠方法 | 保留候选选择、预算、提示与结果回写 |
| `code_context/dead_letters.rs` | 整文件删除 | 改用客户端死信方法；维护面的语义分层留在 `service.rs` |
| `transport.rs` | 删除 `post_json` / `get_json` / `probe_health` / 请求标识 / 共享客户端与凭据注册 | 保留断路器、托管进程监督；把客户端错误分类映射为本地 `ServiceError` |
| `code_context/service.rs` | 调用点替换；`client()` / 凭据字段删除，改为持有客户端句柄 | 保留全部活状态与编排逻辑 |
| `code_context.rs` | 保留配置与策略；`cce_server_command` 保留；`write_cce_server_config` 视上游能力决定去留 | 配置、策略、托管组装 |
| `wf-tools` / `wf-resource` / `wf-api` / `wf-server` / `wf-runtime` | 不改 | 通过 `wf-integration` 的公共类型继续工作 |

## 六、对 cce-client 的接口要求（本集成视角的验收清单）

1. 错误分类必须能驱动本地的断路器与维护面：不可达 / 被拒绝 / 协议不匹配 / 凭据，并携带状态码、业务码、
   业务消息与请求标识；不允许把分类折成单一字符串。
2. 超时必须可每调用覆盖，并给出长任务（索引、死信重试）的显式预算参数与单位。
3. 数字 id 必须同时接受 JSON 数字与十进制字符串（上游两种拼写都出现过）。
4. 必须覆盖本集成交互的 14 个端点；项目作用域路径由客户端负责拼接，调用方不拼路径。
5. 可选字段用 `Option` 表达，不得用默认值伪造缺失语义；2xx 且 `success:false` 必须原样返回（死信"没有可重试项"
   是合法答复）。
6. 依赖面要小：只依赖 HTTP 客户端与契约模型，不引入 server / orchestrator / storage；默认特性不含服务端专用特性
   （如准入 ingest），避免为无关能力付编译成本。
7. 需要语义化版本与变更记录，便于本地锁定版本并评估升级。
8. 可选：若上游愿意提供托管启动所需的最小配置类型与启动参数约定，本地手写 TOML 与启动行可以一并替换；
   不提供也不阻塞本次迁移。

## 七、迁移步骤与验收

1. **建立依赖**：以 crates.io 版本依赖引入 `cce-client`，先并存（新调用面与旧实现同时存在一个提交周期），
   用一条检索与一条导航调用验证行为一致后继续。
2. **替换解码**：把 `retrieval.rs` / `navigation.rs` 的归约函数改为吃 typed 响应；字段级差异在编译期暴露。
3. **替换项目与死信**：`project.rs` 与 `dead_letters.rs` 的请求与解码删除，`service.rs` 调用点改为客户端方法；
   删除 `dead_letters.rs` 文件与其导出。
4. **替换折叠**：`fold.rs` 的自定义 `FoldBatchResponse` 删除，改用客户端类型；本地只保留候选选择与提示。
5. **收尾**：删除 `transport.rs` 的协议部分（HTTP 发送、健康解析、请求标识、共享客户端与凭据注册），
   把错误映射集中到一处；`CodeContextStatus` 的字段含义不变，诊断端点输出保持稳定。
6. **验收**：`cargo clippy --all-targets --all-features` 零新增告警；`wf-integration` 现有 code_context 用例
   （供给、索引中、失败态维护、死信三件套、能力握手、凭据缺失、托管监督）全绿；`wf-api` 诊断与维护面用例全绿；
   `wf-server` openapi 快照不变（本次迁移不改对外端点）；配置示例与 `docs/config/infrastructure.md` 不改语义。

## 八、风险与未决项

- **上游 API 变更节奏**：依赖 crates.io 意味着本地随上游行为变化。缓解方式是本仓库保留薄适配层（错误映射与
  活状态），并锁定次版本；升级时用现有 code_context 用例作为回归网。
- **归约层的字段依赖**：归约函数改为 typed 后，上游字段改名会变成编译错误而不是静默空结果——这是本次迁移的
  主要收益，但也意味着上游字段调整会传导成编译阻塞，需要与上游的发版节奏协调。
- **服务端配置格式**：托管模式仍需按上游配置节名生成 TOML；若上游不提供配置类型，这条漂移面保留在文档中。
- **超时默认值对齐**：索引与死信重试的本地预算需要与上游服务端上限一致，迁移时按上游实现确认后固定。
- **特性与编译成本**：要求默认特性不含服务端专用能力；若上游把 ingest 等放默认特性，本地需要显式关闭。
- **联调方式**：迁移期需要同时改两个仓库（本地适配 vs 客户端补齐），在客户端发布首个版本前以 path 依赖联调，
  发布后切回 crates.io 版本依赖。
- **文档收尾**：`docs/plan/code-context-next-phase.md` 中"上游响应形状是假设前提"这条风险在迁移完成后删除，
  改为"依赖版本与上游发版节奏"；`docs/infra/integration/README.md` 的模块表需删掉已迁移模块的协议描述。
