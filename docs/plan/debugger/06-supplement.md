# 调试器补充设计：覆盖度缺口与优化决策

> 针对 `00~05` 的核查补充。约定不变：中文、自然语言为主，不贴完整代码实现。

## 一、核查结论

`00~05` 覆盖了主干调试对象：单步输入输出、变量 diff、消息 diff、`Route` 分支、hook 单点触发、trigger 三段链路、文本与 JSON 输出、断言与实际值展示。方向正确，复用优先思路成立。

但对照引擎现状，以下高频故障源尚未建模，一期若不补齐会导致调试器只能解释 happy path：

- Agent 迭代只记 `content + tool_call_count`，缺少逐个工具调用的 `name/arguments/result/error/duration`、审批结论、可见性快照（`visible/discoverable/gated/hidden`）。
- LLM 审计缺失：请求响应摘要、token 用量与预算告警、压缩信号分发无处展示。
- 中断恢复缺失：暂停、停止、取消、超时计数、并发门限无 trace 字段。
- Checkpoint 标记缺失：工具前后与压缩前后的边界快照点未建模，无法调试恢复不一致。
- 并发合并缺失：`Fork/Join` 只枚举分支，未解释分支变量与消息的合并结果；`Sync` 与循环轮次变量未建模。
- 嵌套执行缺失：子图与子 agent 的父子链、变量继承与输出映射无递归视图。
- 交互挂起缺失：只有请求响应对，没有挂起态与超时视图。
- Trigger 状态机不完整：只有干跑匹配，缺少每条触发记录的终态（运行中、完成、失败、中止）。
- 错误只有字符串：缺少错误分类（校验错、执行错、可重试、中止）与恢复建议。

另有两个结构性问题：

- Trigger 的匹配仲裁守卫函数为引擎内部可见，外部 crate 无法直接调用，干跑复用在当前可见性下不可行。
- 工作流引擎本身已依赖工具、模型网关、存储等重设施，调试器若直接依赖引擎层则轻量构建目标无法达成。

## 二、优化决策

1. 调试器首版仅依赖基础层（类型、通用工具、条件求值）与通用第三方库（序列化、命令行、错误、文本 diff），不依赖引擎层。hook 与 trigger 首版做数据驱动解释（读 trace 中的记录并说明命中落选原因），真实驱动复用待引擎暴露公开干跑门面后再接入。
2. Trace 模型加厚：每步除输入输出与分支归属外，增补工具调用明细、模型调用摘要、审批与可见性、循环轮次、合并结果、中断与 checkpoint 标记；顶层增补执行状态、错误分类、触发记录终态与断言结果。旧数据不兼容，按当前结构为准。
3. 分支穷尽一期只做路由节点的条件表加默认分支判定；条件边、并行分支、循环边界的枚举列为二期；死边告警复用图校验报告口径，不另起标准。
4. 静态校验不重复实现：图合法性结论以校验器的报告为准，调试器只做求值解释层。
5. 回放路径以导入式为主（一期），静态综合只做路由解释，实时驱动列为二期。hook 与 trigger 同时支持解释已有记录与干跑新事件两种输入。
6. 输出保持文本与 JSON 双形态同一数据源；文本默认折叠超长载荷并支持无色开关；JSON 不折叠不染色。断言失败记录期望与实际并返回非零退出码。
7. 调试器作为应用层叶子存在，不被任何生产 crate 反向依赖；工作区注册后以单次编译检查验证依赖方向。

## 三、与 `01~05` 的关系

本文件不替换 `01~05`，只收敛其中的开放点：数据源以导入式回放为主，分支范围按上条收敛，实时驱动与符号化枚举明确不在一期，命令行首版只提供离线子命令而不提供交互式视图。后续阶段划分仍沿用 `05` 的八个阶段，内容按本文件的加厚模型执行。
