# 远端部署作业的并发边界与未实现项

本文记录远端部署作业当前确定的运行前提和明确不做的能力，作为后续讨论的稳定依据。作业的提交、进度、取消与持久化现状见远端功能文档。

## 单管理进程前提

当前按后端的在飞作业唯一性由管理进程内的占位表保证，`backends.db` 只保存作业事实。部署模型要求同一数据库只有一个管理进程，多个进程共享同一数据库不受支持，需由部署方式保证单一管理者。

若以后引入多管理进程，需要把唯一性提升为存储层约束：以 `backend` 为唯一键的槽位表，提交时与作业记录在同一事务中插入，终态时在同一事务中删除，启动时清理指向非 live 作业的陈旧槽位。进程内占位与存储层槽位必须共同组成一次原子准入，不能各自独立判断。对应的验收条件是：两个进程并发提交同一后端只有一个成功；进程崩溃后的遗留槽位可在恢复时清理；单进程内仍保持现有的 409 语义。

## 明确不做的能力

- **远端期望状态与自动收敛**：远端服务只接受显式动词。自动重建会在网络抖动时删除仍在服务的目录，风险高于收益。
- **重启后重放远端操作**：远端没有操作游标，重放可能重复执行停止、安装或卸载。管理端重启只收敛本地作业记录，不恢复远端写操作。
- **远端保存作业历史**：管理面是作业唯一所有者；远端只保存安装事实，双份历史会形成两个真相源。
- **中断后自动回滚**：回滚本身是新的长写操作，风险高于原始部署。中断后只通过只读探测呈现远端事实，由操作者决定下一步。
- **进度推送流**：轮询、作业列表和重新 attach 已覆盖主要使用习惯；引入长连接会增加流生命周期与鉴权复杂度。
- **强制中断后的长探测**：强制中断只做短超时探测以呈现事实，不延长停机时间，也不把探测结果当成部署成功。
- **多管理进程分布式锁**：当前部署模型要求单一管理者；未引入高可用需求前不实现存储层分布式准入。
- **远端进程开机自启与守护**：这属于远端维护能力，不在部署作业治理范围内。
