# 图像输入与文件附件：现状分析、问题清单与修改方案

> 对象：CLI（headless / mini / tui）与前端（`apps/web-app`）的图像输入能力，以及前端文件附件处理。
> 后端统一契约（`wf-types::message`）与服务端入口一并纳入对照，目的是定位两端行为分叉。
> 本文档为后续整改的唯一依据；只描述行为与方案，不贴完整代码。
>
> 落实状态：P0 四项与 P1 五项已在本轮落地；P2 中草稿配额、重试缓存、清空语义、CLI 预算展示已落地；
> 运行中消息队列经核实无丢数据（见问题 12 备注），保持原行为；CLI 历史图片光栅渲染列为后续项。

## 一、现状

### 1. 后端统一契约（两端理论上对齐的基准）

- 图片载荷统一为结构化输入：内联 base64 加媒体类型，或远端地址（https / http / data），另带可选渲染提示（auto / low / high / original）。
- 白名单固定四种图片格式，单图上限 10 MiB，单轮总量 20 MiB，单轮最多 8 图；文本附件上限 8 个、单文件 64K 字符、单轮总量 256K 字符，超限截断必须带显式标记与原始长度。
- `/api/v1/info` 下发上述全部数值与图片媒体类型白名单，前端启动时拉取、失败回退内置值。
- 服务端入口：agent 回路与 chat 复用同一套图片校验与附件重插（附件以内联文本块形式并入消息体持久化）；agent 回路额外做 `@` 引用解析，图片类文件引用转为结构化图片载荷并回写解析回执，chat 通道不做引用解析。

### 1. CLI 图像输入现状

- headless（`wf run`）：`--image`（本地路径，可重复）、`--image-url`（远端地址，可重复）、`--image-detail`（整轮统一渲染提示）、`--attach`（文本文件，可重复）四组标志完整可用；三者均拒绝与 `--workflow` 同用；本地图片按扩展名识别媒体类型、读盘内联、统一走共享校验；文本附件读作 UTF-8，含 NUL 判二进制拒绝，超长自动截断并标记。
- mini 交互式：`/image` 负责暂存、列出、清空，`/image-detail` 负责渲染提示，图片随下一轮提示词一并发出、发出后清空；另支持 `@file:` 图片引用由服务端解析。文本附件有随轮发送的字段与消费逻辑，但没有任何命令可以填充它。
- tui 交互式：与 mini 同一套暂存模型（图片列表、附件列表、渲染提示），面板命令为 `session.image` 与 `session.image-detail`，发送时同样随轮发出并清空。同样没有任何入口可以填充文本附件列表。
- 历史回看：会话树与重放均把图片块折叠为占位文本行；mini 的 markdown 渲染把图片标签降级为链接。终端图片光栅与延迟注册能力存在于渲染层，但未与会话图片接通。

### 2. 前端图像输入现状

- 编排器提供文件按钮、图片按钮、粘贴、拖放四条暂存路径，统一经过纯函数预检（类型白名单、单轮张数、单图大小、总量预算），失败以 toast 提示。
- 暂存区显示缩略图、可移除；workflow 模式下图片按钮禁用并显示警告行，另有一行暂存预算（张数、文件数、图片剩余额度）。
- 发送通道区分三类执行：agent 与 chat 携带结构化图片载荷，workflow 拒绝图片并报错；内联图片以数据地址形式暂存，发送时拆分为载荷；远端地址原样透传；渲染提示字段存在但从不赋值。
- 草稿持久化覆盖文本、附件、图片三类；历史气泡渲染图片缩略图并支持点击放大；文本附件以内联块形式随消息体持久化，气泡侧解析回可展开条目；重试上一条用户消息时用名称缓存恢复图片显示名。

### 3. 前端文件附件现状

- 非图片文件走文本附件通道：数量与总量先做预算检查，单文件先过 1 MB 预读门限，通过后读文本、拒绝含 NUL 的二进制，超 64K 字符截断并标记原始长度。
- 发送时附件与图片互相独立：agent 与 chat 以结构化字段发送，服务端重插为内联块；workflow 把附件并入输入对象的消息字段。
- 运行中（busy）时纯文本可进队列，带附件或图片的消息直接拒绝并提示等本轮结束；队列内消息支持上移、下移、取回编辑，取回时附件与图片一并回到编辑器。

## 二、问题清单

按严重度排序。判断标准：静默丢数据优先于报错不一致，报错不一致优先于体验与配额问题。

### P0：丢数据或功能缺失

1. 交互式 CLI 文本附件无入口。mini 与 tui 的附件暂存字段存在、发送与清空逻辑存在，但命令表里没有对应的暂存命令，注释中提到的后续命令实际不存在。结果是交互式下文本附件能力完全不可用，只有 headless 可用。
2. 前端 workflow 附件静默丢失。工作流发送把附件并入输入对象时，仅在输入中本来就没有消息键时才写入；表单已提供消息值时，暂存的附件被直接丢弃且无任何提示。
3. 前端 workflow 下仍可暂存图片。图片按钮虽然禁用，但粘贴与拖放共用的文件入口不检查执行类型，图片可进入暂存，发送时才报错。暂存与发送两道关口规则不一致。
4. chat 执行器不支持文件引用解析。服务端引用解析只接在 agent 回路入口，chat 通道没有；前端的提及选择器在 chat 模式下同样提供文件选项，用户在 chat 下引用图片或文本文件不会生效，也不会收到解析回执。

### P1：两端口径不一致

5. 附件大小门限两端行为不同。前端用 1 MB 文件字节数做预读拒绝，超过即整文件拒绝；CLI 无此门限，任意大小读入后截断到 64K。同一文件在一端被拒、在另一端被截断发出。
6. 图片预算计量单位混用。前端暂存盘点用数据地址字符串长度（含 base64 膨胀与头部），预检输入用文件原始字节，剩余额度显示用前者去扣减服务端的解码字节预算。显示值与服务端实际校验值对不上，既可能误报超限也可能放行超限。
7. 媒体白名单热更新只覆盖一半。配置拉取只覆盖图片媒体类型，不覆盖扩展名回退表；服务端下发的白名单也没有扩展名部分。服务端放行媒体类型后，前端的扩展名回退仍用内置表。
8. 图片渲染提示只有 CLI 能设。载荷字段两端都有，CLI 有整轮统一的提示设置，交互式有按会话设置，前端从不赋值，永远走服务端默认。同一模型在两端的图片理解力度不一致，且历史重试也不会恢复提示值。
9. 交互式 CLI 无预算展示。前端有暂存预算行，CLI 只有列表行文本，无总量剩余额度，超限只能靠试错。

### P2：可靠性与体验

10. 草稿图片全量进 localStorage。数据地址 base64 整体持久化，单图可达 10 MB，极易撑爆浏览器配额；写入失败被静默吞掉，且各会话草稿互相挤占，无配额降级提示。
11. 重试的图片名缓存键过弱。键材料只有长度加首尾片段，存在碰撞空间；缓存只记名称与媒体类型，重试必然丢失原渲染提示。
12. 运行中带文件的消息不可排队。复核结论：主路径无丢数据，编排器在忙时把含附件的消息收进内存队列、轮次结束按序发出；直接调用发送入口时因拒绝而保留编辑器内容，需用户手动重发。体验可改进但不列为丢数据缺陷，本轮保持原行为。
13. 清空语义混淆。tui 的清空图片操作顺手清空附件列表，mini 新建会话同样清空两者，但帮助文案只提图片；附件既填不进又受清空影响，行为解释不清。
14. 历史图片在 CLI 只能看占位行。渲染层的图片光栅与延迟注册能力未与会话图片接通，mini 与 tui 永远只显示占位文本，无预览、无查看原图入口，与前端可放大缩略图差距大。

## 三、修改方案

原则：不做向后兼容，不保留遗留行为；服务端校验为权威，前端与 CLI 只做早期失败与诚实展示；同一规则改一处、两端同时对齐。

### 阶段一：堵住丢数据（对应问题 1–4）

- 给 mini 与 tui 补文本附件暂存命令。复用 headless 的读盘、NUL 拒绝、UTF-8 校验、超长截断标记与共享校验逻辑；列表行展示沿用已有的附件描述格式；发送消费与清空语义与图片一致；帮助文案同步补上附件用法。附件字段不再是死字段。
- 修复工作流附件合并规则。发送前先合并表单值与默认回填，再决定附件去向：表单已有消息值时把附件块追加到该值之后，而不是丢弃；表单无消息键时行为保持不变；严格模式下的未知键校验在合并之后执行，避免把合法追加误判为未知键。
- 统一工作流下的图片关口。把执行类型检查前移到文件暂存入口：工作流模式下粘贴、拖放、图片选择器统一拒绝图片并给出与发送时一致的提示；警告行保留，但不再出现可暂存不可发送的中间态。
- 明确 chat 下文件引用的去留。二选一：要么把服务端引用解析接到 chat 通道并回写回执（与 agent 回路一致），要么在 chat 模式下禁用文件类提及并给出提示。不允许选择器可用、服务端无反应的第三态。推荐接通解析，因为选择器与气泡回执展示逻辑本就通用。

### 阶段二：对齐口径（对应问题 5–9）

- 统一附件大小策略。去掉前端 1 MB 预读拒绝，改为与 CLI 一致的读入后截断标记语义；如确需保护内存，门限应以解码后字符数为准并在文案中明示，而不是用文件字节数提前拒绝。
- 统一图片预算计量。暂存盘点与预检统一换算为解码字节（base64 长度折算，不实际解码）；剩余额度显示同样按解码字节计算；超限提示区分单图超限与总量超限，与服务端错误一一对应。
- 补齐白名单同步。要么服务端下发扩展名回退表、前端同步覆盖，要么前端去掉对扩展名表的依赖、未知扩展名直接走媒体类型嗅探失败路径。保持一处来源。
- 给前端补渲染提示设置。编排器增加与 CLI 同档的四档选择，存入草稿并随轮发送；历史重试恢复提示值；工作流模式下隐藏该选项（与图片按钮一致）。
- 给交互式 CLI 补预算行。复用前端预算文案结构：已暂存张数与上限、附件数与上限、图片总量剩余额度；超限命令直接报错并保持暂存不变。

### 阶段三：可靠性与体验（对应问题 10–14）

- 草稿图片降级存储。内存保留全量以保证发送，持久化只存缩略图或引用标识；写入配额失败时丢弃图片持久化但保留文本与附件，并给出一次性提示；重进会话时缺失的图片位显示占位而非破图。
- 重试缓存连带恢复渲染提示，并增强键材料以降低碰撞；缓存未命中时回退服务端默认而不是编造值。
- 运行中消息队列维持现状。经复核主路径无丢数据：编排器忙时收进内存队列按序发出，直接调用被拒时编辑器保留待手动重发；跨刷新持久化列为后续项。
- 澄清清空语义。图片清空与附件清空拆分为独立操作（或明确合一并写进帮助文案），消除只填不满、清空却连带的问题。
- CLI 历史图片展示二选一：短期在占位行旁给出查看原图的方式（如写临时文件后提示路径），长期把会话图片接到已有的图片光栅与延迟注册通路。未接通前，帮助文案如实说明 CLI 只看占位文本。

## 四、验证

- 后端与共享逻辑：全量 clippy 检查；附件与图片校验、引用解析、截断标记的单测覆盖新增分支。
- 前端：附件编解码、图片预检、媒体配置的现有单测全过；新增工作流附件追加、chat 引用策略、预算换算的用例。
- CLI：headless 标志互斥、mini 与 tui 暂存命令解析、发送消费语义的单测；交互式帮助文案与实际命令一致。
- 手工走查：同一图片与同一文本文件在 headless、mini、tui、前端 agent、前端 chat 下的表现一致；工作流下图片不可暂存、附件必达；超限文件两端同断同截。

## 五、本轮落实

- 问题 1：mini 新增 `/attach`（列出、暂存、清空）命令，tui 新增 `session.attach` 面板路由，两端复用 headless 附件读取与校验逻辑；暂存列表与发送消费语义与图片一致，帮助文案同步更新。
- 问题 2：工作流发送改为合并语义，表单已有消息值时把编排器文本与附件块追加到该值之后，不再丢弃暂存附件；非字符串消息值保持原样，交由校验报错。
- 问题 3：文件暂存入口统一检查执行类型，工作流模式下粘贴、拖放、选择器暂存图片直接拒绝并给出与发送时一致的提示。
- 问题 4：chat 通道接入引用解析，文本引用随轮进入会话上下文，图片引用并入结构化载荷，解析回执与 agent 回路同格式持久化并可回显。
- 问题 5：去掉前端 1MB 预读拒绝，读入后按 64K 截断标记，与 CLI 一致。
- 问题 6：前端暂存盘点、预检输入、剩余额度统一换算为解码字节，远端地址按未知大小计入张数；并发读取导致超限时在落盘前二次拦截。
- 问题 7：服务端 `/info` 新增扩展名白名单字段，前端同步覆盖扩展名回退表，单一来源。
- 问题 8：前端编排器新增渲染提示选择（默认、auto、low、high、original），随暂存图片发送并持久化；历史重试恢复提示值；载荷类型补齐 original 档。
- 问题 9：mini 与 tui 暂存列表及暂存成功回执新增预算行（张数、文件数、解码字节与字符用量）；发送时分别提示图片与文件随轮发出。
- 问题 10：草稿图片超过持久化预算时仅驻内存，不再写入存储；不足额时行为不变。
- 问题 11：重试图片名缓存键加入全串哈希，缓存连带记录渲染提示，重试恢复提示值。
- 问题 13：清空语义拆分，图片清空与文件清空各自独立；新建会话清空两者不变，帮助文案如实描述。

## 六、后续项

- CLI 历史图片渲染：会话树与重放的占位行保持不变；将图片接到终端光栅与延迟注册通路，或提供原图导出查看方式，独立立项。
- 运行中队列持久化：队列仍为内存态，刷新丢失；如需跨刷新排队，需为队列设计持久化格式，独立评估。
