# 代码上下文服务（CCE）下阶段任务

本文承接 `docs/plan/code-context-service-state-control.md` 第五节的剩余缺口，给出下阶段可执行的任务说明。
已完成部分（活状态对象、子系统级健康、传输层熔断、折叠阶段预算、进程优雅停机与数据隔离）不再复述，
这里只描述尚未落地的工作、已定稿的设计决策、改动面与验收标准。

## 一、范围与取舍

- 范围：把 code-context 服务从"能安全降级的外部依赖"推进到"能自我供给索引、能观察、能认证、能排障"的完整子系统。
- 非目标：不引入第二套配置/状态源；不在本轮重写 wf-agent 的通用配置热重载（见任务五的边界说明）。
- 优先级依据：没有项目与索引供给时，服务"可用"却检索为空，功能价值为零，因此索引生命周期排第一；
  其余按"排障成本 > 使用体验 > 运维便利"排序。

| 任务 | 价值 | 依赖 | 改动面 |
|---|---|---|---|
| 一、项目与索引生命周期 | 检索真正可用 | 无 | 中（infra + runtime + 工具默认值） |
| 二、状态观测端点 | 排障与运维 | 一（状态字段） | 中（api + server + 快照 + 前端） |
| 三、凭据与协议握手 | 可对接远程/多租户 | 无 | 小（infra + config） |
| 四、托管首次拉起自愈 | 减少一次重启 | 无 | 中（infra + runtime） |
| 五、配置热重载 | 改配置免重启 | 依赖通用重载机制 | 小（仅预留接缝） |
| 六、工具能力可见性 | 避免无效工具调用 | 无 | 中（resource 层） |
| 七、日志与请求关联 | 故障可定位 | 无 | 小（infra + runtime） |
| 八、死信与人工重索引 | 失败可修 | 一（项目状态） | 中（infra + api + server） |

## 二、设计决策（本轮定稿）

以下决策覆盖原文档中"待定/建议"的表述，实现以本节为准。

1. **供给模式是显式枚举，不在运行期猜测。** `IndexSupplyMode` 只有两值：`managed`（运行时负责项目与索引）
   与 `external`（部署方负责，运行时只读 `default_project_id`）。配置期由 `transport_mode` 派生默认值
   （`managed` → `managed`，`external` → `external`）并可显式覆盖，派生结果写进有效配置，运行期只读枚举。
2. **归属唯一事实是 workspace 根。** 引导期的 `project_root`（缺省进程工作目录）是项目归属依据；
   项目按规范化后的 `root_path` 精确匹配（软链与大小写差异落到同一记录）。
   `default_project_id` 降级为显式覆盖：仅当供给关闭，或调用方显式要求时才使用。
3. **增量索引交给服务侧 watch，不嫁接运行时文件观察器。** wf-agent 的变更观察器绑定检查点分区与
   检查点管理器，把它接入索引链路会引入第二套合并窗口与所有权；托管模式直接调用服务侧
   `watch/start|stop`（默认开启，配置可关），外部模式一律不动 watch。合并窗口参数因此归上游，本地不再新增调优点。
4. **不解析上游索引统计的复合结构。** 索引请求走项目作用域端点（`/api/project/{id}/index`），避免全量端点
   请求体歧义；进度用"阶段 + 开始时间 + 项目 `last_indexed`"表达，失败原因保留原文，不猜测统计字段语义。
5. **索引不阻塞引导，失败为终态。** 引导期只做"列项目 → 缺失则建 → 判断是否需要索引"，随后派发后台任务；
   索引失败记入项目状态不自动重试。**项目解析失败**例外：状态保持"未解析"，下一次调用可惰性重试一次，
   使服务恢复后无需重启进程（索引本身仍不自动重跑）。
6. **凭据只声明环境变量名。** 与仓库既有"声明不含密钥"的约定一致，配置项是环境变量名，值在服务构建期读取一次；
   认证头加在共享 HTTP 客户端的默认头上，一处生效即覆盖检索、导航、折叠与健康探测。
   值不进入状态快照、日志与错误信息，缺变量即报"凭据不可解析"并快速失败。
7. **握手以能力探测为准并只做一次。** 能力 = 健康可解析 + 项目端点存在；结果缓存到配置重新应用为止。
   401/403 归类为凭据问题（不跳闸、不重试）；端点缺失（404/解码失败）归类为不兼容。上游提供版本端点后，
   再在同一位置改为区间比较，不新增第二条判定路径。
8. **首次拉起与重启共用同一套监督状态机。** `start_sidecar` 只建状态与派发任务，相位为"启动中"；
   引导期做有界等待，超时/失败不再是终态。相位补 `RetryWait`（进程拉起但不就绪的重试等待），
   与 `Restarting`（异常退出后退避）区分。数据目录锁由监督任务持有：任务启动时抢、彻底停止时释放，
   重试期间保持独占。二进制缺失不可自愈，直接终态并提示配置。
9. **日志落盘由本侧动作保证，不猜上游 logger 字段。** 子进程 stdout/stderr 追加写入数据目录下的
   `cce.log`（配置里的 logger 路径保持不变，作为服务自身文件日志的去处）；失败告警附带该文件尾部若干行。
   级别通过子进程环境变量覆盖。清理方式写进文档，不引入自动轮转。
10. **热重载只留接缝。** `CodeContextService::apply_config` 是唯一入口，返回"是否需要停旧起新"；
    运行时提供 `reconfigure_code_context`（应用配置 → 必要时停止并重新拉起托管进程 → 重新烘焙两条折叠链）。
    触发器留待通用配置重载落地后接入，本轮不出现"只有这一节可热改"的第二套机制。
11. **能力可见性遵守"仅当确认不可用才隐藏"。** 谓词读活状态：服务停用、启动失败或已缓存健康结论缺失该子系统时隐藏
    对应工具；健康结论尚未产生时保持可见（无证据不等于不可用）。装配期过滤工具定义与预取工作流，
    不复制快照，因此服务恢复后新发起的执行立刻看到完整工具集。
12. **观测端点只读缓存。** 不触发探测、不改断路器状态；诊断视图不含令牌、错误栈与绝对路径
    （workspace 内路径降级为相对路径）。
13. **死信与人工重试按已确认契约接线，且只做人工动作。** 契约取自上游 `cce-api`：列表
    `GET /api/project/{id}/dead-letters`（`{project_id, files:[{file_path, version, modules:[...], updated_at}]}`）、
    重试 `POST .../dead-letters/retry`（`{files:[]}`，空表示全部）、确认 `POST .../dead-letters/acknowledge`
    （`{file_path, module?}`），两者回 `{success, affected, message}`。本侧不实现自动重试策略：索引失败与死信都
    保持可观状态，由人决定何时重试。
14. **维护通道独立于检索通道。** 新增 `CallScope::Operations`：只要求服务进程可用，不要求任何子系统，
    因为死信与重索引恰恰发生在"索引正在跑"或"索引已失败"时——此时检索范围本就被禁用。对应的项目 id
    取"活状态里已知的 id"，因此 `Failed` 状态必须保留失败前操作的 id，而不是把它丢掉。
15. **失败索引的唯一恢复入口是显式重索引。** `retry_index` 在服务可达且当前未索引时把状态置回"索引中"
    并派发同一套全量索引任务；供给为外部模式时直接拒绝（重索引的归属在部署方）。

## 三、任务一：项目与索引生命周期

### 现状

`RetrievalPolicy.default_project_id` 是配置里的裸数字（`crates/infra/wf-integration/src/code_context.rs`），
没有任何环节保证这个 id 在服务里存在、指向当前 workspace，也没有任何环节触发索引。
服务侧能力齐备且本次已确认：项目列表/创建/详情（`GET/POST /api/project`）、全量索引
（`POST /api/index`、`POST /api/project/{id}/index`）、增量索引（`POST /api/index/incremental`）、
索引统计（`GET /api/index/stats`）、监听启停（`POST /api/project/{id}/watch/{start,stop}`、
`GET /api/project/{id}/watch/status`）、死信列表/重试/确认。项目记录的 `id` 在列表响应中是十进制字符串，
`root_path` 是绝对路径，`last_indexed` 为空表示从未索引。

### 目标

从"配置一个 id"变成"声明一个 workspace，由运行时保证它在服务里存在且已索引"。

### 设计要点

1. **归属关系**：workspace 根（引导期的 `project_root`，缺省为进程工作目录）是唯一事实；
   `default_project_id` 降级为显式覆盖（见设计决策 2）。
2. **解析与缓存**：`CodeContextService` 增加项目状态（未解析 / 解析中 / 索引中 / 已就绪 / 失败），
   解析 = 列项目 → 规范化 `root_path` 后精确匹配 → 未命中则创建 → 记下数字 id 与 `last_indexed`。
   结果只存在活状态里，不写回配置文件。
3. **索引供给**：`last_indexed` 为空时触发一次全量索引，索引期间工具按未就绪快速失败并给出可读原因；
   已有 `last_indexed` 则只校验存在性，不重复索引（重启不重建索引是本任务的硬性验收项）。
4. **增量与监听**：托管供给模式下由服务侧 watch 承担增量（默认开启，配置可关）；外部模式一律不动 watch。
   两种模式的差别由 `IndexSupplyMode` 显式表达（设计决策 1、3）。
5. **长任务不阻塞引导**：索引可能持续数分钟且依赖 embedding，必须在后台任务里执行；
   引导期只决定"是否需要索引"，不等结果。索引失败记入项目状态并保留原因，不重试整轮（重试是人工动作）。
6. **工具接线**：工具 handler 的 `project_id` 默认值改为"状态里的解析结果 → 配置覆盖 → 报错"，
   调用方显式传入的 `project_id` 仍然优先；解析失败时错误信息指向项目状态而不是裸数字。
7. **死信**：只提供读取、重试与确认三个动作（见任务八），不做自动重试策略；`Failed` 状态保留项目 id，
   使死信维护与人工重索引在失败后仍然可用。

### 涉及模块

`wf-integration`（`code_context/project.rs` 新增项目通道：请求/响应形状与状态机；`service.rs` 增加项目状态）、
`wf-runtime`（引导期解析与后台索引任务、watch 启停）、`wf-tools`（默认项目取值）、`wf-config`（供给模式与覆盖项）。

### 验收标准

- 全新 workspace + 托管服务：不做任何手工操作，首次语义检索就有结果；状态里能看到项目 id 与索引完成时间。
- 重启 runtime：不重复全量索引，检索立即可用。
- 索引期间检索工具明确返回"索引进行中"，而不是空结果或超时。
- 服务里同路径项目已存在时不重复创建；路径用软链/大小写差异表达时不产生第二个项目。
- 外部模式下不触发索引、不动 watch，行为与当前一致。

## 四、任务二：状态观测端点

### 现状

`CodeContextService::status()` 已返回可序列化的完整快照（开关、传输模式、端点、启动失败原因、健康结论与
年龄、断路器相位与剩余冷却、子进程相位/重启次数/pid），但没有消费者：`ApiContext` 未持有该句柄，
`wf-server` 没有路由，前端与 TUI 没有入口。可参照的既有形态是存储诊断
（`crates/app/wf-api/src/infra/diagnostics.rs`）与 `/api/v1/system/dependencies`、`/api/v1/system/stale` 这组
`crates/app/wf-server/src/api/system/` 下的只读端点。

### 目标

一条只读端点即可回答"code-context 现在能不能用、为什么不能用、索引到哪一步"。

### 设计要点

1. `ApiContext` 增加 code-context 服务句柄（`Option<Arc<CodeContextService>>`），装配期由 runtime 注入；
   `wf-api` 增加只读查询函数，把服务快照与项目/索引状态合成一个面向诊断的视图（不暴露内部错误栈）。
2. `wf-server` 在 `api/system/` 下新增模块并注册到 `api/system.rs` 的路由集合，路径挂在 `/api/v1/system/code-context`；
   处理器只做传输适配，语义留在 `wf-api`。
3. 契约同步是硬要求：新增 `#[utoipa::path]` 后必须刷新提交的 `crates/app/wf-server/openapi.json`
   （`WF_REFRESH_OPENAPI=1` 跑快照用例），再在 `tools/openapi-codegen` 生成前端类型，否则快照漂移用例与
   源码路由一致性用例都会失败。
4. 前端：诊断页展示同一份视图；`vite --mode preview` 的 fixture 需要补一条，避免预览模式空面板。
   TUI 侧作为可选项接入已有的状态面板，不阻塞本任务验收。
5. 该端点不得触发探测或副作用（不能在诊断时把断路器状态改掉）；只读取缓存快照（设计决策 12）。

### 验收标准

- 服务关闭、启动失败、可达但 embedding 降级、断路器开路、子进程重启中、索引进行中，六种状态都能从该端点一眼读出原因。
- 端点调用不产生对外请求（可用无网络的托管失败场景验证）。
- `cargo clippy --all-targets --all-features` 与 OpenAPI 快照/路由一致性用例全绿；前端类型生成后无手改。

## 五、任务三：凭据与协议握手

### 现状

集成层没有任何凭据入口，请求头只有 JSON 内容类型；而 CCE 的 admission 形态用
`Authorization: Bearer <token>` 认证（回退头为 `x-api-token`），并按 token 绑定项目作用域与限流。
协议兼容也没有校验：端点硬编码，版本不匹配表现为 422/不可解码响应，工具只报"调用失败"。

### 设计要点

1. 传输配置增加令牌声明项，形式为环境变量名（设计决策 6），值在服务构建期读取一次并只挂在共享客户端的
   默认头上；探测请求同样携带（否则健康探测会得到 401 而被误判为不可用）。不回显到日志、不进状态快照。
2. 401/403 的语义固定为"凭据问题"，不进入断路器（当前 4xx 已不跳闸），错误文案直接说明是凭据/作用域问题。
3. 握手：服务启动或首次使用时做一次能力探测，明确区分"端点缺失（版本不匹配）"与"可达但拒绝（凭据/作用域）"。
   CCE 当前没有版本端点，因此握手以能力探测为准：健康响应必须能解析出子系统结论，且项目端点存在；
   任一项缺失则进入"不兼容"状态并给出明确原因，而不是逐调用失败。
4. 若后续 CCE 提供版本端点，握手改为版本区间比较（设计决策 7）。

### 验收标准

- 带 token 对接 admission 形态可正常检索；缺 token/错 token 时报"凭据"错误且不触发断路器冷却。
- 令牌不出现在日志、状态端点、错误信息里。
- 对旧版本服务（缺端点）给出"不兼容"状态，且不产生持续的对外请求。

## 六、任务四：托管首次拉起自愈

### 现状

托管模式的第一次拉起在引导期同步完成：失败即终态（记录 `startup_error`、调用快速失败、需要重启进程），
而进程启动之后的崩溃会按预算重启。同一条生命周期存在两套处置方式，`runtime.lock` 也在引导期抢、
随 `RunningSidecar` 释放，失败路径与重试路径的所有权不一致。

### 设计要点

1. 把"首次拉起"并入监督任务：`start_sidecar` 只负责建状态与派发任务，返回时相位是"启动中"；
   引导期做有界等待（`managed_startup_timeout_ms`）以便首轮调用不空转，超时/失败不再是终态。
2. 监督任务的相位补 `RetryWait`（进程拉起后不就绪的重试等待）与 `Restarting`（异常退出后退避），
   并把"进程未就绪"表达为可读原因：二进制缺失（不可自愈，直接终态并提示配置）与进程拉起后不就绪（按预算重试）分开。
3. 数据目录锁的所有权交给监督任务：任务启动时抢、彻底停止时释放；重试期间保持独占，避免两个进程短暂并行。
4. 消费者侧不变：非就绪相位一律快速失败；恢复后无需重启 runtime，下一次调用自动恢复。

### 验收标准

- 二进制缺失：一次明确失败并给出配置原因，不进行无意义重试。
- 进程启动即崩：按预算重试，状态显示重试次数与最近原因；期间工具快速失败。
- 进程就绪后被杀：按预算重启，恢复后工具无需额外操作即可用。
- 同一 workspace 第二个 runtime 仍被锁拒绝。
- `RunningSidecar` 的显式关闭与 `Drop` 两条路径都能释放锁与临时文件（现有用例覆盖后补一条重试场景）。

## 七、任务五：配置热重载（仅预留接缝）

### 现状

运行时没有通用配置重载机制，`[code_context]` 改动只能重启进程；折叠链在引导期从有效服务配置烘焙，
因此即便改了配置也不会影响已注册的模板。

### 建议

1. 本轮只做接缝，不做独立重载通道：`CodeContextService::apply_config` 是唯一入口
   （替换策略与端点、重置健康缓存与断路器、返回是否需要停旧起新），
   `wf-runtime::Runtime::reconfigure_code_context` 提供"应用配置 + 必要时重启托管进程 + 重新烘焙两条折叠链"的单一函数。
2. 触发器留待通用配置重载落地后接入（文件变更或管理端点），避免出现"只有这一节可热改"的第二套机制。
3. 需要明确写进文档的约束：折叠链是执行期只读的节点配置，重载必须在没有进行中的压缩执行时生效；
   端点变化（外部地址或托管端口）一律走"停旧起新"，不允许原地改地址。

### 验收标准

- 在不接入触发器的情况下，重载入口有单元测试覆盖（配置替换 + 折叠链重烘焙 + 借用状态不残留）。
- 未接入触发器前，运行期行为与当前完全一致。

## 八、任务六：工具能力可见性

### 现状

六个 code-context 工具定义是静态常量、无条件注册（`crates/engine/wf-tools/src/handlers.rs`、
`crates/engine/wf-tools/src/predefined/code_context.rs`），模型在任何状态下都能看到它们；
预取子工作流的 agent 模板也硬编码了这六个工具。服务停用或被降级时，模型会浪费轮次调用必然失败的工具。

### 设计要点

1. 在资源装配阶段引入能力谓词：工具集合按"服务开关 + 调用范围可用性"过滤，映射关系与运行期门禁一致
   （折叠与导航只需进程可达；关键词检索需 BM25；语义检索需 embedding）。映射以工具 id → 调用范围的单函数表达，
   由工具定义所在模块持有，装配期与运行期共用同一份。
2. 谓词来源必须是 `CodeContextService` 的活状态，不能在装配期复制快照，并遵守"仅当确认不可用才隐藏"（设计决策 11）。
3. 语义检索降级只隐藏 `code_search`，不连带隐藏 `code_keyword_search` / 导航 / `read_file_folded`。
4. 预取子工作流在模板装配时按同一谓词决定工具集；全部不可用时整条预取工作流不注册，
   避免拉起一个只会报错的子代理。
5. 需要接受的既有约束：agent 的工具集合在执行装配期确定，恢复对"已在运行的执行"不生效；
   若要求迭代内刷新，需要单独评估成本，不在本轮做。

### 验收标准

- 服务停用：模型工具清单里没有这六个工具，预取工作流不可调度。
- 仅 embedding 降级：只剩关键词检索、导航与折叠可用。
- 服务恢复后新发起的执行能看到完整工具集合。
- 工具定义与 schema 快照、golden 用例保持同步（定义本身不变，只变可见性）。

## 九、任务七：日志与请求关联

### 现状

托管进程的 stdout 被丢弃、stderr 直通宿主，生成的配置虽然钉了日志文件路径但没有把输出目标切到文件，
因此服务自身的结构化日志实际不会落盘；折叠/检索调用也没有请求标识，出问题只能靠时间对齐。

### 设计要点

1. 日志落盘由本侧动作保证（设计决策 9）：子进程 stdout/stderr 追加写入 workspace 的 code-context 数据目录内的
   `cce.log`，级别通过子进程环境变量覆盖；生成配置里的 logger 文件路径继续指向同一目录，供服务自身文件日志使用。
2. 子进程失败时把日志尾部若干行并入告警原因，让"进程起不来"不再只有退出码。
3. 每次服务调用附带一个由 wf-agent 生成的请求标识头（`x-request-id`），并在本侧日志里打印该标识；
   服务侧是否记录该头取决于 CCE，需要上游配合，属于可选项，不阻塞本任务。
4. 日志体积：托管模式下日志随数据目录存续，需要在文档中说明清理方式（不引入自动轮转，避免与 CCE 自身
   日志策略冲突）。

### 验收标准

- 托管服务启动后 `cce.log` 有内容；进程异常退出时告警里带日志尾部。
- 一次折叠/检索调用能在 wf-agent 日志里用同一个请求标识串起来。
- 日志目录与 `.gitignore` 约定一致，不进入版本控制。

## 十、任务八：死信与人工重索引

### 现状

服务侧的死信能力齐备（按文件 × 模块记录失败、支持重试与确认），但 wf-agent 完全没有消费者：索引失败或
部分文件反复失败时，运维只能登录服务侧操作，而这恰恰是最需要从 agent 侧发起动作的时刻。同时"索引失败
保持终态、重试是人工动作"这句话在此前没有对应的人工入口——失败后除了重启进程无路可走。

### 目标

一条维护面即可回答"哪些文件被服务放弃了、能不能重试、要不要确认"，并给出失败索引的显式重索引入口。

### 设计要点

1. **维护通道与检索通道分离**：`CallScope::Operations` 只要求服务进程可用（复用"折叠"这个进程级通道作为
   可用性判据），不看向量/BM25/embedding 三个子系统，因此索引进行中、索引失败时维护仍然可用。
2. **项目 id 在失败后保留**：`ProjectState::Failed` 携带失败前操作的 id。缺了它，死信读不到、重索引也无从下发。
3. **契约形状与解码**：列表/动作响应都按已确认的上游结构解码，形状不符报"协议不匹配 + 原因"，
   不静默返回空死信；`success: false` 是合法答复（例如"没有可重试项"），不当作传输失败。
4. **超时分层**：重试会重跑解析与 embedding，按 600s 独立预算；列表与确认用单次调用超时。
5. **失败分类**：本地前置条件（外部供给、已在索引中）报"拒绝"，属调用方需要改变的东西；
   服务不可达或拒绝报"不可用"，让调用方退避而不是立刻重试。
6. **端点**：`GET/POST /api/v1/system/code-context/dead-letters[/retry|/acknowledge]`、
   `POST /api/v1/system/code-context/reindex`。路由只做传输适配，协议在 `wf-integration`，语义在 `wf-api`。

### 涉及模块

`wf-integration`（`code_context/dead_letters.rs` 新增通道：形状、解码、三动作；`service.rs` 维护入口与
`OperationError`）、`wf-api`（`infra/code_context.rs` 维护面与错误分类）、`wf-server`（四个路由 + OpenAPI 快照 +
前端类型）。

### 验收标准

- 索引失败后：状态显示失败原因与项目 id；死信可读、可重试、可确认；重索引把状态带回"索引中"并最终"已就绪"。
- 索引进行中：维护照常可用，检索仍明确拒绝；重复重索引被拒绝而不是并行跑两次。
- 外部供给模式：重索引被拒绝并提示归属在部署方，死信读写仍按配置的项目 id 工作。
- 服务不可达：维护动作报"不可用"，不产生"空死信"这种误导性结果。

## 十一、执行顺序与验证

1. 先做任务一（索引供给）与任务七（日志落盘）——前者决定功能是否成立，后者决定后续排障成本。
   同一轮顺带修掉 `wf-api` 的三处既有失败（见风险与未决项），否则"受影响 crate 全量通过"无法作为验收依据。
2. 再做任务四（自愈）与任务三（凭据/握手）——两者都只改 infra 与配置，风险低，可并行。
3. 接着任务六（能力可见性）——会改动模型可见行为，需要单独一轮全量回归。
4. 然后任务二（观测端点）——依赖任务一的项目状态字段，且需要刷新 OpenAPI 快照与前端类型。
5. 任务八（死信与人工重索引）——依赖任务一的项目状态，且需要刷新 OpenAPI 快照与前端类型。
6. 最后任务五（热重载接缝）——等通用配置重载方案明确后再接触发器。

每个任务完成后的统一验证：

- `cargo clippy --all-targets --all-features` 零新增告警。
- 受影响 crate 的单测与集成测试（infra 侧新增形状/状态机用例，runtime 侧至少一条端到端用例）。
- 涉及工具行为的任务额外跑 `-p wf-tools` 全量与 harness fixture。
- 涉及 `wf-server` 路由的任务额外跑 openapi 快照与路由一致性用例，并重新生成前端类型。

## 十二、风险与未决项

- **上游响应形状的前提**：项目列表按 `{"projects":[...]}` 解码、创建请求按 `{"name","root_path"}` 发送、
  索引走项目作用域端点。任一形状变化都表现为项目状态"失败 + 解码原因"，不会静默产生空检索；
  需要上游契约文档固化后才去掉这条前提。
- **索引供给的模型成本**：全量索引会消耗 embedding 配额与时间。策略固定为"仅当项目不存在或从未索引时自动触发"，
  其余靠显式命令；托管供给模式下 watch 带来的增量成本由上游合并窗口控制。
- **能力可见性的执行期语义**：工具集合在装配期固定，恢复只对新执行生效；是否要迭代内刷新需单独评估。
- **协议不兼容的判定标准**：CCE 目前没有版本端点，能力探测只能覆盖"端点是否存在"，无法覆盖语义变化；
  长期需要上游提供版本或契约版本号。
- **观测端点的信息边界**：诊断视图不输出令牌、错误栈与绝对路径；索引统计字段的语义未固化，因此不进入视图。
- **失败面的定案**：工作树里 `wf-api` 的三处既有失败均属"读取路径已按执行域收敛、夹具未跟上"这一类，
  修法是让夹具与语义一致而非放宽读取路径——检查点夹具改用执行域实体类型（`workflow_execution`），
  agent 执行用例在执行前安装进程级压缩参数（该参数的缺失在设计上就是硬失败，不允许静默回退）。
