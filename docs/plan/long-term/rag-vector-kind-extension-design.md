# RAG 向量种类扩展设计

> 本文是稀疏向量、多向量与相关查询能力的正式设计方案，立项门槛沿用 `sparse-writes.md`；门槛未满足时不启动实现。整体数据源装配见 `docs/plan/rag-data-source-abstraction-design.md`。

## 0. 结论速览

* 扩展点在 `vector-contracts`，不改 `keyword-contracts`。稀疏不是关键词检索的别名，多向量也不是把 chunk 切得更小的自动化开关。
* 一个 collection 在创建时声明唯一检索种类：稠密、稀疏或多向量。种类不同的集合不能混写，也不能静默降级查询。
* 契约用“向量数据枚举”统一 write/query 的载荷形状，保留 `ScoredPoint` 的 higher-is-better 结果语义；跨种类的多路融合留在 `wf-rag`。
* 插件 `vector-encoding` 从校验位升级为真正的编码器端口，但仍是同步纯函数，输出必须符合具名 schema；错误整批失败。
* 变更编码形状或编码器后必须 reindex 整个 collection。开发期不做旧向量兼容，也不做自动迁移。
* 先稀疏后多向量；具名向量作为寻址能力在确有混合集合需求时再启用。

## 1. 适用场景

### 稀疏向量

* 长尾词面命中：型号、错误码、法条编号、人名等需要精确 term 权重的查询。
* 无 embedding 服务时的可检索集合：词表可直接构造稀疏表示，冷启动成本更低。
* 可解释召回：命中项能展示词项权重，便于诊断为什么召回某个块。

### 多向量

* 长块内的细粒度匹配：查询只与块内一小段相关时，单向量压缩会丢失位置信息。
* 高精度问答：以更大的索引和查询成本换取 late interaction 的排序质量。

### 具名向量

* 同一记录需要同时保存标题向量与正文向量，或需要在一条记录上寻址多个编码结果。
* 它不是第三种打分算法，而是向量槽位的命名方式；只有出现真实的混合集合需求时才启用。

## 2. 与现状的关系

* 当前 `VectorStorage`、`VectorPoint`、`VectorQuery`、`CollectionSpec` 只支持单个稠密向量。`vector-contracts` 的 crate 文档已把稀疏、多向量、具名向量、prefetch 融合列为推迟项。
* 关键词混合通路是稀疏方案的基线；更细切分加父块提升是多向量方案的基线。立项论证必须说明新方案赢过哪一个基线。
* `vector-encoding` 插件当前只校验 JSON 对象形状，不改变写入。该校验位是未来 schema 的接入点，不是已实现的稀疏或多向量写入。
* 关键词索引保持独立。稀疏检索走 `VectorStorage` 的新种类，不塞进 `KeywordIndex`，也不复用 `KeywordScope`。
* 现有 fusion、rerank、advisor、postprocessor、citation 与 eval 不需要新算法；它们只接收统一后的 `RetrievedChunk`。

## 3. 正式实现需补充的功能

### 3.1 契约形状

* `CollectionSpec` 增加检索种类与种类参数。稠密继续要求单向量维度、距离和量化配置；稀疏要求词表维度上限与非负索引；多向量要求单向量维度、每点向量数上限和距离。未声明时保持稠密，声明与写入不一致即建集合失败。
* `VectorPoint` 的向量载荷改为具名向量数据：稠密保存单向量，稀疏保存递增索引数组与有限权重数组，多向量保存定长上界内的向量序列。每种形状都要求长度一致、数值有限、索引非负且递增；空查询拒绝，空写入按非法输入处理。
* `VectorQuery` 的查询载荷与集合种类一致：稠密传单向量，稀疏传稀疏向量，多向量传查询向量序列。查询参数不跨种类复用，例如稠密的量化控制在稀疏集合上直接报错。
* `VectorStorage` 增加能力查询方法，返回后端支持的种类集合；后端未认领的种类必须返回明确的 unsupported 错误，不允许用空结果或错误排序假装支持。
* `ScoredPoint` 保持 id、score 与 payload 不变。稀疏后端可在 payload 中以可选 explain 字段返回命中词项，但 explain 缺失不得影响召回与排序。
* 具名向量若启用，collection 声明允许的名称集合，point 以名称到向量数据的映射保存，查询必须指定名称。未声明名称一律失败。

### 3.2 后端执行矩阵

* 内存后端先实现稀疏倒排与多向量精确 MaxSim，作为契约一致性参考实现，不追求生产规模。
* simvec 只在确认底层引擎支持对应结构后认领；不支持时返回 explicit unsupported，不做近似伪装。
* Qdrant 按服务端实际能力认领，先稀疏后多向量，并在启动时做版本与能力探测。能力不足时 fail fast，不降级成稠密查询。
* 每个后端都要通过同一组契约对齐测试：过滤、分页、删除、计数、分数顺序、维度校验和不支持种类的错误码。近似计数仍按现有契约说明处理，不用于精确一致性断言。

### 3.3 摄取路径

* 在 `wf-rag` 定义编码器端口，宿主或插件实现。编码器输入文本与选项，输出带种类的向量数据；插件实现仍是同步纯函数，禁止网络访问和索引写入。
* 摄取时先按 schema 校验整批编码输出，再写向量；任一点非法则整批失败，不写半批数据。
* payload 增加编码名、编码 schema 与 collection kind；source 状态记录编码器指纹。指纹变化时旧向量视为失效，必须显式 reindex，不自动兼容旧表示。
* 删除 source、overwrite、增量更新与父块提升继续走现有流程；稀疏或多向量点使用同一 chunk id 与 `namespace/source` 约定。

### 3.4 查询与融合

* `pipeline` 增加按种类分派的查询入口，稠密路径保持现有行为。稀疏走倒排召回，多向量走 late interaction，返回点级分数后再还原为 `RetrievedChunk`。
* 稀疏与稠密要同时召回时，在 `wf-rag` 内分别查询后作为两个候选列表进入现有 fusion。解析器只做列表融合，不直接把不同尺度的分数相加。
* RRF 与 Concat 不依赖原始分数，可用于所有种类。Weighted 要求每个候选列表提供可比的归一化分数；不能提供的后端在集合配置阶段禁止 Weighted，而不是运行时猜测权重。
* 多向量后端只向上返回点级聚合分数，不把每个子向量当作独立命中；窗口扩展与父块提升仍按点 id 处理。
* 查询配置增加可选的召回种类、稀疏候选数与多向量预算；缺省关闭时行为与现有稠密路径一致。

### 3.5 插件与配置

* `vector-encoding` 的输出契约从任意 JSON 对象收紧为具名 schema，并携带种类标识；开发期直接替换旧校验形状，不保留宽松路径。
* 插件声明新增的向量种类由 manifest 权限约束，只有原生后端开放注册；Lua 与 Wasm 不提供编码通道。
* 配置中的 encoder 名未知时启动或摄取前失败；执行失败整批失败，不走内置编码器回退，避免把错误向量写入索引。
* 插件协议字段只做加性演进；破坏形状时直接更新协议与所有消费点，不并存两个协议版本的实现路径。

### 3.6 观测与验证

* 检索指标增加种类、编码器、候选列表数与融合模式，沿用现有 latency、candidates 与 hits 字段。
* 评测沿用 `eval.rs` 与宿主侧 eval 工具：分别对比关键词混合、细切分父块提升两条基线，记录命中率、首命中排名与成本。
* 验证覆盖 schema 拒绝用例、后端能力矩阵、跨后端排行一致性、删除与重建、编码器指纹变化后的 reindex、feature 关闭时的可读错误。

## 4. 模块归属

* 契约、类型与能力查询留在 `vector-contracts`，后端实现继续与契约同 crate，保持当前权衡不拆散。
* 编码器端口、schema 校验、插件桥接与查询分派留在 `wf-rag`，不进入叶子契约包。
* source 状态与编码指纹归 `wf-api` 的持久化 source 域；`wf-runtime` 只负责按配置打开后端并注入句柄。
* 不为稀疏或多向量新建替代 crate，不引入旧实现的兼容包装层。

## 5. 立项门槛

沿用 `sparse-writes.md` 的门槛，稀疏与多向量分别计数：只在真实集合上出现可复现的质量或成本收益、出现无 embedding 服务的部署约束，或某后端原生支持使适配缺口只剩薄层时才立项。门槛证据出现前只保留本文作为参考，不写执行分支。

## 6. 实施顺序

* 第一步：收紧向量契约形状与能力查询，补 schema 校验和内存参考实现。
* 第二步：接入 `vector-encoding` 的真实写入与查询编码，完成 source 指纹和 reindex 语义。
* 第三步：按后端能力逐项认领，先稀疏后多向量，每认领一项补跨后端一致性测试。
* 第四步：接入 fused 查询与 Weighted 的归一化约束，跑基线对比评测。
* 第五步：具名向量只在出现混合集合需求后立项实现，不随前四步默认上线。

## 7. 不做事项

* 不把稀疏检索路由到关键词后端，也不把 `KeywordIndex` 扩成向量后端。
* 不做跨尺度分数直加；Weighted 无法保证可比分数时禁止启用。
* 不在多向量实现前放宽 chunk 长度上限，不用索引成本掩盖切分问题。
* 不做排序、recommend、discover、分组、快照、分片、别名与 gRPC 传输；这些与向量种类扩展是不同职责。
* 不做旧向量格式兼容或自动迁移；开发期直接替换契约形状并要求 reindex。
