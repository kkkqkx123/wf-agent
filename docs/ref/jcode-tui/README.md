# wf-agent TUI 渲染优化设计（参照 jcode 引擎）

本文档分析 `wf-agent` 仓库中 TUI 模块（`crates/app/cli/wf-tui`，约 1.9 万行）的渲染管线现状，并参照已分析的 `jcode` TUI 引擎，给出可落地的渲染优化设计。

## 文档目录

- `01-现状与瓶颈.md`：wf-tui 渲染链路拆解、数据流、与 jcode 的逐项差距、瓶颈定位。
- `02-目标架构设计.md`：优化后的分层、模块边界、核心数据结构、缓存键设计。
- `03-关键实现细节.md`：增量准备、三级重绘、流式缓速、Markdown 增量化、主题 buffer 适配、动画纯核、性能分级。
- `04-落地路线与验证.md`：分阶段实施计划、风险、度量与测试回归方案。

## 结论速览

wf-tui 已经具备一套可用的流式 TUI：事件循环、帧率限制器、reducer、markdown 流式切分、快照测试、ANSI diff 录制器都在。它的核心问题集中在"每一帧都从头重建整屏内容"：

1. `InteractiveController::draw_scrollback` 每帧对全部 scrollback 行调用 `HistoryLine::display_lines(width)` 重新做字形换行，`MAX_SCROLLBACK` 上限 10000 行，成本随历史增长线性上升。
2. `MarkdownStream::push` 每收到一个 token 就用 `pulldown-cmark` 重解析整个累积缓冲区（上限 64 KiB），一条长消息上呈 O(n²)。
3. 重绘只有"整帧"一档，滚动条/状态栏/动画的变化都会触发全屏 buffer 重建。
4. 没有准备结果缓存（prepare cache）、没有渲染区域分级、没有性能分级策略、没有确定性时钟。

参照 jcode 的设计，优化方向是引入四层能力：**增量准备缓存**、**重绘范围分级**、**流式缓速与解析节流**、**可注入时钟与性能分级**。预期收益是：稳态流式帧的 CPU 成本从 O(历史行数) 降到 O(新增行数)，markdown 解析从 O(n²) 降到 O(n)，并让渲染路径可离线回归。

## 阅读顺序

先读 `01-现状与瓶颈.md` 建立基线，再读 `02-目标架构设计.md` 看整体方案，`03-关键实现细节.md` 给出具体数据结构和算法，最后按 `04-落地路线与验证.md` 分阶段实施。
