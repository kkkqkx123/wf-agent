# 回溯（Rewind）设计方案总览

> 目标：拆解 `atomcode` 的 rewind 实现，澄清当前项目在“回到某个用户回合”这件事上已经具备什么、缺什么，给出一份可直接落地的回溯设计。
>
> 基线：`atomgit-atomcode/atomcode` 主干（含 2026-10-16 缺失对象隔离改造）；本仓库当前主干。文中文件路径用于定位，行号仅作辅助。

## 术语界定

本文严格区分四个易混概念：

- **检查点（checkpoint）**：某一时刻执行状态或工作区文件状态的持久化记录，可单独恢复。当前项目已有执行状态检查点与文件检查点两套。
- **回溯点（rewind point）**：一次用户回合的边界记录。它本身不是一份新快照，而是把“这一回合开始前的工作区树、会话位置、提示词”与“这一回合结束后的工作区树”关联起来的一行账本。
- **回溯账本（rewind ledger）**：按会话组织的回溯点序列，有界保留、可列举、可作废。
- **会话锚（session anchor）**：把一个前端会话（命令行标签页、网页会话）与后端消息、检查点、回溯点关联起来的稳定标识。

一句话：检查点是“快照”，回溯点是“回合索引”，回溯是把会话与代码一起退回到某个回合之前的组合操作。

## 核心结论摘要

| 决策点 | 结论 | 理由 |
|---|---|---|
| 是否需要新的存储形态 | 否，复用现有 Git 对象库与 SQLite 元数据库 | 当前文件检查点已经有独立对象库、引用命名空间、GC 与 SQLite 迁移机制，再建影子仓库是重复建设 |
| 是否需要新 crate | 否，在检查点子系统的既有四层内加模块 | 遵循既有分层，避免出现第五套检查点实现 |
| 回合边界如何取快照 | 优先引用链上已有检查点，缺失时按需补拍 | 现有 `CheckpointTiming` 已按迭代产生检查点，逐回合再全量扫描两次成本过高 |
| 会话如何锚定 | 在 agent loop 请求上新增会话标识，并随消息持久化 | 当前 `agent_loop_id` 每次运行新生成，服务端无法把多回合串成一个会话，回溯账本没有稳定主键 |
| 会话回退如何实现 | 按会话投影截断消息，不做物理删除 | 保留审计痕迹，回退可复核；与现有“投影”表述一致 |
| 文件回退如何实现 | 复用选择性恢复，先拍恢复树再改工作区 | 现有 `restore_selected` 已能按文件清单恢复，缺的是安全前置与事务 |
| 作用域 | 会话、代码、两者 | 与 `atomcode` 一致；命令行只暴露两档，避免误操作 |
| 命令入口 | `/rewind` 斜杠命令加双击 Esc 手势 | 与现有命令表、面板路由、Esc 语义一致，不引入新模式 |
| 网页入口 | 消息气泡加“回到此处” | 与现有重试、继续同型扩展，复用同一套接口 |

## 范围

范围内：

- 回溯账本的数据模型、持久化位置与保留策略。
- 回合边界的捕获接缝，以及与会话、检查点的关联。
- 会话回退与文件回退的组合语义、冲突判定、失败降级。
- 应用门面接口、传输层路由、命令行与网页交互。
- 磁盘预算、缺失对象、事务恢复三类安全边界。

范围外：

- 工作流图级别的整图回放（属调试器域，另行设计）。
- 跨工作区、跨仓库的回溯。
- 多人协作下的回溯冲突协调（沿用单工作区串行假设）。
- 把回溯做成版本控制提交（不写用户仓库的引用与分支）。
