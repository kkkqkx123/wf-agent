# 上下文压实后续工作设计方案

## 背景

预算驱动的深压实第一阶段已落地：单压实管线支持计划模式（`CompactionPlanItem` 逐项跑摘要链、聚合后一次写回）、空计划回退单摘要、阈值决策、入历史前蒸馏与文件去重、交接流程与归档恢复工具、压实状态 checkpoint 持久化。

第一阶段分析中确认的剩余事项，按依赖关系排成七个阶段。全部改动遵循既定原则：不新增第二条压缩链、不做策略选择器、配置只做调参、可替换点留在资源层、历史只追加不改写。

## 阶段划分与依赖

- A 计划有界化：单轮 item 上限、超大块拆分、相邻小块合并。无前置依赖，最先做。
- B 事件瘦身：完成事件只回 outcomes，不回显计划，不重复摘要正文。依赖 A（outcomes 语义在 A 定型后冻结）。
- C 块表回收：失活且已归档的块移出热状态，只留交接索引。依赖 A（计划只读活跃块，回收不影响计划构造）。
- D 背压合并：每会话最多一个在途计划，新版本触发等待在途结算。依赖 C（块表回收后版本语义更清晰）。
- E 寻址代替传值：Direct 路径以进程内附件传递快照与计划，hook 数据只留审计字段；Routed 路径发布时序列化一次。无前置依赖。
- F 工作流硬上限护栏：工作流发射侧超限时构造一次性无状态计划，复用同一管线。依赖 A 与 E（复用有界计划与取数路径）。
- G 调用分档与可观测性：`depth` 映射摘要调用档位、交接提示资产化、压实指标打点。依赖 A 与 F（档位语义与指标口径以前面的定型为准）。

实施顺序为 A → B → C → D → E → F → G。

## 阶段 A：计划有界化

### 现状

`build_plan` 按“压到目标即停”产生计划，但单轮 item 数量无上界：大量小 `Raw` 块会产生数百个 item，每个 item 对应一次串行摘要链调用。体积与延迟同时随块数线性增长。

### 方案

计划构造增加三条有界规则，全部在 `wf-execution-shared` 的 compaction 引擎内完成，不动事件契约：

1. 单轮 item 上限：新增调参 `plan_max_items`，默认 8。达到回收目标或达到上限即停，溢出部分留待下一轮 settlement。目标未达成且已达上限时不降级为单摘要，保持多轮收敛。
2. 超大块拆分：单个 `Raw` 块超过单次调用预算（新增调参 `summary_call_budget_tokens`，默认按窗口比例折算，兜底固定值）时，按预算切成多个 item，保持块内顺序。切分后的 item 共享 `block_id`，完成事件按块聚合 outcomes。
3. 相邻小块合并：同 `depth` 且在快照内相邻的多个小 `Raw` item，在合并后不超过单次调用预算的前提下合并为一个 item。合并只发生在计划构造阶段，块表本身不合并，保持块粒度的回收记账。

### 验收

- 块数翻倍时单轮事件体积与调用次数封顶；
- 超大单块仍可收敛（多轮切分完成）；
- 现有计划聚合单测继续通过，新增边界单测覆盖上限截断、拆分、合并。

## 阶段 B：事件瘦身

### 现状

完成事件回执携带完整压缩后消息数组（含摘要正文）与逐块 outcomes；审计拷贝已只带 `plan_count`，无需改动。摘要正文在“回执 + 历史写回”两条路各出现一次。

### 方案

收紧完成事件载荷，发射侧与消费侧同步改：

1. 删除无人消费的 `summary` 文本字段（可从消息数组推导）；原计划体本来就不回显，保持不变；
2. 工作流变量表目标的完成事件不再带消息数组：登记表写回是其唯一消费路径，事件只带 outcomes 与版本锚点；
3. agent 目标的完成事件保留消息数组：自消费写回就是经由该事件落历史的，事件本身即传输通道，不存在重复。

块号保持现有字符串形式，不做数字化：块号本身已很短，数字化节省有限且损害可读性。

### 验收

- 同等规模下完成事件体积降至 outcomes 量级；
- agent 会话消费侧单测覆盖“事件无正文仍能正确过渡块状态”；
- 工作流压缩端到端单测继续通过。

## 阶段 C：块表回收

### 现状

`CompactionState.blocks` 只增不减：`Sealed` 块与失活块永久驻留热状态，计划构造虽只读活跃块，但状态体积、checkpoint 体积与遍历成本随会话长度无界增长。

### 方案

1. 回收条件：失活（`active == false`）且内容已归档（交接索引持有其指针，或自然落盘的摘要块）的块移出 `blocks`，只保留交接索引条目。自然压缩产生的失活小块（被 drop 的）无摘要可归档，历史本身即存档，直接移除。
2. 回收时机：交接归档成功后、分支截断重建时、以及每次计划应用后顺带执行，不新增独立触发点。
3. 安全约束：`pending_plan` 引用的块在计划结算前不得回收；`next_block_seq` 单调递增不受回收影响，保证块号永不复用；分支截断重建逻辑改为“保留引用块 + 移除其余”，语义不变。

### 验收

- 长会话块表规模收敛到活跃块加近期窗口；
- checkpoint 增量计算覆盖回收前后的块表差异；
- 分支截断与计划结算的并发边界单测通过。

## 阶段 D：背压合并

### 现状

在途保护以版本为粒度（`begin/end_compression_flight` + 发射 guard），但新版本可以在旧计划在途时发射第二个信号，同一会话可堆积多个计划事件。

### 方案

发射侧在决策前检查在途状态：若同一会话存在未结算的压缩 flight，无论版本是否推进，本轮只做决策记账（热估算、块同步照常），不发射新信号。旧计划结算（完成、失败、过期）后，下一轮 settlement 自然基于最新状态重新决策。新版本的消息不会丢失：历史只追加，计划永远基于结算时的最新快照构造。

豁免：强制安全网路径（provider 报上下文超限）不受合并约束，仍立即发射。

### 验收

- 连续多轮超限只产生一个在途计划；
- 强制路径单测不受影响；
- 结算超时后 emitter 不再空等（已有超时上Park 机制保持不变）。

## 阶段 E：寻址代替传值

### 现状

同步接管（Direct 路径）虽然是同进程调用，发射侧仍把完整快照与计划序列化进 hook 数据，执行侧再反序列化回来：一次完整的 JSON 往返纯属浪费。异步路由（Routed 路径）必须带快照，跨监听器只能走事件。

### 方案

区分两条通道的载荷：

1. hook 上下文新增可选附件（快照与计划的共享所有权）；hook 数据只保留审计字段（目标、版本、用量、计划长度）。条件表达式与模板只读审计字段，不受影响。
2. Direct 通道：发射侧同时挂载附件，执行侧优先从附件取数，零 JSON 往返；手写上下文（无附件）回退到 JSON 解析，保持兼容。
3. Routed 通道：发布时由附件序列化一次（跨监听器边界必须序列化），无附件时回退到 JSON 字段。
3. 审计拷贝保持现状：本来就不带快照。

### 验收

- Direct 路径下同等规模信号的序列化开销归零；
- Routed 路径行为不变（路由单测覆盖）；
- 版本前移导致取数失败时按过期路径处理，不重试。

## 阶段 F：工作流硬上限护栏

### 现状

工作流 LLM 节点发射侧永远传空计划，超限时只有单摘要一条路。长循环与大扇出场景下，单摘要输入可能超过单次调用预算，导致截断或失败。

### 方案

工作流发射侧保留单摘要默认行为，仅在估算超过硬上限时升级：

1. 升级条件：估算 token 超过上下文上限的硬上限比例（复用压实硬上限比率语义，按该节点的上下文上限折算），且存在可写回的命名数组。
2. 一次性无状态计划：把当前命名数组快照按单次调用预算切成若干 item（`block_id` 为临时编号，`depth` 为 0），不写块表、不落状态。管线零改动：多 item 聚合与单次写回逻辑已支持计划模式，outcomes 为空时按现有空 outcomes 路径处理。
3. 失败语义不变：失败仍走现有错误分支表，单摘要失败与计划失败对发射侧无区别。

这不是第二条压缩链：计划构造是一次性函数调用，执行的是同一条管线；无状态也意味着不需要工作流侧的块状态机。

### 验收

- 长循环工作流超限时走计划聚合完成，不再截断；
- 普通规模工作流行为零变化（空计划路径单测覆盖）；
- 端到端压缩单测新增超限用例。

## 阶段 G：调用分档与可观测性

### 现状

三处“复用但未分化”：`depth` 字段只做摘要链嵌套 guard，未用于挑选提示变体；交接提示资产已注册但交接流程仍用硬编码常量；压实关键转折（KEEP 兜底追加、交接进入、计划截断）只有日志，没有指标。

### 方案

1. `depth` 映射调用档位：同一构建器再注册一条同形重压链（baked 提示为新增的 `@standard/llm-summary-repress` 资产，走现有模板注册与用户覆盖机制），管线按 `depth` 选链执行（`depth >= 1` 走重压链，缺席配置回退主链）。默认档位行为与现状完全一致；调用配置（profile）暂不分档，后续需要时再参数化。
2. 交接提示资产化：交接流程改从 `@standard/handoff` 嵌入资产取文本，删除硬编码常量（版本常量与资产键同处一处，改文本时同步 bump）。提示版本号记入交接产物的校验备注。用户覆盖机制沿用现有 `skip_if_exists` 语义；agent 引擎不持有资源登记表，故解析走嵌入资产而非运行时登记表。
3. 压实指标：在现有指标登记表下新增压实收集器，打点只覆盖“静默”转折：计划发射（按模式与是否激进标注）、交接进入（按原因标注）、KEEP 兜底追加（按条数）、单轮截断。成功与失败主路径已有审计事件、触发器账本与日志，不再重复打点。打点只接在 agent 协调器侧（已有登记表句柄）；管线侧不另铺收集器。缺席时打点为空操作。

### 验收

- 重压 item 走变体提示，输出质量回归由 fixture 覆盖；
- 交接文档标注提示版本，用户覆盖提示后版本随之变化；
- 指标面板可回答“本周交接几次、各因几次、KEEP 兜底几次”。

## 配置项清单

全部进 `[compaction]` 段，只做调参：

- `plan_max_items`：单轮计划 item 上限；
- `summary_call_budget_tokens`：单次摘要调用预算，缺省按窗口比例折算；
- 其余阶段（回收、背压、寻址、工作流护栏、档位、指标）不新增用户可调参数，行为由既有阈值与固定策略决定。

校验规则延续现有风格：上限为正整数，调用预算为正整数且不大于窗口。

## 事件契约变更清单

- 完成事件：移除计划体回显与摘要正文，保留版本锚点、用量、outcomes。消费者同步改（agent 会话消费侧、工作流写回侧）。
- 请求事件：Direct 通道 hook 数据不再带快照与计划体，保留审计字段；Routed 事件不变。
- 新增指标不经过事件总线，不影响契约。

## 测试计划

- 引擎单测：上限截断、超大块拆分、相邻合并、回收条件、背压合并、寻址取数失败回退、无状态计划构造、档位查表。
- 运行时单测：管线计划聚合（已有）、路由快照路径、写回版本锚点、交接提示版本记录。
- 端到端：工作流超限计划聚合、长会话块表收敛、交接后搜索恢复。
- 性能基线：同等规模下请求事件与完成事件体积对比，Direct 路径序列化开销对比。

## 风险与回退

- 寻址取数失败：按过期路径处理，不重试，不阻塞主循环。
- 变体提示缺失：查表失败时回退默认提示，保证链路不断。
- 指标缺席：打点为空操作，不影响主流程。
- 任何阶段均可独立回退：A 与 B 改动内聚于引擎与事件层，C 与 D 为发射侧策略，E 为通道优化，F 为发射侧升级条件，G 为资源与观测。各阶段验收独立，不互相锁死。
