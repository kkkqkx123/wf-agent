# 01 现状与瓶颈

## 1. 渲染链路全景

wf-tui 的渲染路径可以分成五段：事件循环、帧调度、状态归并、内容准备、绘制。

### 1.1 事件循环

入口在 `crates/app/cli/wf-tui/src/tui.rs`：

- `TerminalGuard` 进入 `TerminalModes::TUI`（`terminal.rs:30`），即 raw mode + alt screen + bracketed paste + 隐藏光标。
- `Terminal<CrosstermBackend<io::Stdout>>` 持有全屏后端。
- `TuiApp::run`（`tui.rs:146`）先热重载主题信号，再调用 `event_loop`（`tui.rs:211`）。

事件循环每一轮做固定的事：

1. `check_suspend` 处理 Ctrl-Z。
2. `session.handle_events()` 排空交互事件。
3. `drain_data()` 归并后台 fetch 结果。
4. `ensure_interactive()`、`request_data()`。
5. `frame.set_now(now)`，决定是否 `request_frame()`。
6. `event::poll(timeout)` 读取按键/Resize。
7. 满足条件时 `terminal.draw(|frame| self.draw(frame, &data))`（`tui.rs:300-308`）。

关键常量：`POLL_INTERVAL = 100ms`（`tui.rs:56`）、`DATA_TTL = 5s`、`NOTICE_TTL = 6s`。也就是说，空闲时最坏 100ms 一次循环，脏标记或交互流式时按帧率上限走。

### 1.2 帧调度

`framer.rs` 是纯数学的帧率限制器：

- `MIN_FRAME_INTERVAL_MS = 9`（约 120 FPS 上限，`framer.rs:14`）。
- `FrameRequester`（`framer.rs:51`）合并请求，`deadline()` 取"请求时刻"与"速率地板"的较大值。
- 时间由调用方通过 `set_now` 注入，本身可在单测中验证。

这部分设计是好的，问题不在调度，而在"每次被允许绘制时做什么"。

### 1.3 状态归并

- `reducer.rs` 的 `SessionReducer` 把 `ExecutionStreamEvent` 折成 `MiniCommit` + `FooterState`，纯数据、无 IO、可单测。
- `InteractiveController::handle_events`（`interactive.rs:521`）把 `TurnEvent` 交给 `handle_turn_event`（`interactive.rs:598`）。
- 流式文本进入 `MarkdownStream`，产出 committed / streaming 两段（`interactive.rs:634-657`），写入 `pending_scroll` 与 `streaming`。
- `settle_scrollback`（`interactive.rs:756`）把 pending 行追加进 `scrollback`，超过 `MAX_SCROLLBACK = 10_000` 时从头部丢弃。

### 1.4 内容准备

内容模型在 `transcript.rs`：

- `HistoryLine` 保存**源文本** `Text<'static>`，明确不保存按宽度固定的渲染缓存（`transcript.rs:4-9`），理由是 resize 重排。
- `display_lines(width)`（`transcript.rs:179`）在每次调用时按 `unicode-segmentation` 逐字形换行，逐字形构造 `Span`。
- `wrap_line`（`transcript.rs:253`）对每个字形分配字符串。
- `render_row`（`transcript.rs:324`）会先 `" ".repeat(width)` 清整行，再逐 span 裁剪写入。

`history_cell.rs` 定义了另一套 `HistoryCell` trait（`history_cell.rs:27`）与若干单元类型，但全屏交互路径实际使用的是 `HistoryLine`。两套内容抽象并存，属于历史包袱。

### 1.5 绘制

`InteractiveController::draw`（`interactive.rs:929`）：

```
Layout: [Min(5) scrollback] [Length(4) footer] [Length(1) input]
  draw_scrollback(scroll_area)
  footer.draw(footer_area, frame.buffer_mut(), theme)
  draw_input(input_area)
```

`draw_scrollback`（`interactive.rs:947`）是热点：

```rust
for line in &self.scrollback {
    lines.extend(line.display_lines(width));   // 全量重排
}
if let Some(streaming) = &self.streaming {
    // 取 spinner，重排 streaming 行，插入 spinner span
}
let capacity = inner.height;
let max_scroll = lines.len() - capacity;
// 计算 start / view_scroll，skip(start)，Paragraph 渲染 visible
```

也就是说：即使视口只显示最后 40 行，每一帧都会把 1 万行全部换行成 `Vec<Line>`，再 `skip` 掉前面绝大多数。

## 2. 数据流与失效信号

当前没有统一的"内容版本号 / 布局版本号"，每一帧都视为脏。可用的失效信号散落在各处：

- 内容事件：`scrollback.append(pending_scroll)`、`streaming` 的替换。
- 宽度：`Layout` 由 `frame.area()` 决定，宽度变化没有单独记录。
- 主题：SIGUSR2 更新 `self.theme` 并置 `dirty`。
- 动画：`AnimationController` 内部用 `Instant::now()` 计算帧。
- 流式：`self.interactive.is_some()` 无条件要求重绘（`tui.rs:236`、`tui.rs:243`）。

缺少版本号意味着缓存无法做精准失效，只能"全量重建"。

## 3. 与 jcode 的逐项差距

| 能力 | jcode | wf-tui 现状 | 影响 |
| --- | --- | --- | --- |
| 准备结果缓存 | `FullPrepCacheKey` / `BodyCacheKey`，容量与字节双限 | 无 | 每帧全量重排 |
| 增量准备 | `prepare_body_incremental` / `prepare_body_prepended` | 无 | 追加/前插都是全量 |
| 重绘分级 | idle / spinner-only / full 三档 | 只有 full | 动画与 notice 也重建全屏 |
| 视口 | 精确的 viewport/anchor | `skip(start)` + Paragraph | 已可见但不缓存 |
| 流式缓速 | `stream_buffer.rs` 比例控制器 | 直接显示 delta | 突发 token 引起布局抖动 |
| Markdown 增量 | 已提交边界 + 局部解析 | 每次 push 全量重解析 | O(n²) |
| 主题适配 | buffer 单点亮度翻转 | 每个 widget 各自取色 | 无统一 choke point |
| 动画核 | 拆分 crate + 查找表 + opt-level 3 | `motion.rs` 每次 `Instant::now()`、逐字符 span | 无用分配 |
| 性能分级 | `PerformanceTier` + `SystemProfile` | 有 `capabilities.rs` 但未接策略 | 能力探测未用于降级 |
| 可测试时钟 | `TestClock` 注入 | `Instant::now()` 直接调用 | 动画/TTL 不可复现 |
| 状态抽象 | `TuiState` trait（dyn） | 渲染直接读 `TuiApp` 字段 | 渲染路径无法独立快照 |
| 同步输出 | 有 | `capabilities.synchronized_output` 已探测但未使用 | 流式可能撕裂 |
| 帧预算度量 | 有锚点平滑度、视觉探针 | 只有 `DiffRecorderBackend`（diff-record feature） | 缺回归基线 |

## 4. 瓶颈定位（按收益排序）

### B1. 全量 scrollback 重排（最高）

位置：`interactive.rs:960-963`。
成本：`O(Σ 字形数)` 每帧，1 万行文本约数十万字形，逐字形分配 span。
触发：任何 `dirty || interactive` 帧，流式期间每帧都触发。

### B2. Markdown 全量重解析（高）

位置：`markdown.rs:76` `push` → `boundary()`（`markdown.rs:214`）→ `last_top_level_block_start`（`markdown.rs:248`）对整个 buffer 跑 `Parser::new`。
成本：每个 token 一次 O(当前 buffer 长度)，一条 64 KiB 消息累计 O(n²)。
触发：每个 `LlmDelta`。

### B3. 单档全屏重绘（高）

位置：`tui.rs:301-308` 无条件 `terminal.draw` 整帧。
成本：整块 `Buffer` 重建 + ratatui 后端 diff。虽然 ANSI 字节被 diff 压缩，但 CPU 的 buffer 构造是整屏。
触发：spinner、notice、usage 变化。

### B4. 流式无缓速（中）

位置：`interactive.rs:634-657`，delta 到达即进入 `MarkdownStream` 与 `streaming`。
后果：供应商突发输出时，单帧内容跳变、布局抖动、spinner 与文本竞争。

### B5. 动画与主题的重复计算（中）

- `motion.rs:151` `shimmer_spans` 每次调用 `Instant::now()`，并为每个字符构造一个 `Span`。
- `animation.rs:170` 起每个帧方法都调用 `Instant::now()`。
- 主题在 `theme.rs` 按 widget 取色，浅色终端需要逐 widget 处理（虽然当前已有 `light_default`，但缺少统一适配点）。

### B6. 可测试性缺口（中）

- 渲染直接读 `TuiApp`/`InteractiveController` 字段，快照测试 `tui_snapshot.rs` 只覆盖 `HistoryLine::display_lines` 与少量 widget，不覆盖整帧序列。
- 动画/TTL/重绘节奏依赖真实 `Instant`，无法确定性回放。

### B7. 缺度量（低但关键）

`tui_debug/diff_recorder.rs` 能记录每帧 ANSI 字节数（`diff-record` feature），但没有帧内耗时、重排行数、解析字节数，也没有把这些纳入 CI 基线。

## 5. 设计约束

落地优化时必须尊重 wf-agent 的仓库约定（`AGENTS.md`）：

- 每个 crate 的 `lib.rs` 直接声明 `pub mod`，子文件扁平命名，禁止 `mod.rs`。
- 禁止在代码注释里引用文档编号（P1、§4.1 等），注释只描述代码意图。
- 代码与注释使用英文，文档使用中文。
- 安全项：不使用 `unwrap`（测试用 `expect`），避免 `dyn`（若必须，集中记录），子 crate 保持 DAG。
- 目前处于开发阶段，无需考虑向后兼容，优先保持架构合理。

这些约束对设计的影响：新增缓存层应放在 `wf-tui` 内部新模块（扁平文件），而不是引入新 crate；若要把动画数学拆出，需要新建 workspace 成员并登记到根 `Cargo.toml` 的 `per-package profile overrides`，成本略高，可作为后续阶段。
