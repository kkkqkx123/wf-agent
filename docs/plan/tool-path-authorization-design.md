# 工具路径授权与增量说明设计方案

本文分析当前工具执行权限控制中的路径边界，给出路径授权预设与通用增量说明的设计方案。
引用路径相对仓库根目录，只描述结论与意图，不贴实现代码。

## 一、现状：路径限制由三层门控叠加形成

### 1. 审批判定层：决定“是否问人”

- `crates/foundation/wf-types/src/tool/file_permission.rs` 定义 `Full / Write / Read / Denied` 四档文件权限与默认规则集。默认拒绝 `.env`、`.env.*`、凭据、密钥、证书等路径，把 `package.json`、`tsconfig.json`、`.git/**` 等设为只读，其余默认可写。规则按声明顺序首条命中生效。
- `crates/engine/wf-tools/src/approval/file_policy.rs` 用 glob 匹配路径，参数提取覆盖常见路径字段；shell 命令复用 `wf-sandbox` 的分链和词法分析，按重定向区分读写，补丁按标记行提取路径。这里的归一化只处理反斜杠和 `file://` 前缀，不折叠 `..`，也不解析软链接。
- `crates/engine/wf-tools/src/approval.rs` 的判定顺序为：总开关 → 工具名白名单 → 文件权限 → 写保护 → 风险等级分支。文件权限不命中（含敏感文件）返回 `Ask`，转人工确认而不是硬拒绝。
- `crates/engine/wf-tools/src/protect.rs` 维护写保护模式表，但硬拒绝分支只有在协调器注入 `ProtectController` 时生效；当前生产装配没有看到注入点，该分支主要出现在测试中。
- 另一层风险是 `auto_approve_patterns` 位于文件权限检查之前：若配置宽泛的工具名自动放行，敏感文件规则会被整体跳过。

### 2. 执行作用域层：决定“能否真正落盘”

- `crates/foundation/wf-types/src/config/file_scope.rs` 定义 `ResolvedFileScope`：`enabled`、`read_prefixes`、`write_prefixes`、`checkpoint_prefixes`、`workdir`。作用域按全局默认 → 父执行 → 节点声明 → 调用参数逐层合并，显式空列表表示拒绝全部。检查点前缀必须是写前缀的子集，工作目录必须落在读/写前缀内，所有前缀必须位于工作区根之内。
- `crates/app/wf-server/src/directory.rs` 把请求携带的目录作为默认作用域，读写与检查点前缀都是该目录。`check_explicit_file_scope` 只允许请求方收窄，不允许把绝对路径扩到请求目录之外。
- `crates/engine/wf-tools/src/scope_gate.rs` 先做词汇前缀包含，再做物理路径检查（不存在文件用父目录规范化），返回界内、界外、软链接逃逸三态。
- `crates/engine/wf-tools/src/filesystem/scope.rs` 解析路径后执行门控；写操作在所有沙箱模式下都 fail-closed，`Lenient` / `Disabled` 只放宽读。
- `crates/engine/wf-tools/src/filesystem/handlers_write.rs` 的 `finish_write_gate` 要求写路径同时落在写前缀和检查点前缀内，否则拒绝。这是为了避免“写成功但检查点不记录、无法恢复”的隐性副作用。
- `crates/engine/wf-tools/src/shell.rs` 让启动目录和命令抽取出的读写路径共用同一个门，并把前缀注入沙箱文件系统策略；会话 shell 走同一套判定。

### 3. 沙箱与命令分析层：底层路径规则

- `crates/infra/wf-sandbox/src/default_policy.rs` 的默认文件系统路径列表为空且模式严格；`crates/infra/wf-sandbox/src/policy.rs` 按字段合并策略，执行作用域注入的前缀会覆盖空默认值。
- `crates/infra/wf-sandbox/src/strategy/shell/vfs_paths.rs` 负责命令分词、重定向识别和路径提取，审批层和执行层共用它，避免两套分析漂移。
- `crates/infra/wf-sandbox/src/allow_once.rs` 提供按命令指纹的一次性放行码，但它是命令级临时例外，不是路径授权，也不能越过执行作用域。

### 4. 关键不变量

**人工批准一次工具调用，不等于可以写任意路径。** 审批层解决“是否可信”，执行作用域解决“能否安全落盘并恢复”。任何新授权通道都必须保持这个分离。

## 二、问题清单

1. **路径授权粒度太粗。** `crates/app/tui/tui-components/src/approval_overlay.rs` 的 `ApprovalRemembered` 只按工具名记住会话决定；用户按 `a` 允许一次 `write_file` 后，该会话内所有路径的写文件调用都会被自动放行。无头模式的 `--approve-prefix` 同样是工具名/命令前缀维度。
2. **工作区外路径没有受控通道。** `check_within_workspace` 与 `check_explicit_file_scope` 拒绝工作区外的绝对路径。`approve_changes --paths`（`crates/app/cli/wf-cli-shared/src/cmd/approval.rs`）已经支持批量按路径批准检查点变更，但那是变更合并审批，不是工具执行授权。
3. **环境配置任务反复打断。** 默认规则把 `.env`、`.env.*` 等设为拒绝，天然需要逐次人工确认；用户想一次性授权“本会话可以改这些配置文件”时，只能放宽整类工具或改全局规则，代价过高。
4. **`/tmp` 语义缺位。** 代码中出现的 `/tmp` 大多是内部溢出文件、检查点临时 git 目录和测试夹具。工作区内的 `.wf/tmp` 是易失暂存区，被检查点扫描忽略；系统临时目录里的溢出文件不在作用域内，模型无法用文件工具读回。若用户显式以 `/tmp` 作为会话目录，它本来就是合法工作区，不需要硬编码特例；除此之外，审批无法让它进入作用域。
5. **模型看不到授权状态。** 稳定系统头只给出工作目录（`crates/engine/wf-resource/src/dynamic/system_context.rs`），作用域错误只提示“在工作目录内并保持路径在允许前缀下”，不列出实际前缀。`crates/engine/wf-agent/src/approval.rs` 的 `RejectionMessageBuilder::build_user_message_hint` 有工具名变化提示模板，但只在测试里被调用，没有接到真实授权变化上。
6. **命令路径抽取存在读写偏差。** 重定向目标被识别为写，但 `rm -rf /tmp/x` 中的 `/tmp/x` 在路径抽取里是读；做路径级授权时必须以执行层实际解析出的路径为准，不能直接用审批层原始 token。

## 三、设计目标与不变量

- 审批层的授权结果不直接越过执行层：它决定是否还需要问人，必须经过作用域解析把授予路径显式纳入临时写前缀，落盘仍由作用域门、检查点门和沙箱裁决。
- 工作区外路径只有在**显式预设或显式人工授权**下才能进入作用域；模型调用参数永远不能申请扩大作用域。
- 工作区外写入默认不进入检查点，必须在授权、工具结果和模型说明中明确告知“不可恢复”，不得静默放行。
- 不可覆盖的安全底线（密钥、证书、凭据）先于任何授权判定，预设不能把硬拒绝项变成可写。
- 增量说明只在状态变化时生成，按稳定键替换旧说明，不随每轮对话重复注入。
- 不保留旧配置兼容映射，不升级版本号，不新增“替代版”模块；所有改动落在现有模块。

## 四、路径授权模型

### 1. 统一授权条目

在 `crates/foundation/wf-types` 定义统一的授权条目，供配置、交互响应和执行层共用。字段表达：路径或 glob、操作类型（读/写/配置）、适用范围（当前执行/整个会话）、过期时间、来源（预设/命令行/交互）、原因说明、是否可恢复。

授权判定放在 `ToolApprovalCoordinator::check_approval` 的文件权限阶段之前或作为其最高优先级层，并把 `auto_approve_patterns` 移到文件权限判定之后，避免工具名白名单绕过安全底线。判定顺序固定为：硬拒绝底线 → 有效授权 → 文件权限规则 → 写保护 → 风险等级分支。

路径匹配必须使用执行层解析后的规范化路径：绝对路径直接保留，`~` 和环境变量在会话启动时展开，相对路径按工作目录解析，符号链接按同一套物理路径检查。命令抽取出的原始 token 不直接用于授权匹配。

### 2. 路径授权预设

预设是命名的、声明式的授权集合，在会话开始前选择，多个预设取并集；会话中途追加的授权也进入同一个授权存储。预设只提供候选路径，不改变“必须问人”的其它风险判定。

建议内置三类预设：

- **工作区预设**：当前默认行为，只读读写均限定在请求目录，写必须可检查点恢复。
- **用户配置预设**：面向环境设置任务，路径来自用户家目录下的显式配置文件清单，例如 shell 配置、应用配置、env 文件；清单必须由用户或配置声明，不使用宽泛通配。该预设默认只授予特定文件的写权限，读权限可包含相邻配置目录。
- **临时目录预设**：面向测试与构建任务，根目录取进程环境提供的临时目录，不在代码里写死 `/tmp`。该预设授予的写路径显式标记为“非检查点、会话结束可丢弃”，并设置较短期限。

用户可以在工具审批配置段中自定义预设：每个预设声明名称、路径列表、操作类型、过期策略、是否允许工作区外、是否要求二次确认。启动时校验：工作区内路径必须落在工作区根内；工作区外路径必须声明为非检查点；同一个路径出现在多个预设时按最窄权限和最短期限收敛。

### 3. 工作区外路径如何真正生效

仅放宽审批不足以让工作区外路径可用，需要把授权结果翻译成执行作用域的一部分，同时保留审计和恢复语义：

- `ResolvedFileScope` 增加一组显式的“临时写前缀”。它们进入读前缀和写前缀，但**不进入** `checkpoint_prefixes`，且与检查点前缀互斥。
- `finish_write_gate` 允许写落在检查点前缀或临时写前缀；命中后者时在工具结果和消息元数据中标记不可恢复，而不是当成普通成功。
- shell 门、沙箱文件系统策略、MCP 与代码上下文的读门都要把临时写前缀纳入同一套判定，避免某一执行器漏掉。
- `check_within_workspace` 的约束只作用于常规前缀；临时写前缀只允许来自预设或会话级显式授权，并受来源目录和期限约束。服务端按请求传来的 `file_scope` 仍不得携带工作区外绝对路径，外部路径只能由宿主选择的预设引入。
- 临时写路径上的删除操作需要独立的删除授权；不能因为给了写权限就默认允许删除。`wf-sandbox` 的 `allowed_remove_paths` 保持单独配置。

### 4. 入口与生命周期

- **会话开始前**：命令行提供可重复的授权路径参数与预设选择参数；配置文件提供预设定义和默认启用的预设。适合“这一轮就要改用户配置”或“测试任务需要临时目录”的场景，一次性完成授权。
- **会话中途**：审批响应扩展为可携带批量路径（`crates/foundation/wf-types/src/interaction/tool_approval.rs`），交互层提供“允许这些路径”的输入；复用文件变更审批 `--paths` 的多路径表达方式。
- **TUI 记忆**：`ApprovalRemembered` 从“工具名 → 是否允许”收敛为“工具名 + 规范化路径 + 操作 → 授权”，避免粗粒度记忆绕过新通道。`/new` 清空会话时同步撤销所有会话级授权。
- **无头模式**：`--approve-prefix` 保留工具/命令预授权语义，新增路径参数写入同一个授权存储；不并行维护第二套策略引擎。
- **撤销与过期**：授权记录带会话 id、执行 id 和期限；撤销后尚未使用的授权立即失效，已进入执行中的调用保持当次一致性，不追溯回滚已完成写入。

## 五、通用增量说明抽象

### 1. 两种承载方式

现有尾消息机制服务于“必须放在末尾以提高注意力”的信息：当前时间、待办、工作区树、工具可见性变化。路径授权变化不需要这种强调，因此引入与位置解耦的增量说明：

- **尾消息承载**：保留现有行为，用于需要模型立即注意的内容，例如工具被封禁、工具声明变化。
- **内联承载**：用于补充性增量说明，例如新增/撤销的路径授权、未来其它上下文提示。它作为独立、带标记的消息出现在装配后的对话中，但不要求位于末尾。

抽象本身只描述“是什么变化”和“如何承载”，不规定具体插入点；具体用途通过承载方式声明。

### 2. 说明条目

在 `crates/engine/wf-execution-shared/src/agent_prompt` 定义统一的增量说明条目：稳定键、文本、承载方式、输入快照指纹。稳定键用于替换旧说明，指纹用于判断是否需要生成新说明。

配套提供统一的过滤与装配函数：按稳定键清除旧说明，按当前快照生成说明，再按承载方式放置。内联说明放在稳定系统头之后、易变尾消息之前；尾消息仍追加在末尾。原始用户任务消息保持纯净，不被说明改写。所有说明都使用用户角色加元数据标记，避免系统角色被网关合并进前缀系统块，也避免工具角色引入伪造的调用关联。

### 3. 与现有机制的收敛

- `crates/engine/wf-execution-shared/src/agent_prompt/tail_ops.rs` 中分散的 `dynamic_context`、`tool_visibility`、`tool_change` 标记收敛为同一说明类型下的不同稳定键；`strip_dynamic_context_messages` 和 `strip_tool_announcements` 合并为按键清理的单一路径。
- `crates/engine/wf-agent/src/tool_snapshot.rs` 的工具快照差异继续生成工具变化文本，但产物改为增量说明条目，承载方式保持尾消息，因为“工具不可再调用”需要模型立刻知道。
- 路径授权变化新增说明条目，承载方式为内联；只在授权快照发生差异时生成，无变化时不注入。
- `RejectionMessageBuilder::build_user_message_hint` 只有工具名变化且未被调用，不再单独保留；拒绝信息仍走工具结果信封，授权状态变化走统一说明。
- 装配只在组装边界改写对话副本；智能体会话历史保持 append-only，`message_ops` 的插入/替换仍只服务工作流草稿上下文，不用于 agent 历史。

### 4. 说明内容边界

路径授权说明只列增量：新增/撤销的路径、操作类型、期限、是否可恢复，并明确“仍需满足执行作用域和检查点约束”。不输出凭据内容，不把“审批已放行”表述成“可绕过作用域”。初始即存在的预设授权也在循环入口生成一次说明，后续仅在变化时更新。

作用域错误信息同步增强：列出当前允许的读前缀、写前缀和临时写前缀，减少模型试错。

## 六、落地顺序

1. 契约层：定义授权条目、预设配置与增量说明条目，统一元数据标记和稳定键；配置解析支持预设与启动期授权参数。
2. 授权层：在 `wf-tools` 建立会话授权存储与判定入口，收敛工具名白名单顺序，接入硬拒绝底线与路径归一化。
3. 执行层：扩展 `ResolvedFileScope` 的临时写前缀，接通文件系统、shell、沙箱、MCP、代码上下文的读写门与不可恢复标记。
4. 交互层：审批响应支持批量路径，TUI 与无头 CLI 接入路径授权；服务端保留工作区边界，预设只能由宿主选择。
5. 提示层：落地增量说明抽象，迁移工具变化说明，新增路径授权说明与更具体的作用域错误提示。
6. 文档与自检：更新 `docs/engine/tools/`、`docs/config/` 中对应语义说明，补充配置模板注释；只新增必要测试，不额外扩大编译范围。

## 七、验证要点

- 授权优先级：硬拒绝项不能被预设或会话授权放行；工具名白名单不能绕过敏感文件规则。
- 路径正确性：`..`、软链接、大小写、反斜杠、`file://`、家目录展开与临时目录展开在审批和执行层得到同一结论。
- 工作区边界：常规前缀不能越出工作区；临时写前缀只能来自预设或显式授权，且不能进入检查点前缀。
- 不可恢复语义：临时写路径的成功结果带不可恢复标记；检查点前缀内写仍保持原有可恢复行为。
- 生命周期：会话级授权在 `/new`、执行结束或过期后撤销；中途追加的授权能立即生效且不污染其它会话。
- 说明幂等：授权无变化时注入为空；同一稳定键只保留最新说明；工具变化说明仍在末尾，路径说明不占用末尾；系统前缀字节保持稳定。
- 命令路径偏差：`rm` 等写类命令的参数路径按写授权判定，不因审批层将其识别为读而错误放行。

## 八、非目标与风险

- 不硬编码 `/tmp` 或任何用户路径；临时目录来自进程环境或用户配置，工作区外路径来自预设。
- 不允许模型通过工具参数申请扩大作用域；预设选择权始终在用户或宿主配置。
- 不做旧配置别名、旧审批记忆的兼容迁移；开发期版本号保持不变。
- 工作区外写入天然不受检查点保护，必须接受“不可恢复”代价；如果任务需要可恢复性，应把这些路径纳入工作区而不是使用临时预设。
- 授权说明不应成为安全边界，它只改善模型理解；真正的拒绝仍由执行层产生。

## 九、本轮落地范围

已落地：

- `wf-types` 定义路径授权条目与预设，工具审批配置支持 `active_presets` 与 `[presets.<name>]`，内建 `scratch` 预设从进程临时目录派生路径。
- `wf-tools` 审批协调器在文件权限判定前应用路径授权；工具名白名单移到文件权限之后；凭据、密钥、证书不受授权影响。
- `file_scope` 新增临时写前缀，与检查点前缀互斥；文件系统、shell、MCP、沙箱共用该前缀集；临时写入的结果文本标记不可恢复。
- 配置装配把非检查点授权前缀注入默认执行作用域，工作区根约束只作用于常规前缀。
- `wf-execution-shared` 提供统一增量说明条目，工具变化沿用尾承载，路径授权说明使用内联承载并按稳定键替换；作用域错误列出实际前缀。

尚未落地：会话中途新增授权的持久化通道与 TUI 路径级记忆 UI。当前授权在会话开始前由预设批量生效，会话中途仍走逐次审批。

## 十、状态持久化与披露控制的补充落地

- `PathGrant` / `PathGrantPreset` 增加 `disclosure`（`paths` / `category` / `none`）。模型说明由 `AuthorizationState` 生成：`paths` 列具体路径，`category` 只列预设名，`none` 完全不发送。
- `AuthorizationState` 记录已应用预设、生效授权与可披露分类，随 `AgentStateSnapshot.authorization` 与 `AgentLoopState.authorization` 持久化；恢复时优先用快照状态，只有新运行才从宿主审批配置初始化。
- 授权说明在每轮请求装配时从持久化状态重算，先移除旧的同键说明再追加，避免压缩历史残留导致说明与权限不一致。
- `AgentLoopEntity` 提供会话级预设应用/撤销入口，可更新持久化授权状态；CLI/TUI/slash 命令与服务端入口尚未接线。
- 启动期 `assemble_agent_prompt` 不再推导授权说明，避免读到调用方未解析的 scope 造成“工具能写但模型不知道”的偏差。
