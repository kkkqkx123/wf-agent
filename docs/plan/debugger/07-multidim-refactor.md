# 调试器多维补齐重构方案：循环 / 合并 / 中断 / 检查点 / 交互 / 子 Agent / 大模型成本

> 范围：本文件承接 `06-supplement.md` 指出的覆盖度缺口，给出 `debugger` 为系统性补齐七个调试维度所需的重构路径。约定不变：中文撰写、自然语言为主、不贴完整代码实现；所有事实声明附 `file:line` 引用。

## 一、现状盘点

调试器当前为应用层叶子独立目标，包名为 `wf-debugger`、二进制为 `wf-debug`（`crates/app/debugger/Cargo.toml:1-13`），库入口以扁平文件声明十余个公开模块（`crates/app/debugger/src/lib.rs:1-14`），无任何生产 crate 反向依赖。依赖仅为基础层与通用第三方库（`crates/app/debugger/Cargo.toml:15-23`），不依赖引擎层，符合补充设计中轻量构建的决策（`docs/plan/debugger/06-supplement.md:28`）。

各模块当前职责大致如下：`model.rs` 承载 trace 信封、步骤记录与十余种视图（`crates/app/debugger/src/model.rs:15-103` 为信封与步骤，`105-279` 为各视图）；`observe.rs` 只做变量与消息的前后 diff（`crates/app/debugger/src/observe.rs:38-150`）；`replay.rs` 做逐步骤聚合计数（`crates/app/debugger/src/replay.rs:42-104`）；`branches.rs` 评估单个路由决策点（`crates/app/debugger/src/branches.rs:35-106`）；`hook_dbg.rs` 按类型分组解释 hook 命中与跳过（`crates/app/debugger/src/hook_dbg.rs:30-96`）；`trigger_dbg.rs` 做模板干跑与已有记录汇总（`crates/app/debugger/src/trigger_dbg.rs:35-136`）；`agent_dbg.rs` 以内置静态策略核对工具调用（`crates/app/debugger/src/agent_dbg.rs:22-117`）；`assert.rs` 覆盖步骤、变量、路由、hook、trigger 与三类工具断言（`crates/app/debugger/src/assert.rs:5-42`，求值在 `69-267`）；`format.rs` 与 `timeline.rs` 分别负责人读文本、机读 JSON 与线性时间线（`crates/app/debugger/src/format.rs:4-89`，`crates/app/debugger/src/timeline.rs:12-50`）；`cli.rs` 提供七个子命令的解析、加载与分发（`crates/app/debugger/src/cli.rs:15-24` 为命令枚举，`111-306` 为分发）。

对照引擎现状，七个维度的缺口如下。

循环维度只记录了循环标识、轮次、当前条目与是否失败（`crates/app/debugger/src/model.rs:169-177`），而引擎的循环状态包含迭代对象、下一消费下标、最大迭代数、已启动迭代数、连续失败与累计失败、当前迭代失败标记、失败策略、连续失败阈值、导入变量、迭代启动标记与本轮已完成节点（`crates/engine/wf-workflow/src/loop_state.rs:30-70`），且状态以栈的形式存放在保留变量键下以支持嵌套与检查点恢复（`crates/engine/wf-workflow/src/loop_state.rs:22-29`，读写在 `75-97`）。因此嵌套循环隔离、计数循环与可迭代循环的区分、失败吸收策略的实际效果、迭代上限的触发来源、断点恢复后是否重放或跳过本轮节点，均无法解释；回放、时间线与断言当前也完全不消费循环视图。

合并维度只记录了汇合节点、分支数、吸收的失败数与汇总值（`crates/app/debugger/src/model.rs:179-188`），而引擎的分支结果包含分支标识、成败、输出、错误与分支公开变量快照（`crates/engine/wf-workflow/src/barrier.rs:1-12`），失败策略区分快速失败、错误继续与阈值失败（`crates/engine/wf-workflow/src/barrier.rs:50-62`），汇合结局区分成功、失败与部分成功。调试器因此说不清每个分支各自产出什么、哪个分支的变量被合并、阈值策略下为何是部分成功而非失败。

中断维度只记录了类型字符串、是否恢复与明细（`crates/app/debugger/src/model.rs:190-198`），回放仅以字符串匹配统计超时（`crates/app/debugger/src/replay.rs:73-79`），时间线不展示中断（`crates/app/debugger/src/timeline.rs:12-50`）。而引擎的中断信号区分活跃、暂停与停止（`crates/foundation/wf-core/src/interruption.rs:12-23`），且工作流快照中已有中断统计总量、类型分布、平均耗时与恢复率，以及中断记录、事件记录与超时计数（`crates/engine/wf-workflow/src/state.rs:31-60`）。暂停与停止的区分、取消与超时的归因、中断持续时长与恢复率、父子执行间的中断传播，均无处展示。

检查点维度只记录了时机字符串与检查点标识（`crates/app/debugger/src/model.rs:200-205`），文本输出仅打印时机、时间线仅打印时机标签（`crates/app/debugger/src/format.rs:73-75`，`crates/app/debugger/src/timeline.rs:34-40`）。而引擎的检查点时机覆盖节点前后、节点错误、工作流起止、暂停、取消与超时（`crates/engine/wf-workflow/src/checkpoint/strategy.rs:9-18`），节点策略还支持按节奏触发（同文件策略结构），hook 点到检查点时机的映射已有明确归属（`crates/engine/wf-workflow/src/hook.rs:79-113`）。调试器回答不了应存未存、 cadence 与实际是否一致、恢复边界是否对齐、hook 请求的检查点与策略驱动的检查点如何区分。

交互维度只记录了交互标识、提示、是否挂起、响应与是否超时（`crates/app/debugger/src/model.rs:207-217`），回放只统计挂起数（`crates/app/debugger/src/replay.rs:70-72`）。而引擎的交互注册表是进程级挂起通道表，支持注册、完成、移除、挂起数与是否挂起查询（`crates/engine/wf-workflow/src/interaction.rs:20-67`），等待端在丢弃时自清理以防泄漏（同文件等待结构的设计意图在 `92-100` 附近），审批请求本身也带有挂起队列（`crates/engine/wf-execution-shared/src/approval.rs:17-33`）。挂起与超时的区分、等待时长、未完成即丢弃的泄漏或自清理、交互与审批的关联，均无法调试。

子 agent 维度仅靠步骤嵌套数组表达父子关系（`crates/app/debugger/src/model.rs:101-102`），回放只对子步骤计数而丢弃其 diff 与失败明细之外的信息（`crates/app/debugger/src/replay.rs:80-86`），时间线把子步骤打平成附属标签（`crates/app/debugger/src/timeline.rs:41-47`），策略核对不下钻子步骤。而引擎的 agent 实体记录了父执行标识、子执行标识集、层级深度、根执行标识与祖先链（`crates/engine/wf-agent/src/entity.rs:17-59`），触发式子执行配置包含结果变量、是否等待完成、超时、对话锚点、输入模式与写回位置（`crates/engine/wf-agent/src/trigger.rs:41-63`）。父子变量继承与输出映射、对话切片的锚点与回退、写回冲突的取舍、层级深度与环，均无递归视图。

大模型成本维度只记录了 profile、模型、提示与补全 token、内容预览、工具调用数与错误（`crates/app/debugger/src/model.rs:131-147`），而回放、格式化与时间线当前完全不消费该视图（`crates/app/debugger/src/replay.rs:42-104` 无 token 累加，`crates/app/debugger/src/format.rs:4-78` 只打印工具，`crates/app/debugger/src/timeline.rs:12-50` 无模型事件）。而引擎的单次请求用量包含提示、补全、合计、推理、缓存读写的 token 数、费用与模型（`crates/engine/wf-execution-shared/src/token_tracker.rs:17-33`），且决策轨道与成本轨道分离、估算标记不混入决策（同文件头部设计说明在 `1-11`）。预算来源、告警阈值、超限与压缩触发、估算与厂商上报的区分、缓存命中对成本的影响，均无法解释。

## 二、结构性问题归纳

第一，步骤记录正在演变为上帝结构。七个维度若各自直接加字段与视图，步骤定义、回放聚合、文本格式化、命令分发四处必须同步修改，新增一个维度就触碰全部核心文件。

第二，遍历逻辑重复且对嵌套不一致。回放、时间线、断言、策略核对、hook 与 trigger 各自循环顶层步骤；子步骤有时计数、有时打平、有时忽略，没有统一的深度优先遍历与路径标识。

第三，弱类型字符串字段过多。中断类型、检查点时机、节点类型、许可结果多为自由字符串，回放靠字符串包含判断超时等做法脆弱，新增取值时编译器无法提示遗漏。

第四，机读输出丢信息。格式化 JSON 只回显输入断言而不含断言结果、不含变量与消息 diff，机读方可复算但回归比对不便（`crates/app/debugger/src/format.rs:80-89`）。

第五，命令层臃肿。七个子命令各自持有加载、求值、打印与退出码逻辑（`crates/app/debugger/src/cli.rs:123-306`），新增维度会继续拉长同一文件。

第六，内置策略为手抄副本。agent 工具契约以静态表形式镜像引擎模板（`crates/app/debugger/src/agent_dbg.rs:32-94`），模板一变调试器即过期，且拒绝文案靠子串匹配，误判空间大。

第七，缺少从引擎到 trace 的导入器。当前 trace 全靠手写或测试构造，真实运行的节点记录、循环栈、分支结果、中断统计、token 用量无法一键转为可调试输入，补齐维度后手写成本更高。

## 三、重构原则与约束

继续保持应用层叶子定位，不被任何生产 crate 反向依赖；默认构建仍只依赖基础层与通用第三方库，不引入引擎重设施。确需复用引擎真实语义时，以可选特性门控的桥接模块承载，默认关闭。

遵循仓库既有规范：每个 crate 的入口直接声明公开模块，扁平文件，不使用嵌套模块目录；只按职责拆分，不为求新另起替代性模块；开发阶段不保留旧数据兼容，不做版本迁移，旧 trace 按新结构为准，不保留冗余兜底逻辑。

输出保持文本与 JSON 同源；断言与策略核对失败一律同时给出期望与实际，并以非零退出码结束，便于门禁集成。

## 四、目标目录与模块职责

重构不改变对外二进制形态，只调整库内分工。调整方向是把当前大文件按职责拆薄，把各维度收敛为职责对等的分析器，把遍历、汇总、输入、呈现收拢为共享层。

 trace 信封建议拆为 trace 主体、步骤核心与视图三类扁平文件：trace 主体负责 trace 级标识、初始变量、模板集与断言集；步骤核心负责步骤身份、输入输出、成败、错误分类、耗时与嵌套引用；视图按职责归组，例如工作流视图收敛循环轮次与合并结果，agent 视图收敛工具调用、模型调用、审批与可见性，运维视图收敛中断、检查点与交互， hook 与 trigger 视图保持独立。每组只描述本职责的数据，不互相引用。

新增统一遍历模块，职责是提供唯一的深度优先步进器，产出路径、深度与父子引用；所有分析器、回放、时间线、断言都走该步进器，子步骤不再各自特殊处理。新增统一报告模块，职责是合并各分析器的分报告与覆盖率，文本与 JSON 只消费该统一报告。新增输入模块，职责是 trace 加载、结构版本校验与变量文件加载，把当前散落在各命令中的加载逻辑收拢。命令解析保留在原解析文件，命令执行按职责下沉到各分析器或统一运行器，避免解析文件继续膨胀。

七个维度各设一个职责单一的分析器文件：循环分析、合并分析、中断分析、检查点分析、交互分析、子执行层级分析、大模型成本分析。既有分支、hook、trigger、agent 策略分析器保留，但统一为相同的分析器形态：输入为 trace 与求值上下文，输出为分报告、断言扩展与展示片段。共享的 diff 能力保留在观察模块，不下沉到各分析器。

## 五、统一遍历与统一报告的设计要点

遍历语义上，顶层步骤按序号推进，子步骤按父子引用递归进入；每个访问点同时可见当前步骤、祖先链与深度；hook、trigger、工具、模型调用作为步骤的附属事件按固定顺序挂靠，避免时间线与回放对同一 trace 产出不同顺序。覆盖率语义上，路由分支、循环轮次、合并分支、触发模板、中断恢复路径分别计数，最终汇总为统一覆盖率视图，而不是各模块自说自话。

报告语义上，每个分析器只产出本职责的结论：命中明细、落选原因、计数、违规或告警；统一报告负责合并冲突（例如同一工具失败同时被工具分析与成本分析提及）与排序；文本呈现负责折叠超长载荷并支持无色开关，机读呈现不折叠不染色，且必须包含 diff、断言结果与各分报告，纠正当前机读丢信息的问题。

## 六、七维度补齐方向

循环补齐需要表达嵌套与恢复语义。trace 侧除轮次标识外，应记录循环栈快照的摘要信息：迭代对象类型、当前下标、上下界、失败计数与策略、本轮已完成节点；分析侧解释每一轮为何进入下一轮、失败被吸收还是向上传播、上限由哪一层配置触发、恢复后本轮节点是否重放；断言侧支持轮次断言、失败阈值断言与上限触发断言；展示侧按循环标识分组轮次，避免长循环淹没主线。

合并补齐需要表达分支级因果。trace 侧记录每个分支的成败、输出摘要、错误与公开变量快照摘要；分析侧复述失败策略的求值过程：快速失败在第几个分支止损、阈值策略的分子分母、错误继续时吸收了哪些失败；断言侧支持分支结果断言、合并结局断言与变量合并断言；展示侧在汇合点内嵌分支表，失败分支附实际错误。

中断补齐需要表达类型与恢复。trace 侧将中断类型收敛为枚举口径：暂停、停止、取消、超时，并记录持续时长与是否恢复；分析侧汇总类型分布、平均耗时与恢复率，对标引擎快照已有统计口径；断言侧支持中断次数断言、超时阈值断言与未恢复中断告警；展示侧把中断作为时间线一等事件，而非仅在步骤内附注。

检查点补齐需要表达预期与实际的对照。trace 侧将时机收敛为枚举口径：节点前后、节点错误、工作流起止、暂停、取消、超时，并记录检查点标识与触发来源（策略驱动或 hook 请求）；分析侧对照节奏配置解释应存未存的缺口，以及恢复边界是否落在最新检查点之后；断言侧支持检查点存在性断言与边界新鲜度断言；展示侧在时间线上以独立事件呈现检查点，而非仅作步骤标签。

交互补齐需要表达生命周期。trace 侧记录交互从挂起到完成或超时的终态、等待时长与响应摘要；分析侧区分正常完成、超时、未完成即丢弃三类终态，并关联同步骤的审批请求；断言侧支持挂起残留断言、超时断言与响应内容断言；展示侧对超时与残留挂起高亮实际等待时长与提示内容。

子执行补齐需要表达层级与数据流。trace 侧记录父子引用、层级深度、根标识、结果变量、是否等待、超时、对话锚点、输入模式与写回位置；分析侧校验祖先链完整性、深度合理性、写回冲突的取舍，并解释子执行输入切片的回退原因；断言侧支持层级深度断言、写回位置断言与超时传播断言；展示侧提供可折叠的递归视图，默认只展开一层，支持按路径下钻。

大模型成本补齐需要表达用量与预算。trace 侧在单次调用中补齐合计、推理、缓存读写 token 数、费用与模型标识，在 trace 级记录预算来源、告警阈值与超限标记；分析侧区分决策用量与成本用量，解释告警与超限由哪一次请求触发、估算值与厂商上报值是否一致、缓存命中如何影响费用；断言侧支持单步用量断言、累计预算断言与超限告警断言；展示侧汇总调用次数、总 token、总费用与超限点，并支持按模型与 profile 分组。

## 七、命令与输入层的调整

解析与执行分离：解析文件只保留命令与参数形状，加载与版本校验收拢到输入模块，执行逻辑下沉到统一运行器与各分析器。新增维度不再新增顶层子命令，而是作为统一检查的子分析参与默认报告；确需单独深挖的维度（如成本明细、层级下钻）再提供聚焦子命令，避免命令数量与维度数量线性膨胀。

退出码语义统一：断言失败、策略违规、未恢复中断、残留交互、超限未告警均归入非零退出；仅做只读展示时保持零退出。文本与 JSON 共享同一退出判定来源。

## 八、结构版本与导入策略

不做旧数据兼容，trace 结构按新模型为准；版本标识仅用于明确报错，不做自动迁移。导入器以 JSON 形态对接引擎快照，避免调试器默认依赖引擎类型：节点记录、循环栈、分支结果、中断统计、token 用量、父子引用均先转为 trace 的 JSON 视图再参与分析。确需调用引擎真实求值语义的场景，放在特性门控的桥接模块中，默认构建不受影响。

内置 agent 策略不再手抄：以引擎模板为唯一来源，在构建期或测试期生成调试器可读的策略快照；拒绝文案的匹配从子串收敛为策略判定口径，偶发失败与策略拒绝明确区分。

## 九、阶段划分与验收

先做共享层：统一遍历、统一报告、输入收拢与机读补全，验收为既有样例在新管线下输出一致且机读包含断言结果与 diff。再按依赖顺序补维度：先循环与合并（工作流主干），再中断与检查点（运维主干），再交互与子执行（嵌套与人机主干），最后大模型成本（用量主干）。每个维度验收为内置样例覆盖正常与异常各一例、文本与 JSON 双形态一致、对应断言失败时给出期望与实际。随后做命令收敛与策略单源，验收为解析文件行数不再随维度增长、策略快照由生成流程产出。最后补充导入器，验收为一份真实快照可一键转为 trace 并通过统一管线输出报告。

## 十、风险与取舍

主要风险在于引擎语义漂移：hook 门控点、trigger 仲裁与预算、循环失败策略、合并阈值、压缩写回的版本取舍都可能先于调试器变化。缓解方式是分析器只做数据驱动解释，真实驱动复用放在特性门控之后，并以引擎快照口径为唯一对照，不自创标准。

其次是快照成本：每步全量克隆变量在大 trace 下昂贵。首版仍以全量快照保证正确，优化只针对未变化值的共享，且优化不得改变 diff 语义。

最后是范围蔓延：七个维度一次铺开容易失控。按上节阶段顺序交付，每个阶段结束即有一个可用的调试器，避免长期不可用。

## 十一、与既有设计的关系

本文件不替换总览与可观测、分布、hook 与 trigger、格式化与断言、落地方案中的结论，只收敛补充设计指出的缺口。数据源仍以导入式回放为主，分支穷尽仍以路由解释为一期范围，实时驱动仍为二期；本文件的共享层与七个分析器是对该路线的结构承载。
