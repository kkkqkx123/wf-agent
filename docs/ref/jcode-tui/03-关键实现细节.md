# 03 关键实现细节

本章给出各优化点的具体设计。算法用伪代码描述，落地时对应 `wf-tui` 内的新模块。

## 1. 增量准备（替代全量重排）

### 1.1 数据结构

`HistoryLine` 保持不变（仍保存源文本），新增一层索引：

```
struct RowIndex {
    /// 每条源行占据的显示行数（在当前 width 下）
    heights: Vec<u16>,
    /// 显示行总数
    total: usize,
    /// 前缀和，用于 O(log n) 定位第 k 条源行的起始行
    prefix: Vec<usize>,
}
```

`PreparedScrollback` 同时保存 `rows: Vec<Line<'static>>` 与 `RowIndex`。滚动与视口只需要 `RowIndex`，不需要重新换行。

### 1.2 追加（最常见的流式路径）

scrollback 是 append-only（除 trim 和 replay 前插）：

```
fn prepare_append(cache, new_lines, width):
    for line in new_lines:
        rows = line.display_lines(width)
        cache.rows.extend(rows)
        cache.index.push(rows.len())
    cache.source_version = current_version
```

成本：O(新增字形数)。这是把稳态流式帧从 O(历史) 降到 O(新增) 的关键。

### 1.3 前插（replay 早期分页）

`ReplayEarlier`（`interactive.rs:565`）会把更早的行前插到 `scrollback` 头部。处理方式：

```
fn prepare_prepend(cache, new_lines, width):
    prepared = flatten(new_lines.display_lines(width))
    cache.rows = prepared.rows ++ cache.rows
    cache.index = prepared.index ++ shift(cache.index, prepared.total)
    // 视口需要补偿：view_scroll 增加 prepared.total，保持视觉锚点
```

现有代码已在 `interactive.rs:586-589` 做了 `view_scroll` 补偿，准备层复用同样的语义。

### 1.4 整段替换与裁剪

- `ReplayLoaded` 整段替换：直接全量重排。
- trim（`scrollback.drain(0..drop)`）：不重排，只从 `rows` 头部切掉对应显示行并更新 `index` 偏移。为避免 `Vec::drain` 在头部反复搬移，可用 `VecDeque` 或让索引保存 `base_offset` 逻辑起点。

### 1.5 宽度变化

宽度变化才做全量重排。因为 `HistoryLine::display_lines(width)` 的语义必须保留（resize 重排是 `transcript.rs:4-9` 明确的 ground rule），缓存只是把"每帧都算"变成"宽度变了才算"。

## 2. 重绘范围分级

### 2.1 上一帧缓冲的复用

ratatui 的 `Terminal::draw` 每帧从零构造 buffer，再做后端 diff。要做局部重绘，渲染层自己保留上一帧 buffer：

```
struct FrameCache {
    buffer: Buffer,        // 上一帧完整缓冲
    scrollback_area: Rect,
    footer_area: Rect,
    input_area: Rect,
    animation_area: Option<Rect>,
}
```

绘制：

- `Full`：清空 cache.buffer，完整绘制，`terminal.draw` 直接提交。
- `FooterOnly`：以 `cache.buffer` 为种子，只清空并重绘 footer/input/notice 区域。
- `SpinnerOnly`：以 `cache.buffer` 为种子，只清空并重绘 `animation_area`。

实现上，ratatui 允许先构造 `Buffer`，再用 `Frame` 语义把 widget 渲染进 buffer（`Footer::draw` 已经是 `frame.buffer_mut()` 风格，见 `footer.rs:239`）。提交时用 `terminal.draw` 或 `terminal.backend_mut().draw(buffer.content().iter())`。为避免版本耦合，建议封装一个 `present(terminal, buffer, dirty_rects)`。

### 2.2 动画区域记录

`SpinnerOnly` 需要一个精确 `Rect`：

```
fn record_spinner_area(area: Rect) { SPINNER_AREA.store(pack(area)); }
```

对应 jcode 的 `LAST_IDLE_ANIMATION_AREA`。注意 spinner 前缀插在 streaming 行首（`interactive.rs:967-978`），所以区域是 streaming 行第一行的行首若干列，加上 footer 可能的状态动画。

### 2.3 判定函数

```
fn redraw_scope(prev: &RenderVersions, cur: &RenderVersions,
                area_changed: bool, view_changed: bool) -> RedrawScope {
    if area_changed || view_changed
        || prev.scrollback_version != cur.scrollback_version
        || prev.streaming_version != cur.streaming_version
        || prev.theme_mode != cur.theme_mode { return Full; }
    if prev.footer_version != cur.footer_version
        || prev.notice != cur.notice { return FooterOnly; }
    if prev.motion_tick != cur.motion_tick { return SpinnerOnly; }
    Never
}
```

`Never` 表示无需提交帧，`FrameRequester` 也不需要 `request_frame`。

### 2.4 与帧率限制的关系

`FrameRequester` 不变。变化的是 `request_frame` 的调用条件：只有 `scope != Never` 才请求，且携带 scope。`SpinnerOnly` 可以按较低帧率（如 10 FPS 的 spinner 桶）请求，避免 120 FPS 空转。

## 3. 流式缓速（RevealController）

参照 jcode `stream_buffer.rs`，在 delta 到达与可见文本之间加一层比例控制器：

```
struct RevealController {
    pending: String,      // 已到达未显示的文本
    revealed_bytes: usize,
}
```

核心参数（可调）：

- `BASE_REVEAL_CPS = 180`：基准显示速度。
- `REVEAL_BACKLOG_GAIN = 3.0`：积压越多显示越快。
- `MAX_REVEAL_CPS = 960`：上限。
- `MAX_REVEAL_STEP = 50ms`：单帧最大推进时间，防止卡顿后一次性倾泻。

每帧（或每 tick）调用：

```
fn advance(&mut self, now_ms) -> Option<Frame> {
    let dt = now_ms - last;
    let backlog = pending.len() - revealed;
    let cps = min(MAX_REVEAL_CPS, BASE_REVEAL_CPS + backlog * GAIN);
    let n = clamp(cps * dt, 0, backlog);
    revealed += n;
    // 按字符边界推进，返回新可见文本
}
```

收益：

- 供应商突发时，单帧布局变化被平滑，spinner 与文本不再竞争。
- 每帧新增字形数有上界，配合增量准备，帧成本可预测。
- 积压清零后自然追上，不改变最终内容。

与 markdown 的分工：缓速控制"显示多少字节"，markdown 控制"显示成什么样式"。缓速产生的可见前缀再进入 markdown 解析（或直接进入 committed 区）。

## 4. Markdown 解析节流与增量化

现状：`MarkdownStream::push`（`markdown.rs:76`）每个 token 都跑一次 `boundary()`，其中 `last_top_level_block_start`（`markdown.rs:248`）对整个 buffer 调 `Parser::new`。

### 4.1 节流（低风险、立即收益）

把"累积"与"解析"分开：

```
fn push(&mut self, delta: &str) {
    self.buffer.push_str(delta);
    self.dirty = true;          // 只标脏，不解析
}

fn parse_if_due(&mut self, now_ms) -> Option<MarkdownFrame> {
    if !self.dirty || now_ms - self.last_parse < PARSE_INTERVAL_MS { return None; }
    self.last_parse = now_ms;
    ... 现有 push 的解析逻辑 ...
}
```

解析在帧准备阶段调用，一帧最多解析一次。`PARSE_INTERVAL_MS` 取 16 到 33ms（对应 30 到 60 FPS），显著降低解析频次。

### 4.2 增量化（进一步）

维护已提交前缀的解析结果，只解析未提交尾部：

```
struct MarkdownStream {
    buffer: String,
    committed_upto: usize,   // 已有
    parsed_blocks: Vec<Block>, // 已提交块的渲染结果缓存
    parse_cursor: usize,     // 已解析到的字节位置
}
```

由于 markdown 解析存在"引用定义会回改前文"以及"表格未闭合会改变列宽"的语义（`markdown.rs:198-241`），完全的流式解析有正确性风险。稳妥方案是分层：

1. 维护"安全前缀"：最后一个被空行确认闭合的顶层块之前，解析结果不可变，缓存 `parsed_blocks`。
2. 只对安全前缀之后的尾部重新解析（通常只有最后一个块）。
3. 引用定义/表格/围栏未闭合时退化为全量解析（沿用现有 holdback 规则）。

上层用完全相同的 `render_plain_text` 做最终化兜底（`markdown.rs:155` `final_plain_text`），保证与全量渲染一致。

### 4.3 已提交/流式的边界保持不变

`MarkdownFrame { new_committed, new_streaming }` 的对外语义不变，只改变内部触发时机。已有大量等价性测试（`markdown.rs:948` `assert_streamed_equals_full`）可以直接复用来验证优化后的实现。

## 5. 主题 buffer 单点适配

现状：`theme.rs` 提供 `ColorRole` 与 `dark_default` / `light_default`（`theme.rs:312`、`theme.rs:329`），样式在每个 widget 内解析。好处是简单，坏处是新增浅色适配需要碰每个 widget。

参照 jcode `theme_mode.rs`：

1. 新增 `ThemeMode { Dark, Light }`，启动时由 OSC11（`capabilities.rs` 已探测 `default_colors`）或配置决定。
2. 绘制完成后，对整个 `frame.buffer_mut()` 做一次适配：

```
fn adapt_buffer_for_theme(buf: &mut Buffer, mode: ThemeMode) {
    if mode == Dark { return; }
    for cell in buf.content.iter_mut() {
        // 色相保持的亮度翻转
        if let Some(fg) = cell.fg_for_theme() { cell.set_fg(flip(fg)); }
        if let Some(bg) = cell.bg_for_theme() { cell.set_bg(flip(bg)); }
        // Color::Reset 保持不变，让终端自身背景透出
    }
}
```

3. `Color::Reset` 保留，这样终端自己的浅色背景可以显示。

好处：

- 主题适配只有一个 choke point，新增角色不需要改 widget。
- 与 `ColorDepth`（`capabilities.rs:72`）联动：只有 truecolor 才做精确翻转，ANSI16/256 走降级映射。
- 与现有 `Theme::light_default` 不冲突：`light_default` 可作为"显式浅色配置"，buffer 适配作为"未显式配置时的兜底"。两者取其一，避免双重翻转。

## 6. 动画纯核与降本

现状 `motion.rs` / `animation.rs`：

- 每次调用 `Instant::now()`（`motion.rs:152`、`animation.rs:174` 等）。
- `shimmer_spans`（`motion.rs:151`）为每个字符构造一个 `Span` 和一个 `Color`。
- spinner 每次查询都重算帧。

优化：

1. **统一注入时钟**：所有动画 API 接收 `now_ms`（来自可注入时钟，见第 8 节），去掉内部 `Instant::now()`。
2. **shimmer 只着色高亮带**：高亮带宽度是 `0.2 * len`（`distance < 0.1` 两侧），带外字符共用一个暗色 span。把每字符 span 降为三段 span（前暗、带内亮、后暗），分配从 O(n) 降到 O(1) 到 O(带宽)。
3. **查找表**：shimmer 的 `pos - sweep_pos` 与颜色由简单函数决定，可预计算 sweep 相位表；spinner 帧表直接常量数组。
4. **拆分动画核到新 crate（后续）**：对应 jcode `jcode-tui-anim`，在根 `Cargo.toml` 增加 workspace 成员与 `[profile.dev.package.wf-tui-anim] opt-level = 3`，让三角函数/颜色插值在 dev 构建下也优化。前提是工作区约束允许新增成员；当前阶段可先把纯函数集中在 `motion.rs`，便于后续搬迁。

## 7. 性能分级策略

参照 jcode `perf.rs`：

```
enum PerformanceTier { Full, Reduced, Minimal }

struct TuiPerfPolicy {
    tier: PerformanceTier,
    redraw_fps: u32,
    animation_fps: u32,
    enable_decorative_animations: bool,
    enable_synchronized_output: bool,
    enable_mouse_capture: bool,
    enable_focus_change: bool,
    simplified_transcript: bool,
}
```

输入：`capabilities.rs` 的 `TerminalCapabilities`（终端类型、color depth、synchronized output、focus events）加上系统负载/内存（可参考 `wf-metrics` 或 `num_cpus`）。

档位行为：

- `Full`：动画、shimmer、同步输出、鼠标捕获全开。
- `Reduced`：关闭装饰性 shimmer 与空闲动画，动画帧率降低，保留 spinner。
- `Minimal`：关闭动画，禁用鼠标/焦点事件，transcript 走简化渲染（例如折叠工具详情）。

策略对象在启动时构造一次，注入渲染层。

## 8. 可注入时钟

现状大量 `Instant::now()` 让动画/TTL/重绘节奏不可复现。新增：

```
trait Clock { fn now_ms(&self) -> u64; }
struct SystemClock { origin: Instant }
struct TestClock { now: AtomicU64 }  // 测试可 advance/set
```

需要改造的点：

- `AnimationController`（`animation.rs:116`）与 `motion.rs` 的动画函数。
- `NoticeQueue`（`state.rs:207`）的 TTL。
- `InteractiveController::now_ms`（`interactive.rs:1000`）与 `DoublePressTracker`。
- `framer.rs` 已经是注入式（`set_now`），保持一致。

测试注入 `TestClock` 后，可以断言"第 N 帧的 spinner 字符"、"notice 恰好在 TTL 后消失"，无需 sleep。

## 9. 同步输出

`TerminalCapabilities.synchronized_output`（`capabilities.rs:32`）已探测但未使用。在支持 DEC 2026 的终端上，帧提交前后包一层：

```
BeginSynchronizedUpdate ... draw ... EndSynchronizedUpdate
```

只在 `Full`/`FooterOnly` 帧使用；`SpinnerOnly` 帧频繁同步反而增加开销。不支持时禁用，行为回退到现状。

## 10. 帧预算度量

扩展 `tui_debug/diff_recorder.rs`（`diff_recorder.rs:25`）为一个可在测试中启用的度量后端：

```
struct FrameMetrics {
    frame_index: u64,
    changed_cells: usize,
    ansi_bytes: usize,
    duration_us: u64,
    reflowed_lines: usize,   // 本帧实际换行的源行数
    markdown_bytes_parsed: usize,
}
```

度量点：

- `prepare.rs` 记录本帧实际换行的行数与解析字节数。
- `metrics.rs` 包装 backend `draw` 记录 ANSI 字节与耗时。
- 测试里以预算断言：稳态流式帧 `reflowed_lines == 新增行数`，`markdown_bytes_parsed <= 阈值`。

这把"优化是否生效"变成可回归的断言，避免后续改动悄悄退化。
