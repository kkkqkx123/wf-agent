# 远端执行数据的本地备份

## 一、职责边界

本地备份发生在管理端 `wf-server`，不是远端节点自备份，也不是 CLI 直接落盘。管理端通过服务端注册表找到远端主机，经本地回环隧道访问远端只读同步接口，把执行数据写到管理端本地目录。

远端节点使用 `remote-node` feature，显式不包含后端管理域；`remote-node` 与 `backends` 同时开启会在启动时拒绝，避免远端再管理一层远端。

## 二、启用条件与配置

备份链路需要同时满足：

* 管理端启用 `backends` 域：`backends.toml` 中 `enabled = true` 或 `WF_BACKEND_ENABLED`。
* 配置 `backup_dir` 或 `WF_BACKEND_BACKUP_DIR`。未配置时不启动备份循环；手动触发也会失败。
* 注册表条目配置 `backup_executions`，列出要备份的远端执行 id。条目还可覆盖 `backup_interval_secs`、`backup_retention_count`、`backup_retention_days`。

全局默认值：备份周期 1 小时，保留 10 份，保留 7 天。备份文件与索引默认放在 `backup_dir` 下，索引库名为 `backends.db`；也可用 `registry_path` 指定索引位置。

远端同步请求携带两个上下文：

* `x-api-key`：来自 `WF_BACKEND_REMOTE_API_KEY`，不写入配置文件。
* `x-wf-directory`：优先取条目的 `backup_directory`，回退到管理端全局 `backup_directory`，可由文件或 `WF_BACKEND_BACKUP_DIRECTORY` 配置。

## 三、备份内容

一次备份对应一个执行 id。远端专用端点 `GET /api/v1/remote-sync/executions/{id}/bundle` 在一次响应中返回完整恢复快照，响应体就是快照对象本身；管理端也接受被 `bundle` 字段包裹的旧形态，便于滚动升级期间的下发兼容。快照包含：

* 持久化执行记录（workflow、agent、chat）。
* 统一历史视图、artifact 条目与审计摘要。
* 完整检查点链与每个检查点的状态 blob。
* 执行上下文归档文件，字节随快照保存。
* 格式版本、导出时间、源修订号与快照摘要。

远端先做一次执行归属检查，再导出快照，避免不同执行的数据混在同一响应里。检查点始终完整导出，超限快照由响应体字节上限按失败处理。快照摘要只覆盖可恢复数据：执行记录、checkpoint、文件归档与包体标识；导出时间、摘要字段自身以及 history、artifacts、audit 这些派生视图都不计入。bundle 中的 `source_revision` 等于该摘要，`source_sequence` 来自写路径维护的持久修订号；可恢复数据变化会同时推进序号并改变摘要。派生视图随 bundle 返回用于审查，但不影响漂移检测，也不会被恢复路径写回远端存储。

## 四、触发与调度

计划备份由管理端后台循环驱动：

* 使用共享 interval，首次立即 tick 被跳过；到期状态以内存记录为缓存、以索引中该目标的最大创建时间为持久兜底，因此重启不会让所有目标同时到期。
* 循环自身的节奏由全局 `backup_interval_secs` 决定，可用 `WF_BACKEND_BACKUP_INTERVAL_SECS` 覆盖；条目级 `backup_interval_secs` 只决定该目标在某轮里是否到期。只调小条目级间隔不会加快轮次。
* 迟到的 tick 直接跳过，不补积压。
* 到期状态按“后端名 + 执行 id”分别记录，一个执行成功不会掩盖另一个执行的状态。
* 到期时刻带有按目标名派生的确定性抖动，把同一轮任务摊开；连续失败的目标按指数退避拉长间隔并设上限，成功即清零。
* 到期任务按小批量并发执行；单次拉取超时与响应体字节上限可配置，默认为 15 秒和 64 MiB。检查点不再截断；超限快照按失败处理。响应体按流式分块读取，超限时立即中止，不先整体缓存。
* 成功才推进该执行的上次成功时间；失败保留已有修订号、备份 id 与成功时间，只更新尝试时间、失败次数和错误，下一周期按退避重试。
* 同一目标的定时备份与手动触发由进程内锁串行化，不会并发写盘与裁剪。
* 关闭服务时取消循环并回收隧道子进程。

远端 inventory 只读取持久修订表，返回序号、摘要、更新时间与状态，不再为每个目标导出 bundle。只有序号增大且摘要变化才判定为正常更新并触发备份；序号不变但摘要变化、序号变小、执行缺失、修订行缺失和修订表整体缺失分别记录为原地改写、回滚、远端丢失、状态不完整和需要重建，不自动覆盖远端数据。后台对账使用完整导出复核摘要，启动时执行一次，之后按 `backup_reconcile_interval_secs` 周期重复（默认 6 小时，设为 0 只在启动执行）。

重建以调用方已知的序号为下限，不重置为 1：重建后远端序号等于管理端基线，比对落到“无变化”，目标立即回到正常状态；若重建期间内容确有变化，摘要不同仍判为损坏。修订行单条缺失但内容可完整导出时，也按该目标单独重建，不需要清空整表。重建端点接收目标列表，每个目标携带自己的序号下限。

手动触发通过 `POST /api/v1/system/backends/{name}/backups` 走同一条备份路径；CLI 对应 `wf remote backup-now NAME --execution ID`。后端不存在返回 404，其他失败按服务端执行错误返回。

## 五、同步请求与校验

管理端从条目的本地隧道地址发起 GET 请求。拉取成功后不会直接写盘，而是依次校验：

* HTTP 状态为成功；
* 响应信封 `success` 为真；
* `data` 存在；
* `bundle` 是对象；
* `execution_id` 等于请求的执行 id；
* `source_sequence` 是大于零的整数；
* `source_revision` 与 `payload_digest` 存在且一致。

任一条件不满足都按失败处理：不写文件、不写索引、不推进到期时间、不触发裁剪。这样鉴权失败、目录不匹配、执行不存在等错误信封不会被写成“空备份”。

## 六、落盘与索引

校验通过后，管理端把恢复快照写入 `backup_dir` 下按后端名分目录的 `{execution}-{created_ms}-{suffix}.json` 文件。

后端名、执行 id 和文件后缀都必须通过路径组件校验，拒绝路径分隔符和相对路径成分。

写入过程使用同目录临时文件：创建仅所有者可读写的临时文件，边写边算 SHA-256，同步文件内容，再改名为最终 JSON 并同步目录项。这样断电后不会留下"名字已发布、内容为空"的文件，摘要描述的确实是落盘字节。备份目录权限收紧到仅所有者可进入，包体序列化为紧凑 JSON 并带合成体版本字段。落盘前会规范化根目录与后端目录，真实目录不在根目录内则拒绝写入。索引写入失败会删除已发布文件，避免留下未登记的备份。新备份首次读回校验失败时，按索引行、文件顺序回滚刚写入的快照，不让无效记录成为最新备份。索引记录包含 id、后端、执行、创建时间、字节数、SHA-256、文件路径、远端序号、源摘要和快照摘要；路径相对 `backup_dir` 存储，换目录后记录跟随新根目录。旧版本索引里的绝对路径仍可读取。

索引路径解析统一基于规范化根目录和目标父目录：父目录或目标文件是符号链接时也会检查真实落点，`backup path escapes root` 一律拒绝校验、导出与裁剪，文件不会被误删。`backup_dir` 自身是符号链接时，规范化后的真实路径仍视为根内。父目录不存在时校验按 `missing_file` 处理，导出返回明确错误，裁剪记告警并跳过，不会通过创建目录让检查通过。

## 七、保留策略

每次成功备份后按“后端 + 执行”分别裁剪，数量上限和时间上限任一命中即删除：

* 该执行按创建时间倒序，超出数量上限的记录进入删除列表。
* 超过保留天数的记录进入删除列表。
* 先删索引行，再删文件；文件不存在视为已清理，文件删除失败只记告警。

裁剪配额按目标独立，某执行的备份不会挤掉另一个执行的历史。配置与条目中的数量上限和天数上限都必须大于零，零值在启动期或写入期被拒绝，避免删光包含刚写入那一份在内的全部备份。

这样不会出现索引指向已删文件的记录；文件删除失败最多留下孤儿文件，不影响列表可信度。

## 八、查询与手动拉取

管理端接口：

* `GET /api/v1/system/backends`：后端视图含 `last_backup_ms` 与 `backup_error`，顶层含 `backup_round_error`。
* `GET /api/v1/system/backups`：全部备份索引。
* `GET /api/v1/system/backends/{name}/backups`：单个后端的备份索引。

CLI：

* `wf remote backups [--backend NAME]` 展示 id、后端、执行、时间、大小、SHA-256 与路径。
* `wf remote backup-verify ID` 重新读取该文件并与索引记录比对，返回 `ok`、`missing_file` 或 `digest_mismatch`，同时给出记录的与实际的大小和摘要。
* `wf remote backup-export ID DEST` 从服务端导出经复验的备份包到本地文件，写入用唯一临时文件加原子改名；导出前服务端复验摘要与大小，客户端落盘前再次复算摘要，不符则拒绝写出。
* `wf remote backup-check FILE [--expect-sha256 SHA]` 离线检视本地备份包：检查结构、已知格式版本、执行 id 一致性、记录与检查点数组、源修订号和摘要字段一致性，并可比对已知摘要；任一检查不通过都以失败退出。不访问服务端。
* `wf remote sync-state [--backend NAME]` 展示每目标的持久同步位点、修复状态、本地快照读取状态和最近错误，可按后端过滤。
* `wf remote sync-reset --backend NAME --execution ID` 把单个目标标记为重新基线：清空持久序号与摘要、丢弃内存到期状态，下一轮忽略持久位点与本地快照序号，拉取一次新快照并采纳其位点。不删备份文件，也不动远端数据；失败重试期间该标记保持，直到一次成功备份采纳新位点。备份轮次在开始时读状态、结束时写入，因此写入入口还会比对"这次有没有带来新快照"：没带来就保留标记，避免复位落在两次之间时被这一轮写回旧结论。
* `wf remote backups [--backend NAME] [--repairable]` 展示备份索引；`--repairable` 只保留待修复目标的最新通过复验的备份。
* `wf remote backup-restore ID [--apply] [--replace]` 对已验证快照先做 dry-run，再加 `--apply` 恢复到远端同一执行 id；目标内容与快照不一致时需再加 `--replace`，否则只报告差异不写入。远端节点需设置 `WF_RECOVERY_RESTORE_ENABLED=1`。应用成功后管理端采纳远端写入的新序号与摘要，目标状态直接回到正常。
* `wf remote recover [--backend NAME] [--execution ID] [--apply]` 批量处理 `remote_missing` 与 `remote_corrupt`：按创建时间从新到旧遍历候选，取第一份复验与 dry-run 都通过的备份，`--apply` 才写入，并在应用后重读 sync state。恢复模式按状态选择，`remote_missing` 用新建、`remote_corrupt` 用替换。全部候选不可用时，跳过原因汇总每份的失败阶段。
* `wf remote backup-relink [--apply]` 预览或执行存量绝对路径索引迁移；默认只预览，只有 `--apply` 才写库。执行后统计重写、保持、未解析与失败条数，并列出未解析和失败的索引 id。
* `wf remote status` 展示每行的 `last_backup_ms` 与 `backup_error`，并显示顶层的 `backup_round_error`，让整轮失败在终端可见。
* `wf remote pull ID DEST` 是独立的手动路径：从当前连接地址拉取完整恢复快照并写本地文件，不写索引、不参与裁剪；任一步失败都直接报错。

对不存在的备份 id，校验接口返回 404；文件缺失与内容变更都返回 200 且 `verified` 为假，但通过 `status` 明确区分，不会被合并成一个布尔结论。

## 九、对账与周期复核

服务启动时对备份目录做一次对账：清理由中断写入留下的临时文件，统计"目录里有文件但索引没记录"、"索引有记录但文件缺失"与"索引记录存在但文件内容摘要不符"三类计数，并聚合为一条告警。对账不跟随符号链接目录或文件；结构完整的孤儿快照会被重建索引，但随后同步轮会立即复验并在必要时从远端重新拉取。计数出现在同一条聚合告警中，但不扩展指标字段。

同一套对账与远端复核在启动后按 `backup_reconcile_interval_secs` 周期重复，默认 6 小时，设为 0 只在启动执行一次。轮询只读修订表、只比较记录下来的摘要，因此远端内容被改动而修订行未同步更新时轮询看不出来；周期性的全量导出复核是发现这类静默损坏的唯一途径，其间隔直接决定检出窗口。

根目录无法解析或读取时对账以失败结束，计入轮级错误状态并告警，不会以空报告伪装成健康状态；无法列出的后端目录计入 `unreadable_dirs` 并进入同一条告警，跳过不等于零。

孤儿文件会在对账时被受控收养：解析 JSON 结构、校验 `backup_version` 与 `execution_id`（含与文件名前缀的一致性），按落盘字节重算大小与摘要后重建索引行。收养 id 使用文件 mtime 与新随机后缀合成，不与原文件名冲突。结构不可识别、版本不支持或校验不通过的文件保持孤儿并计入 `adopt_rejected`；索引写入失败计入 `adopt_failed`。收养幂等，收养后的记录与常规记录同等参与校验、导出与裁剪。

每次成功备份并在裁剪完成后，管理端会对刚写入的备份立即执行一次摘要校验，结果进入既有校验指标；因此被保留策略淘汰的备份至少经过一次读回验证。

更换 `backup_dir` 后，如需让存量绝对路径记录在新目录下可查询，可调用 `GET /api/v1/system/backups/relink` 预览，或 `POST /api/v1/system/backups/relink` 并在请求体中设置 `{"apply": true}` 执行。迁移只改索引 `path`，不移动文件、不改大小与摘要；根外绝对路径进入未解析清单，不做破坏性改写。命令重复执行是幂等的，已是相对路径的记录保持原样。这是显式一次性运维动作，不会在启动时自动执行，也没有常驻兼容层。

## 十、指标与检出

备份链路接入服务端指标，随 `/metrics` 导出：

* 成功与失败次数（失败带 `backend` 与受限的 `reason` 标签）、单次耗时、备份字节数直方图。
* 校验成功与失败次数（失败带 `missing_file` / `digest_mismatch` 标签）、裁剪数量。
* 最近一次对账发现的孤儿文件数、缺失文件数与摘要不一致文件数。

失败仍会记日志并写入轮级错误状态，指标只作为抓取与告警的数据源，不在进程内发送通知。备份指标只按后端名与受限的失败原因打标签，不按执行 id 展开，序列基数随后端数增长。

报告生成复用同一份指标：备份失败数、校验失败数、孤儿文件数、缺失文件数和摘要不一致数分别对应 `max_backup_failures`、`max_backup_verify_failures`、`max_backup_orphan_files`、`max_backup_missing_files`、`max_backup_digest_mismatches` 阈值，位于全局指标配置的 `anomaly_thresholds` 下。默认失败数与校验失败数阈值为 10，孤儿、缺失与摘要不一致为 0；超过阈值时分别产生中、中、低、高、高严重度的 `Anomaly`，备份成功/失败次数与字节数也进入报告趋势。

抓取侧可使用如下 Prometheus 表达式补告警，通知由抓取方负责，进程内不投递：

```promql
# 一小时内备份失败超过 10 次
increase(backup_failure_count[1h]) > 10
# 校验失败超过 10 次
increase(backup_verify_failure_count[1h]) > 10
# 当前存在孤儿、缺失或内容变化文件
backup_orphan_count > 0 or backup_missing_count > 0 or backup_digest_mismatch.count > 0
```

## 十一、恢复边界

当前产物是可恢复快照，但不是热恢复镜像。远端恢复是一个收敛动作：应用快照后目标的可恢复投影等于快照投影，同一份快照重复应用结果不变。目标状态按三态判定并分别处理：`absent` 新建，`identical` 直接返回 `noop` 不写数据，`divergent` 只在显式允许替换时覆盖。不提供新建 id 映射或冲突合并。运行中的目标一律拒绝，需先取消；归属其他目录的目标不覆盖。

恢复写入执行记录、检查点元数据、检查点 blob 与执行上下文归档；bundle 里的 history、artifacts、audit 是用于摘要与审查的派生视图，不写回远端存储。运行时会话、队列、锁、凭据、工作区文件历史引用与派生视图都不恢复，恢复记录也不会重新调度执行。

恢复完成后远端修订行按 bundle 的投影重建，摘要等于快照摘要也等于后续一次全量导出的结果，序号取"本地当前与快照序号较大者加一"；管理端在同一响应里采纳该序号与摘要，因此目标立即回到正常状态，不会被下一轮判为内容损坏。归约到同一个投影也覆盖了文件归档组件：归档导入本身不推进修订组件，若沿用恢复后的现状组件，含归档的执行会在下次对账时被判为摘要不一致。

标准路径是：先 `backup-verify` 确认文件与索引一致，再 `backup-restore ID` 做 dry-run，确认目标状态、动作与计数后用 `backup-restore ID --apply` 执行；目标内容不一致时还要加 `--replace`。所有 checkpoint blob 在 dry-run 与 apply 前都会解码校验，坏 blob 不会造成部分写入。执行记录、检查点元数据与修订行在同一个事务内提交，事务之外只有检查点 blob 与文件归档两段：blob 按 id 覆盖写，可重复执行；归档整体替换放在事务之后，失败时目标行已是新值而归档仍是旧值，下一次比对会报告该差异，重放同一份快照即可收敛。读回路径仍可用：`backup-export` 导出原始字节，`backup-check` 离线检视。导出接口返回服务端原始字节文本，客户端按原样落盘并复验摘要，因此本地文件的摘要与索引记录一致。

摘要校验的威胁模型：SHA-256 与文件同机同目录体系存放，没有带外信任根。校验能发现介质损坏、截断与意外改写，不能发现蓄意篡改（攻击者可同时替换文件与索引行）。异地信任需要另行将 `backup_dir` 与索引纳入独立的完整性机制。

备份默认写入管理端本地目录，与被备份的管理面同机；管理端所在机器整体故障时这套备份随之丢失。异地容灾需把 `backup_dir` 放到独立存储并自行复制。

恢复快照始终包含完整检查点链，没有检查点数量配置。响应体字节上限是硬失败阈值，超限快照不会落盘。坏元数据行仍按既有逻辑跳过并告警。
