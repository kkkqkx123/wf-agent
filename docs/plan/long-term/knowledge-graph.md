# 知识图谱索引长期参考

本文是推迟项的立项参考，不是实现计划。正式实现之前，先重读立项门槛一节；
门槛未满足时，用现有元数据抽取加路由选择的组合覆盖原始需求，不建图谱。

## 0. 结论速览

* 图谱解决多跳关系与实体为中心的问题，是稠密检索回答不了的一类查询，
  不是检索精度的渐进优化。
* 现状无任何图谱代码；原始需求先用抽取写标签、路由按标签分流的组合顶住。
* 正式实现是独立新职责，按职责分离原则独立成 crate，不塞进现有管线 crate；
  与现有稠密加关键词是并列的检索域，经多域路由统一融合。

## 1. 适用场景

* 多跳关系问答：查询答案分散在多个块，需经实体关联两跳以上才能拼全，
  稠密检索只能召回单跳相似块。
* 实体为中心的知识问答：人物、设备、组织及其属性与归属，
  查询主语是明确实体而非一段描述。
* 关系约束查询：问的是实体之间的关系（谁负责、谁依赖、谁审批），
  而非包含关键词的段落。
* 结构化过滤叠加非结构化文本：先按实体属性收窄范围，再在范围内做语义检索，
  纯元数据过滤表达不了关系条件。

## 2. 与现状的关系

* 现有管线只有稠密向量与关键词两个检索域，加多域路由做扇出融合；
  图谱将来是第三个检索域，复用同一扇出融合框架。
* 元数据抽取可写实体标签，路由选择可按标签分流：这是无图谱时的过渡组合，
  能覆盖“按实体收窄”类需求，覆盖不了“关系遍历”类需求；
  分不清两者区别的用例一律先用过渡组合验证。
* 插件裁判与评估框架可直接复用：图谱问答同样先跑命中率，再用裁判评答案。

## 3. 正式实现需补充的功能

* 抽取：实体与关系抽取（模型或规则实现），输出具名三元组形状；
  抽取失败的块回退纯稠密索引，不阻塞整批摄取。
* 构建：实体对齐与去重（同名消歧、别名归一），关系去重；
  对齐冲突保留多候选并记来源，不做静默合并。
* 存储：图存储后端（嵌入式优先，远端其次），点边模型独立于向量契约；
  实体属性进索引以支持关系条件过滤。
* 生命周期：按源文档删除、覆写、增量更新图谱，源删除时其独占实体与
  关系同步移除，与向量侧的源删除语义对齐。
* 查询：实体链接（查询提及映射到图实体）、关系遍历（有限跳数加预算）、
  遍历结果与稠密、关键词结果统一进融合；遍历超预算即停并标记截断。
* 管线消费：路由配置新增图谱域，缺省关闭；多域扇出已存在，只需新增一域。
* 插件形状：抽取、链接、遍历各环节的建议型钩子可参照现有五种扩展补齐，
  同样原生限定、同样失败回退；不先于执行实现加形状。
* 评估：多跳问答集（答案需两跳以上），命中率按“关键实体是否召回”统计，
  再用裁判评最终答案。

## 4. 模块归属

* 图谱是新职责：抽取对齐、图存储、遍历查询与现有稠密管线无共享逻辑，
  按职责分离原则独立成 crate，与现有管线 crate 并列，不做替代模块。
* 现有管线 crate 只增加一个检索域的扇出入口，不引入图模型依赖；
  图 crate 依赖向量契约做范围内的语义检索，不反向依赖管线。

## 5. 立项门槛

以下全部满足时再立项：

* 有至少一个真实集合，其核心查询经判定属于关系遍历类，
  且过渡组合（标签加分流）实测答不对。
* 有可用的实体抽取手段（模型能力或规则质量）达到可接受的准确率，
  抽取质量是图谱的前置门槛，不可与图谱本身同项立项。
* 明确首个图存储后端（嵌入式优先），避免存储未定先写遍历。

## 6. 不做事项

* 不做开放域自动本体构建；实体与关系类型由集合方声明，宿主不猜。
* 不做跨集合实体对齐；对齐只在集合内，跨集合用路由分流。
* 不把图谱作为默认检索域；缺省关闭，无配置时行为与改前一致。
* 不在抽取质量达标前启动存储与遍历实现。

## 7. 图引擎选型：linkrs 评估

结论：linkrs 可作为内置图引擎，但只取 embedded 形态，且必须隔在
窄契约之后集成，不直接依赖其整栈；服务形态（HTTP、gRPC、C API、
管理台、命令行）一律不在 Scope 内。

匹配点：嵌入式接口按 SQLite 方式使用（打开、会话、执行、事务），
支持内存模式，可覆盖测试与临时集合；schema 全的标签边模型
（标签加边类型加类型化属性）恰好契合“类型由集合方声明”的不做事项；
Cypher 兼容的多跳查询覆盖有限跳遍历；批量写入与事务覆盖摄取；
按源删除可经查询语句表达，与向量侧的源生命周期语义对齐；
同作者、同协议、同开发阶段无兼容包袱。

失配与风险，按立项前必须消除的顺序排列：

* 依赖重量：嵌入式接口拖入存储加查询加事务加全文加迁移整栈，
  但最小嵌入配置已实证可编译，重型原生依赖可出闭包。
  上游已将全文、迁移改为可选依赖，并将嵌入与 C 接口特性解绑。
  唯一残留是查询 crate 对全文的非可选依赖，经核查其无门控引用
  只落在轻量类型模块（查询表示、结果、元数据、错误），引擎模块
  仍按特性门控，不引入存储引擎即无实质成本，接受现状，不再要求改动。
* 抽取开放性与 schema 全的摩擦：文档抽取天然开放，新实体类型需先建模；
  约定建模时机为集合创建时声明，摄取时只允许已知类型，未知类型拒绝而非建表。
* 向量归属：linkrs 的向量走外部服务或自带引擎；本项目范围内的语义检索
  继续走自有向量契约，图库只负责结构遍历，不重建向量索引，避免双写与双份维度校验。
* 版本传导：双方皆开发期无兼容，linkrs 侧破坏性变更会直传导；用路径依赖钉死版本，升级时同步改。

集成形态：定义窄图存储契约（打开、建空间、写三元组、限预算遍历、按源删除），
linkrs embedded 实现作为首个后端；查询语句拼装收敛在后端实现内部，
上层只见契约方法，便于替换。

## 8. 多后端模式借鉴

向量与全文的多后端经验可直接抄三条：契约 trait 加多后端加宿主注入；
后端能力不齐时返回明确不支持而非降级跑错结果；新种类缺省关闭，
默认行为冻结。不可照搬一条：向量与全文后端语义同构（文本进、命中出），
图后端语义不同构（遍历对相似），融合必须经归一化，不做分数直加。
依赖层面先复用本工作区已有的嵌入向量、全文、关系库，再谈新增。
