# 工具可用性变化的检查与通知：问题清单与修改方案

## 背景与范围

运行实例在入口处需要回答两个问题：当前这次运行到底能用什么工具，以及工具集合发生变化时如何让模型感知到。涉及两条入口：直接的 agent 循环入口和工作流中的 agent 循环节点；涉及四个通知通道：每轮的工具声明、稳定的系统头、可发现工具的元数据块、动态尾与可见性通告。

本文先梳理现状，再给出问题清单，然后重点分析两个语义问题：新增或删除工具只体现为声明数组悄然变大变小是否可接受、可否保留前缀缓存初衷；可用工具与注册工具混用是否存在语义缺陷。最后给出分阶段修改方案。

## 现状梳理

### 入口检查现状

直接入口在执行前做一次 fail-fast 校验，对照活注册表检查配置中的五个名单：可用池、初始可见、可发现、隐藏、已激活。未知名字报错误，已禁用报警告，互斥组合报错误，非空可用池之外的条目报错误。校验通过后，配置名单原样存入运行实体，此后冻结。

工作流入口先从节点配置与网关解析出静态设置：可用池取自可用加初始的并集，初始缺省时回退到可用池，可发现与隐藏透传，已激活从工作流变量中的激活标记收集。然后组装提示词、归一化历史、创建协调器并执行。工作流路径不经过直接入口的 fail-fast 校验，依赖定义期的静态引用检查，活注册表在运行时刻的漂移不再报错。

两种入口在运行实体创建时都会做一次历史归一化：把上游桶形状重写为本轮目标形状，并丢弃陈旧的动态尾。实体创建后，每轮请求组装时重新读取活注册表并重新做纯函数决议，决定本轮可见、可发现、门控、隐藏四个桶以及通用代理是否启用。

### 通知模型的现状

模型通过四个通道感知工具：

* 工具声明数组：每轮按名单排序后生成线上传输声明，是模型决定调什么工具的唯一结构化依据。
* 稳定系统头：入口组装一次，作为首条系统消息常驻，包含环境、技能、工作流、自定义段以及技能与模型上下文摘要的富化。
* 可发现元数据块：入口预渲染， assembly 时注入首条系统消息，每轮按是否启用通用代理决定是否替换占位或尾部追加。
* 可见性与易变尾：工具可见性节点在工作流变量中写拦截或激活标记，并在默认消息上下文追加一条尾部系统通告；下一 agent 循环入口把该通告导入初始历史。易变尾另起一条用户角色的标记消息，承载时间、待办、钉选、工作区等易变数据。

运行时拦截只在执行期生效，不改变声明数组，这是为了保持请求前缀字节稳定。

## 问题清单

### 入口检查类问题

* 校验不对称：直接入口有活注册表强校验，工作流节点入口没有。同一份名单在两条入口行为不一致，工作流中的拼写错误或过期工具名要到真正调工具时才暴露。
* 可用池推导绕过校验：工作流设置把可用池算成可用与初始的并集，初始名单中超出可用池的条目被自动并入，不再触发池外错误。相当于入口自己把本该报错的输入洗白了。
* 快照语义缺失：入口冻结的是名单而非决议结果，没有记录决议时的注册表版本、工具名排序、声明哈希。每轮重算时无法区分是有意变更还是注册表后台漂移。
* 空名单含义重载：空可用池表示全部注册工具，空初始名单表示全部可用工具可见。没有办法表达不带任何工具的纯问答运行，显式空与未设置是同一含义。
* 运行时覆盖点悬空：每轮决议与执行期门控都预留了按轮覆盖输入，但三个调用点都填空集合，注释承认将来接线时会漂移。扩展点长期以空值运行等于没有扩展点。
* 激活状态只进不出：入口把激活标记种子化为运行期发现状态，运行中通用代理的调用只记录发现事件，不提升门控工具。门控工具在轮内永远等不到激活，激活只能发生在下一循环的循环边界。

### 通知通道类问题

* 新增或删除工具只改变声明数组长度与内容，没有显式的增删通告。模型看到的只是一个悄然变大或变小的数组，需要自己猜测是能力新增、能力下线还是临时不可用。
* 删除工具伴随历史重写：归一化会把已归档历史中的旧调用形状改写为新桶形状。旧调用在新形状下可能是非法形状，改写后模型既看不到原始调用，也看不到删除原因。
* 稳定头只组装一次：技能与模型上下文摘要在入口富化一次，轮内注册表或技能装载器变化不再刷新系统头。声明数组每轮跟进，系统头停留在入口时刻，两者可能互相矛盾，例如头里还介绍着已经下线的工具。
* 拦截与声明互相矛盾：被拦截的工具仍保留在声明数组中，模型按声明发起调用，执行期再以错误消息拒绝。这是用一轮浪费换前缀稳定，需要显式告知模型不要再试，否则模型会重试。
* 通告只在循环边界导入：可见性尾消息只在下一循环收集初始历史时导入，正在运行的循环轮内感知不到拦截变化。执行期门控知道被拦，提示词不知道被拦。
* 逐轮历史投影默认关闭：工作流入口明确关闭逐轮投影以保缓存，循环边界的一次归一化之后，轮内桶变化不再改写历史。默认行为下历史形状与新声明可能长期不一致。

## 重点分析：声明数组悄然变大变小与前缀缓存的关系

结论是：悄然变化不会让前缀缓存彻底归零，但会让当初为缓存所做的取舍全部变成净亏损，属于最差的组合。

先说为什么不是彻底归零。请求体上有多个独立的缓存断点：工具声明尾、系统块、首条消息、末条消息。工具数组变化主要打掉工具断点及其序列化顺序之后的内容，系统块与首条消息的断点在某些服务端实现下仍可能部分命中。排序让无变化时的跨轮请求字节稳定，这个收益依然存在。真正昂贵的是变化的那一轮：工具断点失配，之后的内容全部重算。

再说为什么悄然变化让初衷失效。工具声明在请求体的靠前位置，数组中部插入或删除会使插入点之后的所有字节后移。排序保证了确定性，但也保证了插入点不可控：新工具名按字母顺序落入中部而非尾部，后缀全部失效。如果把新工具追加到尾部，前缀命中率更高，但会失去跨进程确定性。当前选择了确定性，就要接受中部插入必然打掉大段前缀。删除同理，且删除往往伴随历史重写，消息体的字节也一起变，形成工具与历史的双重失配。

更关键的是成本与收益不匹配。缓存失配本身不可怕，可怕的是付了失配成本却没有换来模型理解。显式的增删通告同样会导致失配，但至少模型能正确归因：新增意味着可以试新能力，删除意味着不要再调旧工具，拦截意味着声明不可信。悄然变化付了同样的失配成本，模型却只能看到数组变了，需要用一到两次试错来猜原因，试错的调用与错误消息又进一步污染历史与缓存。拦截场景最典型：声明不变所以前缀命中，但每次调用都以错误消息结束，省下的缓存命中被浪费的轮次吃掉。

因此修改方向不是追求变化时也不失配，而是不做无意义的失配：循环边界的有意变更允许失配，但必须配显式通告；轮内的后台漂移不应该进入本轮声明，应该冻结或隔离到下一循环；拦截不改声明的做法只在配有显式不要再试的指示时才成立。

## 重点分析：可用工具与注册工具是两个概念

当前语义把两者混在一起，根源是空名单表示全部注册工具。

注册工具是宿主能力：当前进程能执行什么，由注册表、插件装载、模型上下文服务连接状态决定，随时间漂移。可用工具是任务意图：这次运行需要什么，由任务定义中的五个名单决定，应该在入口冻结。把可用缺省解释为全部注册，等于把意图绑定到了一个随时间漂移的能力集合上。同一份配置在不同时刻启动会得到不同的声明数组，不可复现，不符合最小权限。后台新增的工具会自动漏进正在运行的循环，可能是用户从未授权的能力。后台删除的工具会让正在运行的循环在下一轮悄然失去能力，而入口校验在启动时明明是通过的。

并集推导进一步破坏了意图。可用本应是闭世界白名单，初始、可发现、隐藏都应该是它的子集。把初始并入可用，让初始可以走私可用之外的工具，闭世界变成开世界。校验中池外错误的本意是提醒用户把名单配齐，推导逻辑却让工作流入口永远配不错也看不出来。

空名单的双重含义还堵住了纯问答场景。想表达不带工具运行时，没有合法的显式值，只能依赖隐藏名单逐个排除，或者依赖运行时拦截。新注册的工具在空池语义下会自动出现，排除法永远追不上新增。

正确的语义应该是三态：未设置表示继承定义层默认值，显式空表示不带工具，非空表示闭世界冻结。冻结对象应该是入口时刻的决议快照而非名单字符串：记录当时可见集合的排序与声明哈希，后续轮次用活注册表与冻结快照取交集，新增能力不自动进入，删除能力转为显式不可用通告而非静默消失。新工具的采纳只发生在下一循环边界或显式激活事件，与可见性节点的激活机制统一。

## 修改方案

### 第一阶段：冻结快照与显式差异

* 入口在实体创建后保存一份工具快照：当时决议的可见排序、声明哈希、可发现集合哈希。不要求引入外部版本号，用排序加哈希即可判断是否漂移。
* 每轮组装请求前比较快照与本轮重算结果。循环边界的有意变更直接采纳并生成一条显式的工具变化尾通告，说明新增、删除、激活、拦截四类变化，不复用可见性节点的旧模板，单独描述声明数组的变化原因。
* 轮内的后台漂移不进入本轮声明：声明仍按快照渲染，漂移记录到运行期状态，留待循环结束或下一循环采纳。正在运行的循环不再因为模型上下文服务刷新或插件热加载而中途变阵。
* 删除与禁用不再静默消失：声明中移除的同时，在尾通告中说明该工具已下线或禁用，历史归一化保留原始调用形状供审计，只改写真正非法的形状，避免把删除原因洗掉。

验收：同一配置重复启动在注册表不变时声明字节一致；注册表中途增删工具不改变正在运行循环的声明数组；循环边界的变化必有一条对应的显式通告。

### 第二阶段：修正可用语义

* 区分未设置、显式空、非空三种可用取值。未设置走定义层继承，显式空表示纯问答，非空表示闭世界。空初始的含义同步收敛：只在可用未设置时才表示全显，显式空可用下空初始表示无工具。
* 删除可用池的并集推导，初始、可发现、隐藏必须为可用的子集，否则在工作流入口同样报错，与直接入口校验对齐。把直接入口的校验函数下沉为两条入口共享的前置检查，工作流节点缺内联定义或缺画像时已有的错误语义保持不变。
* 通用代理不再豁免白名单：它是声明数组的一员，其启用状态由可发现集合是否非空决定，但其自身是否允许注入仍受可用快照约束。未注册通用代理时保持现有回退语义，但要在通告中说明可发现工具暂时不可达，而不是静默不启用。

验收：纯问答配置不再被新注册工具污染；池外条目在两条入口都报错；通用代理缺席时的可发现工具不再静默悬空。

### 第三阶段：统一拦截与激活的提示词契约

* 拦截保持不改声明数组，但必须配显式的不要再试指示。拦截生效后，下一轮的尾通告中列出被拦截工具，模型不需要再用一次失败调用来发现。
* 激活统一走显式事件：循环边界的激活标记继续有效，轮内不再有隐式激活。通用代理的调用只记录发现度量，不改变门控状态，避免模型误以为调过一次就等于已激活。
* 通告的导入时机从仅循环边界扩展为每轮按需刷新：声明快照变化或拦截集合变化时，刷新尾通告并替换旧通告，而不是追加多条。稳定头中与工具相关的富化段随快照一起刷新，头与声明不再互相矛盾。

验收：被拦截工具在通告后不再被模型重复试调；激活前后声明数组的变化与通告一一对应；稳定头中的技能与模型上下文摘要与当前快照一致。

### 第四阶段：缓存友好的变化编码

* 声明数组在快照冻结期内保持排序与字节稳定，这是缓存友好的基本盘，不做改动。变化只发生在采纳新快照的那一轮，允许该轮失配，但用显式通告换理解。
* 新工具在采纳时按排序插入，不再为凑前缀命中率而追加到尾部。确定性优先于单轮命中率，因为通告本身已经改变了尾部字节，尾部追加省不下多少。
* 历史投影策略与变化类型绑定：新增工具不重写历史，删除工具只改写非法形状并保留原文，桶切换引起的形状变化继续走现有的幂等归一化。默认关闭逐轮投影的立场不变，避免无变化时 churn 前缀。

验收：无变化的连续轮次声明与系统头字节稳定；有变化的轮次失配可解释，且历史不再因无关变化被重写。

## 风险与回退

* 快照冻结可能让用户觉得新工具生效太慢。回退是循环边界自动采纳，正在运行的长循环不受影响，下一循环自然生效，不需要手动重启。
* 显式通告会增加系统提示体积。通告只列变化的工具名与一句话原因，不重复全量元数据，全量介绍仍由稳定头与可发现块承担。
* 三态可用语义需要迁移现有配置。存量配置中缺省可用即全量的行为在迁移期内保留，但要在校验中给出警告，引导用户显式声明意图，而不是直接改变行为。
* 任何阶段均可独立回退：快照、语义修正、通告契约、缓存编码四层互相只通过快照与通告交互，不共享存储格式。回退某一层时，其余层退化为现状的静默行为，不破坏运行。
