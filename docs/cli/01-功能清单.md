# wf-cli（Rust 版 CLI App）功能清单

> 本文档基于 TS 版 `apps/cli-app` 的功能面与 `docs/analysis/atomcode-tui.md`、`docs/analysis/codex-tui.md`、`docs/analysis/codex-ratatui-implementation.md`
> 的终端交互参考分析（渲染/事件机制），结合 Rust 侧已有 crate（`wf-api` / `wf-runtime` / `wf-storage` 等）的成熟度，给出 Rust 版 CLI 的功能范围与优先级。
> 设计原则遵循 `apps/cli-app/docs/spec/design-philosophy.md`。
>
> 本文档在 2026-08 修订：基于对 codex TUI 源码（`/workspace/codex`）的复核，修正了渲染引擎选型与多行输入组件方案（详见「二、技术选型」与「七、与 TS 版的差异决策」）。

## 一、产品定位

Rust 版 CLI（下文统称 **wf-cli**）替代 TS 版 `modular-agent`，提供两种入口形态：

| 形态 | 触发条件 | 目标用户 |
| :--- | :--- | :--- |
| **Headless CLI** | 非 TTY / `--no-tui` / 显式子命令 | 脚本、CI、自动化调用 |
| **TUI 交互** | TTY 且无子命令参数（或 `--tui`） | 日常开发操作 |

两种形态共享同一套领域调用层（命令 → adapter → `wf-api` → 存储），TUI 只是交互外壳。

## 二、技术选型

| 层 | 选型 | 依据 |
| :--- | :--- | :--- |
| 渲染 | **ratatui 0.30**（monolith，`default-features=false` + `crossterm` feature） | 标准 `ratatui::Terminal` 自身即双缓冲 diff 渲染（`draw` + `flush` 逐格比较前后 Buffer）。wf-cli 为**全屏 alt-screen 模式**，无需派生 custom_terminal（codex 的 `custom_terminal.rs` 双缓冲/`Put`/`ClearToEnd` 是为其 **inline 视口 + scrollback 写入**服务的，见 03 文档「二、渲染层」） |
| 交互组件 | **自研核心组件**（SelectList/单行 Input/弹窗栈/图表）；**多行 TextArea 评估第三方**（见下） | ratatui 无零装饰现成组件；Codex 同路线，全库未用 `widgets::Chart/Gauge/BarChart/Canvas/Scrollbar` |
| 多行 TextArea（P1） | 首选 **`tui-textarea-2`**（0.12.x，2026-07 活跃）或 **`ratatui-textarea`**（0.9.x，ratatui 官方组织维护）；二者均基于官方拆分 crate `ratatui-core`/`ratatui-widgets`，与 ratatui 0.30.2 兼容。**弃用** `tui-textarea` 0.7.0（2024-10 停更，绑定 ratatui ^0.29） | 多行编辑器（kill buffer/undo/历史）自研成本高（codex 的 `textarea.rs` 约 4000 行 + vim 子模块）；先评估第三方，API 不满足时再裁剪自研核心子集（视觉换行 + 光标保持可视 + 历史，不做 vim） |
| 终端后端 | **crossterm**（raw mode + bracketed paste + kitty 键盘增强） | 两参考一致 |
| Markdown | **pulldown-cmark** → ratatui `Line` | Codex markdown_render，含表格列分类 |
| ANSI 输出解析 | **ansi-to-tui** | Codex ansi-escape crate |
| 语法高亮（P2） | **syntect** | Codex render/highlight，带超限保护 |
| 换行/截断 | textwrap + 自研 URL 感知 wrap | Codex wrapping.rs |
| 事件循环 | tokio `select!`（biased）+ FrameRequester 限帧调度 | Codex App::run + frame_requester（120FPS 上限） |

## 三、整体架构

```
┌────────────────────────────────────────────────────────────┐
│                      wf-cli (crates/wf-cli)                  │
│  ┌──────────────┐   ┌───────────────┐   ┌────────────────┐  │
│  │  Command 层   │   │  TUI 引擎      │   │  Output 层      │  │
│  │ (clap 子命令) │   │ (事件循环+屏幕) │   │ (text/json/silent)│ │
│  └──────┬───────┘   └──────┬────────┘   └───────┬────────┘  │
│         │                  │                     │           │
│  ┌──────┴──────────────────┴─────────────────────┴────────┐  │
│  │                    Adapter 层（领域门面）                 │  │
│  └────────────────────────┬─────────────────────────────────┘  │
└───────────────────────────┼─────────────────────────────────────┘
                            ↓
                  wf-api（ApiContext / 命令执行）
                            ↓
      wf-runtime（Runtime: registries, storage, llm, sandbox, mcp）
```

- **Command 层**：基于 `clap` 的命令组定义（~20 个命令组），全局 flag：`-v/--verbose`、`-d/--debug`、`-l/--log-file`、`-c/--config`、`--tui`、`--output <text|json|silent>`。
- **Adapter 层**：把 `wf-api` 的返回类型映射为 CLI 展示模型，错误统一转换为 `CLIError`（带 exit code）。
- **TUI 引擎**：事件循环 + 屏幕管理 + 模态框系统（设计见 `02-ui布局与页面划分.md`、`03-组件设计方案.md`）。
- **执行模式**：沿用 TS 版三模式模型 — `blocking`（同步等待）、`foreground`（TTY 内子进程实时流）、`background`（日志文件 + `status/cancel/follow` 管理）。
  - **并发约束（重要）**：`foreground` 执行与 TUI 同进程，agent/execution 执行必须运行在 tokio 独立 task 中（经 `wf-api` 事件订阅驱动 UI），严禁执行路径内同步阻塞 TUI 事件循环（如沙箱、脚本求值、LLM 请求）。
  - **TTY 交互路径**：TUI 模式下 stdin/stdout 被界面占用，工具需要交互式终端（`$EDITOR`、vim、git rebase）时，必须经 `Tui::with_restored` 暂停 TUI、恢复终端模式、运行外部程序后重绘（见 03 文档「二、渲染层」）。

## 四、Headless CLI 功能清单

按领域分组，标注优先级（与 Rust 迁移阶段对齐）。**P0**：Rust 基础设施已具备；**P1**：依赖执行引擎补全；**P2**：依赖 LLM/沙箱/MCP 等完整生态。

| 命令组 | 子命令 | 说明 |

| `workflow` (wf) | register / register-batch / list / show / update / delete / clone | 工作流 CRUD，`show --versions` |
| `workflow graph` | show / nodes / analyze / stats | 图结构与统计 |
| `workflow version` | list / diff / rollback / changelog | 版本管理 |
| `template` | register-node(s) / register-trigger(s) / list / show / delete | 节点/触发器模板 |
| `llm-profile` | register / list / show / update / delete | LLM 配置档 |
| `script` | register / list / show / validate / execute / delete | 脚本资产 |
| `tool` | register / list / show / validate / execute / delete | 工具资产 |
| `trigger` | register / list / show / update / delete | 触发器资产 |
| `checkpoint` | create / list / show / load / delete | 检查点管理 |
| `storage` | diagnostics / health / cleanup | 存储诊断 |
| `message` | list / show | 消息查询 |
| `variable` | list / set / show / delete / definition | 执行变量 |
| `event` | list / show / stats / subscribe / timeline | 事件查询与订阅 |
| `search` | `search <query>` | 全库全文检索 |

### 4.2 P1 — 执行管理（依赖 wf-executor/wf-workflow 完成度）

| 命令组 | 子命令 | 说明 |
| :--- | :--- | :--- |
| `execution` | run / status / cancel / pause / resume / list / show / delete / follow | 工作流执行生命周期，`run` 支持 `-i/--input`、`--blocking/--background`、`--log-file` |
| `execution progress` | show | 进度追踪 |
| `execution compare` | two / range / trend | 执行对比（性能分析） |
| `agent` | run / start / pause / resume / stop / status / show / list / messages / delete | Agent 生命周期，`run` 支持 `--stream`、`-m/--max-iterations`、`-t/--tools` |
| `agent iteration` | show / list / metrics / analyze | 迭代分析 |
| `agent error` / `agent perf` | analyze / stats / recover / profile / bottleneck / trend | 错误与性能分析 |
| `approval` | config / check / batch / file / mcp | 审批规则与检查 |
| `user-interaction` | list / show / create / update / delete / enable / disable | 交互记录 |
| `query` | executions / agent-loops / tasks | 记录查询 |
| `task` | list / show / stats | 任务统计 |
| `hook` | register / list / show / delete / export | 钩子管理 |
| `metrics` | show / export / by-tags / snapshot | 指标导出 |

### 4.3 P2 — 生态与高级能力（依赖插件/沙箱/MCP 补全）

| 命令组 | 子命令 | 说明 |
| :--- | :--- | :--- |
| `plugin` | list / show / load / activate / deactivate / reload / unload + `config show/update` | 插件管理 |
| `skill` | register / register-batch / list / show / delete | 技能管理 |
| `mcp` | connect / disconnect / list / resources / tools / status / enable / disable | MCP 服务器管理 |
| `sandbox` | status / presets / strategies + `policy` | 沙箱状态与策略 |
| `agent-profile` | register / list / show / delete | Agent 配置档 |
| `template/trigger` 子组 | register-templates-batch 等 | 批量注册 |

### 4.4 通用要求（所有命令组）

- **输出路由**：`text`（表格/键值/状态，复用 Formatter 设计）/ `json`（`{success,type,entity,data,message,timestamp}` 信封）/ `silent`。
- **错误语义**：`CLIError` 层级（配置错误/存储错误/校验错误/执行错误/资源不存在），映射退出码（0 成功、1 业务失败、2 参数错误、3 配置错误、4 执行中被打断）。
- **模式降级**：headless 下 `foreground/background` 自动降级为 `blocking`。
- **交互 handler**：headless 下工具审批与追问走 readline 提示（`[y/n/edit/skip]`），TUI 下走模态框。

## 五、TUI 功能清单

### 5.1 屏幕（详见 `02-ui布局与页面划分.md`）

> **概念模型以 `wf-api`/`wf-types` 为准**：`ExecutionType::{Workflow, AgentLoop}` + 共享 `ExecutionStatus` + `ExecutionHierarchy`（执行树），
> agent 执行与 workflow 执行是**同级统一概念**，不存在 Thread 概念（TS/RS 均已废除）。因此：
> **执行跟踪统一为单一 Executions 界面**；Agent / Workflow 仅在处于前台交互会话时才需要专门界面。

| 屏幕 | 优先级 | 功能 |
| :--- | :--- | :--- |
| Dashboard（主菜单） | P0 | 入口导航：Workflows / Agent / Executions / Checkpoints / Search / Settings |
| Workflow 列表 + 详情 | P0 | 资产视角：列表（name/version/nodes/status）→ 详情（键值 + 操作：view graph / edit / delete）；可对某次执行 enter 前台 |
| Executions（执行跟踪，统一） | P0 | `ExecutionType` 类型无关的执行列表（agent loop + workflow，可过滤）+ 进度/状态（Created/Running/Paused/Stopped/Completed/Failed/Cancelled）→ 详情 follow |
| Session（前台会话，类型无关） | P0 | Agent 或 Workflow 前台运行时的实时界面：日志流 + 底部输入 + 状态行 + 阶段感知输入（Idle/Streaming/Approval） |
| Checkpoints | P1 | 检查点列表 + 详情/加载 |
| Search（全文检索） | P1 | 查询输入 + 结果列表 → 详情 |
| Settings | P1 | 配置项查看/编辑（读写 config.toml，编辑走 `$EDITOR` + `with_restored`） |

### 5.2 模态框（详见 `03-组件设计方案.md`）

`ConfirmModal`（删除/危险操作）、`PasswordModal`（捕获型，askpass）、`ModelPicker`、`SessionPicker`、`FileViewer`、`DiffViewer`、`FileSelectionDialog`（P1）、`HelpModal`（`?` 键）。

### 5.3 关键交互特性

| 特性 | 说明 | 优先级 |
| :--- | :--- | :--- |
| 渲染 | 标准 `ratatui::Terminal` 差异渲染（monolith 内置双缓冲 diff），全屏 alt-screen | P0 |
| 输入 type-ahead | Streaming 阶段缓冲输入，TurnFinished 时释放 | P0 |
| 输入节流与合并 | 统一经 FrameRequester 限帧（120FPS 上限）；resize 事件合并 | P0 |
| 历史导航 | 输入历史（↑/↓、P1 支持 Ctrl+R 反向搜索）、会话恢复（`--resume`） | P0 |
| 命令 palette | `/` 打开，模糊搜索、↑/↓ 导航 | P0 |
| 外部程序运行 | `with_restored`：暂停 TUI → 恢复终端 → 运行 `$EDITOR` 等 → 恢复重绘 | P0 |
| stderr 抑制 | 子进程/后端 stderr 重定向，避免污染界面（headless 走 `-l/--log-file`） | P0 |
| 粘贴支持 | bracketed paste + 无支持终端的 `paste_burst` 突发检测；图片粘贴降级链（P2） | P1 |
| 配置热重载 | 500ms 轮询 config mtime，Idle boundary 应用 | P1 |
| 信号处理 | SIGINT/SIGTSTP/SIGCONT，raw mode RAII 恢复 | P0 |
| 终端降级 | 非 TTY → plain 输出；kitty 协议协商（P2） | P1 |
| 多行输入 | P0 单行输入；多行（最大 6 行）随 TextArea 组件在 P1 引入 | P1 |
| 渲染回归测试 | **insta snapshot 测试**：所有 UI 渲染变更必须附带快照（对齐 Codex AGENTS.md 要求） | P0（开发要求） |

## 六、优先级与阶段划分

| 阶段 | 内容 | 依赖 |
| :--- | :--- | :--- |
| **CLI-1** | clap 骨架 + config 加载 + Output 路由 + 模式检测；P0 命令组（资产/元数据 CRUD + 查询） | wf-api（已有） |
| **CLI-2** | TUI 引擎（标准 ratatui Terminal 事件循环/渲染/组件/模态框）+ Dashboard + Workflow 列表/详情 + Executions 跟踪 + Session 前台会话（单行输入） | 自研，参考 atomcode-tui |

| **CLI-4** | 生态命令（plugin/skill/mcp/sandbox）+ 配置热重载 + 高级 TUI 特性（通知/paste_burst/OSC 8 超链接） | wf-plugin/wf-tools 补全 |

## 七、与 TS 版的差异决策

1. **缩减命令面**：TS 版 ~200 子命令中部分（如 `predefined`、`metrics export` 的细粒度选项）Rust 版合并或裁剪，保留核心 CRUD + 执行 + 分析。
2. **概念模型以 wf-api 为准**：废除 TS cli-app 的 Threads 屏幕（Thread 概念已在 TS/RS 中废除）；agent 执行与 workflow 执行按 `ExecutionType` 统一为单一 Executions 跟踪界面，Agent/Workflow 专门界面仅在对应会话处于前台时启用。
3. **渲染基于 ratatui 标准 Terminal**：采用 ratatui 0.30 monolith 的低层原语（`Buffer`/`Line`/`Span`/`Style`/`Layout`/`Constraint`/`Clear`/`Rect`/`Paragraph`）+ 标准 `Terminal`（自带双缓冲 diff）。**不派生 custom_terminal**——codex 的自定义双缓冲与 `insert_history_lines`（scroll region 写 scrollback）是为其 inline 视口模式服务的，wf-clip 为全屏 alt-screen 模式，收益低而测试成本高（codex `diff_buffers` 有 100+ 行宽字符边界测试）。放弃自研完整渲染器（atomcode-tui 18K 行渲染器路线），避免重复造轮子。
4. **单一进程**：不采用 TS 版 child-process fork 执行，`foreground` 执行通过 `wf-api` 事件订阅在同一进程内完成（独立 tokio task，事件驱动 UI），TTY 交互经 `with_restored` 路径。
5. **多行输入组件外购优先**：P0 自研单行 Input；P1 多行 TextArea 优先评估 `tui-textarea-2` / `ratatui-textarea`（均基于 ratatui 官方拆分 crate `ratatui-core`/`ratatui-widgets`，与 ratatui 0.30.2 兼容），避免重蹈 codex `textarea.rs` 4000 行自研成本。
