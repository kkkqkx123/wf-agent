# 执行历史与检查点保留、收藏与归档设计

## 目标

为执行记录、任务记录、触发器记录和两类检查点增加统一的按时间保留策略，并提供用户可理解的收藏、归档语义：

- 收藏：保存完整执行快照（含历史、检查点、文件归档），长期受保护，可恢复到可审查或从检查点续跑的状态。
- 归档：导出快照后清理状态检查点与执行文件历史，仅保留执行历史与派生视图。
- 过期：归档超过历史保留期后删除执行相关数据；收藏永不自动删除。

## 现状问题

1. `CheckpointRetentionConfig.max_age` 与时间清理策略已存在，但生产路径创建 strategy 时传入 `None`，只有写入后检查，没有覆盖空闲执行的周期扫描。
2. 文件检查点 GC 基于 git ref 可达性；ref 存在就不会回收，`keep_recent_heads` 只是数量保护，不是时间过期。
3. 任务与触发器记录只有手动清理端点，前端硬编码 30 天，没有服务端统一配置与调度。
4. 收藏服务只保存 `kind/id`，目标被删除后收藏悬空。
5. 执行 bundle 已能导出记录、历史、artifact、审计、完整检查点 blob 和文件归档，但没有接入收藏与归档。

## 生命周期模型

生命周期与 `ExecutionStatus` 正交，不新增 `Archived` 状态：

- `active`：正常执行记录。
- `preserved`：收藏，保存 bundle，清理器永久跳过。
- `archived`：已导出 bundle，状态检查点和文件历史已清理，执行历史保留。

生命周期记录与 bundle 分片存在于服务端持久快照中，不放在前端拥有的 `web:preferences`。

## 配置

新增基础设施域 `retention.toml`，由配置编排器加载、合并默认值并校验。关键设置：

- 总开关、扫描周期、批量大小、默认只预览（`dry_run`）。
- 状态检查点保留天数与数量上限、收藏保护。
- 文件历史 ref 过期天数与 GC 数量保护。
- 归档后执行历史保留天数、最近 N 条保护、运行/暂停保护。
- 任务记录与触发器记录保留天数。

设置页通过类型化服务端接口读写运行时策略；文件配置是初始默认值，运行时修改写入独立快照。

## 清理流程

清理编排在 `wf-api`，调度在 `wf-runtime`，传输在 `wf-server`：

1. 调度定时器始终存在，每次 tick 读取当前策略；禁用或预演模式直接跳过，因此设置页修改后无需重启。单飞执行，禁止并发扫描。
2. 汇总工作流与 agent 执行，按最近 N 条和运行中状态过滤。
3. 收藏执行跳过；归档执行到达历史保留期后删除完整执行数据。
4. 普通执行到达检查点与文件历史保留期中较早的窗口时归档：先导出 bundle，再删除状态检查点、解除执行文件 ref，最后执行文件 GC。
5. 所有非收藏执行按检查点时间阈值再做一次增量清理，覆盖仍在活跃期的旧检查点。
6. 按任务/触发器保留期清理记录。
7. 输出候选数、实际删除数、失败项；`dry_run` 只生成报告。

时钟读取和持久化失败时不执行删除；删除分批、幂等，并有持久水位供重启续扫。

## 恢复语义

bundle 恢复不会复活原运行时句柄。按钮语义为“恢复执行快照”，恢复后可查看完整历史并从检查点发起续跑。恢复目标存在且内容不一致时需要显式替换确认。

## 安全边界

- 收藏判断必须在检查点删除之前完成。
- 文件历史必须先解除 ref 再 GC，单跑 GC 不会清理仍可达的历史。
- 归档不使用批量删除接口；批量删除会删执行记录，与归档语义相反。
- 不在 `web:preferences` 保存破坏性策略。
- 首次部署默认 `dry_run = true`，避免启动后静默删除历史数据。

## 验证

- 策略校验：周期、批量、天数正数边界。
- 清理行为：收藏不删、运行中/暂停不删、最近 N 条不删、归档保留历史但无检查点、过期执行完整删除。
- bundle：收藏与归档后仍能校验并恢复完整快照。
- 调度：runtime 关闭时定时器停止，存储层关闭前完成关停。
- 契约：OpenAPI 快照与前端类型同步生成。
