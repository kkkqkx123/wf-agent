# wf-plugin 设计思想

本包是插件运行时：统一的插件 trait、统一的清单结构、统一的贡献注册语义，之下挂三种执行后端。引擎只面向抽象编程，永远感知不到插件具体用哪种后端实现。

## 统一层

* **统一 trait**（`src/plugin.rs`）：生命周期钩子加贡献注册加声明重载，所有后端实现同一接口。
* **统一清单**（`wf-plugin-sdk/src/manifest.rs`）：插件标识、版本、入口、权限声明、Wasm 与 Lua 限额段。未知字段直接拒绝，避免拼写错误静默生效。
* **统一贡献**：节点类型、工具类型、LLM 编解码、事件处理、中间件经由 `ContributionRegistrar` 注册，冲突解决策略由引擎持有。

## 后端分档

| 后端 | 隔离强度 | 适用场景 |
|------|----------|----------|
| Wasm（含 core-module 与 component 双路径） | 强：燃料预算、 epoch 中断、内存上限、模块体积上限、WASI 授权默认拒绝 | 不可信第三方扩展的首选 |
| Lua | 弱：受限标准库加解释器指令钩子（超时与内存），同进程 | 受信的轻量脚本 |
| Native | 无：在宿主进程内直接装载动态库，无沙箱 | 仅限完全受信的第一方扩展 |

权限声明的强制力随后端分档：只有 Wasm 具备运行时强制；Lua 与 Native 上的声明仅为准入与审计输入（黑名单匹配，Lua 另有库裁剪）。不要把权限声明理解为跨后端的统一安全边界。

## 门控与调优分离

只有门控能阻断加载：清单合法性、权限黑名单、SDK 版本、签名、路径收敛，以及三后端启用开关（`PluginSystemConfig` 的 `lua_enabled`、`native_enabled`、`wasm_enabled`，运行时经 `PluginConfig` 同名透传，默认全开）。想停掉一类后端就关开关，不要用限额零值去表达开关语义。

## 资源限制

解析优先级由弱到强为：代码内建默认值、引擎全局默认（`PluginSystemConfig` 的 `lua_defaults` 与 `wasm_defaults`）、单插件清单声明。Wasm 的单次调用超时在两级都缺省时再回落到引擎守卫超时。数值限额永不阻断加载，只做安全降级并告警：超时类零值表示关闭该层（外层守卫仍在），内存类零值回落内建默认（内存没有外层兜底，不可表达无上限），超大池水位钳制到上限。生效后的限额在加载日志中一次性可见。Native 不设专属限额，其可配置面即守卫超时、名单、权限拒绝名单与启用开关。

## 演进路线

需要对非受信代码设防时，把插件迁移到 Wasm，而不是给动态库套脚本式沙箱仿真；Wasm 双路径保持相同的贡献语义与限额语义，调用方无需区分。
