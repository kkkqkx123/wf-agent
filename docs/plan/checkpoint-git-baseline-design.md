# 检查点库基线增量存储设计（借用外部仓库对象）

本文是《文件检查点与外部 Git 同步设计》的姊妹篇。前者的目标是打通
检查点库与真实 git 仓库的交付链路；本文解决的是另一个独立问题：
**检查点内部对象库的初始构建成本与写放大**，方法是借用原始 git 仓库
的某个提交作为基线，实现增量存储、历史回引。

## 1. 问题：初始全量复制与写放大

### 1.1 现状

内部裸对象库（`git_store`，每工作区一个，默认位于全局数据目录）初始为空。
会话首次捕获时，当前流程把整个工作区符合条件的文件全量写成
blob → 逐级构造 tree → 生成 commit，挂到 `refs/wf/main`（或 actor ref）。

对于一个大仓库（几万文件、几百 MB 文本），这意味着：

1. **首次捕获全量写入**：所有未被 ignore 的文件内容都要经过
   哈希 + 压缩 + 落盘，即使它们与 git 仓库 HEAD 完全一致、一字未改。
2. **对象库体积接近原仓库**：用户仓库里已有的内容在检查点库里
   又完整存了一份，磁盘占用接近翻倍。
3. **会话冷启动延迟**：大仓库下首次检查点建立是一次明显的卡顿点。

此后的每次小修改本身开销是可控的（git 内容寻址下，只写变更文件的
blob 和受影响的祖先 tree 链），这部分属于内容寻址模型的固有成本，
不是本设计要解决的问题。**问题的核心是初始基线的全量复制**：
这些对象在用户的 `.git/objects` 里本来就有，且不可变（内容寻址保证
同一哈希必为同一内容），重复存储是纯粹的浪费。

### 1.2 关键观察

- 用户仓库中任意提交可达的 tree/blob 都是**内容寻址且不可变**的，
  与内部库使用完全相同的对象格式和哈希算法，天然可以直接共享；
- git 原生支持 **alternates**（`objects/info/alternates`）：一个对象库
  可以把另一个对象库声明为只读备用源，查找时先查本地、再查备用源，
  写入永远只落本地。这正是"增量存储 + 历史回引"需要的机制；
- 内部库的 ref 模型（`refs/wf/main` 等）与对象来源无关，ref 可以
  直接指向一个位于外部对象库中的提交。

## 2. 方案比较

### 2.1 方案 A：种子拷贝（copy-on-seed）

建立内部库时，解析用户仓库的基线提交，把它的 commit 对象、
整棵 tree 及全部 blob **一次性拷入**内部对象库，然后
`refs/wf/main` 指向该提交。

- 优点：内部库完全自包含，之后不依赖用户仓库的任何内容；
  用户 rebase、gc、删除仓库均不影响检查点库。
- 缺点：首次建立仍然是一次全量对象写入，只省去了"后续重复
  内容"的写入，冷启动成本几乎不变；磁盘占用依旧接近翻倍。
  只是把"每次会话都全量"变成"每个工作区首次全量"。

### 2.2 方案 B：alternates 只读借用（推荐）

内部库创建时写入 `objects/info/alternates`，指向用户仓库的
`<repo>/.git/objects`。基线提交对象**不拷贝**，直接把
`refs/wf/main` 指向基线提交哈希。此后：

- 读取未变更文件内容 → 命中 alternate，从用户仓库对象库取出，零拷贝；
- 捕获变更文件 → 新 blob/tree/commit 只写内部库本地对象目录；
- `log` / `is_ancestor` / `merge_base` 遍历越过基线进入外部历史时，
  对象查找自动落到 alternate，天然可穿越（gix-odb 的分层查找
  对上层调用者透明）。

- 优点：初始建立零对象拷贝，冷启动成本从"全量写入"降为
  "解析一个提交 + 写一个 ref"；磁盘零重复；历史可完整回溯。
- 缺点：内部库不再自包含，存在对用户仓库的外部依赖
  （见第 5 节风险与降级）。

### 2.3 结论

采用**方案 B 为主**，方案 A 作为降级路径保留（见 4.4）。
方案 B 的依赖是"只读 + 按哈希取不可变对象"，风险可控。

## 3. 详细设计

### 3.1 与冻结规则的冲突修订

`git_store.rs` 目前冻结规则声明"用户的 `.git` 从不读也不写"。
本设计将其修订为：

- **写入仍然绝对禁止**：检查点侧对用户仓库永远只读；
- **读取从"从不"放宽为"仅在基线模式下、且仅限对象库层"**：
  只通过 alternates 按哈希读对象，不读用户 refs 的实时状态作为
  语义依据（基线解析成固定哈希后，用户后续的 ref 移动不影响内部库）；
- 不设 refs 级双向绑定——这与同步设计文档 2.4 节的立场一致，
  本设计只是对象层的只读借用，不改变"两个库松耦合"的架构取舍。

### 3.2 配置设计

新增配置项，与 `store_in_workspace` 平级（同为存储形态选项）：

```toml
[file_checkpoint]
# 方式一：分支尖端（跟踪某分支）
[file_checkpoint.baseline]
branch = "main"

# 方式二：分支 + 提交哈希前缀（临时指定某个固定点）
[file_checkpoint.baseline]
branch = "main"
commit_prefix = "a1b2c3d"

# 方式三：分支倒数第 n 个提交（branch~n 语义）
[file_checkpoint.baseline]
branch = "main"
behind = 3
```

解析规则：

- `branch` 必填，`commit_prefix` 与 `behind` 互斥、均可选；
  两者都缺省 = 分支尖端；
- `commit_prefix` 在用户仓库内做前缀消歧，非唯一或不存在则报错；
  语义是"临时指定"——解析成完整哈希后即固定，不随分支移动；
- `behind = n` 解析为该分支历史上倒数第 n 个提交（沿第一父链），
  等价于 `branch~n`；
- 解析发生在**种子时刻**：解析出的完整提交哈希作为基线锚点
  持久化到检查点元数据，之后每次打开检查点库都使用该锚点，
  不再重新解析配置（用户分支前进、rebase 均不影响已建库）；
- 工作区不是 git 仓库、或配置的分支/提交不存在 → 按库的
  `failure_behavior` 处理（默认报错并回落到无基线全量模式）。

### 3.3 种子流程（建库时一次性执行）

```
1. 解析配置 → 基线完整提交哈希 B，验证对象存在且可达
2. 写入 objects/info/alternates，指向用户仓库对象库
3. 读取基线 commit 对象（经 alternate），验证格式合法
4. 写 refs/wf/main = B（CAS，与普通 ref 更新同一路径）
5. 基线锚点（哈希 + 解析来源 + 用户仓库 objects 路径）写入检查点元数据
```

要点：

- **不拷贝任何对象**，`refs/wf/main` 直接指向外部库中的提交；
- 基线 tree 即内部 main 的初始 tree。首次捕获沿用现有
  "与 main ref 求差异、只写有差异文件"的路径——工作区与基线
  一致的文件不会产生任何新对象，这就是增量收益的来源；
- 各 actor edit ref 首次提交以 main 当前头（即基线链上的提交）
  为父，DAG 祖先关系从基线自然延续，三路合并的 merge-base
  计算无需任何特殊处理；
- 多检查点会话共享同一内部库，种子只发生一次；后续打开时
  校验元数据中的锚点仍可解析（见 4.2），不重复种子。

### 3.4 读取与遍历

- 对象查找：gix-odb 打开内部库时自动加载 alternates，
  上层 `find_data` / `read_tree` / `read_commit` 无需感知来源；
- 历史遍历：`log` / `all_commits` 越过基线后进入外部历史。
  需要设定**遍历边界**：`all_commits`（GC、全量枚举类操作）
  在遇到基线锚点时停止下钻，把基线视为根——外部历史不属于
  检查点的管理范围，枚举它没有意义且可能很深；
  `is_ancestor` / `merge_base` 在两个内部 ref 之间计算，
  两者共同祖先最远到基线，通常在进入外部历史前就会命中，
  无需特殊处理；
- provenance / timeline / diff 等上层视图以 ref 和 tree 为准，
  不受对象来源影响。

### 3.5 写入与 GC

- 写入路径完全不变：新对象一律写内部库本地对象目录
  （gix-odb 保证 alternate 只读、写入只落主库）；
- 内部 GC 扫描只清理本地对象目录中不可达的对象，**绝不触碰
  alternate 中的对象**（它们物理上就不在内部库目录里，
  天然隔离，只需确保 GC 遍历不把 alternate 当作待清理集合）；
- 基线锚点提交在用户仓库中的存活性由用户仓库自身保证
  （见第 5 节），内部 GC 不做担保也不做清理。

### 3.6 与 git 同步方案的协调

基线机制与《文件检查点与外部 Git 同步设计》互补而非重叠：

1. **天然初始对账点**：同步设计中"导出前需要存在有效对账点，
   无则首次导出全量 materialize"。基线模式下，内部 main 的起点
   就是一个真实的外部提交，基线锚点**就是**首个对账点的内部侧
   坐标，首次导出可以直接以 (基线提交 → main 当前树) 求差异，
   避免全量物化；
2. **方向一致性**：基线从用户仓库指向内部（对象借用），
   同步设计的导出/导入是内容级显式同步，两者层次不同：
   对象借用解决存储效率，同步动作解决交付语义；
3. **导入路径受益**：导入以对账点为 merge-base 计算外部 HEAD
   差异；基线模式下若用户外部提交恰好在基线链上，
   差异计算可以借助 alternate 中的历史对象，无需内部库存有
   对应内容；
4. **配置正交**：基线配置（`baseline`）与存储位置配置
   （`store_in_workspace`）相互独立，可自由组合——
   独立分支模式（in-workspace 自包含交付）下也可以启用基线，
   但此时自包含承诺被打破（内部库依赖外部仓库对象），
   文档需明确提示：**需要自包含交付的场景应使用方案 A
   （种子拷贝），通过配置项选择**。

## 4. 风险与降级

### 4.1 用户仓库历史改写（rebase / force-push / 分支删除）

基线锚点是固定哈希。若用户在仓库上 rebase、force-push 或删除
了包含基线提交的分支，基线对象会变成不可达，用户仓库下次
`git gc` 后可能物理删除，内部库经 alternate 查找将失败。

防线（多层）：

1. **种子时校验可达性**：基线提交必须从用户仓库某个现存 ref
   可达才允许建库。分支尖端与 `branch~n` 天然可达；
   `commit_prefix` 临时指定时同样做可达性校验，不可达即拒绝
   （并提示：临时指定的提交可能随时被 gc，建议配合
   `git keep` 类手段或改用 branch/behind 形式）；
2. **打开时校验**：每次打开检查点库验证锚点对象仍可解析，
   失败即进入降级流程；
3. **降级流程**：锚点丢失时按序尝试——
   a. 重新按配置解析（分支可能已移动到等价或更新的提交，
      但历史改写后内容树可能不同，需用户确认）；
   b. 用户确认后切换新基线：把旧 main 树与新基线树求差异，
      差异对象补写本地库，ref 重挂到新基线；
   c. 无法恢复时回落到方案 A / 全量模式，按 `failure_behavior`
      报错或重建。

### 4.2 用户仓库移动 / 删除

alternates 记录的是路径。仓库对象目录被移动或删除后锚点不可解析，
走 4.1 的同一降级流程。元数据中记录的解析来源（仓库路径）用于
给出准确的错误提示。

### 4.3 子模块 / 浅克隆 / 稀疏对象

- 用户仓库为浅克隆时，`behind` 解析可能越过浅边界，
  解析失败按配置错误处理，提示改用 commit_prefix 或 branch；
- 子模块内容不在主仓库对象库中，按现有 ignore/捕获规则处理，
  与基线机制无关。

### 4.4 方案 A 作为显式备选

提供 `baseline.mode = "borrow" | "copy"`（默认 `borrow`）：
`copy` 模式执行种子拷贝，换取消除外部依赖，适用于
"交付时要求检查点目录自包含"的场景。两种模式共用同一套
解析、锚点、校验逻辑，仅"是否拷贝对象"一步不同。

## 5. 明确不做

1. **不借用用户 refs**：内部库永不读取用户分支的实时指向，
   基线一经解析即为固定哈希；分支的后续移动通过显式
   "重定基线"操作（或导出/导入同步）体现，不做自动跟踪；
2. **不写用户仓库**：包括 ref、对象、config 在内的任何写入；
3. **不自动跟随基线前进**：用户仓库 HEAD 前进后，内部库
   不自动重定基线；重定基线是显式动作，需校验与确认
   （涉及旧 main 树与新基线树的差异补写）；
4. **不改变 ref 分层模型**：`main/edit/review/feat/human`
   的语义、审批策略、冲突流程全部不变，基线只影响
   "第一个提交从哪来、未变内容存在哪"。

## 6. 待决问题

1. **首次导出的差异范围**：基线锚点作为初始对账点后，
   首次导出是按 (基线 → main) 全差异生成一个提交，
   还是要求用户先手动对齐工作区？倾向前者，但工作区存在
   用户手工修改时需要与同步设计 3.1 的干净度检查合并考虑。
2. **重定基线的交互形态**：锚点丢失的降级路径中"切换新基线"
   是否需要前端确认界面，还是 CLI 提示 + 自动执行即可。
3. **`behind` 语义细节**：沿第一父链（`~` 语义）还是任意拓扑
   （`@~` 语义在 merge 提交上的差异）；倾向第一父链，行为可预测。
4. **多工作区共享同一用户仓库**时的 alternates 路径记录：
   绝对路径 vs 相对路径（相对路径可迁移但解析复杂度更高），
   倾向绝对路径 + 打开时校验。
