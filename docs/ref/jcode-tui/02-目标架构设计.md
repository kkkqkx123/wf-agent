# 02 目标架构设计

## 1. 总体思路

参照 jcode，把渲染从"每帧从状态重建整屏"改成"事件驱动地更新分层缓存，每帧只做失效部分的工作"。核心是三个分离：

1. **状态与内容分离**：状态（`AppState` / `InteractiveController`）只负责产生事件与版本号，渲染层只读一个 `RenderModel`。
2. **准备与绘制分离**：内容换行、markdown 样式、布局几何属于"准备"（prepare），结果按缓存键复用；"绘制"只把准备好的行写进 buffer。
3. **全帧与局部重绘分离**：帧调度决定重绘范围（full / footer / spinner），而非只有一档。

## 2. 目标分层

```
事件层 (events / event_dispatch / reducer)
      │  产生带版本的渲染输入
      ▼
渲染模型层 (RenderModel / TuiState)
      │  只读快照 + 版本号（messages_version, width, theme_mode, motion_tick）
      ▼
准备层 (PrepareCache)
      │  换行结果 / markdown 样式 / 视口几何，按 key 复用
      ▼
绘制层 (ui_draw)
      │  只写失效区域
      ▼
帧调度层 (FrameRequester + RedrawScope)
```

在现有文件基础上，新增模块（扁平命名，符合仓库约定）：

| 新模块 | 职责 | 参照 |
| --- | --- | --- |
| `render_model.rs` | 渲染只读视图 trait `RenderModel` + 版本号 | jcode `TuiState` |
| `prepare.rs` | 换行/markdown 准备缓存与失效 | jcode `ui_prepare.rs` |
| `prepare_cache.rs` | 缓存键与容量控制 | jcode `FullPrepCacheKey` / `BodyCacheKey` |
| `reveal.rs` | 流式文本缓速控制器 | jcode `stream_buffer.rs` |
| `perf.rs` | 性能分级策略 `PerformanceTier` / `TuiPerfPolicy` | jcode `perf.rs` |
| `theme_mode.rs` | Dark/Light 与 buffer 级适配 | jcode `theme_mode.rs` |
| `clock.rs` | 可注入时钟（测试确定性） | jcode `TestClock` |
| `metrics.rs` | 帧预算度量 | jcode 探针 + wf-tui `diff_recorder.rs` |

这些模块都放在 `wf-tui` 内，先不拆新 crate；动画数学核的拆分（对应 jcode `jcode-tui-anim`）放到后续阶段，因为它需要新增 workspace 成员与 profile override。

## 3. 核心数据结构

### 3.1 RenderModel

渲染层不再直接读 `TuiApp`，而是读一个只读快照：

```
trait RenderModel {
    // 内容
    fn scrollback_lines(&self) -> &[HistoryLine];
    fn streaming_line(&self) -> Option<&HistoryLine>;

    // 版本号（失效信号的唯一来源）
    fn scrollback_version(&self) -> u64;   // 内容变更即 +1
    fn streaming_version(&self) -> u64;    // 流式文本每次推进 +1
    fn theme_mode(&self) -> ThemeMode;
    fn motion_tick(&self) -> Option<u64>;  // 动画帧，静态时为 None（不失效）

    // 布局输入
    fn width(&self) -> u16;
    fn view_scroll(&self) -> usize;
    fn is_animating(&self) -> bool;
}
```

`InteractiveController` 实现该 trait。测试用 `TestRenderModel` 实现同一 trait（对应 jcode 的 `TestState`），让整帧绘制可以离线断言。

关键点：`motion_tick` 在动画关闭或不存在动画时返回 `None`，这样静止帧不会因为动画而重排。

### 3.2 准备缓存（prepare）

```
struct PreparedScrollback {
    width: u16,
    /// 每条源行对应的显示行区间 [start, end)
    row_ranges: Vec<Range<usize>>,
    /// 扁平化后的显示行
    rows: Vec<Line<'static>>,
    /// 源版本
    source_version: u64,
    /// 最近一次完整准备的字节估算（用于容量控制）
    approx_bytes: usize,
    /// committed 前缀的稳定标记（增量追加的基础）
    committed_nodes: usize,
}

struct PreparedFrame {
    scrollback: PreparedScrollback,
    streaming_rows: Vec<Line<'static>>,
    /// 视口起止（显示行索引）
    viewport: Range<usize>,
    /// 当前重绘范围
    scope: RedrawScope,
}
```

失效规则：

- `source_version` 变化：走增量路径（见下）。
- `width` 变化：全量重排。
- 主题模式变化：不重排，只重着色（在 buffer 层做，见 03 章）。
- `motion_tick` 变化：只影响 shimmer/流式行，不重排 committed。

### 3.3 缓存键

参照 jcode 的 `BodyCacheKey`，wf-tui 的准备缓存键：

```
struct PrepareKey {
    source_version: u64,     // scrollback_version 或 streaming_version
    width: u16,
    theme_mode: ThemeMode,
    motion_bucket: Option<u64>,  // 动画每 100ms 才换桶，避免每帧失效
    images_signature: u64,       // 预留：未来内联图/文件预览
}
```

`motion_bucket` 用"动画帧率下取整到 100ms"而不是每帧，保证动画之外的静态内容不因为 tick 变化而重排。

容量控制对齐 jcode：

- `SCROLLBACK_CACHE_MAX_ENTRIES = 4`
- `SCROLLBACK_CACHE_MAX_BYTES = 16 MiB`
- `SCROLLBACK_CACHE_OVERSIZED_MAX_ENTRIES = 1`

超过字节上限时不缓存超大 scrollback，退化为每帧增量（仍比全量便宜）。

## 4. 失效信号设计

当前失效信号分散。目标是给每个输入一个显式版本号：

| 输入 | 版本号 / 信号 | 变化点 |
| --- | --- | --- |
| scrollback 内容 | `scrollback_version` 单调 +1 | `settle_scrollback` 追加、`ReplayLoaded`/`ReplayEarlier` 替换/前插、trim |
| streaming 文本 | `streaming_version` 单调 +1 | `handle_turn_event` 的 `LlmDelta` |
| 宽度 | `width` 直接比较 | `frame.area().width` |
| 主题 | `theme_mode` 比较 | SIGUSR2 / OSC11 探测 |
| 动画 | `motion_tick`（bucket） | 动画控制器 |
| 滚动位置 | `view_scroll` | 按键 |
| footer | `footer_version` | reducer footer 变化 |

`InteractiveController` 增加一个 `versions: RenderVersions` 字段，在对应变更点 `bump()`。这属于最小侵入：不改现有业务逻辑，只在既有赋值点补一行递增。

## 5. 重绘范围分级

参照 jcode 的三级重绘：

```
enum RedrawScope {
    Full,        // 内容/宽度/主题/滚动变化
    FooterOnly,  // 仅 footer/输入/状态变化
    SpinnerOnly, // 仅动画帧推进
}
```

判定在 `TuiApp` 层完成：

- 有内容版本变化、宽度变化、主题变化、按键导致的滚动 → `Full`。
- 只有 `motion_tick` 推进且 streaming 行没变 → `SpinnerOnly`。
- footer 的 phase/usage/notice 变化但 transcript 未变 → `FooterOnly`。

绘制层：

- `Full`：照常整帧 `terminal.draw`。
- `FooterOnly` / `SpinnerOnly`：复用上一帧的整屏 buffer，只重绘目标区域，再交给后端 diff。这需要保留上一帧 buffer（`ratatui::buffer::Buffer`），并在 `draw` 里做"seed + 局部覆盖"。

`SpinnerOnly` 还需要记录动画区域的 `Rect`（对应 jcode 的 `LAST_IDLE_ANIMATION_AREA`），用原子打包的矩形或普通字段保存。给定区域后，可以只重建该区域而不是整块 buffer 的 `clone_from`。

## 6. 与现有模块的衔接

- `tui.rs`：保留 `TuiApp` 与事件循环骨架，把 `draw` 拆成 `prepare` + `ui_draw`，并在循环里计算 `RedrawScope`。
- `interactive.rs`：`draw_scrollback` 改为消费 `PreparedFrame`；新增版本递增点。`handle_turn_event` 里把 `stream.push` 改为 `reveal.push` + 节流后的 markdown 解析。
- `framer.rs`：保留，新增 `request_frame_scoped(scope)` 或在 `TuiApp` 维护 `pending_scope`。
- `reducer.rs`：保持不变，footer 变化通过 `footer_version` 暴露。
- `markdown.rs`：`MarkdownStream` 拆出"解析"与"累积"两阶段，解析按节流触发。
- `theme.rs`：新增 `ThemeMode` 与 `adapt_buffer`，`Theme` 的 `ColorRole` 继续作为角色来源。
- `capabilities.rs`：`TerminalCapabilities` 作为 `SystemProfile` 的一部分输入，驱动 `TuiPerfPolicy`。

## 7. 非目标

- 不重写 ratatui 后端 diff（它已经工作良好）。
- 不引入 GPU/图像渲染。
- 不改变 reducer 的语义与现有快照内容。
- 不破坏 `wf-mini`（它不依赖本 crate 的渲染路径，见 `reducer.rs:1-8` 的说明）。
