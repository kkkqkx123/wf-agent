# 执行持久版本号设计

## 一、目标

把当前“每次轮询都完整导出 bundle 再算摘要”的远端修订号，换成由写路径维护的持久版本号，使管理端 inventory 可以O(1)读取版本变化，并能区分正常更新、回滚和损坏。

本设计是下一阶段的实现任务，不在当前批次改数据模型。

## 二、当前问题

现有 `source_revision` 是导出快照内容的 SHA-256。它有三个结构性缺陷：

* inventory 每轮对每个目标完整导出一次，把 history、artifacts、audit 和文件归档都重新计算一遍，目标多时开销大。
* 摘要没有单调性。远端被回滚到旧内容、或坏数据被写成“新状态”，管理端只能看到“版本不同”，无法判定这是更新还是事故。
* 摘要覆盖派生视图，但恢复路径不写回这些视图，恢复后重新导出的摘要与备份摘要不一致。

## 三、数据模型

在执行存储层新增一张按执行 id 聚合的修订表，字段包括执行 id、单调递增序号、内容摘要、更新时间、变更来源和变更原因。序号是漂移判定的主依据，摘要是内容一致性的校验依据，二者缺一不可。

摘要只覆盖可恢复投影：bundle 版本、执行 id、执行记录、checkpoint blob 与文件归档，以及解码所需的 checkpoint 标识。history、artifacts、audit 是派生视图，不进入摘要；导出时仍可随 bundle 返回用于审查，但不影响修订号。

## 四、写入路径

* workflow 与 agent 执行记录的保存和删除，由对应存储适配器在同一事务内推进修订号。
* checkpoint 状态的保存与删除，由 checkpoint 状态管理器推进修订号；写入元数据与推进修订号必须同事务。
* 文件归档提交后，由归档写入器推进修订号。git 提交与修订表无法同事务，因此采用“先提交、再推进、失败由对账修复”的顺序，并让对账以摘要为准。
* history、artifacts、audit、标题、统计等派生读取不推进修订号。
* 恢复写入完成后显式推进修订号，reason 标记为恢复；新序号必须大于当前序号与备份序号，避免把恢复误判成回滚。

不能在业务层逐点补调用，因为执行记录写入点分散在引擎、API、恢复与测试夹具中。修订号必须落在存储适配器和 checkpoint 状态管理器这类统一出口。

## 五、判定语义

inventory 返回每目标的序号与摘要。管理端按如下规则处理：

* 序号增大且摘要变化：正常更新，按计划拉取新快照。
* 序号不变但摘要变化：内容被原地改写，标记远端损坏。
* 序号变小：回滚，标记远端损坏或需要审批的回滚事件。
* 远端没有执行记录：远端丢失。
* 有执行记录但没有修订行：远端状态不完整，触发一次全量重建并告警。

只有“正常更新”触发自动备份；损坏、回滚和丢失只写状态，继续走人工恢复流程。

## 六、检查与修复

修订表是快速路径，摘要是慢速校验路径。启动或定时对账可以用一次完整导出重算可疑目标的摘要，不参与每轮 inventory。发现序号与摘要不一致时，不自动覆盖远端，只记录可取证状态。

修订表本身丢失时，按执行列表逐个完整导出并重建初始修订号；重建期间 inventory 返回“需要重建”，管理端不把它当成远端丢失。

## 七、接口与兼容

远端 inventory 返回序号、摘要和更新时间；bundle 仍返回完整快照。备份索引增加远端序号字段。管理端 sync state 用序号代替内容摘要作为比对基线，同时保留摘要用于校验。

开发阶段不做旧摘要到新序号的兼容映射。存量备份在下一阶段上线后由一次重建任务补齐基线，旧备份只作为可导出历史文件保留。

## 八、实施顺序

* 先让规范摘要只覆盖可恢复投影，并补测试确认派生视图变化不改变修订号。
* 在存储层引入修订表与统一推进接口。
* 接入执行记录、checkpoint 状态、文件归档三类写入路径。
* inventory、bundle、备份索引与 sync state 切换到序号优先的比较方式。
* 增加回滚、原地改写、修订表丢失和恢复后推进四类测试。

## 九、非目标

不引入跨数据库的分布式事务；不做自动冲突合并；不把远端节点改造成管理端；不在本阶段实现配置或进程的自愈启动。

当前批次的先行修改已经让规范摘要只覆盖可恢复投影，并把派生视图排除在修订号之外；这为该设计提供了摘要语义基础，但不改变本设计仍是下一阶段实现任务。

## 十、实施状态

本设计已经落地：

* `wf-storage` 新增按执行 id 聚合的 `execution_revision` 表与统一推进入口。执行记录、checkpoint 行和文件归档写入落在该存储出口；业务写入与修订行在同一数据库事务内提交，git 归档提交后的推进失败由对账修复。
* 规范摘要由 `wf-storage::revision` 统一定义，只覆盖记录、带标识的 checkpoint blob 与文件归档；history、artifacts、audit 不进入摘要。
* 远端 inventory 直接读取序号、摘要和更新时间，不再导出 bundle；额外返回 `remote_missing`、`incomplete`、`needs_rebuild` 状态供管理端区分故障。
* 管理端 sync state 用序号作为比对基线并保留摘要；序号增大且摘要变化才触发备份，原地改写、回滚、丢失和修订表缺失只记录状态。
* 备份索引与 bundle 增加 `source_sequence`；恢复后显式推进修订号，新序号大于当前序号与备份序号。
* 远端提供全量导出对账与修订表重建入口；启动后台对账只记录可取证状态，不覆盖远端数据。
