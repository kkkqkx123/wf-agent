# 检查点库基线增量存储设计（借用外部仓库对象）

本文是《文件检查点与外部 Git 同步设计》的姊妹篇。前者的目标是打通
检查点库与真实 git 仓库的交付链路；本文解决的是另一个独立问题：
**检查点内部对象库的初始构建成本与写放大**，方法是借用原始 git 仓库
的某个提交作为基线，实现增量存储、历史回引。

两篇文档共享同一份冻结规则修订、同一套外部仓库只读打开方式
与同一套元数据键约定，实施时先落地基线所需的只读能力，
同步设计的导入路径直接复用。

## 1. 问题：初始全量复制与写放大

### 1.1 现状

内部裸对象库（每工作区一个，默认位于全局数据目录）初始为空。
会话首次捕获时，当前流程把整个工作区符合条件的文件全量写成
对象并逐级构造树，最终生成提交挂到主干引用。

对于大仓库，这意味着首次捕获要对所有未被忽略的文件做
哈希、压缩与落盘，即使它们与用户仓库的提交内容完全一致。
对象库体积接近原仓库翻倍，会话冷启动出现明显卡顿。

此后小修改的开销是内容寻址模型的固有成本，不在本文范围。
**问题的核心是初始基线的全量复制**：这些对象在用户仓库的对象库
里本来就有，且内容寻址保证同一哈希即同一内容，重复存储是浪费。

### 1.2 适用前提

基线机制只在同时满足以下条件时启用，任一不满足即按配置的
失败策略回落到无基线全量模式：

- 工作区位于一个 git 仓库之内，能够定位到其对象库；
- 用户仓库与内部库的哈希算法一致（内部库固定使用 Sha1，
  算法不同则拒绝建基线，不做跨算法映射）；
- 基线配置节存在（缺省关闭，显式 opt-in）。

### 1.3 关键观察

- 用户仓库中任意提交可达的树与文件对象都是**内容寻址且不可变**的，
  与内部库使用相同的对象格式与哈希算法，可直接共享；
- git 原生支持备用对象库声明：一个对象库可以把另一个对象库
  声明为只读备用源，查找时先查本地、再查备用源，
  写入永远只落本地。所用对象库实现在打开时会自动加载该声明，
  上层读写无需感知来源，这正是增量存储加历史回引需要的机制；
- 内部库的引用模型与对象来源无关，引用可以直接指向
  位于外部对象库中的提交。

## 2. 方案比较

### 2.1 方案 A：种子拷贝

建库时解析用户仓库的基线提交，把该提交对象、整棵树及全部文件对象
一次性拷入内部对象库，然后主干引用指向该提交。

- 优点：内部库完全自包含，之后不依赖用户仓库的任何内容；
  用户改写历史、清理仓库、删除仓库均不影响检查点库。
- 缺点：首次建立仍是一次全量对象写入，冷启动成本几乎不变；
  磁盘占用依旧接近翻倍。只是把每次会话全量变成每个工作区首次全量。
- 实施要求：拷贝应基于打包传输而非逐对象松散写入，
  否则大仓库下种子过程漫长且产生大量小文件。

### 2.2 方案 B：备用库只读借用（推荐）

内部库创建时写入备用库声明，指向用户仓库的对象库。
基线提交对象不拷贝，直接把主干引用指向基线提交哈希。此后：

- 读取未变更文件内容时命中备用库，零拷贝；
- 捕获变更文件时新对象只写内部库本地对象目录；
- 日志、祖先判断与合并基点计算在越过基线进入外部历史时，
  经由备用库自动解析，对上层调用透明。

- 优点：初始建立零对象拷贝，冷启动成本从全量写入降为
  解析一个提交加写一个引用；磁盘零重复；历史可完整回溯。
- 缺点：内部库不再自包含，存在对用户仓库的外部依赖
  （见第 4 节风险与降级）。

### 2.3 结论

采用方案 B 为主，方案 A 作为显式备选保留。
方案 B 的依赖是只读加按哈希取不可变对象，风险可控；
需要自包含交付的场景选择方案 A。

## 3. 详细设计

### 3.1 冻结规则修订

当前冻结规则声明用户的仓库从不读也不写。
本设计连同同步设计将其修订为以下表述，实施时同步更新
对象库模块头的冻结注释，两篇文档共用同一版本：

- **写入默认仍然禁止**：除用户显式触发的导出提交动作
  调用外部 git 工具链外，检查点侧不对用户仓库做任何写入，
  包括引用、对象与配置；
- **读取从从不放宽为仅限对象层的只读借用**：
  只通过备用库声明按哈希读对象，不读取用户分支的实时指向
  作为语义依据，不跟踪分支移动；
- 不设引用级双向绑定，与同步设计不做引用级绑定的立场一致。

### 3.2 配置设计

新增可选配置节，与存储位置选项平级。整个基线节缺省不存在即关闭，
非 git 工作区即使配了也按失败策略处理。

配置包含模式与选择器两部分。模式为借用或拷贝，缺省借用。
选择器支持三种等价形式：分支尖端、分支加提交哈希前缀、
分支倒数第 n 个提交。其中提交前缀可独立使用，
分支信息仅用于可达性提示与日后重定基线；
倒数语义沿第一父链，行为可预测。

解析规则：

- 解析发生在种子时刻，解析出的完整提交哈希作为基线锚点
  持久化到检查点元数据，之后每次打开都使用该锚点，
  不再重新解析配置；
- 提交前缀在用户仓库内做前缀消歧，非唯一或不存在则报错；
- 种子时刻校验锚点对象存在且为合法提交；可达性仅作提示性检查，
  不可达只告警不拒绝（分支移动后旧锚点仍可能有效，
  存活性由存在性决定）；
- 工作区不是 git 仓库、算法不一致、分支或提交不存在时，
  按失败策略处理：报错模式直接失败，告警模式记录后
  回落到无基线全量模式，忽略模式静默回落；
- 与存储位置配置相互独立可自由组合，但在工作区内置库
  加借用模式下自包含承诺被打破，文档与日志需明确提示，
  需要自包含交付的场景应选拷贝模式。

### 3.3 外部仓库定位

禁止硬编码工作区下点 git 目录加 objects 的拼接路径。
定位流程为：从工作区向上发现仓库根，处理工作树、
点 git 文件与裸仓库等形态，解析公共目录得到真正的对象库位置，
同时读取仓库哈希算法做一致性校验。

备用库声明文件写入内部库的对象库信息目录，
内容为规范化后的绝对路径。浅克隆仓库中倒数解析可能越过
浅边界，解析失败按配置错误处理并提示改用提交前缀。
子模块内容不在主仓库对象库中，按现有忽略与捕获规则处理，
与基线机制无关。

每次打开检查点库时校验声明路径仍有效：
路径失效但经重新发现能定位到同一仓库时自动重写声明；
锚点对象不可解析时进入第 4 节降级流程。

### 3.4 种子流程（建库时一次性执行）

种子只发生一次，多会话共享同一内部库时以后到者为准做幂等判断。
流程按自然语言描述为：解析配置得到完整基线哈希并验证对象存在；
写入备用库声明；经备用库读取基线提交验证格式合法；
以原子比较交换方式创建主干引用指向基线；
将锚点三元组（哈希、解析来源、对象库路径）写入检查点元数据。
全程不拷贝任何对象。

要点：

- 基线树即内部主干的初始树。首次捕获沿用现有与主干引用求差异、
  只写有差异文件的路径，一致文件不产生任何新对象；
- 各执行者编辑引用首次提交以主干当前头为父，
  有向无环图的祖先关系从基线自然延续，合并基点计算无需特殊处理；
- 种子过程加库级互斥，防止多会话并发重复种子。

### 3.5 读取与遍历边界

对象查找经由支持备用库的句柄完成，上层读写无需感知来源。
但枚举类操作必须设定遍历边界，把基线锚点视为根：

- 全量提交枚举与提交日志在遇到锚点时停止下钻，
  外部历史不属于检查点的管理范围；
- 最近保留头的祖先展开同样止于锚点；
- 祖先判断与合并基点计算在穿越锚点后若仍未命中，
  按无共同祖先处理，不继续深入外部历史；
- 上层视图以引用与树为准，不受对象来源影响。

### 3.6 写入与回收

写入路径完全不变，新对象一律写内部库本地对象目录，
备用源只读。回收需同时满足三条：

- 回收扫描只枚举内部库自有对象目录，绝不触碰备用库内容；
- 回收可达性计算必须使用加载了备用声明的同一句柄，
  并把基线锚点加入根集合，否则会把借用链误判为不可达；
- 打包操作不得把备用库对象吸入本地包（默认行为即排除备用对象，
  实施时需以测试锁定该行为）。

基线锚点提交在用户仓库中的存活性由用户仓库自身保证，
内部回收不做担保也不做清理。

### 3.7 与同步方案的协调

基线机制与同步设计互补而非重叠：

- 基线锚点天然是首个对账点的内部侧坐标，
  首次导出可直接以锚点到主干当前树的差异生成提交，
  避免全量物化；
- 基线解决存储效率，同步动作解决交付语义，两者层次不同；
- 导入路径复用同一套外部仓库只读打开方式；
  若用户外部提交恰好在基线链上，差异计算可借助备用库历史对象；
- 对账点与基线锚点共用元数据键值存储，但键空间分离，
  各自独立演进。

## 4. 风险与降级

### 4.1 用户仓库历史改写

基线锚点是固定哈希。用户改写历史后基线对象可能不可达，
下次清理后可能物理删除，内部库经备用库查找将失败。

防线为种子时校验存在性、打开时校验可解析性、
失败后进入降级流程。降级按序尝试：重新按配置解析；
用户确认后切换新基线；无法恢复时按失败策略报错或重建。

切换新基线的正确做法是移植提交：在新基线之上创建一个新提交，
其树内容等于旧主干树，新增差异对象补写本地库，
主干引用前移到该移植提交。旧历史在回收宽限期内保留可回滚。
禁止简单地把引用重挂到新基线，那会丢弃旧主干的全部过程历史。

### 4.2 用户仓库移动或删除

声明记录的是路径，仓库移动或删除后锚点不可解析。
打开时先尝试经重新发现修复声明路径，修复成功则继续；
否则走同一降级流程，元数据中的解析来源用于给出准确的错误提示。

### 4.3 拷贝模式作为显式备选

拷贝模式与借用模式共用解析、锚点与校验逻辑，
仅是否拷贝对象一步不同。拷贝应基于打包传输实现，
种子后删除备用声明，内部库完全自包含。

## 5. 明确不做

- 不借用用户引用：内部库永不读取用户分支的实时指向，
  基线一经解析即为固定哈希；
- 除显式导出提交外，不写用户仓库，包括引用、对象与配置；
- 不自动跟随基线前进，重定基线是显式动作，需校验与确认；
- 不改变引用分层模型，主干与编辑、评审、协作、人工引用的
  语义、审批策略与冲突流程全部不变。

## 6. 已决策事项

- 倒数语义沿第一父链；
- 备用声明使用绝对路径加打开时校验与自动修复；
- 可达性仅告警，存在性才是硬门槛；
- 首次导出差异范围为锚点到主干当前树的全差异单提交，
  与同步设计的干净度检查合并考虑。

## 7. 待决问题

- 重定基线的确认交互形态由调用界面决定，
  核心库只提供校验与移植原语，不绑定界面。
