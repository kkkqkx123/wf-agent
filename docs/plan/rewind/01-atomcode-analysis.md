# atomcode 回溯实现分析

> 分析对象：`https://github.com/atomgit-atomcode/atomcode`，克隆于 `/tmp/atomcode`（只读参考）。
> 关键实现：`crates/atomcode-capabilities/src/session/rewind.rs`、`crates/atomcode-coding/src/runtime.rs`、`crates/atomcode-tui/src/rewind.rs`。
> 关键设计文档：`docs/plans/2026-07-28-rewind-design.md`、`2026-07-28-rewind-implementation-plan.md`、`2026-10-16-rewind-missing-objects.md`、`2026-10-13-incremental-workspace-checkpoint-design.md`。

## 一、职责划分：三层，单一所有者

| 层 | 位置 | 职责 |
|---|---|---|
| 存储与账本 | `atomcode-capabilities::session` | 影子 Git 对象库的捕获、恢复、差异、配额与 GC；回溯账本的读写与保留；只回答“能存吗、能取吗” |
| 操作与事务 | `atomcode-coding::runtime` | 唯一持有回溯动作：列举目标、校验前置条件、编排会话与代码两侧、提交或补偿 |
| 投影与交互 | `atomcode-tui` / `atomcode-cli` | 纯选择器：拉取目标列表、展示面板、提交一个请求、等待一个终态 |

这条边界的价值在于：界面层不做文件写入，也不把“撤销”与“回滚”拼在一起；任何入口（命令行、后台、协议驱动）走的是同一个运行时操作。

## 二、捕获接缝

- 复用原生会话已有的 `SnapshotHook::turn_start` 与 `turn_complete`，不为回溯单独造回合状态机，内核保持中立。
- `turn_start` 只记录提示词序号与预览，不扫描工作区（对话回溯即使没有代码侧也可独立工作）。
- `turn_complete` 才落盘“回合后树 + 文件变更摘要”，**包括取消与失败的回合**，因此账本不会漏回合。
- 捕获失败对普通回合是尽力而为，但必须记录明确的不可用原因供界面展示，不允许静默成功。

## 三、数据模型

- `RewindPoint`：回合标识、提示词序号与预览、回合前树、回合后树、变更文件清单。
- `RewindLedger`：带版本号（当前为 2），按会话持久化，最多保留 100 个点，旧版本账本仍可读。
- 旧账本里只有树标识、没有新字段时，消费者按“仅会话”投影，不会因缺字段而整体失效。
- 失败语义：账本写入失败必须回滚到上一版点列表并上报失败，**不得伪造成功**。

## 四、存储形态：独立影子仓库

- 路径为 `<用户数据目录>/rewind/<项目哈希>/<会话标识>`，是一个独立裸仓库。
- 捕获时始终显式传 `--git-dir` 与 `--work-tree`，因此从不触碰用户自己的 Git 索引、HEAD 与分支。
- 通过 `alternates` 借用真实仓库已有对象，避免重复存储大文件。
- 引用命名：`refs/atomcode/turn-<id>/before`、`refs/atomcode/turn-<id>/after`、`refs/atomcode/recovery/current`、`refs/atomcode/capture/*`。
- 恢复前先拍一棵“恢复树”写进 `recovery` 引用，任何回滚失败都能退回改动前状态。

## 五、安全边界：四道闸门

这四道闸门是 atomcode 回溯设计中最值得学习、也最容易被忽略的部分。

1. **磁盘底线**。可用空间低于阈值（2 GiB）或库体积超过预算（500 MiB）时拒绝捕获；保留策略触发 `gc --prune=now`；环境变量可整体关闭代码回溯。
2. **对象完整性预检**。恢复前在一个批量进程内探测目标树及其派生树、blob 是否存在且类型正确；缺失只隔离该点并投影为“仅会话”，Git 或 IO 报错仍按错误上报。子模块（gitlink）属于其他仓库，跳过。
3. **捕获引用钉住**。捕获时在持锁状态下写临时引用，账本持久化成功后才释放；普通保留与清理不得回收被钉住的对象；崩溃遗留的钉是保守行为，不自动删除。
4. **先提交后回收**。保留策略先把“旧点集合 + 新点集合”一并钉住，等账本写入成功后才允许回收旧引用；回滚期间旧根必须仍然可用。

第 4 条修的是一个真实缺陷：先删旧引用、再写新账本，一旦写入失败就会出现“账本回滚了、对象没了”的不可恢复状态。

## 六、事务语义

- `RewindTransactionJournal` 落盘为旁车文件，状态机为“已准备 → 已应用 → 已提交”。
- 入口：`begin_rewind`；出口三选一：`commit_rewind`（成功）、`compensate_rewind`（主动补偿）、`recover_rewind`（重启后恢复）。
- `RewindTransactionGuard` 在析构时若未显式终结，默认发“恢复”而不是“提交”，即失败时选择保守方向。
- 只有运行时空闲时接受回溯请求；运行中只允许取消，取消后清空并抑制双击手势，避免连按 Esc 溢出成回溯。
- 请求在变更工作区之前校验：代次、会话绑定、会话修订号、目标点是否可用。任一不符即失败且不改工作区。

## 七、作用域与缺失降级

- `RewindScope::{Conversation, Code, ConversationAndCode}` 在运行时是完整三档。
- 界面只给两档（仅会话、会话加代码），代码单改没有独立入口，减少误操作面。
- 点不可用、对象缺失、代码回溯关闭时，统一降级为“仅会话”，并给出显式原因（未启用、无会话、失败三类），而不是禁用整个面板。

## 八、界面交互

- 入口是双击 Esc（空闲态），并保留 `/rewind` 斜杠命令。
- 面板初始选中 `(current)`，对它按回车是**空操作**——这是防误触的核心设计。
- 两步提交：先选回合，再选作用域，作用域默认“仅会话”。
- 运行中 Esc 只取消；取消会清空并抑制回溯手势。
- 界面不自己算差异、不自己写文件，只提交一个请求并等待一个终态，之后整体重绘。

## 九、演进教训

| 阶段 | 事件 | 教训 |
|---|---|---|
| 早期 | 双击 Esc 直接执行撤销 | 手势与破坏性操作绑定，误触代价高 |
| 5.0.5 | 每会话独立影子库无配额、无回收，可能耗尽磁盘，代码回溯整体关闭 | 存储形态必须先解决配额、余量与回收，再谈功能 |
| 后续 | 改为项目共享对象库、借用源仓库对象、加预算与空间检查、可中断超时、孤儿清理后重开 | 无界存储是不可接受的设计债 |
| 缺失对象隔离 | 旧点对象缺失不再阻断新点，投影为仅会话 | 局部故障必须能降级，不能整体瘫痪 |
| 钉住与顺序修正 | 引用钉住存活到持久化提交；保留先钉后回收 | 回收与提交的先后顺序决定崩溃后能否恢复 |

## 十、可借鉴与不借鉴

值得借鉴：

- 单一所有者（运行时）与纯投影界面，杜绝界面层直接改文件。
- 复用既有回合接缝，不新造状态机。
- `(current)` 默认空操作、两步提交、运行中抑制手势。
- 缺失对象隔离为“仅会话”，而不是整个功能不可用。
- 先钉后回收、写失败回滚账本、析构默认走恢复。
- 恢复前先拍恢复树，失败可退。

不照搬：

- 独立影子仓库与 `alternates` 借用。当前项目已有自己的 Git 对象库与引用命名空间，再建一套会带来双份清理与双份一致性负担。
- 逐回合两次全量扫描。当前项目已有按节奏产生的检查点，应优先引用链上检查点，避免重复扫描。
- 账本文件旁车。当前项目已有 SQLite 元数据库与迁移机制，账本应入库，便于按会话查询与保留裁剪。
