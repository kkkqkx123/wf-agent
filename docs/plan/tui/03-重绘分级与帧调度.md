# 重绘范围分级与帧调度

## 本文参考的 jcode 设计

| jcode 设计 | 位置 | 本文取用的部分 |
| --- | --- | --- |
| 事件循环唯一绘制点 | `jcode-tui` `tui/app/run_shell.rs` 的 `needs_redraw` 分支 | 所有重绘请求（tick、输入、总线事件）汇入同一处节流与判定 |
| 三级重绘路径 | 同文件：`idle_animation_only_available` / `draw_idle_animation_only`、`spinner_only_available` / `draw_status_spinner_only`、`draw_full` | 整帧、底部区域、动画区域三档提交路径的划分 |
| 上一帧动画区域记录 | `run_shell.rs` 的 `StatusSpinnerRenderer.seeded_animation_area`、`LAST_IDLE_ANIMATION_AREA`（原子打包 `Rect`），配合 `tui/ui_animations.rs` | 记录动画包围矩形，使局部重绘无需整块缓冲复制；wf 单线程绘制改用普通字段 |
| 绘制入口重置动画区域 | `tui/ui.rs` 的 `ui::draw` 第一步 `record_idle_animation_area(None)` | 每帧先清记录、绘制中重建的约定 |
| 按状态分级的重绘节奏 | `tui/redraw_schedule.rs`：`REDRAW_IDLE=250ms`、`REDRAW_PASSIVE_LIVENESS=1000ms`、`REDRAW_REMOTE_STARTUP=1000ms`、`REDRAW_DEEP_IDLE=5000ms`、`REDRAW_DEEP_IDLE_AFTER=30s` | 空闲/深度空闲等状态用不同轮询周期，而非固定一档 |
| 真实变化与动画推进的区分 | 同文件 `periodic_redraw_required` | 范围判定函数的输入语义 |
| 动画帧率与重绘调度解耦 | `jcode-config-types` 的 `display.animation_fps`（默认 60，限幅 1..=120） | 动画按自身帧率推进、重绘调度按需取用，避免 120 FPS 空转 |
| 局部提交仍走标准绘制 | `draw_full` / `draw_status_spinner_only` 最终都经 ratatui 提交 | 本文封装统一呈现方法、整帧路径保持标准接口的依据 |

## 现状

事件循环位于 `crates/app/cli/wf-tui/src/tui.rs`。循环每轮处理挂起、交互事件、后台数据、主题热重载，再按脏标记与帧率限制决定是否整帧绘制。绘制条件是脏标记或交互控制器存在时请求帧，满足速率限制即整帧提交。轮询间隔为一百毫秒，帧率上限约一百二十帧。

绘制入口按纵向切分保留通知行，交互控制器内部再按滚动区、状态栏、输入行切分。滚动区绘制每次重建全部显示行，状态栏与输入行每次重绘。通知行、状态动画、加载指示的变化都会触发整屏缓冲重建，终端后端的差异比较虽然压缩了实际输出字节，但缓冲构造的处理器成本仍是整屏量级。

帧率限制器在 `crates/app/cli/wf-tui/src/framer.rs` 中实现，数学纯粹且时钟可注入，设计良好。问题在于它只区分是否重绘，不区分重绘范围。所有请求合并为同一档，动画推进与内容变化走同一提交路径。

对照 jcode，差距在于缺少重绘范围判定与局部提交路径。jcode 只有一个绘制点，但进入绘制前先判定是整帧还是仅动画行，空闲动画只重绘记录过的动画区域。重绘节奏按状态分级，深度空闲时周期显著拉长。

## 修改目标

让动画与状态栏变化不再重建整屏内容排版，让空闲时帧率受策略控制而非固定上限。

## 方案

引入三档重绘范围：整帧、仅底部区域、仅动画区域。判定函数消费两份版本快照并比较内容版本、流式版本、底部状态版本、通知、主题、宽度、滚动位置、动画时刻的差异。内容与布局相关变化走整帧，仅底部状态变化走底部区域，仅动画推进走动画区域，其余情况不提交帧。

为支持局部提交，渲染层保留上一帧的完整缓冲与各区域几何。整帧路径清空并完整绘制，与现状一致。底部区域路径以上一帧缓冲为种子，只清空并重绘底部相关区域。动画区域路径只清空并重绘记录过的动画区域。提交时统一封装为呈现方法，内部仍走终端绘制接口，避免与终端库版本耦合。

动画区域需要精确记录。流式行首的指示符与底部可能的状态动画是唯二的动画源，绘制时记录其包围矩形，供下一帧局部重绘使用。记录方式采用普通字段即可，当前为单线程绘制路径，无需原子操作。

帧调度保持现有限制器不变，新增携带范围的请求方式。应用层维护待处理范围并按严重程度合并，整帧优先于底部区域优先于动画区域。动画范围的请求按动画帧率而非整帧上限触发，避免高频空转。

事件循环的改动集中在判定与提交两处。循环顶部收集版本快照，绘制前计算范围并选择提交路径。通知行的存续继续驱动重绘，但其变化只产生底部区域范围，不再升级为整帧。挂起恢复、尺寸稳定、主题热重载三类事件继续产生整帧。

## 与现有模块的衔接

布局切分比例保持不变。底部状态栏与输入行的绘制方法保持签名不变，局部路径只是限制其生效区域。尺寸防抖、数据拉取、覆盖层、模态框的逻辑不变，覆盖层与模态框出现时强制走整帧。

## 验收

动画帧的变更单元格数显著下降，整帧路径的快照输出与之前逐字节一致。判定函数具备完整的真值表测试，三种范围下的缓冲等价性可离线断言。空闲动画帧率受策略控制，不再以整帧上限空转。

## 风险与回退

主要风险是自持缓冲与终端后端状态不一致。缓解方式是整帧路径仍走标准绘制接口，局部路径只在连续两帧均为局部时启用，任何整帧事件都重建种子。若出现残影，回退到全部走整帧提交，判定逻辑保留用于度量。
