# 文件检查点与外部 Git 同步设计

## 1. 背景与问题

文件检查点子系统目前维护一个内部裸 Git 对象库（`git_store`），以
`actor 编辑 ref → review ref → feature ref → main ref` 的分层 ref 模型管理文件历史，
冲突合并采用标准三路合并（底层复用 `gix_merge` 的 diff3 文本合并，
冲突产出标准 `ours/base/theirs` 标记）。

实践中暴露出以下问题：

1. **能力重复**：内部合并模型在算法层面与 git 原生合并完全一致（同一实现），
   重复的是 ref 编排、冲突登记、多父 DAG 管理等外围设施。
   二者不是竞争关系，而是"同一算法、两个对象库"。
2. **轻量场景下的纯开销**：当各支线（actor）修改点专注、无严重冲突时，
   内部的 review/feature 两跳合并总能干净通过。此场景下用户实际需要的
   只是把最终结果在真实项目仓库里提交一次，检查点的分层合并是多余环节。
3. **两个世界割裂**：检查点的 main ref 与用户真实项目仓库的 git 历史互不可见，
   用户手工 git 操作（提交、rebase、丢弃）产生的状态变化，检查点侧无法感知和衔接，
   导致"手动 git + 丢弃检查点"成为事实上的逃生通道。

本设计的目标是：**不推翻现有内部合并模型，增加与外部 git 的同步能力**，
把内部检查点定位为"过程级安全网"，把真实 git 提交定位为"交付级同步"，
让轻量场景可以从检查点直接落到 git 提交，绕过不必要的环节。

## 2. 设计思路

### 2.1 定位划分：安全网 vs 交付

- **内部检查点库**：高频、细粒度、可回滚的执行过程记录。
  它的价值在于 actor 隔离、审批策略、精确回滚，这些是 git 原生工作流
  不便提供的；保留它，不弱化。
- **外部 git 仓库**：用户协作与交付的最终事实源。
  检查点结果最终应能以普通 git 提交的形态进入它。

两个库保持**松耦合**：不做 refs 级双向绑定（见 2.4），通过显式同步动作衔接。

### 2.2 同步方向：以导出为主，导入为辅

- **导出（检查点 → 外部 git）为主路径**：覆盖"支线专注、无严重冲突、
  直接在 git 里一起提交就足够了"的主场景。
- **导入（外部 git → 检查点）为辅路径**：覆盖用户在外部手工提交后，
  检查点侧需要重新对齐基线的场景，复用现有 human ref /
  手工变更捕获的"人工内容永不自动合并"语义。

### 2.3 导出的最小语义

导出动作的最小语义是：**将检查点 main ref 当前树 materialize 到真实工作区，
并生成一次外部 git 提交**。要点：

- 内容来源是检查点 main ref 的树快照，通过现有的工作区物化机制写入真实工作区，
  外部 git 随后按普通工作区变更对待（用户可用任意 git 工具提交）。
- 导出前做一次**干净度检查**：真实工作区若存在与检查点无关的未提交修改，
  需要向用户确认或拒绝，避免把不相干的脏状态混入导出提交。
- 导出后**记录对账信息**（检查点 main commit id ↔ 外部 git commit id 的对应关系），
  作为后续导入合并的 merge-base 依据，防止重复导出产生空差异提交。
- 冲突场景不特殊处理：若内部 main 存在未解决冲突（trailer 标记），
  导出直接拒绝并提示先解决冲突。冲突解决仍走检查点自身的 resolve 流程，
  不把冲突区域抛给外部 git。

### 2.4 明确不做的：refs 级双向绑定

不考虑让内部库直接使用真实仓库 `.git` 下的 refs（如挂载到独立命名空间）。
原因：

- 真实仓库的 rebase / force-push / 历史改写会破坏内部 DAG 的祖先关系假设；
- 检查点库需要独立的 GC 与生命周期，与项目 git 历史耦合后无法独立清理；
- 检查点的 actor/review 分层 ref 会污染用户的 ref 空间视图。

松耦合 + 显式同步牺牲一点便利，换取两个库各自的完整性，这是本设计的核心取舍。

### 2.5 导入的最小语义

导入动作的最小语义是：**把外部 git 的净变更作为一次人工提交捕获进检查点库**。
要点：

- 以最近一次导出记录的对账点为 merge-base，计算外部 git HEAD 相对它的差异；
- 差异内容落到 human ref（或等价的人工来源通道），沿用
  "人工编辑永不自动合并、需显式 approve"的既有语义；
- 外部历史与内部 DAG 无祖先关系时（例如用户 rebase 过），按无 base 的
  add/overwrite 语义捕获并明确提示，不做猜测性合并。

## 3. 流程说明

### 3.1 导出流程（主场景）

```
[agent 执行中]
  actor 写入 → 提交检查点 → （按策略）review/feature 合并 → main ref 前进
[agent 结束，用户触发导出]
  1. 前置检查
     a. main ref 无未解决冲突（有则拒绝，提示走冲突解决）
     b. 真实工作区无不可解释的脏文件（有则要求用户确认/清理）
     c. 存在有效对账点（无则视为首次导出，全量 materialize）
  2. 物化
     将 main ref 树与工作区当前状态求差异，仅写入有差异的文件
  3. 外部提交
     生成建议提交信息（来源：本次导出涉及的 actor/时间范围摘要），
     由用户确认后在外部仓库执行普通 git 提交；也可仅物化、由用户自行提交
  4. 记录对账点
     写入 (内部 main commit id, 外部 git commit id) 对应关系
[后续执行]
  agent 继续在内部库上工作，不受导出影响
```

说明：第 3 步的提交动作本身交给外部 git（用户或既有 git 工具链）完成，
检查点侧不重新实现提交编排；它只负责"把内容准确放到工作区 + 留下对账依据"。

### 3.2 导入流程（辅场景）

```
[用户在外部仓库手工提交 / 协作者推送]
  1. 触发方式
     a. 手工变更轮询发现外部 HEAD 越过对账点（复用现有轮询通道）
     b. 用户显式发起"从 git 导入"
  2. 差异计算
     以对账点为 merge-base，计算外部 HEAD 的净文件差异
  3. 捕获
     差异落到 human ref，标记为人工来源，不自动合并；
     若与内部 main 有重叠修改，进入既有冲突流程（feature ref 阻塞 + 人工解决）
  4. 对账点更新
     导入捕获完成后推进对账点到当前外部 HEAD
```

### 3.3 轻量场景的推荐组合

针对"无严重冲突、各支线专注"的典型场景，推荐工作方式：

- 检查点照常捕获（保留回滚能力），agent 结束后直接走导出流程；
- 无需在检查点侧进行额外的冲突人工介入——干净合并自动完成，
  结果一次性落到外部 git 提交；
- 用户也可以选择更激进的"只捕获、不自动合并"策略（审批策略取 manual），
  平时完全用 git 提交交付，仅在确实需要回滚时回到检查点侧操作。
  这相当于把现有"接受该问题 + 手动 git"的做法正规化，
  但不丢弃检查点的捕获与回滚能力。

## 4. 与现状的关系

- 现有内部三路合并、冲突标记、冲突解决、审批策略**全部保留**，不修改语义；
- 新增能力仅有三块：导出动作、导入捕获扩展、对账点存储；
- 现有工作区物化机制与人工变更捕获通道被复用，不新造并行机制；
- 逃生通道（完全关闭文件检查点、纯 git 工作流）继续可用，
  本设计提供的是两者之间的中间形态。

## 5. 待决问题

1. **导出提交的执行方**：由检查点侧直接调用外部 git 提交，还是仅物化 +
   生成建议信息交给用户/前端执行？前者省事，后者保留用户对提交内容的最终控制。
   倾向后者，待审查确认。
2. **对账点存储位置**：随检查点元数据存储（随会话迁移），还是存于外部仓库的
   本地配置中（跟随项目）？跟随项目更符合多人协作，但需要处理仓库克隆后的
   首次对账建立。
3. **导入的自动触发阈值**：手工变更轮询发现外部提交后是自动捕获，
   还是仅提示用户显式导入？自动捕获与"人工内容永不自动合并"原则不冲突，
   但会产生用户未预期的内部提交记录。
4. **多检查点会话共享一个工作区时**的对账点归属与互斥（同一时刻只允许一个
   会话导出）。
