# 远端备份与恢复链路实现核对

核对对象：`wf-agent` 提交 `dc8dc82`（add execution persistent-revision for remote backup）。

核对方式：静态阅读源码，逐条对照 `docs/features/remote/backup.md` 与 `docs/features/remote/error-handling.md`。未执行编译与运行验证，结论依据为代码路径与既有单测断言。

## 一、结论摘要

备份到本地的产物是单个执行的完整恢复快照，恢复路径已打通到远端只读节点，链路可用。远端漂移检测分两级：轻量 inventory 轮询读修订表，重量 reconcile 全量导出复核。

主要问题集中在状态机的闭环，而不是数据形态：

* 恢复成功后管理端没有回写同步位点，远端序号已前进而本地基线未动，下一轮备份会把刚恢复好的目标判成内容损坏。已在单测中体现（恢复后摘要不变、序号加一）。
* 修订表重建把序号重置为一，与本地基线必然冲突，判成回滚后没有任何自动或半自动出口。
* 单行修订缺失只能人工处理，而整表丢失反而能自动重建，修复成本倒挂。
* 本地备份的损坏与丢失不进入同步状态机，只在启动对账和每轮校验里被动体现，`sync-state` 看不到。

本地重新同步的起点设计成立（持久位点优先、最新备份兜底、都没有则从头备份），范围受 `backup_executions` 白名单约束，只补最新一份、不补历史份，也不做增量；但备份目标的真相源只在本地，本地索引库整库丢失后无法从远端反向重建目标列表。

## 二、备份到本地的数据形态

一次备份对应一个执行 id，远端在单次响应里返回完整快照，结构见 `crates/app/wf-api/src/execution_bundle.rs:71`。

快照包含持久化执行记录、统一历史视图、artifact 条目、审计摘要、完整检查点链（每个检查点的元数据与状态 blob）、执行上下文归档文件、格式版本、导出时间、源序号与摘要。

摘要只覆盖可恢复投影（`execution_bundle.rs:102`）：执行记录、检查点元数据与 blob、文件归档。导出时间、摘要字段自身、history、artifacts、audit 不计入（`execution_bundle.rs:144`）。这条边界很关键，它让派生视图变化不会引发备份，也让恢复后重算的摘要能与备份时一致。

落盘时管理端额外写入 `backup_version` 字段（`crates/app/wf-server/src/backends/backup.rs:222`），该字段不参与摘要。落盘字节的 SHA-256 与索引行同源（`backup.rs:311`），因此索引里的摘要描述的是真实落盘内容。

请求走 `GET /api/v1/remote-sync/executions/{id}/bundle`（`backup.rs:452`），响应先做结构校验再进入落盘：状态码、`success`、`data`、`bundle` 对象、执行 id 一致（`backup.rs:421`）、`payload_digest` 存在；随后再校验 `source_sequence` 大于零、`source_revision` 与 `payload_digest` 相等（`backup.rs:226`）。任一不满足即失败，不写文件、不写索引。

## 三、远端损坏与丢失的检出

### 3.1 轻量轮询：只读修订表

每轮备份开始前，管理端按后端批量拉取 inventory（`crates/app/wf-server/src/backends/manager.rs:768`），分批以避免单一长 URL 拖垮全部目标（`manager.rs:351`）。

远端 inventory 直接读持久修订表，不为任何目标导出快照（`crates/app/wf-server/src/api/observation/bundle.rs:146`）。状态取值：

| 状态 | 判定条件 | 位置 |
|---|---|---|
| `remote_missing` | 执行不在该目录的执行列表里 | `bundle.rs:198` |
| `needs_rebuild` | 修订表整体没有任何行且执行列表非空 | `bundle.rs:182` |
| `incomplete` | 该执行的修订行读不出来 | `bundle.rs:210` |
| `ok` | 修订行正常 | `bundle.rs:203` |

管理端把远端状态映射为本地判定（`manager.rs:849`）：`remote_missing` 记远端丢失，`needs_rebuild` 记待重建，其余非 `ok` 一律记内容损坏。

### 3.2 与本地比对：序号加摘要

比对基线来自持久同步位点，缺失时回落到最新本地备份的源序号与源摘要（`manager.rs:521`）。判定规则在 `manager.rs:536`：

| 远端序号相对基线 | 摘要 | 结论 |
|---|---|---|
| 更大 | 变化 | 正常更新，触发备份 |
| 更大 | 相同 | 内容损坏（序号空转） |
| 更小 | 任意 | 回滚 |
| 相等 | 变化 | 内容损坏（原地改写） |
| 相等 | 相同 | 无变化，跳过 |

只有"序号更大且摘要变化"会触发备份，其余异常只记录状态，不覆盖远端，也不写本地备份（`manager.rs:873`）。

### 3.3 重量复核：全量导出比对

启动时执行一次对账（`manager.rs:640`），对每个目标调用 reconcile 端点。远端对每个执行做完整导出，把导出摘要与修订行记录的摘要比对（`bundle.rs:311`），不一致报 `digest_mismatch`，导出失败报 `export_failed`，修订行缺失报 `incomplete`。

管理端据此写取证状态（`manager.rs:456`）：`incomplete` 映射为内容损坏（`manager.rs:459`），`digest_mismatch` 映射为内容损坏（`manager.rs:473`），只有 `needs_rebuild` 会触发远端重建（`manager.rs:491`）。

### 3.4 修订表的维护

修订表由存储写入路径自动推进：任何记录或检查点的保存都会带上组件更新并推进序号（`crates/infra/wf-storage/src/backend.rs:275`），推进逻辑在 `crates/infra/wf-storage/src/revision.rs:261`。文件归档单独推进（`revision.rs:334`），因为 git 提交与修订表无法共用事务。

重建只能由修订表整体丢失触发，重建后序号固定为一（`revision.rs:410`）。

## 四、从本地备份恢复远端

入口有三层：CLI 批量编排、管理端单目标恢复、远端只读节点写入。

CLI 的 `recover` 只处理 `remote_missing` 与 `remote_corrupt` 两种状态（`crates/app/cli/wf-cli-shared/src/cmd/remote.rs:44`），按后端与执行过滤后逐个处理（`remote.rs:414`）。每个目标取该执行创建时间最新的一份备份（`remote.rs:48`），先向服务端复验摘要（`remote.rs:438`），再做 dry-run（`remote.rs:463`），加 `--apply` 才执行写入（`remote.rs:473`）。任一环节失败只记录原因并继续下一个目标。

管理端单目标恢复先复验、再导出原始包体、再转发给远端（`manager.rs:1360`）。

远端恢复端点只在 `WF_RECOVERY_RESTORE_ENABLED=1` 时注册（`crates/app/wf-server/src/api/recovery.rs:20`），handler 把 bundle、dry-run 标志与目录范围交给 `restore_bundle`（`recovery.rs:47`）。

`restore_bundle` 的校验顺序（`execution_bundle.rs:388`）：格式版本、执行 id 非空、重算摘要并与两个摘要字段比对、源序号大于零、执行记录非空、记录 id 与目录归属一致、检查点归属一致、归档路径安全、全部检查点 blob 可解码。任一失败都在写入前终止。

写入前还要确认目标执行不存在（`execution_bundle.rs:471`），已存在直接报冲突。dry-run 到此返回计划，不做任何写入（`execution_bundle.rs:486`）。

实际写入顺序：执行记录、检查点（含元数据与 blob）、文件归档，最后推进修订行（`execution_bundle.rs:490` 至 `:543`）。恢复后修订序号取本地当前序号与备份序号较大者加一（`revision.rs:369`），保证恢复动作永远不会被误判为回滚。

恢复边界：不写回 history、artifacts、audit 三个派生视图；不恢复运行时会话、队列、锁、凭据、工作区文件历史引用；跨三套存储没有单一事务。

## 五、本地损坏与丢失的检出

### 5.1 启动对账

服务启动后异步跑一次仓位对账（`manager.rs:640` 调 `manager.rs:656`）。对账做四件事：清理中断写入残留的临时文件、统计目录有文件而索引无记录（孤儿）、索引有记录而文件缺失、记录存在但内容摘要不符（`backup.rs:497`）。结构完整的孤儿文件会被重新登记进索引（`backup.rs:527`、`backup.rs:652`），其余只统计不删除。

计数进入指标与一条聚合告警（`manager.rs:662`），根目录不可读时对账以失败结束并计入轮级错误。

### 5.2 每轮校验最新一份

每个备份轮次对每个目标取最新一份备份（`manager.rs:499`），读回文件重算 SHA-256 与字节数并与索引比对（`manager.rs:1419`），结果只用于判定这一份是否可用（`manager.rs:512`）。

只要本地这份无效，即使未到下次到期时间也会立即重新拉取（`manager.rs:888` 与 `manager.rs:916`）。备份成功后还会立即读回校验一次，失败则删索引行再删文件，不让坏快照成为最新备份（`manager.rs:941`、`manager.rs:1009`）。

## 六、本地位点与同步范围

位点计算在 `manager.rs:521`：优先取持久同步状态里的序号与摘要，没有就取最新备份的源序号与源摘要，两者都没有视为首次同步。首次同步直接按正常更新处理，会拉一次全量。

同步范围由注册表条目的 `backup_executions` 白名单决定（`manager.rs:770`），远端只按目录范围列出执行，不做"远端有而配置没有"的反向发现。

到期判定结合内存缓存、同步状态与索引最大创建时间三处时间戳（`manager.rs:894`），加按目标名派生的确定性抖动（`manager.rs:1128`），失败按指数退避封顶（`manager.rs:1121`）。

每次同步都是完整快照，没有增量、没有断点续传、没有分片（`backup.rs:208`）。

## 七、合理性判断

设计上成立的部分：

* 职责划分清晰。远端只保留执行能力与只读同步端点，备份、索引、恢复编排都在管理端，远端不需要知道"谁在备份我"。
* 摘要边界选得准。只覆盖可恢复投影，派生视图抖动不会污染漂移检测，恢复后重算摘要能与备份时对上。
* 两级检测的成本模型合理。常规轮询只读修订表，代价与执行规模无关；只有启动或显式对账才做全量导出。
* 异常不自动覆盖远端。原地改写、序号回退、执行缺失都只记录取证状态，把决定权留给操作者，避免用一份可能过期的备份盖掉远端更新的数据。
* 落盘做到了崩溃安全。私有临时文件、边写边算摘要、同步文件、改名、同步目录项，索引写失败会回滚已发布文件。
* 保留策略按目标隔离，退避与抖动按目标独立，失败不推进位点也不触发裁剪。
* 恢复默认 dry-run，且在写入前解码全部检查点 blob，坏 blob 不会造成部分写入。

不够合理的部分见下一节，核心是"状态机只建模远端，不建模本地，也不建模恢复动作"。

## 八、缺陷与风险

### 8.1 阻塞级

**恢复成功后位点不回写，下一轮把刚恢复的目标判成损坏。**

恢复把远端序号推进为"本地当前与备份序号较大者加一"（`revision.rs:369`），摘要按恢复后的组件重算。对不含文件归档的执行，恢复后摘要与备份摘要完全相同，这一点由单测直接断言（`execution_bundle.rs:630`）。而管理端的同步位点只在三处写入：远端失败（`manager.rs:558`）、备份成功（`manager.rs:981`）、备份失败（`manager.rs:1034`）。恢复路径不写位点。

于是下一轮 inventory 返回"序号大一、摘要相同"，命中"序号更大且摘要未变"的分支（`manager.rs:546`），被判为内容损坏。此后每轮都跳过备份，`recover` 又会因为它处于 `remote_corrupt` 而反复选中它，再次恢复时远端已存在同名执行，dry-run 直接冲突失败。目标进入可复现的死循环，且 `recover` 无法自清。

**修订表重建把序号重置为一，与本地基线必然冲突，且没有出口。**

`rebuild` 固定写入序号一（`revision.rs:410`）。重建只在整表丢失时触发（`bundle.rs:182`），这意味着所有目标的行都从零开始。管理端基线的序号通常大于一，下一轮比对落入"序号更小"分支（`manager.rs:548`），被判为回滚。

回滚状态不在 `recover` 的处理范围（`remote.rs:44` 只匹配丢失与损坏），服务端也没有单目标位点重置接口，重启也无济于事，因为重建后修订表已有行，不再满足 `needs_rebuild`（`bundle.rs:182` 只看表是否为空）。结果是整表丢失这一种情况会让全部目标永久停止备份，只能手工改库。

### 8.2 重要级

**单行修订缺失的修复成本高于整表丢失。**

表非空而某个目标的行缺失时，inventory 报 `incomplete`（`bundle.rs:210`），管理端映射为内容损坏（`manager.rs:459`），不进重建列表；reconcile 同样报 `incomplete`，同样不进重建列表（`manager.rs:460` 只对 `needs_rebuild` 收集 id）。重建端点本身支持按 id 指定（`bundle.rs:338`），但没有任何路径会为单行缺失发起重建。运维上要修复一个坏行，反而得把整张表清空来触发全局重建，而全局重建又会撞上上一节的回滚死锁。

**恢复只接受"目标不存在"，而损坏场景的目标通常还存在。**

损坏判定来自"序号相同而摘要变化"或"序号空转"（`manager.rs:546`），此时执行记录仍在，`restore_bundle` 会以冲突拒绝（`execution_bundle.rs:471`）。文档把"先归档或删除目标"交给操作者，但没有提供任何归档、软删除或强制覆盖的命令，dry-run 的失败信息也不带这一步的操作指引。批量 `recover` 在这种情况下会稳定产出"dry run failed"的跳过项。

**批量恢复只取最新一份备份，不复验失败后回退。**

`latest_backup` 只按创建时间取最大一条（`remote.rs:48`），不复验候选集；这份备份校验失败就整目标跳过（`remote.rs:447`），不会尝试次新的一份。而本地最新备份恰好是唯一可能损坏的那一份（写入失败会被回滚，但事后介质损坏不会被回滚）。保留策略内明明还有若干份可用备份，恢复却因为"最新一份坏了"而放弃。`--repairable` 也只是先筛状态再取最新，不改变这一点。

**本地损坏与丢失不进入同步状态机。**

同步状态只记录远端序号、摘要、备份 id 与修复状态（`crates/app/wf-server/src/backends/types.rs:193`），没有任何本地字段。本地文件缺失时，`sync-state` 仍显示正常；本地损坏只在启动对账的日志与指标里体现（`manager.rs:662`），运行期删除索引或文件不会触发任何对账。用户想确认"我本地哪些备份没了"，只能逐个 `backup-verify`。

**运行期没有周期性远端全量复核。**

reconcile 只在启动时跑一次（`manager.rs:640`）。轮询只比对修订行里的摘要，如果远端内容被改动而修订行没有同步更新，inventory 仍返回正常，运行期完全看不出来。也就是说，检测"内容是否完好"的能力被绑定在重启频率上；长期不重启的管理端，对静默损坏没有检出能力。

**恢复后文件归档组件没有推进，账本与实际内容不一致。**

恢复时文件归档通过 `archive_import` 写入（`execution_bundle.rs:535`），该函数不推进修订组件（`crates/infra/checkpoint/checkpoint-file/src/archive.rs:162`）。正常写入路径是在 git 提交后单独推进（`crates/app/wf-api/src/infra/context.rs:335`），恢复路径漏了这一步。而 `advance_after_restore` 用的是恢复后的现状组件（`revision.rs:374`），于是含文件归档的执行恢复后，修订行摘要描述的是"缺了文件归档"的投影，与下一次全量导出的结果不同，下次对账会把这份正确的数据判成摘要不一致。

### 8.3 次要级

* 每个备份轮次对每个目标读回整份文件复算摘要（`manager.rs:888` 调 `manager.rs:1419`），IO 成本与目标数乘以单份体积成正比，且每小时重复一遍。
* 文件归档以十六进制字符串存放（`execution_bundle.rs:65`），体积翻倍，与响应体上限叠加后更容易触发硬失败；而检查点与归档都不再截断，超限即整目标失败。
* 恢复端点未开启时返回 404，管理端只把它包装成"restore failed: 404"（`manager.rs:1404`），不提示是开关未启用。
* 历史备份份数丢失不检测、不补齐。保留策略内的次新备份被删掉，对账只增加一个缺失计数，不会重新拉取，也不会从索引中移除该行，列表里长期存在指向空文件的记录。
* 恢复写入跨三套存储无事务，中途失败会留下部分状态，而"目标必须不存在"的前置条件让重试必须先人工清理。

## 九、改进建议

按性价比排序：

1. 恢复成功后同步位点。`restore_bundle` 返回新的序号与摘要，管理端在 `restore_backup` 成功后回写同步状态，把修复状态置为正常。这一步能同时解掉"恢复后立刻损坏"与"`recover` 反复选中同一目标"两个问题。
2. 重建时保留序号。让重建端点接受管理端已知的序号作为下限，或按目标逐个重建并沿用基线序号，避免重建后必然回滚；同时把 `incomplete` 也纳入按 id 重建的范围。
3. 补一个单目标位点重置能力。至少给出显式的运维命令，让回滚与损坏状态有受控的人工出口，而不是要求改库。
4. 恢复候选改为"从新到旧遍历并复验"，取第一份通过校验的备份，而不是只试最新一份。
5. 本地状态入账。同步状态增加本地有效性字段，`sync-state` 与后端视图同时展示本地缺失与摘要不一致，让"本地丢了"在常规查询里可见。
6. 降低周期复核对齐成本。启动时复核之外的轮次按轮转抽样复核，或按"距上次复核时间"逐目标排队，把全量导出的开销摊到多个周期。
7. 恢复路径复用导出侧的组件构造，写入文件归档后显式推进归档组件，让恢复后的账本与导出结果自洽。
8. 为损坏场景补一个受控的归档动作（重命名目标或移动到隔离 id），使"目标已存在"不再是不可恢复的硬冲突。

## 十、待确认事项

* 检查点组件的摘要一致性没有单测覆盖。现有对账正常路径的用例使用不含检查点的执行（`bundle.rs:386` 的夹具只保存 agent 记录），若检查点索引元数据与 `metadata_document` 的字段集合存在差异，含检查点执行的漂移检测会持续误报。建议补一个含检查点与文件归档的恢复后再对账用例。
* 归档组件缺失导致的账本偏差，需要一次真实的两端对账才能确认严重程度；静态阅读只能确认组件没有被推进。
* 若远端在恢复后发生一次真实写入，序号会变成"恢复序号加一"且摘要变化，第五节提到的死循环会被自然打破。因此上一节的判断成立范围为"恢复后远端无新写入"，这恰是灾备场景的常态。
