# Markdown 解析节流与增量解析

## 现状

流式解析的核心类型位于 `crates/app/cli/wf-tui/src/markdown.rs`。每次收到文本增量都会触发一次边界计算，边界计算会对整个累积缓冲区做一次解析器遍历以定位最后一个顶层块起点。缓冲区上限为六十四 KiB，一条长消息会触发与长度成正比的重复解析，总体呈平方级增长。

该解析器同时承担引用定义回退、表格滞留、换行门限三类正确性保护，语义已经过大量等价性测试沉淀。问题不在语义，而在触发时机：累积与解析耦合在同一次调用中，调用频率等于增量到达频率，帧准备阶段无法合并多次增量。

交互控制器在 `crates/app/cli/wf-tui/src/interactive.rs` 的增量处理分支中直接消费每一次解析结果，产出已提交与流式两段文本并写入待沉淀队列与流式行。突发到达时单帧可能触发多次解析，且解析结果立即进入排版，加剧布局抖动。

对照 jcode，差距在于缺少解析节流与已提交前缀复用。jcode 把重量级解析放在准备阶段并缓存，流式文本先经过缓速再进入解析，解析频率与帧率对齐而非与增量到达频率对齐。

## 修改目标

把解析频率从按增量触发改为按帧触发，并为后续增量化保留结构。对外交付的已提交与流式语义保持不变，最终兜底渲染路径保持不变。

## 方案

第一步只做节流，不改变解析语义。把累积与解析拆成两个阶段。增量到达时只追加缓冲区并标记为脏，不做任何解析。帧准备阶段检查脏标记与距离上次解析的时间间隔，只有超过间隔才执行一次解析并产出帧。间隔取一帧到两帧的数量级，可配置，默认对齐常见帧率。

为支持节流，流式类型需要新增脏标记、上次解析时刻、可注入的时钟来源。时钟来源与后续可注入时钟方案共用，避免引入第二套时间机制。帧准备阶段是唯一的解析触发点，交互控制器的增量分支只做累积，消费解析结果的位置后移到准备阶段。

第二步在节流稳定后做增量化。维护已确认闭合的安全前缀及其解析结果缓存，只对安全前缀之后的尾部重新解析。安全前缀的定义沿用现有语义：被空行确认闭合的顶层块之前视为不可变。引用定义、表格未闭合、围栏未闭合三类场景退化为全量解析，沿用现有滞留规则，不追求这些分支的增量收益。

已提交与流式的对外语义保持不变。最终兜底方法继续作为全量正确性后盾，任何增量路径的输出都必须与全量渲染一致。现有随机分块等价性测试直接复用，作为回归护栏。

样式渲染侧的两个渲染函数存在大量重复逻辑，节流落地时不顺手重构，只保证它们消费的源文本来自同一节流后的可见前缀。重复逻辑的合并另行安排，避免与性能改动耦合。

## 与现有模块的衔接

增量分支的沉淀逻辑保持不变，只是触发时机从到达时改为帧准备时。待沉淀队列、滚动覆盖位、流式行的更新逻辑不变。超限截断路径保持同步语义，截断时直接产出结果而不经过节流。

## 验收

现有等价性测试全部通过，包括段落、列表、表格滞留、围栏代码、引用链接、混合文档等场景。每帧解析字节数从平方级降为线性，可通过帧度量中断言。固定增量序列下最终文本与节流前完全一致。

## 风险与回退

主要风险是节流导致流式可见性延迟。缓解方式是间隔上限取小值，并保证最终完成时立即刷新，不依赖节流间隔。其次是增量化分支的正确性风险，缓解方式是仅对安全前缀增量、可疑结构退化为全量。若出现不一致，回退到节流但不增量的形态，仍保留大部分收益。
