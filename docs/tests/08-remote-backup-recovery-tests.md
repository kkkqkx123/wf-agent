# 08 远端备份与恢复链路测试

> 范围：跨两个服务端实例的备份、检测与恢复链路，含新增的两节点集成测试与端到端脚本
> 与既有分层的关系：本篇只覆盖管理端与执行端分离后的链路，不重复单端命令面的用例清单

## 为什么需要新的测试层

既有单元测试覆盖的是纯逻辑：修订决策、摘要计算、响应解码、状态行写入。它们无法回答链路是否成立，因为恢复闭环的每一个断点都跨进程：管理端发起的请求、执行端的路由装配、目录作用域的匹配、状态机在下一轮的判定，以及备份文件在磁盘上的真实字节。

既有端到端脚本只启动一个服务端，管理端与执行端同体。备份链路的输入来自另一个节点，恢复写入也落在另一个节点，单节点线束结构上无法表达。因此这条链路需要两层新增验证：进程内双节点的集成测试，以及真实二进制的命令行端到端脚本。

## 三层分工

| 层 | 载体 | 覆盖内容 | 判定依据 |
|---|---|---|---|
| 单元 | 各 crate 的 `#[cfg(test)]` | 修订决策与摘要、响应解码、事务内修订写入、归档替换 | 函数返回值与存储状态 |
| 集成 | `crates/app/wf-server/tests/backup_recovery_nodes.rs` | 两个真实服务端之间的完整链路 | 对外状态行、导出摘要、恢复计划 |
| 端到端 | `e2e/run-remote-backup.sh` | 真实二进制与命令行的编排路径 | 退出码与输出包络字段 |

集成层是主证据：它同时约束管理端的调度、执行端的写路径与服务端契约；端到端层只补命令行到服务端的编排与参数透传。

## 双节点夹具

夹具在同一个临时目录下建立三个位置：执行节点的工作目录、管理节点的工作目录、备份根目录。执行节点的数据直接写入内存存储，因为正常产生执行记录需要完整引擎运行；除此之外，两个节点之间的每一次交互都是真实 HTTP。

| 组件 | 配置 | 作用 |
|---|---|---|
| 执行节点 | 内存存储、临时端口、恢复路由开启 | 提供快照数据与恢复写入目标 |
| 管理节点 | 后端域开启、备份根指向临时目录、探测与备份周期各一秒、周期全量复核关闭 | 调度备份、检测异常、编排恢复 |
| 注册条目 | 隧道端口即执行节点真实端口、备份目录与执行记录目录一致 | 让管理端直连，且目录作用域匹配 |

周期全量复核在测试中刻意关闭：它会在复核时自动重建丢失的修订行，测试就失去了观察中间状态的机会。真实部署保留默认周期，两者的差别只影响观察窗口，不影响判定。

备份周期压到一秒是必要的：丢失与损坏只能由备份轮次发现，手动触发备份不做库存比对。等待一律用轮询加超时上限，不依赖固定睡眠。

## 集成用例与判定

| 用例 | 构造 | 判定 |
|---|---|---|
| 远端丢失后恢复 | 删除执行记录与修订行 | 状态先转 `remote_missing`；恢复计划动作为 `create`；远端导出摘要回到备份摘要；状态随后稳定在 `ok` 且失败计数归零 |
| 目标一致时幂等 | 不做破坏，直接恢复 | 预演与应用都报 `noop`；序号不变；状态保持 `ok` |
| 目标不一致时必须显式覆盖 | 远端记录推进一次，产生新摘要 | 不带覆盖标志被拒且远端内容不变；带覆盖标志报 `replace`，摘要回到快照 |
| 修订表整体丢失后重建 | 清空执行节点的修订表 | 状态先转 `needs_rebuild`；按已知序号重建后序号等于基线而非一；状态回到 `ok`，摘要不变 |
| 跨目录不覆盖 | 用另一个目录作用域发起恢复 | 请求被拒；原目录的目标内容不变 |
| 本地快照损坏后重拉 | 覆盖管理端备份文件为无效内容 | 索引出现新快照；状态回到 `ok`，本地读取状态为 `ok` |

第二条和第三条合起来界定"幂等 + 显式覆盖"的边界：一致时重复执行不写数据，不一致时必须由调用方表态。

第四条针对的是序号语义：整表丢失后若从一重建，本地基线必然更大，回滚判定会让目标永久停摆。用例直接断言重建结果等于已知基线。

## 端到端脚本

脚本自行启动两个节点：执行节点带恢复开关，管理节点带后端域与备份目录。固件沿用现有的脚本流程，先在执行节点上跑出一次真实执行，再用该执行 id 注册备份目标。注册请求直接走 HTTP，因为命令行注册不携带备份目标列表与备份作用域。

用例序列为：触发备份、复验快照、列出索引、观察状态、删除远端执行、等待丢失、批量恢复并应用、等待状态回落、确认执行体重新可见、复位位点并确认重新基线，共十一个判定点。判定以退出码与包络字段为准，状态类判定用轮询等待目标值；状态类判定失败时同时打印 `repair_status` 与 `error`，否则只能看到状态名而看不到原因。

脚本在无法产生执行时整层跳过并说明原因，与既有本地执行层的约定一致：跳过不等于通过。

## 过程中暴露的缺陷

新增测试第一次运行时全部失败在同一处，随后又暴露另外四处。每一处都不是测试写错，而是链路里真实存在的断点。前三处由集成层发现，后两处由端到端层发现：集成层用自己的请求构造响应，端到端层用的是真实节点返回的真实字节。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 对任何真实节点的备份都在解码阶段失败 | 解码把响应体当作 `{bundle: {...}}`，执行节点的同步端点返回的是快照本身 | 两种形态都接受：裸快照优先，包装字段兼容 |
| 2 | 丢失与整表丢失永远被判成内容损坏 | 轮次先要求库存行带修订号再判状态，而这两种异常恰好都不带修订号 | 先按状态分流，仅状态正常时才要求修订号 |
| 3 | 恢复被拒：`recovery bundle digest mismatch` | 摘要基于 `serde_json::Value` 序列化，工作区开启了 `preserve_order`，同一内容两次导出的键序不同，摘要就不同 | 摘要改为对键排序后的规范文本取值，与键序无关；补 `digest_ignores_object_key_order` 单测 |
| 4 | 删除已完成的执行后恢复仍报"执行仍在运行" | 存活判断只查注册表里有没有句柄，不看执行状态；删除后句柄仍在，终态被当成活跃 | 存活判断改为读状态，终态即视为不活跃 |
| 5 | 复位后偶尔停在 `remote_corrupt` | 轮次在开始时读状态、结束时写状态，复位落在两次之间就被这轮写回旧结论；失败路径还硬写 `repair_pending` | 写入口加守护：状态行已是复位标记且写入方未采纳新快照时，保留复位标记；诊断字段照常写入 |

第一条说明既有单测的覆盖盲区：解码用例自己构造了包装形态，恰好绕过了真实响应。第二条说明状态机的分支顺序需要由链路级用例约束，纯函数用例看不出来。第三条是链路层独有的：只有跨进程取真实字节才会遇到，纯函数用例里同一份内存数据始终序列化成同一个样子。第五条是时序竞态，只能由真机脚本按真实周期跑出来。

第五条的处理保留了诊断信息而不只是保留状态名：复位期间若某一轮失败，`error` 与失败计数照常记录，`repair_status` 仍是 `rebasing`。判定依据是"这次写入有没有带来复位没见过的快照"——带了就清除标记，没带就说明它写的是复位要逃离的那个位点。目标根本没有快照时不保留标记，否则一个永远拉不到快照的目标会一直躲在复位状态后面。

## 尚未覆盖

- 运行中的目标被拒绝：句柄判活已改为按状态判断并有端到端证据，但"目标确实在运行"这一分支仍需可注入的活跃执行注册表才能构造。
- 归档多余文件的清理：需要挂载文件检查点管理器并在快照外写入文件。
- 事务写入失败后的重放：需要可注入失败的存储后端。
- 周期全量复核的长期资源占用与并发下的时序抖动，目前只验证了关闭该周期后的稳定行为。

## 运行方式

集成层随 `cargo test -p wf-server --test backup_recovery_nodes` 运行，默认并行即可，用例之间不共享端口与目录。端到端层需要先同步构建产物，再单独执行脚本；它不进主门禁，避免让默认验证依赖脚本执行能力。

本机执行时需在 `cargo`、`rustfmt` 前设置 `RUSTUP_TOOLCHAIN=stable-x86_64-unknown-linux-gnu`：`rust-toolchain.toml` 列了三平台 target，rustup 会尝试下载未安装的两个并卡在下载阶段，表现为命令长时间无输出、零 CPU。

端到端脚本会残留服务端进程，重跑前用 `pkill -x wf-server` 清理；按进程名匹配而不是按路径，避免匹配到脚本自身。脚本每轮约二十秒，连续三次全绿可作为稳定性证据；单次通过不足以排除时序竞态，本轮的最后一处缺陷就是靠多次重跑才复现的。
