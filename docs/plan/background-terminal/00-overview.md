# 后台终端设计方案总览

> 目标：对比 `ref/opencode` 的后台终端能力，澄清当前项目后端、前端、命令行界面各自如何处理长耗时命令，给出一份可直接落地的后台终端设计。
>
> 基线：`ref/opencode` 主干（`dev` 分支附近）；`wf-agent` 当前主干。文件路径引用以阅读时为准，行号仅作定位辅助。

## 术语界定

本文严格区分三个易混概念：

- **后台任务**：一条已提交但不再阻塞当前交互的 agent 工作（含 shell 命令与子 agent），可稍后通过通知找回结果。
- **后台终端**：承载长耗时 shell 命令的会话载体，提供创建、轮询输出、等待、发输入、调尺寸、终止能力，可为管道或伪终端后端。
- **后台执行**：工作流级别的整图异步执行，与单条 shell 命令的后台化正交。

`opencode` 把前两者解耦实现（任务注册表与终端存储是两个模块），当前项目则把两者揉在 `wf-shell` 会话里，且缺少任务注册与通知闭环。这是本方案的核心差距。

## 核心结论摘要

| 决策点 | 结论 | 理由 |
|---|---|---|
| 是否引入任务注册表 | 是，在执行共享层新增轻量任务注册 | 当前只有会话池，没有跨工具调用的后台任务视图与通知闭环 |
| 输出存储形态 | 短输出走内存环形缓冲，长输出溢出到文件并支持游标分页 | `wf-shell` 现有 256KB 截尾丢历史，`opencode` 用文件加游标解决大输出翻页 |
| 是否新增伪终端类型 | 否，复用 `wf-shell` 现有管道与伪终端双后端 | 后端原语已齐，不新增依赖或新 crate |
| 传输形态 | 轮询为主，事件推送为辅，不新增双向终端套接字 | 现有事件订阅套接字是广播语义，硬塞双向流会污染协议；复用通知事件加轮询输出即可覆盖后台任务场景 |
| 前端形态 | 工具调用卡保持折叠尾部展示，新增后台任务聚合视图 | 与现有工具调用卡与执行流复用同一链路，不引入终端仿真器 |
| 命令行界面形态 | 流式渲染加后台提示，不做交互式终端接管 | 命令行界面当前是服务端事件流的渲染端，不直连本地进程 |

## 范围

范围内：

- 后台 shell 命令的生命周期、输出模型、通知闭环。
- 后端领域划分、传输协议、前端与命令行界面的展示策略。
- 与现有 `wf-shell`、`git` 终端、工作流后台执行的边界划分。

范围外：

- 会话持久伪终端守护进程（`opencode` 的常驻伪终端服务暂不引入）。
- 多用户在线状态与未读持久化（沿用现有通知语义）。
- 交互式全屏接管（如 `vim`、`git rebase -i` 的完整终端仿真）。
