# 上下文压缩插件扩展与分散度分析

本文回答三个问题：当前项目压缩如何支持插件扩展、参照项目的做法与差距、压缩逻辑是否过于分散以及如何收敛。
引用路径均为仓库相对路径，首次出现写全路径。设计讨论以自然语言为主，不贴完整代码。

## 1. 当前压缩管线的位置

压缩不是单个模块，而是一条跨层链路，各段职责如下：

* 预算与阈值推导：`crates/engine/wf-execution-shared/src/token_tracker.rs` 负责窗口到预算的折算，`crates/engine/wf-execution-shared/src/compaction.rs` 负责比例到绝对阈值的解析与策略名归一化。
* 块 bookkeeping 与纯规划：同上 `compaction.rs` 负责块同步、计划构造、重压与丢弃选择、建议校验；`crates/foundation/wf-types/src/message/` 负责视图分段与压缩状态结构定义。
* 决策与信号发射：`crates/engine/wf-agent/src/coordinator/iteration/compression.rs` 负责每轮结算后的判定、背压、审计事件发布、压缩前后检查点；强制安全网也在此。
* 执行：`crates/app/wf-runtime/src/trigger_listener/compression/` 负责摘要链的逐项执行、重试、超时、降级与完成事件聚合；摘要链模板在 `crates/engine/wf-resource/src/predefined/workflow/child/fold_summary.rs`。
* 写回：`crates/engine/wf-agent/src/conversation_compression.rs` 负责版本锚点比对后的视图切换与滞后结果丢弃。
* 配置装配：`crates/app/wf-runtime/src/bootstrap/trigger.rs` 负责策略名到 workflow 标识的解析与缺失回退，`crates/foundation/wf-types/src/config/limits.rs` 定义策略与预算配置。
* 可观测：`crates/infra/wf-metrics/src/collectors/compaction.rs` 与 `crates/app/debugger/src/dimensions/compression.rs` 分别负责指标与调试视图。

结论是逻辑分散在执行共享层、会话层、运行时监听层、资源层、类型层与可观测层，共七处以上直接触点。

## 2. 插件扩展机制

当前仅有两个压缩专用挂点，均面向命名策略。

### 2.1 规划建议

插件通过 `compaction-advisor` 贡献规划建议。契约定义在 `crates/foundation/wf-plugin-sdk/src/contributions.rs`，类型注册在 `crates/infra/wf-plugin/src/contributions/types.rs`，原生后端分发在 `crates/infra/wf-plugin/src/native/plugin.rs`，运行时桥接在 `crates/app/wf-runtime/src/plugin_bridge/advisors.rs`，引擎侧进程级注册表与调用点在 `crates/engine/wf-execution-shared/src/compaction.rs`。

语义为纯整形建议：引擎拥有阈值、版本锚点、写回与审计，插件只建议压哪些区间与删哪些小块。输入为决策快照，输出为条目与丢弃集合。引擎对输出做全量校验与钳制，未知块、越界下标、超配额均被丢弃或截断。缺失、失败或空建议一律回退内建规划。

### 2.2 执行链替换

命名策略的执行链即普通工作流资源。插件用工作流贡献注册一个与策略同名的模板，启动装配按策略名加减后缀解析主链与重压链，缺失主链回退内建并记录指标。链的终端失败语义由模板自带的触发子流程配置声明。

### 2.3 现有覆盖

已覆盖：新策略的分块规划建议、总结链整体替换、建议的合法性兜底、插件卸载时的注册表清理。

未覆盖：阈值与判定本身、预算推导、块同步、版本锚点与写回、检查点、交接、重试超时与降级、词元估算、工具蒸馏与文件去重。这些全部由引擎独占，插件无钩子。

## 3. 现有覆盖是否完整

不完整，缺口集中在五类。

第一，后端覆盖残缺。分发仅在原生后端实现，Lua 与 Wasm 明确不读取建议表，声明模型中也无对应字段。脚本与沙箱插件完全无法扩展压缩。

第二，只能替换、不能增强。内建策略绕过建议查询，插件想微调内建行为必须另起策略名并由运营方修改配置。清单中无压缩专用权限位，无优先级与覆盖语义，同名冲突直接失败。

第三，建议协议过窄。只能建议条目与丢弃，不能建议阈值、激进程度、尾部保留、新块创建、主题合并、重压次数、交接判定、提示风格与模型选择，也不能否决或强制一次压缩。单摘要策略与强制安全网路径根本不查询建议。

第四，执行链校验后置。工作流注册时只做通用资源校验，压缩所需的链形状与回落声明到启动或运行时才发现缺失，只能回退内建。

第五，可观测与干预面缺失。压缩信号走内部钩子同步分发加事件总线审计拷贝，用户触发器被明确禁止订阅作功能触发。插件事件处理器只能被动观察，无取消、无整体替换、无请求级改写。指标只有内建采集器，插件无法扩展。建议协议版本号有发送、无协商。

## 4. 参照项目 pi 的做法

pi 的压缩核心是纯函数加会话管理器的分工。纯规划与摘要生成在 `packages/coding-agent/src/core/compaction/`，输入输出均为显式数据结构，切点查找、上下文估算、摘要生成互相独立。会话编排在 `agent-session.ts`，负责触发、持久化与重试。

扩展模型是事件式整体替换。压缩前事件携带已算好的准备数据、分支条目、触发原因与取消信号，处理器可取消本次压缩，或返回完整的压缩结果从而跳过默认摘要。压缩后有成功与失败事件，扩展可感知来源是否来自其他扩展。另有编程触发接口与上下文用量查询，扩展示例展示了自定义阈值触发与换用廉价模型做摘要。

特点是简单策略友好：默认即单摘要加尾部保留，准备与执行分离，扩展替换成本低。代价是无分块规划概念，复杂策略需扩展自行实现。

## 5. 参照项目 opencode 的做法

opencode 的压缩核心是集中式服务。实现在 `packages/core/src/session/compaction.ts`，统一处理自动、手动与溢出三种触发，内置后台预计算、原生压缩与文本压缩两条执行路径、文本逐级降载、压缩比收缩重试与模板合规复核。

扩展模型是请求级钩子。会话钩子中的压缩钩子可读写系统提示、消息与生成选项，也可直接给出摘要结果从而跳过模型调用。请求管线上的模型与网络钩子同样适用于压缩请求，压缩请求带有类型标记以便与主循环区分。配置只有自动开关、保留量与触发余量三项。

特点是干预点在请求边界而非规划器内部，扩展易于改写提示与选项或短路结果，但不能替换阈值判定与切分算法。后台预计算与缓存复用是其独有的成本优化。

## 6. 当前项目是否需要改进

需要，但不宜照搬。当前项目的分块深压实是差异化能力，不应退化为单摘要。应补的是参照项目已验证的通用扩展形状。

建议按优先级排序：

* 增加压缩前取消与整体替换事件，携带准备数据与触发原因，允许扩展取消或返回完整压缩结果。此举直接对齐 pi 的核心能力，简单策略可绕过全部块 bookkeeping。
* 增加压缩请求级改写钩子，允许扩展在摘要链执行前调整提示与选项，或短路单项结果。此举对齐 opencode 的请求边界干预，且不破坏版本锚点。
* 增加压缩后成功与失败事件，供扩展做审计、索引与降级处理。
* 允许内建策略被增强而非只能被替换，例如保留内建规划、仅改写提示或后处理；或允许建议在单摘要与强制路径下同样生效。
* 打通 Lua 与 Wasm 的建议通道，或明确文档化原生专属并给出脚本侧的等效干预点。现状是静默不可用，最易造成误解。
* 给策略解析与执行链校验前移，提供压缩链的结构校验与启动前报错，而不是运行时回退。
* 补齐权限位、冲突策略与协议协商，避免同名冲突与版本漂移成为隐性故障。

## 7. 分散度判断与收敛方向

### 7.1 是否过于分散

是。同一业务概念分布在七处以上：纯规划、状态结构、决策发射、链执行、写回应用、启动装配、可观测。每处各自持有部分不变量，例如背压锚点在会话层与写回消费者各实现一次，策略名归一化在执行共享层与启动装配各做一次，阈值解析在预算跟踪与压缩规划之间分离。简单策略即使只想要单摘要，也要经过块同步、热估算、计划构造与多项埋点的全套路径，存在为重策略支付固定成本的问题。

### 7.2 其他模块是否应只提供埋点

方向正确，但表述需精确为三层分工，而非把业务逻辑全部搬入资源层。

资源层即 `wf-resource` 是声明式资源注册与渲染层，只应承载模板、提示变体、链形状与结构校验，不应承载执行编排与状态机。把判定、规划、背压与写回搬入资源层会造成层级倒置，因为执行共享层与代理层本就依赖资源层提供模板标识。

建议的分工：

* 决策发射侧只留埋点。会话与迭代协调器只负责采集用量、发布决策输入信号、执行引擎返回的指令，不再内嵌阈值比较与计划构造细节。
* 执行侧只留埋点。运行时监听器只负责按指令运行链、超时重试与事件发布，不再内嵌分块聚合与降级策略选择。
* 业务逻辑收敛到压缩内聚模块。阈值判定、块同步、计划构造、建议查询、执行编排、写回应用、交接判定应归属同一压缩能力边界，对外暴露精简的决策与执行端口。现有 `compaction.rs` 已承担纯规划部分，可作为收敛起点，但需把分散在协调器与管线中的编排逻辑一并纳入，而不是再新建一套替代模块。
* 资源层只承载可替换面。摘要链模板、提示变体、交接文档模板、链形状校验留在资源层，压缩模块通过标识引用它们。简单策略对应简单的模板与空规划，复杂策略对应分块模板与建议查询。

### 7.3 简单策略不应承担重埋点

这是收敛后必须满足的验收条件。埋点应按策略门控：块同步、热估算刷新、文件读取登记、工具蒸馏、计划指标等重埋点仅在分块策略下启用；单摘要策略只走估算、信号、执行、写回与基础指标。策略选择发生在决策之前，埋点开关由策略能力声明驱动，而非由各模块各自判断。如此才能做到引入简单策略时不引入多余埋点，移除重策略时不留孤儿埋点。

实施顺序建议为先定义压缩能力边界与端口，再把发射侧与执行侧的业务细节内聚，最后按策略能力对埋点加门控。过程中不新增替代模块，只改造原模块，避免出现版本式分裂。

## 8. 本次落地说明

两次改造均只改原模块，未新建模块，未保留双轨：

第一轮（最小闭环）：规划建议对全部策略生效，已注册的内建策略建议可增强内建规划，缺失、失败或非法建议仍回退内建；单摘要策略跳过每次追加的块同步，但阈值门控与热估算不变；建议通道的原生后端约束显式文档化。

第二轮（单系统收敛）：压缩信号点成为门控点，否决在接管前取消压缩，替换直接以历史单摘要形态发布完成事件并走原有版本锚点与写回；内建服务由火力内自动接管改为按名显式接管，测试替身随之迁移到同一路径；策略链在启动装配期做结构预检（缺失摘要链仍回退内建并记错，缺失重压链降为调试日志，缺失子流程配置则告警策略降级）；新增压缩权限位（声明式，与检索权限先例一致，可进权限黑名单）；建议协议做显式版本协商（声明版本不一致则告警回退，未声明保持兼容）。

验证情况：压缩后成功与失败事件确认已存在（触发器按事件标准名订阅），无需新代码；七处历史失败测试属同一根因（响亮失败改造后测试进程未安装压缩全局参数），已按既有单测先例补齐；工作流预处理有一处与压缩无关的既有失败，保持原样。

未落地项：请求级改写（需打通建议经管线到链输入再到模板提示的长链，超出本轮资源，替换已覆盖其表达力）、静态钩子定义在分发点的同步求值（分发仍只过动态观察者，触发器走异步路径不变）、插件侧钩子处理器桥接（注册入口存在但尚无调用方，门控端口已就绪）。
