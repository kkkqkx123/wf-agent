# 远端备份恢复闭环修复方案

## 0. 背景与范围

上一轮实现核对（`docs/analysis/remote-backup-recovery-review.md`）的结论是：备份产物与恢复通道本身成立，问题集中在状态机没有闭环。本轮只修状态机与可观测性，不改变备份产物形态，不改变远端只读定位，不引入新的存储后端。

两处必须修的断裂：

* 恢复成功后管理端没有采纳远端写入的新位点，下一轮把刚恢复的目标判成内容损坏，`recover` 反复选中又反复冲突。
* 修订表重建把序号重置为一，本地基线必然更大，判成回滚后没有任何出口。

范围之外：不做备份产物加密，不做异地副本，不做把损坏执行原地覆盖恢复（需要先有受控归档语义），不改备份文件格式版本。

## 1. 设计原则

* 账本必须描述内容。修订行的摘要要等于一次全量导出的结果，否则对账会持续误报。
* 位点必须跟随事实。远端写入新的序号后，管理端要么采纳，要么清掉重来，不能保留一个永远对不上的旧值。
* 异常必须有出口。任何停在异常状态的判定都要有受控的恢复动作，不能要求改库。
* 失败继续大声。校验不过不落盘、不推进、不裁剪的既有约定不变。
* 本地状态可见。同步状态同时描述远端位点与本地快照可读性，而不是只描述远端。

## 2. 恢复路径闭环

### 2.1 问题

恢复写入执行记录与检查点时会自动推进修订行，但文件归档的导入路径不推进组件，最后一步又用"恢复后的现状组件"重算摘要。两个后果：

* 不含文件归档的目标，恢复后摘要与备份摘要相同但序号加一，管理端看到"序号前进而摘要不变"，按既有规则判成内容损坏。
* 含文件归档的目标，账本摘要缺归档组件，与下一次全量导出的结果不同，对账把正确的数据判成摘要不一致。

同时管理端的同步状态只在远端失败、备份成功、备份失败三处写入，恢复路径完全不写，所以即使远端状态正确，本地仍停在旧位点。

### 2.2 改动

远端侧用备份自身的投影重建修订行，而不是用恢复后的现状组件：

* `RevisionStore::advance_after_restore` 改为接收组件集合，写入前统一排序，摘要由该集合投影得出，序号仍取"本地当前与备份序号较大者加一"以保持单调。
* `restore_bundle` 在预校验阶段就算出组件的规范形式，写入记录、检查点、归档后把它交给修订行，因此恢复后的摘要必然等于备份摘要，也等于后续全量导出的摘要。
* `RestorePlan` 增加远端序号与远端摘要两个字段，应用后回填真实序号，dry-run 时序号为零表示尚未确定。

管理端侧采纳远端写入的位点：

* 恢复成功后把返回的序号与摘要写进同步状态，修复状态置为正常，失败计数清零，备份 id 指向本次使用的快照。
* dry-run 不写，避免预演污染状态。

这样恢复动作变成一次正常的状态转移：远端序号为备份序号加一，本地位点同步更新为同一值，下一轮比对落到"序号相等且摘要相等"，不触发备份也不报损坏。

### 2.3 为什么序号仍然加一

若把序号直接设成备份序号，恢复后远端会出现"内容比位点新但序号没变"的中间态，与并发的备份轮竞争时容易产生歧义。加一保证单调，且由管理端同一次响应采纳，不存在中间窗口。

## 3. 重建序号与局部重建

### 3.1 问题

重建固定写序号一。整表丢失时所有目标从零开始，本地基线的序号通常更大，比对落到回滚分支。回滚既不在批量恢复的处理范围，也没有单目标重置入口，重启也无效，因为重建后表已非空，不再触发待重建判定。

单行缺失更尴尬：判定为不完整后映射成内容损坏，既不重建也不能自愈，反而要清空整表才能触发重建。

### 3.2 改动

* 重建接受调用方已知的序号作为下限，写入序号取该下限（不低于一），而不是加一。重建后远端内容未变，摘要等于备份摘要，比对落到"相等且摘要相等"，直接回到正常状态。
* 若重建期间远端内容确实变了，摘要会不同，比对落到"相等但摘要变化"，仍然报损坏，不会掩盖真实变化。
* 复核阶段对"修订行缺失"也做一次全量导出：能导出且摘要可算，说明内容健康，按该目标单独重建；导出失败才判为损坏。
* 重建端点改为请求体传目标列表，每个目标带自己的序号下限，取代原来的逗号分隔 id 查询参数。

管理端在复核时按"持久位点优先、最新备份兜底"取已知序号，与备份轮的基线算法保持同一来源，避免两处口径不一致。

### 3.3 状态自愈

一份健康但未到期的目标，此前只在备份成功时刷新状态，导致"待重建""待修复"等标记可能滞留到下一次真正备份。现在增加一条规则：比对结果是无变化且本地快照可读时，若状态不是正常，就写一次正常状态。这条规则同时覆盖重建完成、恢复完成与人工重置之后的滞留。

## 4. 位点重置出口

任何比对异常最终都要能回到可比较的状态。新增单目标重置：把该目标标记为重新基线，清空持久序号与摘要，并丢弃内存到期状态；下一轮忽略持久位点与本地快照序号，拉取一次新快照并采纳其位点，重新建立可比较的基线。

只清空持久位点是不够的：本地最新备份的索引行里同样记着旧序号，基线算法的兜底会把它取回来，于是又被判成同一次回滚。因此重置必须同时屏蔽两个来源，并让这个意图在失败重试中保持，直到一次成功备份采纳了新位点。

这个意图还要能活过一次写入竞态：备份轮次在开始时读状态、结束时写状态，复位若落在两次之间，这轮就会带着复位前的结论把标记写回旧状态；备份失败路径同样是硬写修复中状态。处理放在写入口统一判断——状态行已是重新基线、且本次写入没有带来复位没见过的快照（备份 id 未变）时，保留标记，其余字段照常写入。带了新快照就说明这是采纳，标记随之清除；目标根本没有快照时不保留，否则一个永远拉不到快照的目标会一直躲在标记后面。

不删备份文件，不删索引行，不动远端数据。后端不存在返回未找到，其余失败按服务端错误返回。

对应命令为远端子命令 `sync-reset`，参数为后端名与执行 id。

## 5. 本地状态入账

### 5.1 问题

同步状态只描述远端。本地最新一份快照缺失或损坏时，状态仍显示正常，只有启动对账的日志与指标能看出，运行期删除索引或文件也不会触发重新对账。用户要确认"本地哪些备份没了"只能逐个复验。

### 5.2 改动

同步状态增加本地读取状态一个字段，取值四种：

| 取值 | 含义 |
|---|---|
| `ok` | 最新一份快照读回校验通过 |
| `missing_file` | 索引有记录但文件不存在 |
| `digest_mismatch` | 文件存在但大小或摘要与索引不符 |
| `unverified` | 尚无本地快照，或读取过程本身失败 |

写入时机与远端位点同一次写：备份成功后直接记正常（刚校验过），远端失败与备份失败保留上一次的结论，健康跳过时刷新为当轮结论。

数据库原地扩展：建表语句带上该列，已有库通过列存在性检查后补列，默认值为未校验，旧行不需要回填。

## 6. 周期复核

### 6.1 问题

轮询只比对修订行里的摘要。远端内容被改动而修订行没有同步更新时，轮询仍报正常；能发现内容级损坏的全量导出复核只在启动时跑一次，检测窗口等于重启周期。

### 6.2 改动

新增复核周期配置，默认六小时，零表示只在启动跑一次。后台循环按周期执行本地仓位对账与远端全量复核，与启动那次使用同一套逻辑。

周期复核的开销与目标数乘以单份快照体积成正比，因此默认值取较大间隔，并在配置层允许显式关闭。

## 7. 恢复候选回退

恢复此前只取最新一份备份，校验失败即跳过，不尝试次新的一份。而最新一份恰是唯一可能事后损坏的那份，保留策略内明明还有可用快照。

现在按创建时间从新到旧遍历候选，逐个复验并做预演，取第一份两项都通过的快照执行；全部失败时把每份的失败原因聚合进跳过原因，便于判断是文件损坏、服务端复验失败还是远端冲突。

`--repairable` 的筛选同步改为遍历候选取第一份通过复验的。

## 9. 待拍板开放点

* 恢复后远端序号为备份序号加一，随后一次真实写入再加一，位点会跳过一号。连续性与可读性之间选了单调，若运维希望序号连续，需要在恢复时抑制记录写入的中间推进，代价是恢复路径要绕开存储层的统一推进逻辑。
* 本地状态只保留最近一次的结论，没有历史。若要回答"这份备份何时开始不可读"，需要独立的事件表。
* 周期复核默认六小时是折中值。大执行的全量导出成本高，若目标多、快照大，应下调目标数或改成分批轮转，本轮未做抽样。
* 损坏目标仍然无法原地恢复。恢复要求目标不存在，而损坏判定出现在目标存在时。受控归档（改成隔离 id 或移入回收站）涉及执行主键与全部引用，本轮不做，只提供位点重置作为可比较性出口。
* 多个管理进程共享同一备份目录时，位点仍是单写者假设，本方案不引入分布式锁。
* 检查点组件与存储元数据的摘要一致性仍缺测试覆盖，本轮未补含检查点与文件归档的恢复后对账用例。

新增或改写的用例：

* 恢复计划回填远端序号与摘要，应用后的值等于实际写入的修订行；dry-run 序号为零。
* 重建沿用调用方序号，下限为零时回落为一，重建摘要等于随后全量导出的摘要。
* 位点重置写入重新基线标记并清空序号与摘要；本地备份仍带旧序号时基线仍为空；失败重试保持该标记；从未有位点的目标返回未清除。
* 旧库缺少本地状态列时原地补列，旧行默认未校验且数据可读。
* 陈旧写入不抹掉重置标记：带旧快照的失败写入保留 `rebasing` 但照常记录错误与失败计数；带新快照的采纳清除标记并发布新位点；无快照目标不保留标记，失败可见。
* 两节点链路：远端丢失后新建式恢复并回到健康、一致目标为无操作、不一致目标需显式覆盖且覆盖后摘要收敛、整表丢失按已知序号重建、跨目录作用域不动目标、本地快照损坏后重拉。

环境说明：本机 stable 原为 1.93，不满足既有 `checkpoint-base` 使用的 `atomic_try_update`，已通过 rsproxy 镜像升级到 1.100.0。默认特性需要系统 luajit，已安装 `libluajit-5.1-dev` 后编译通过。`rust-toolchain.toml` 列出的三平台 target 未在沙箱安装，执行时显式使用本机 stable 通道：`cargo`/`rustfmt` 前设 `RUSTUP_TOOLCHAIN=stable-x86_64-unknown-linux-gnu`，否则 rustup 会去下载另外两个 target 并卡住。

未覆盖：含检查点与文件归档的恢复后再对账用例；运行中的目标被拒绝（需要可注入的活跃执行注册表）；归档多余文件清理；事务写入失败后的重放；周期复核在长时间运行下的资源占用。测试分层与逐条判定见 `docs/tests/08-remote-backup-recovery-tests.md`。
