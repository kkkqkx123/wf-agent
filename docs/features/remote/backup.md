# 远端执行数据的本地备份

## 一、职责边界

本地备份发生在管理端 `wf-server`，不是远端节点自备份，也不是 CLI 直接落盘。管理端通过服务端注册表找到远端主机，经本地回环隧道访问远端只读同步接口，把执行数据写到管理端本地目录。

远端节点使用 `remote-node` feature，显式不包含后端管理域；`remote-node` 与 `backends` 同时开启会在启动时拒绝，避免远端再管理一层远端。

## 二、启用条件与配置

备份链路需要同时满足：

* 管理端启用 `backends` 域：`backends.toml` 中 `enabled = true` 或 `WF_BACKEND_ENABLED`。
* 配置 `backup_dir` 或 `WF_BACKEND_BACKUP_DIR`。未配置时不启动备份循环；手动触发也会失败。
* 注册表条目配置 `backup_executions`，列出要备份的远端执行 id。条目还可覆盖 `backup_interval_secs`、`backup_retention_count`、`backup_retention_days`。

全局默认值：备份周期 1 小时，保留 10 份，保留 7 天。备份文件与索引默认放在 `backup_dir` 下，索引库名为 `backends.db`；也可用 `registry_path` 指定索引位置。

远端同步请求携带两个上下文：

* `x-api-key`：来自 `WF_BACKEND_REMOTE_API_KEY`，不写入配置文件。
* `x-wf-directory`：优先取条目的 `backup_directory`，回退到管理端全局 `backup_directory`，可由文件或 `WF_BACKEND_BACKUP_DIRECTORY` 配置。

## 三、备份内容

一次备份对应一个执行 id。远端专用端点 `GET /api/v1/remote-sync/executions/{id}/bundle` 在一次响应中返回：

* 执行包：统一历史视图、artifact 预览、审计摘要、bundle 版本与导出时间。
* 检查点链：该执行的检查点记录、转移分析和时间范围。

远端先做一次执行归属检查，再导出两部分数据，避免不同执行的数据混在同一响应里。拉取请求带 `checkpoint_limit` 查询参数，必须为大于零的整数，传 0 返回 400。检查点链的三个来源分别按下推到存储查询的尾部窗口读取，再按 `(timestamp, id)` 排序、去重并保留最近若干条；产物用 `truncated` 与 `total_count` 自证是否被裁剪，防止检查点很多的执行让每轮备份都放大内存。检查点链包含元数据和记录，不包含文件历史 blob 或数据库快照；历史时间线有上限，artifact 只保留预览。因此备份文件用于事后复查和人工复现，不是热恢复镜像。

## 四、触发与调度

计划备份由管理端后台循环驱动：

* 使用共享 interval，首次立即 tick 被跳过；到期状态以内存记录为缓存、以索引中该目标的最大创建时间为持久兜底，因此重启不会让所有目标同时到期。
* 迟到的 tick 直接跳过，不补积压。
* 到期状态按“后端名 + 执行 id”分别记录，一个执行成功不会掩盖另一个执行的状态。
* 到期时刻带有按目标名派生的确定性抖动，把同一轮任务摊开；连续失败的目标按指数退避拉长间隔并设上限，成功即清零。
* 到期任务按小批量并发执行；单次拉取超时、响应体字节上限、检查点条数上限都可配置，默认分别为 15 秒、64 MiB、500 条。响应体按流式分块读取，超限时立即中止，不先整体缓存。
* 成功才推进该执行的上次成功时间；失败保留原时间并在下一周期自然重试。
* 同一目标的定时备份与手动触发由进程内锁串行化，不会并发写盘与裁剪。
* 关闭服务时取消循环并回收隧道子进程。

手动触发通过 `POST /api/v1/system/backends/{name}/backups` 走同一条备份路径；CLI 对应 `wf remote backup-now NAME --execution ID`。后端不存在返回 404，其他失败按服务端执行错误返回。

## 五、同步请求与校验

管理端从条目的本地隧道地址发起 GET 请求。拉取成功后不会直接写盘，而是依次校验：

* HTTP 状态为成功；
* 响应信封 `success` 为真；
* `data` 存在；
* `bundle` 与 `checkpoints` 都是对象；
* 两者的 `execution_id` 都等于请求的执行 id。

任一条件不满足都按失败处理：不写文件、不写索引、不推进到期时间、不触发裁剪。这样鉴权失败、目录不匹配、执行不存在等错误信封不会被写成“空备份”。

## 六、落盘与索引

校验通过后，检查点链被合入 bundle 的 `checkpoints` 字段，然后写入 `backup_dir` 下按后端名分目录的 `{execution}-{created_ms}-{suffix}.json` 文件。

后端名、执行 id 和文件后缀都必须通过路径组件校验，拒绝路径分隔符和相对路径成分。

写入过程使用同目录临时文件：创建仅所有者可读写的临时文件，边写边算 SHA-256，同步文件内容，再改名为最终 JSON 并同步目录项。这样断电后不会留下"名字已发布、内容为空"的文件，摘要描述的确实是落盘字节。备份目录权限收紧到仅所有者可进入，包体序列化为紧凑 JSON 并带合成体版本字段。落盘前会规范化根目录与后端目录，真实目录不在根目录内则拒绝写入。索引写入失败会删除已发布文件，避免留下未登记的备份。索引记录包含 id、后端、执行、创建时间、字节数、SHA-256 和文件路径；路径相对 `backup_dir` 存储，换目录后记录跟随新根目录。旧版本索引里的绝对路径仍可读取。

索引路径解析统一基于规范化根目录和目标父目录：父目录或目标文件是符号链接时也会检查真实落点，`backup path escapes root` 一律拒绝校验、导出与裁剪，文件不会被误删。`backup_dir` 自身是符号链接时，规范化后的真实路径仍视为根内。父目录不存在时校验按 `missing_file` 处理，导出返回明确错误，裁剪记告警并跳过，不会通过创建目录让检查通过。

## 七、保留策略

每次成功备份后按“后端 + 执行”分别裁剪，数量上限和时间上限任一命中即删除：

* 该执行按创建时间倒序，超出数量上限的记录进入删除列表。
* 超过保留天数的记录进入删除列表。
* 先删索引行，再删文件；文件不存在视为已清理，文件删除失败只记告警。

裁剪配额按目标独立，某执行的备份不会挤掉另一个执行的历史。配置与条目中的数量上限和天数上限都必须大于零，零值在启动期或写入期被拒绝，避免删光包含刚写入那一份在内的全部备份。

这样不会出现索引指向已删文件的记录；文件删除失败最多留下孤儿文件，不影响列表可信度。

## 八、查询与手动拉取

管理端接口：

* `GET /api/v1/system/backends`：后端视图含 `last_backup_ms` 与 `backup_error`，顶层含 `backup_round_error`。
* `GET /api/v1/system/backups`：全部备份索引。
* `GET /api/v1/system/backends/{name}/backups`：单个后端的备份索引。

CLI：

* `wf remote backups [--backend NAME]` 展示 id、后端、执行、时间、大小、SHA-256 与路径。
* `wf remote backup-verify ID` 重新读取该文件并与索引记录比对，返回 `ok`、`missing_file` 或 `digest_mismatch`，同时给出记录的与实际的大小和摘要。
* `wf remote backup-export ID DEST` 从服务端导出经复验的备份包到本地文件，写入用唯一临时文件加原子改名；导出前服务端复验摘要与大小，客户端落盘前再次复算摘要，不符则拒绝写出。
* `wf remote backup-check FILE [--expect-sha256 SHA]` 离线检视本地备份包：检查结构、已知格式版本、执行 id 一致性、检查点对象，并可比对已知摘要；任一检查不通过都以失败退出。不访问服务端。
* `wf remote backup-relink [--apply]` 预览或执行存量绝对路径索引迁移；默认只预览，只有 `--apply` 才写库。执行后统计重写、保持、未解析与失败条数，并列出未解析和失败的索引 id。
* `wf remote status` 展示每行的 `last_backup_ms` 与 `backup_error`，并显示顶层的 `backup_round_error`，让整轮失败在终端可见。
* `wf remote pull ID DEST` 是独立的手动路径：从当前连接地址拉取通用 bundle 与检查点链并写本地文件，不写索引、不参与裁剪；任一步失败都直接报错。

对不存在的备份 id，校验接口返回 404；文件缺失与内容变更都返回 200 且 `verified` 为假，但通过 `status` 明确区分，不会被合并成一个布尔结论。

## 九、启动期对账

服务启动时对备份目录做一次对账：清理由中断写入留下的临时文件，统计"目录里有文件但索引没记录"与"索引有记录但文件缺失"的条数，并聚合为一条告警。对账不跟随符号链接目录或文件，只计数并告警，不删除、不追入；计数出现在同一条聚合告警中，但不扩展指标字段。其余对账只报告，不自动删除任何备份文件。对账结果中的孤儿文件数与缺失文件数同时写入备份指标。

更换 `backup_dir` 后，如需让存量绝对路径记录在新目录下可查询，可调用 `GET /api/v1/system/backups/relink` 预览，或 `POST /api/v1/system/backups/relink` 并在请求体中设置 `{"apply": true}` 执行。迁移只改索引 `path`，不移动文件、不改大小与摘要；根外绝对路径进入未解析清单，不做破坏性改写。命令重复执行是幂等的，已是相对路径的记录保持原样。这是显式一次性运维动作，不会在启动时自动执行，也没有常驻兼容层。

## 十、指标与检出

备份链路接入服务端指标，随 `/metrics` 导出：

* 成功与失败次数（失败带 `backend` 与受限的 `reason` 标签）、单次耗时、备份字节数直方图。
* 校验成功与失败次数（失败带 `missing_file` / `digest_mismatch` 标签）、裁剪数量。
* 最近一次对账发现的孤儿文件数与缺失文件数。

失败仍会记日志并写入轮级错误状态，指标只作为抓取与告警的数据源，不在进程内发送通知。备份指标只按后端名与受限的失败原因打标签，不按执行 id 展开，序列基数随后端数增长。

报告生成复用同一份指标：备份失败数、校验失败数、孤儿文件数和缺失文件数分别对应 `max_backup_failures`、`max_backup_verify_failures`、`max_backup_orphan_files`、`max_backup_missing_files` 阈值，位于全局指标配置的 `anomaly_thresholds` 下。默认失败数与校验失败数阈值为 10，孤儿与缺失为 0；超过阈值时分别产生中、中、低、高严重度的 `Anomaly`，备份成功/失败次数与字节数也进入报告趋势。`/metrics` 字段保持不变。

抓取侧可使用如下 Prometheus 表达式补告警，通知由抓取方负责，进程内不投递：

```promql
# 一小时内备份失败超过 10 次
increase(backup_failure_count[1h]) > 10
# 校验失败超过 10 次
increase(backup_verify_failure_count[1h]) > 10
# 当前存在孤儿或缺失文件
backup_orphan_count > 0 or backup_missing_count > 0
```

## 十一、恢复边界

当前产物是审计导出包，不是热恢复镜像。可用的读回路径是：先 `backup-verify` 确认文件与索引一致，再 `backup-export` 导出到本地，最后 `backup-check` 离线检视。不提供把备份包导入为可执行状态或重放执行的命令；这属于独立的只读导入设计，不在本链路内。导出接口同时返回服务端原始字节文本，客户端按原样落盘并复验摘要，因此本地文件的摘要与索引记录一致。

检查点条数上限已下推到三个来源的存储查询，仅作用于远端同步链的合成体字段；通用 `get_checkpoint_chain` 等全量读取路径不受影响。坏元数据行仍按既有逻辑跳过并告警，因此 `total_count` 是存储记录数，极少数情况下可能大于实际返回条数。
