# 工具调用路径权限与审批闭环加固

本文基于当前实现梳理工具调用审批链路的问题，并给出分阶段修改方案。本文只描述问题、边界与落地顺序，不贴完整实现代码。

## 一、现状问题清单

### 1. 审批后的参数改写未重新审批

审批请求携带原始参数，用户或模型审查器可以在响应中回传 `edited_parameters`。Agent、Workflow 与 API 三条执行路径都会直接用改写后的参数覆盖原参数执行，但覆盖后没有重新跑审批策略。批准一个低风险调用后改写路径或命令，可以绕过原本的敏感路径与命令门禁。

### 2. HTTP 审批端点信任调用方策略

`/api/v1/approvals/check` 与 `/api/v1/approvals/execute-tool` 从请求体读取 `ToolApprovalOptions`。调用方可自带文件权限规则、工具名通配与路径授权，从而把原本需要人工确认的调用变成自动批准。服务端鉴权默认关闭，未显式开启时风险更高。执行 scope 仍然限制最终落盘位置，但 scope 内的敏感文件仍可能被绕过审批。

### 3. 审批路径与执行路径归一化不一致

审批层只替换反斜杠与 `file://`，不折叠 `..`，也不做物理路径解析；执行层会做词法归一化和软链接逃逸检查。带 `..` 的敏感路径可能不匹配审批规则，却仍落在允许 scope 内并被写入。

### 4. 路径授权没有期限

`ttl_secs` 只在配置与序列化中存在，判定逻辑从不检查时间。内置 `scratch` 预设声明的一小时有效期实际上会延续到执行结束。

### 5. TUI 会话记忆过于粗放

TUI 的“本会话允许/拒绝”按工具名记忆。用户允许一次 `write_file` 后，该会话内任意路径的写文件调用都会被自动回答，和路径授权粒度不匹配。

### 6. 审批通知缺少应答闭环事件

请求侧发布 `ToolApprovalRequested` 并持久化交互记录，但应答侧只改记录状态并唤醒等待通道，`ToolApprovalResponded` / `ToolApprovalFailed` 事件没有发布点。前端只能依赖本地 UI 状态更新，事件流无法完整还原一次审批。

### 7. 会话中途授权入口与冻结的执行 scope 不匹配

实体已有 `apply_authorization_preset` / `revoke_authorization_preset`，但没有宿主入口，且运行时修改授权状态不会同步修改已经冻结在工具执行上下文里的 scope。本次不开放该入口：在 scope 能做到共享可变之前，只提供审批层的撤销能力会造成“提示有权限但落盘被拒”的假授权。该问题单独留在后续设计中处理。

## 二、修改阶段

### 阶段一：审批后的参数改写重新过闸

在审批协调器加入统一的“改写参数复核”入口：用改写后的参数构造等价审批请求，再次执行完整策略；只有复核结论为自动批准时才允许执行，其他结论一律拒绝并给出原因。Agent、Workflow、API 三条路径共用这个入口，避免三套判定漂移。

复核不再次询问人：一次交互只对应一组参数；参数变化后要求重新发起调用，防止通过响应参数逐步试探权限。

### 阶段二：服务端审批策略只取宿主配置

移除审批 HTTP 请求体中的策略字段。服务端统一从宿主解析后的审批配置取有效策略；配置缺失时使用引擎平衡默认策略。请求体只保留执行标识、工具标识、调用参数等事实数据。无交互宿主仍按既有规则在需要人工确认时快速失败。

### 阶段三：路径判定对齐与授权有效期

审批层复用执行层的词法归一化，路径 grant、权限规则、shell 抽取路径统一折叠 `..`；拒绝 NUL 与明显异常的过长路径。给每条已解析授权记录增加签发时间，判定与模型说明都过滤已过期授权；预设展开时写入签发时间。

### 阶段四：TUI 按调用指纹记忆

会话记忆从“工具名 → 决策”改为“工具名 + 操作 + 参数路径 → 决策”。无显式路径的工具退化为参数指纹，避免同一工具在不同目标上共享决定。清会话时仍清空全部记忆。

### 阶段五：审批应答事件闭环

在应答持久化成功后发布 `ToolApprovalResponded`，失败路径发布 `ToolApprovalFailed`。事件携带交互标识、执行标识与工具名，不携带响应正文，避免把审批内容二次扩散到事件订阅面。

## 三、不变量

- 审批放行永远不扩大执行 scope、检查点边界或沙箱策略。
- 人工回答只针对当次参数；参数变化必须重新过闸。
- 宿主配置是服务端审批策略的唯一来源，远端请求只能提供事实数据。
- 授权说明只反映当前有效授权；过期授权不得被提示或执行。
- 事件通知只描述状态变化，不承担权限判定职责。
