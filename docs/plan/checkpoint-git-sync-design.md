# 文件检查点与外部 Git 同步设计

## 1. 背景与问题

文件检查点子系统目前维护一个内部裸 Git 对象库，
以执行者编辑引用经评审引用与协作引用汇入主干引用的分层模型
管理文件历史，冲突合并采用标准三路合并。

实践中暴露出以下问题：

1. **能力重复**：内部合并模型在算法层面与 git 原生合并完全一致，
   重复的是引用编排、冲突登记、多父有向无环图管理等外围设施。
   二者不是竞争关系，而是同一算法、两个对象库。
2. **轻量场景下的纯开销**：当各支线修改点专注、无严重冲突时，
   内部的多跳合并总能干净通过。此场景下用户实际需要的
   只是把最终结果在真实项目仓库里提交一次，检查点的分层合并是多余环节。
3. **两个世界割裂**：检查点的主干引用与用户真实项目仓库的 git 历史互不可见，
   用户手工 git 操作产生的状态变化检查点侧无法感知和衔接，
   导致手动 git 加丢弃检查点成为事实上的逃生通道。

本设计的目标是：不推翻现有内部合并模型，增加与外部 git 的同步能力，
把内部检查点定位为过程级安全网，把真实 git 提交定位为交付级同步，
让轻量场景可以从检查点直接落到 git 提交，绕过不必要的环节。

### 1.1 适用前提

同步动作只在工作区位于 git 仓库内时可用。
非 git 工作区中导出与导入能力整体禁用，检查点按现有行为工作。
同步动作默认关闭或显式触发，不改变现有捕获、合并与审批语义。

## 2. 设计思路

### 2.1 定位划分：安全网 vs 交付

- **内部检查点库**：高频、细粒度、可回滚的执行过程记录。
  它的价值在于执行者隔离、审批策略、精确回滚，这些是 git 原生工作流
  不便提供的；保留它，不弱化。
- **外部 git 仓库**：用户协作与交付的最终事实源。
  检查点结果最终应能以普通 git 提交的形态进入它。

两个库保持松耦合，不做引用级双向绑定，通过显式同步动作衔接。

### 2.2 同步方向：以导出为主，导入为辅

- **导出（检查点到外部 git）为主路径**：覆盖支线专注、无严重冲突、
  直接在 git 里一起提交就足够了的主场景。
- **导入（外部 git 到检查点）为辅路径**：覆盖用户在外部手工提交后，
  检查点侧需要重新对齐的场景，复用现有人工引用与
  人工内容永不自动合并语义。

### 2.3 导出的最小语义

导出动作的最小语义是：将检查点主干引用当前树物化到真实工作区，
并生成一次外部 git 提交。要点：

- 内容来源是检查点主干引用的树快照，通过现有的工作区物化机制写入
  真实工作区。物化层已有按任意提交物化的通用原语，
  导出在其上增加主干专用的前置检查包装，不另起并行机制。
- 导出前做三项前置检查：主干无未解决冲突（以冲突标记引用状态为准，
  有则拒绝并提示走冲突解决）；工作区干净度检查；
  对账点有效性（无则视为首次导出，基线模式下以基线锚点为起点，
  非基线模式下全量物化）。
- 干净度检查定义为工作区相对主干树的扫描差异。
  任何差异都视为可能的用户工作，默认要求确认后才覆盖，
  禁止静默覆盖。确认方式为显式确认标记，由调用方收集。
- 导出幂等：主干树与工作区一致且外部头已对齐时直接返回成功，
  不产生空提交。
- 导出后记录对账信息，作为后续导入的合并基点依据。
- 冲突场景不特殊处理：若内部主干存在未解决冲突，
  导出直接拒绝，冲突解决仍走检查点自身的解决流程。

### 2.4 提交动作的执行方（已决策）

默认仅物化加生成建议提交信息，由用户或前端执行真正的提交，
保留用户对提交内容的最终控制。另提供显式的自动提交选项，
开启后由检查点侧调用外部 git 工具链完成提交。
自动提交是唯一允许向用户仓库写入的显式动作，
除此之外检查点侧不对用户仓库做任何写入。

### 2.5 对账点存储（已决策）

对账点存于检查点自身的元数据键值存储，
内容为内部主干提交、外部提交、外部仓库指纹与时间的对应关系，
随会话迁移。禁止写入外部仓库的任何位置，
不在外部留下备注、配置或附加引用，保持用户仓库不受污染。
多人协作场景下以检查点库持有者为准同步对账，不做跨克隆自动合并。

### 2.6 明确不做的：引用级双向绑定

不考虑让内部库直接使用真实仓库下的引用。原因：

- 真实仓库的改写历史会破坏内部有向无环图的祖先关系假设；
- 检查点库需要独立的回收与生命周期，与项目历史耦合后无法独立清理；
- 检查点的分层引用会污染用户的引用空间视图。

松耦合加显式同步牺牲一点便利，换取两个库各自的完整性，
这是本设计的核心取舍。

### 2.7 导入的最小语义

导入动作的最小语义是：把外部 git 的净变更作为一次人工提交捕获进检查点库。
要点：

- 以最近一次导出的对账点为合并基点，计算外部头相对它的净文件差异；
- 差异内容落到人工引用，标记为人工来源，永不自动合并，需显式批准；
- 外部历史与内部有向无环图无祖先关系时，按无基点的增加与覆盖语义
  捕获并明确提示，不做猜测性合并；
- 差异计算优先复用与基线设计共享的外部仓库只读打开方式，
  直接读取外部提交的树；外部仓库不可读时回落到现有的人工变更
  轮询捕获（工作区级扫描），不新增并行捕获通道；
- 若与内部主干有重叠修改，进入既有冲突流程。

### 2.8 导入的触发方式（已决策）

默认显式触发：手工变更轮询发现外部头越过对账点时仅提示，
由用户显式发起导入。另提供可选的自动捕获开关，
开启后轮询到越过即自动捕获为人工提交。
自动捕获与人工内容永不自动合并原则不冲突，
但会产生用户未预期的内部提交记录，故默认关闭。

## 3. 流程说明

### 3.1 导出流程（主场景）

执行中检查点照常捕获，合并按既有策略推进主干引用。
执行结束用户触发导出：先做前置检查，
含冲突状态、干净度与对账点有效性；再将主干树与工作区求差异，
仅写入有差异的文件；然后按选定方式提交，
默认只物化并给出建议提交信息，可选自动提交；
最后写入对账点。后续执行不受导出影响。

建议提交信息来源于本次导出涉及的执行者与时间范围摘要，
可借助现有的来源与时间线查询能力生成。

### 3.2 导入流程（辅场景）

用户在外部手工提交后，可经显式动作或轮询提示发起导入：
以对账点为合并基点计算外部头的净文件差异；
差异落到人工引用并推进对账点到当前外部头。
重叠修改进入既有冲突流程。

### 3.3 轻量场景的推荐组合

针对无严重冲突、各支线专注的典型场景：检查点照常捕获保留回滚能力，
执行结束后直接走导出流程，无需在检查点侧做额外的冲突人工介入。
也可选择更激进的只捕获不自动合并策略，平时完全用 git 提交交付，
仅在确实需要回滚时回到检查点侧操作。

### 3.4 并发与互斥

同一时刻只允许一个会话对同一工作区执行导出。
互斥以检查点库目录下的锁文件实现，非阻塞获取，
获取失败即返回忙错误，不排队等待。对账点的读写与锁在同一临界区内完成。

## 4. 与现状的关系

- 现有内部三路合并、冲突标记、冲突解决、审批策略全部保留，不修改语义；
- 新增能力仅为导出动作、导入捕获扩展、对账点存储三块；
- 现有工作区物化机制与人工变更捕获通道被复用，不新造并行机制；
- 逃生通道（完全关闭文件检查点、纯 git 工作流）继续可用，
  本设计提供两者之间的中间形态。

## 5. 与基线设计的协调

- 基线模式下内部主干的起点就是一个真实的外部提交，
  基线锚点即首个对账点的内部侧坐标，首次导出直接以锚点到主干
  当前树的差异生成提交；
- 两篇文档共用冻结规则修订、外部仓库只读打开方式
  与元数据键约定，实施顺序上基线先行，导入路径复用其只读能力；
- 基线解决存储效率，同步动作解决交付语义，配置相互正交。

## 6. 待决问题

  核心库只保证提供所需查询原语。
