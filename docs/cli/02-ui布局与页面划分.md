# wf-cli TUI 布局与页面划分设计

> 本设计遵循 `apps/cli-app/docs/spec/design-philosophy.md` 的全部原则：
> **列表驱动导航**（list → detail → modal）、**零装饰**（无边框无冗余头部）、**信息密度**（80x24 预算）、**可预期键位**（↑/↓、Enter、Esc/q、?、Ctrl+Q）。
> 渲染基于 **ratatui 0.30 标准 `Terminal`**（monolith 自带双缓冲 diff），主模式为**全屏 alt-screen**；
> 事件/帧调度参考 `docs/analysis/codex-tui.md` 与 `docs/analysis/atomcode-tui.md`。
>
> **模式决策（2026-08 修订）**：wf-cli 采用**全屏 alt-screen**，不采用 codex 的 inline 视口模式。
> 因此 codex 的 `custom_terminal.rs`（双缓冲 diff 定制）与 `insert_history.rs`（scroll region 写 normal screen scrollback）
> **不直接照搬**——前者由标准 Terminal 承担，后者与 alt-screen 语义冲突（详见「三、各屏幕布局」3.3 与 3.4 的滚动区说明）。

## 一、页面总览

### 1.1 屏幕（Screen）划分

| ID | 屏幕 | 模式 | 优先级 |
| :--- | :--- | :--- | :--- |
| `dashboard` | 主菜单 | Pattern A: Menu | P0 |
| `workflow` | 工作流列表 + 详情（两态 drill-down，资产视角） | Pattern B: List + Detail | P0 |
| `executions` | 执行跟踪（agent + workflow 统一列表 + 详情 follow） | Pattern B + C 混合 | P0 |
| `session` | 前台会话（agent / workflow 运行中专用） | Pattern C: Monitoring | P0 |
| `checkpoints` | 检查点列表 + 详情/加载 | Pattern B | P1 |
| `search` | 全文检索 + 结果列表 | Pattern B | P1 |
| `settings` | 配置项列表 + 值编辑 | Pattern B | P1 |

> **概念模型以 `wf-api`/`wf-types` 为准**：`ExecutionType::{Workflow, AgentLoop}` 同级统一，
> 不存在 Thread 概念（TS/RS 均已废除，TS cli-app 的 Threads 屏幕为过时残留）。
> 执行跟踪由单一 `executions` 屏承担；`session` 屏仅在 agent/workflow 会话处于前台时启用。

### 1.2 导航结构

```
dashboard
 ├─ Workflows ─────→ workflow ──(Enter 详情)──→ workflow-detail
 │                    └─(Enter run)──→ session（前台）
 ├─ Agent ──────────→ session（前台，agent 会话）
 ├─ Executions ─────→ executions ──(Enter 详情/follow)──→ execution-detail
 │                    └─(Enter 前台)──→ session
 ├─ Checkpoints ────→ checkpoints ──(Enter)──→ checkpoint-detail
 ├─ Search ─────────→ search
 └─ Settings ───────→ settings
```

> `executions` 列表按 `ExecutionType`（Workflow/AgentLoop）+ `ExecutionStatus` 过滤；
> `session` 屏类型无关——agent 执行与 workflow 前台执行共用同一套实时界面。

规则：

1. **单一屏幕栈**：`show_screen(id)` 激活新屏幕；`Esc/q` 返回上一屏幕（维护 `Vec<ScreenId>` 栈）。
2. **列表 → 详情是同一个 Screen 的两态**（如 workflow 屏幕内部切换 `ListMode ⇄ DetailMode`），避免屏幕栈膨胀。
3. **模态框是覆盖层**：不进入屏幕栈，独占键盘（捕获型模态框在 Streaming 也生效）。
4. **主模式为全屏 alt-screen**（对齐 design-philosophy Pattern A/B/C）；Session/execution-detail 长日志屏的滚动在 **ratatui 视口内完成**（P0），不做 scroll region 写终端 scrollback——该机制（codex `insert_history.rs`）面向 inline 模式，alt-screen 下语义冲突。长日志屏 P1 可选方案：全屏分页查看器（参考 codex `pager_overlay.rs` 的按 `desired_height` 手动裁剪渲染，退出时内容进 normal scrollback）。
5. 每屏只有 1 行状态栏（底部或顶部），无 header、无面板、无卡片。

### 1.3 屏幕契约

```rust
pub trait Screen {
    fn id(&self) -> ScreenId;
    fn handle_input(&mut self, ev: &InputEvent, ctx: &mut UiContext) -> Result<ScreenAction>;
    fn handle_event(&mut self, ev: &EngineEvent, ctx: &mut UiContext);  // 业务事件（agent/execution 流）
    fn draw(&mut self, ctx: &mut UiContext, frame: &mut Frame);          // 标准 ratatui Frame
    fn on_enter(&mut self, ctx: &mut UiContext);
    fn on_exit(&mut self, ctx: &mut UiContext);
}
```

> 与旧设计差异：`draw` 直接接收标准 `ratatui::Frame`（经 `Terminal::draw` 闭包传入），
> 不再引入自研 `Renderer` trait 与自定义双缓冲。

## 二、全局布局骨架

```
┌──────────────────────────────────────────────┐
│              (可选) 顶部状态行 = 1 行            │  ← Pattern C 专用
├──────────────────────────────────────────────┤
│                                              │
│              内容区 (fill)                    │  ← 屏幕自绘，占满可用空间
│                                              │
├──────────────────────────────────────────────┤
│  ↑/↓ navigate  Enter select  ? help  Esc back │  ← 底部状态行 = 1 行
└──────────────────────────────────────────────┘
```

- **80x24 空间预算**（对齐 design-philosophy）：

| 屏幕 | 状态行 | 内容 | 输入 | 合计 |
| :--- | :--- | :--- | :--- | :--- |
| Dashboard | 1 | 20 | 0 | 21 |
| List | 1 | 21 | 0 | 22 |
| Detail | 1 | 21 | 0 | 22 |
| Screen（前台会话） | 1（顶） | 19 | 2（输入区） | 22 |

- 底部状态行内容：左侧为当前上下文操作提示（按键帮助），右侧为可选项（如 `(3/20)` 滚动位置）。
- **状态行宽度回落**：窄终端下状态行退化为单行裁剪布局（参考 codex `footer.rs` 的单行回落），内容用 ANSI 感知宽度截断函数保证不溢出。

## 三、各屏幕布局

### 3.1 Dashboard（Pattern A: Menu）

```
→ Workflows
  Agent
  Executions
  Checkpoints
  Search
  Settings

↑/↓ navigate  Enter select  ? help  Ctrl+Q quit
```

- 单一 `SelectList` 填满内容区，`→` 标记选中项。
- 菜单项不超过 8 个（信息密度原则）。
- 无 Logo、无版本号、无系统指标（design-philosophy 明确禁止）。
- **Agent 与 Executions 的关系**：`Agent` 入口直接进入前台会话屏（立即新建/恢复 agent 会话）；
  `Executions` 是历史与后台执行的统一跟踪入口（agent loop 与 workflow 同级并列，按 `ExecutionType` 过滤）。

### 3.2 Workflow 屏幕（Pattern B: List + Detail）

**列表态：**

```
→ deploy-api        v2.3  12 nodes  running
  process-queue     v1.1  8 nodes   idle
  notify-slack      v3.0  4 nodes   idle

↑/↓ navigate  Enter detail  N new  R refresh  D delete  ? help
```

- 行内联关键字段：`name  version  nodes  status`（无侧栏）。
- 异步加载：进入屏幕即发起 `list` + 每项 `nodes` 统计，期间显示 `Loader`；失败显示错误行并可 `R` 重试。
- 自动选中第一项。

**详情态（Enter）：**

```
← Back to Workflows

Name:        deploy-api
Version:     2.3
Status:      running
Nodes:       12
Created:     2024-01-15
Description: Production deployment pipeline

[Enter] view graph  [E] edit  [D] delete  [Esc] back
```

- 键值对 `Text` 行，全屏宽度。
- 操作按键在状态行提示（`?` 打开 HelpModal 查看全部）。
- `D` 删除走 `ConfirmModal`；`E` 编辑启动 `$EDITOR`（经 `Tui::with_restored` 暂停 TUI 后运行，见 03 文档「二、渲染层」）；`Enter` 查看图 → 图详情页（graph 行高亮关键节点，P1）。

### 3.3 Session 前台会话屏（Pattern C: Monitoring，类型无关）

> 仅当 agent 或 workflow 会话处于前台运行时启用；类型无关——底层统一为 `ExecutionIdentity { type, id }`。

**Agent 会话：**

```
▶ RUNNING  agent-abc123  msgs:42  iter:3

[12:00:01] ●  Analyzing your request...
[12:00:02] ▲  Calling search(query="...")
[12:00:03] ✓  search → 3 results (120ms)
[12:00:04] ▲  Calling read_file(path="...")
[12:00:05] ✓  read_file → 1.2KB (45ms)
[12:00:06] ●  Found the file. Processing...

> Type your message...

↑/↓ scroll history  Esc normal mode  Ctrl+C cancel
```

**Workflow 前台执行：**

```
▶ RUNNING  exec-7f3a  workflow:deploy-api  12/34 nodes
[12:10:01] node: build ─ started
[12:10:03] ✓ node: build ─ completed (2.1s)
[12:10:05] ▲ tool: run_tests ─ calling
[12:10:06] ✓ tool: run_tests ─ 24 passed (3.8s)

P pause  R resume  C cancel  Esc back to executions
```

- **状态符号语义**（集中定义于主题模块，替代 emoji，避免字体差异）：`●` 助手消息、`▲` 工具调用中、`✓` 成功、`✗` 失败、`▶` 运行中、`⏸` 暂停/审批等待、`○` 就绪。低色终端降级为纯文本标记。
- **顶部状态行（1 行）**：`{icon} {PHASE} {exec_id} {type} {progress}` — 状态行不是面板；进度经 `wf-api::analysis::progress::ProgressTracker` 获取。
- **日志区**：源文本环形缓冲（100 条**源消息**，按当前宽度 `display_lines(width)` 渲染；可见 19 行），滚动查看；工具调用与迭代进度内联在日志中，不单独分区（design-philosophy：no separate panels）。
  - **滚动在 ratatui 视口内完成**（`Paragraph::scroll`），不做 scroll region 写终端 scrollback（理由见 1.2 规则 4）。
- **底部输入区（≤2 行）**：agent 会话有输入（P0 为单行输入 + 状态提示行；P1 引入多行 TextArea 组件后支持 ≤6 行）；workflow 前台执行无输入，仅操作提示行。
- **阶段感知输入**（对齐 TS 版 PhaseManager 与 atomcode-tui UiPhase，agent 会话有效）：

| 阶段 | 状态行 icon | 输入行为 |
| :--- | :--- | :--- |
| `Idle` | `○` | 直接输入，Enter 提交 |
| `Streaming` | `▶`（spinner 动画） | type-ahead 缓冲；Ctrl+C 取消 turn |
| `Approval` | `⏸` | 键盘交给工具审批模态框；Ctrl+O 跳过 |
| `Normal`（vim 模式，P1 可选） | `--NORMAL--` | j/k 滚动、g/G 首尾、Esc 退出 |

### 3.4 Executions 执行跟踪屏（Pattern B + C，统一 agent/workflow）

**列表态（P0）：**

```
→ ▶  agent-loop  exec-9f21  agent-abc123  iter:7   RUNNING
  ●  workflow    exec-7f3a  deploy-api    12/34    RUNNING
  ✓  workflow    exec-6d2b  deploy-api    34/34    COMPLETED
  ✗  agent-loop  exec-5c10  process-queue          FAILED

↑/↓ navigate  T toggle type  S filter status  Enter detail  ? help
```

- 列表行：`status-icon  ExecutionType  exec-id  所属 agent/workflow  progress  ExecutionStatus`。
- 过滤：`T` 切换类型（Workflow / AgentLoop / All），`S` 按 `ExecutionStatus`（Created/Running/Paused/Stopped/Completed/Failed/Cancelled）。
- 数据源：`wf-api::query`（QueryBuilder 过滤/排序/分页）+ `AgentLoopRegistry` 摘要；实时状态经执行事件流刷新。

**详情态（Enter → execution-detail，P1）：**

```
← Back to Executions

Type:        workflow
Exec ID:     exec-7f3a
Workflow:    deploy-api
Status:      running
Started:     2024-01-15 12:10:00
Duration:    38s
Progress:    12/34 nodes (35%)

[12:10:01] node: build ─ started
[12:10:03] ✓ node: build ─ completed (2.1s)

[F] follow live  [P] pause  [R] resume  [C] cancel  [Enter] foreground  [Esc] back
```

- 详情自动订阅事件流实时追加日志（Pattern C 日志区，滚动同 3.3）；`[F]` 切换 live 跟随。
- `[Enter] foreground`：将本次执行提升为 `session` 屏（前台交互）。
- 执行树（`ExecutionHierarchy` 父子/根/分叉）P1 折叠为 drill-down：详情内 `[H] hierarchy`。

### 3.5 Checkpoints / Search / Settings（统一 Pattern B）

| 屏幕 | 列表行内容 | 详情态内容 |
| :--- | :--- | :--- |
| `checkpoints` | `name  created  size` | 元数据 + `[L] load` |
| `search` | 顶部查询输入（1 行）+ 结果列表 | 结果详情（文件/节点/记录） |
| `settings` | 配置键列表 | 值 + `[E] edit`（`$EDITOR` + `with_restored`，校验后写回） |

## 四、键位约定（全局统一）

### 4.1 上下文与回退结构（P0 实现）

键位解析采用 **context → global 回退**的数据结构（参考 codex `keymap.rs`），六种上下文
`global | list | detail | chat | input | modal`，优先级从高到低：**modal 覆盖一切 > 当前屏幕上下文 > global 默认**。
P0 先用内置默认键位表实现该结构，P1 再开放 `keybindings.toml` 覆盖（热重载）。

**禁止**在各屏幕 `handle_input` 中散落裸 `match key` 分支——统一查 `Keymap`，保证上下文回退与可重映射性。

### 4.2 默认键位表

| 键 | 行为 | 生效上下文 |
| :--- | :--- | :--- |
| `↑/↓` 或 `j/k` | 导航列表 | list / detail / chat（滚动） |
| `Enter` | 选择 / drill-down / 提交 | 全部 |
| `Esc` | 返回上一级 / 关闭模态框 / 清空输入 / 退出输入态 | 全部 |
| `q` | 返回上一级 | **仅 list / detail / modal，chat / input 中禁用**（输入态 q 是字符） |
| `?` | HelpModal（列出当前屏幕全部按键） | 全部（input 内经 `Ctrl+?`） |
| `Ctrl+Q` | 退出（有未保存内容时 ConfirmModal） | 全部 |
| `Ctrl+L` | 重绘 | 全部 |
| `/` | 打开命令 palette（输入框内） | chat / input |
| `R/r` | 刷新当前列表 | list |
| `D` | 删除（ConfirmModal 确认） | list / detail |
| `N` | 新建（占位，P1） | list |

- 模态框打开时键盘全归模态框（捕获型模态框无视 phase）。
- `Ctrl+C` 全局：任何状态优先，模态框不可拦截（Streaming 取消 turn，Idle 提示退出）。

## 五、页面切换与过渡

1. **切换流程**：`screen.on_exit()`（清 transient 行）→ 清空内容区 → `screen.on_enter()`（发起异步加载）→ 全屏重绘。
2. **无动画**：零装饰原则，直接替换，不做滑动/淡入淡出（spinner/loader 帧动画除外，经 FrameRequester 调度）。
3. **resize 处理**：
   - 合并连续 resize 事件，仅保留最终尺寸。
   - **宽度变化后内容按新宽度重排（reflow）**：日志区/详情区等含多行 wrap 的内容，因 `HistoryLine` 等持有**源文本**，resize 后按新宽度重新 `display_lines(width)` 渲染（不依赖宽度缓存）。这是 P0 必做项——只"整体重排"而不重算换行会导致 wrap 错乱。
   - 不清屏（保留日志区）；75ms debounce（参考 codex `transcript_reflow`）。
4. **模态框位置**：居中（`Layout` 分区计算），宽度按类型固定（Confirm 60 / Password 50 / Picker 70 / FileViewer 80%）。
5. **帧调度**：所有重绘经 FrameRequester 合并（120FPS 限帧），业务事件（agent/execution 流）即时触发绘制。

## 六、80x24 最小可用性检查

- 所有屏幕状态行固定 1 行；内容区 ≥ 19 行；输入区 ≤ 2 行。
- 列表行一律单行（超宽截断 + `…`），禁止折行导致的行数抖动。
- 状态行内容用截断函数（ANSI 感知宽度）保证不溢出。
- 窄终端（< 80 列）：状态行回落单行布局；内容列裁剪优先保左侧字段。

## 七、渲染回归测试（开发要求）

- 所有屏幕/组件的渲染变更必须附带 **insta snapshot 测试**（对齐 Codex AGENTS.md 的 UI 快照要求），
  便于评审 UI 影响并防止后续重构引入视觉回归。
- 快照按 80x24 与窄宽度两种尺寸各生成一组。
