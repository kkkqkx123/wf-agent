# 05 现状复核与可借鉴差异

> 背景：`01`–`04` 是拆分前针对单体 `wf-tui` 的优化设计。此后 TUI 已拆为 `crates/app/tui/*` 多个 crate，且文档中多数设计点已经落地。本文重新按"当前代码"复核渲染实现，与 `ref/jcode` 逐项对照，给出仍然存在的差异与可借鉴项。
>
> 复核基线：`crates/app/tui/{tui-terminal,tui-style,tui-markdown,tui-core,tui-components,tui-render,tui-debug,tui-clock}` 与外壳 `crates/app/cli/wf-tui`；参照 `ref/jcode/crates/{jcode-render-core,jcode-tui*,jcode-terminal-image,jcode-tui-style,jcode-tui-anim,jcode-app-core}`。

## 结论速览

1. 文档 `01`–`04` 提出的四层能力（增量准备缓存、重绘分级、流式缓速、可注入时钟与性能分级）在当前代码中已经实现，且部分实现（确定性测试时钟、Markdown 增量尾部解析、无头等价性回归）达到或超过 jcode。
2. 仍存在三类实质差异：**帧呈现/局部重绘的正确性**、**内容表现力（高亮、数学、图表、图像）**、**主题与观测体系（感知配色、闪烁/键到绘制延迟等度量）**。
3. 其中第一类是缺陷而非增强：当前"仅动画重绘"路径依赖 ratatui 会保留上一帧缓冲，而 ratatui 0.30 每帧会重置当前缓冲（已用最小实验确认），该路径会把整屏清空。jcode 自持上一帧缓冲并做"种子 + 局部覆盖"，是可直接借鉴的正确做法。
4. 内容表现力方面，本项目的 Markdown 方言、语法高亮、数学公式、图表与终端图像均缺位或仅有占位；这些是 jcode 相对成熟、可分层借鉴的部分。
5. 主题方面，jcode 具备 OKLab 感知配色评估与生成、"和谐度"打分、色盲安全校验，以及"逐帧缓冲级调色板重映射"以覆盖散落的字面色；本项目已有缓冲级明暗适配与角色化调色板，但调色板重映射目前是空实现。

## 一、渲染管线对比

### 1.1 帧调度与重绘分级

| 能力 | 本项目 | jcode |
| --- | --- | --- |
| 帧率限制 | `tui-core/framer.rs`（合并请求 + 9ms 速率地板） | `redraw_schedule.rs`（按策略/状态推导周期 + `MissedTickBehavior::Skip`） |
| 重绘分级 | `RedrawScope{None,AnimationOnly,BottomOnly,Full}` + `decide_scope` 纯函数 | `needs_redraw` 单点，三条呈现路径：整帧 / 动画矩形 / 单格 |
| 空闲退避 | `REDRAW_ACTIVE/IDLE/PASSIVE/DEEP_IDLE`（100/250/1000/5000ms，30s 后深空闲） | `REDRAW_IDLE=250ms / DEEP_IDLE=5000ms / PASSIVE_LIVENESS=1000ms / DEEP_IDLE_AFTER=30s` |
| 可注入时钟 | 有（`tui-clock`，测试可推进） | 无（全部 `Instant::now`；回放用时间覆盖） |
| 性能分级 | `perf.rs`（Full/Reduced/Minimal + 终端/SSH/WSL 判定） | `jcode-app-core/perf.rs`（更细，含 fragile glyph cache、WSL/WindowsTerminal 分支） |

小结：调度与分级两侧思路一致，本项目在"可注入时钟"和"纯粹可测的判定函数"上更干净；jcode 在"按状态推导周期"上更细（例如流式追赶、深空闲休眠、远程未聚焦合并节流）。可借鉴的是把退避与"实时活动原因"显式化（jcode 的 `live_activity_redraw_reason` 可直接用于调试）。

### 1.2 帧呈现与局部重绘（关键差异 + 缺陷）

- jcode：渲染器自持 `last_frame: Buffer`。整帧走 `terminal.draw`；"仅动画/单格"帧以 `last_frame` 为种子只覆盖目标矩形，再 `BeginSynchronizedUpdate` → `flush` → `SavePosition/RestorePosition` → `swap_buffers` 提交。并用"硬清屏 / 软重绘哨兵"两种失效模式区分真实脱同步与滚动重绘，避免中间清屏导致图像占位闪烁。
- 本项目：应用层不持帧缓冲，依赖 ratatui `Terminal` 自带的前后缓冲 diff；`AnimationOnly` 只写"流式指示格 + 状态栏 spinner 格"两格（`wf-tui/src/interactive/render.rs:420`）。
- **缺陷**：ratatui 0.30 的 `Terminal::draw` 在每次绘制结束后会重置即将复用的缓冲（`ratatui-core` `swap_buffers`），官方文档也要求回调"完整渲染整帧"。因此只写两格会让其余单元格变成空格并被 diff 写出——即清屏。已通过最小实验确认：先画整行再只画一格，结果整行只剩那一格。
- 触发面：空闲时 `anim_tick` 仍随时间变化，`decide_scope` 会持续给出 `AnimationOnly`；`anim_rows` 为空（无流式行、非忙）时 `draw_anim_cells_only` 直接返回，等于提交全空帧。忙而无流式文本时同样只写一格。
- 对照 `BottomOnly`：它重绘整个可见 scrollback + footer + input，恰好覆盖会话区，因此不会清屏；但会话区以外的 notice/diagram 由外壳无条件重绘，属于"部分范围恰好被覆盖"的巧合，不是设计保证。

可借鉴：采用 jcode 的"自持上一帧缓冲 + 种子 + 局部覆盖 + 显式 present"结构；在补齐之前，`AnimationOnly` 应退化为 `Full`（或直接移除该档）以避免清屏。

### 1.3 准备缓存

| 维度 | 本项目 | jcode |
| --- | --- | --- |
| 缓存放置 | `tui-render/prep_cache.rs`（`PreparedScrollback` + `RowCache` + `AuxLineMap` + `OversizeCache`） | `jcode-tui:ui.rs/ui_prepare.rs`（消息级 `BodyCacheKey` + 整帧 `FullPrepCacheKey`） |
| 缓存键 | `ScrollPrepKey/HeaderPrepKey/BodyPrepKey`（width、version、hidden） | 键含 width/height/diff_mode/messages_version/diagram_mode/centered/图像签名/展开版本等 |
| 增量路径 | `sync_append/sync_prepend/sync_trim/sync_body_edit`，header 与 body 分离 | `prepare_body_incremental`（追加）/`prepare_body_prepended`（前插）/后缀复用，基于消息边界 |
| 容量控制 | 24 MiB 预算、RowCache 512、AuxMap 2048、Oversize 2 | Body 8 项/32 MiB、Full 4 项/24 MiB、各自 Oversized 2 |
| 行复用粒度 | 以 `HistoryLine::identity()` 为键，宽度变化整体清空 | 以消息 hash 为边界，支持"仅改尾部/仅改头部 + 索引平移" |

小结：两侧都已做到"稳态只处理新增/变化部分"，本项目按 scrollback 行身份缓存，jcode 按消息边界做更通用的前缀/后缀复用。差异主要在复用粒度与键的丰富度（jcode 的键把图像/图表/展开态纳入失效）。若后续引入图表/图像/展开折叠，可以借鉴其"把一切影响几何的输入都编入键"的做法。

### 1.4 视口与滚动

- 本项目：`view_scroll` + `top_for_tail`，追加时直接落到底部；只有"是否暂停自动滚动"（`auto_scroll_paused`），无追赶动画。
- jcode：`resolve_tail_follow_scroll` 在大量追加时按"每帧最多 3 行、滞后不超过一个视口"滑动追赶（`TAIL_CATCHUP_MIN_JUMP=4/MAX_STEP=3`），并对显式导航提供瞬时贴底；附带 `anchor_stability` 可观测层，把重定位/上方插入/大跳/闪烁/整体重排分类统计。

可借鉴：流式大段输出（代码块、工具输出）时引入"滑动追赶"，避免一次性跳变；并把锚点稳定性做成只读观测量用于回归。

### 1.5 流式缓速

- 本项目：`tui-core/stream_pacer.rs`，参数与 jcode 基本一致（180 cps 基准、积压增益 3.0、960 cps 上限、单帧步长 50ms），并有 `SegmentedPacer` 保证文本/推理段按到达顺序释放。
- jcode：`stream_buffer.rs` 采用"比例预算 + 墙钟令牌桶"双预算（`carry` 与 `ceiling_carry`），相邻同类分块合并，并带抖动记录器（100ms 桶的字符数变异系数）。

小结：机制等价，本项目缺少的是"墙钟令牌桶"这层的显式表达与"抖动度量"。可借鉴其抖动指标用于验证平滑度。

## 二、内容准备与 Markdown

| 维度 | 本项目 | jcode |
| --- | --- | --- |
| 解析后端 | pulldown-cmark 0.13 | pulldown-cmark 0.12 |
| 方言 | 表格、任务列表、删除线 | 追加数学、脚注、定义列表、GFM、智能标点 |
| 中立模型 | `document.rs`（StyleRole/FillRole/TextAttrs/StyledSpan/Document） | `jcode-render-core`（model/preprocess/wrap/reasoning/math） |
| 流式 | 已提交/流式边界 + 节流解析 + 尾部增量（`cached_safe_len`） | `IncrementalMarkdownRenderer` 名为增量，实际只有"文本相同"快路径，否则整段重渲染 |
| 语法高亮 | 无（代码块单色，`code_lang` 预留未用） | syntect 5（含 256 项高亮缓存、按行高亮） |
| 数学 | 模型层已留 `latex` 字段，但方言未启用、无渲染分支 | Unicode LaTeX 渲染器（无依赖递归下降），可选外部 TeX → 图像 |
| 离屏懒渲染 | 无 | `render_markdown_lazy`（不可见代码块跳过高亮） |
| 图表 | 无（`deferred.rs` 仅有占位注册，无后端） | mermaid → resvg 栅格 + Kitty/iTerm2/Sixel |
| 换行映射 | `tui-components/transcript.rs` 逐字形换行，无行映射 | `WrappedLineMap`（包裹行 ↔ 源列区间）支撑选择/复制 |

小结：本项目的流式切分与增量解析比 jcode 更"真"（jcode 的"增量"实为全量重渲染），这是可保持的优势。差距集中在**表现力**：语法高亮、数学、图表/图像、离屏懒渲染与包裹行映射。

可借鉴顺序：语法高亮（收益/成本比最高）→ 方言扩展 + Unicode 数学（本项目模型已就绪）→ 离屏懒渲染 → 包裹行映射 → 图表/图像（工程量大，按产品需要）。

## 三、样式 / 主题 / 动效

| 维度 | 本项目 | jcode |
| --- | --- | --- |
| 颜色模型 | 真彩优先，`ColorDomain` 降级到 256/16 色 | 真彩/256 双档 + fragile glyph cache 降级 |
| 调色板 | 角色化 `Theme` + `ThemeOverrides` + 字面色→角色映射（`theme/literal.rs`） | 22 个语义角色 + 用户覆盖 + **逐帧缓冲级调色板重映射** |
| 明暗适配 | 缓冲级一次（`theme_mode.rs`，HSV 明度翻转，`Color::Reset` 透传） | 缓冲级一次（HSL 明度翻转），且强制"先主题后调色板"顺序 |
| 感知配色 | `derive_theme`（BT.601 亮度 + 对比度选主色） | OKLab `harmony`：7 项评分（可读性/区分度/色相和谐/彩度一致性/色盲安全）+ 从种子色生成整套调色板 |
| 动效核 | `anim_core.rs`（256 项角度查找表）+ `motion.rs`（定长 shimmer span）；`tui-style` 有 opt-level=3 override | 独立 `jcode-tui-anim`（3D 采样、字形选择、LUT，`opt-level=3`） |
| 动效时钟 | 统一走 `tui-clock`，全部 `*_at(now_ms)` 变体 | 经 `TuiState::animation_elapsed()/now_millis()` 注入，测试可替换 |

小结：明暗适配与动画纯核的思路已经对齐（且本项目动画时钟注入更彻底）。差距在于：
1. 调色板重映射目前是空实现（`post_process.rs:adapt_buffer_for_palette`），意味着绕过角色、直接写字面颜色的组件无法被用户调色板统一覆盖；jcode 用缓冲级"最近角色吸附 + 相对明度/彩度偏移重表达"解决。
2. 缺少感知层的调色板评估/生成（对比度、区分度、色盲安全、和谐方案）。当提供用户自定义主题时需要，否则容易出现"能设置但不可读"的配色。

可借鉴：先补缓冲级调色板重映射（复用已有 `theme/literal.rs` 的最近角色逻辑，把调用点从 per-style 迁到 per-frame）；再视需要引入 OKLab 评分作为主题校验（先用分析报告，不一定要自动生成）。

## 四、终端能力与图像

- 本项目：`tui-terminal` 探测 kitty 键盘、括号粘贴、焦点事件、色彩深度、OSC52、OSC10/11 默认色，终端类型识别覆盖主流模拟器。
- jcode：额外有 Kitty/iTerm2/Sixel 图像协议探测与输出（Sixel 经 ImageMagick），tmux DCS 透传。
- 共通缺陷（本项目）：`synchronized_output` 字段虽已探测槽位，但没有任何探测把它置真，导致 `should_sync_output` 恒假、同步输出分支实际不可达（与设计意图不符）。

可借鉴：接通同步输出（探测 + 仅对整帧/底部帧启用，动画帧不包），避免流式撕裂；终端图像协议仅在需要内联图/图表时再引入。

## 五、观测与测试

| 能力 | 本项目 | jcode |
| --- | --- | --- |
| 帧度量 | `frame_metrics.rs`（changed_cells、diff_bytes、elapsed、laid_out_rows、parsed_bytes）+ `tui-debug` diff 录制 | prep/body 命中率、阶段耗时、资源归因、每秒绘制数、慢帧 |
| 闪烁/卡顿 | 无 | 闪烁历史、key-to-paint 延迟、draw-call 归因 |
| 平滑度 | 无 | 锚点稳定性记录 + 报告（重定位/上方插入/大跳/闪烁/整体重排） |
| 离线回归 | 无头渲染与 reducer 等价测试、事件录制/回放、故障证据封存 | 回放时间覆盖、截图、glyph 安全性测试 |

小结：本项目的度量已能支撑"缓存是否省了重排/解析"这类回归，但缺少"用户可感知"的度量（闪烁、键到绘制延迟、滚动抖动）。引入 jcode 的闪烁/键到绘制/锚点稳定性三类观测，可把"体感回归"变成可断言项。

## 六、可借鉴清单（按优先级）

1. **修正局部重绘**：自持上一帧缓冲，动画/单格帧以种子 + 局部覆盖呈现；未完成前把 `AnimationOnly` 退化为整帧。这是正确性问题，最高优先。
2. **接通同步输出**：补齐能力探测，整帧/底部帧包 `Begin/EndSynchronizedUpdate`，动画帧不包。
3. **语法高亮**：引入 syntect（或轻量高亮）+ 有限容量缓存；配合"离屏代码块跳过高亮"的懒渲染。
4. **Markdown 方言与数学**：启用数学/脚注/定义列表，落地 Unicode LaTeX 渲染（模型层 `latex` 字段已就绪）。
5. **流式追赶**：追加超过一屏时按"每帧有限步 + 滞后上限"滑动到尾部。
6. **缓冲级调色板重映射**：把字面色按最近角色吸附并相对重表达，纳入 `finish_frame` 固定顺序。
7. **主题感知校验**：以 OKLab 计算对比度/区分度/色盲安全，作为配置校验与告警，而非强制自动生成。
8. **感知侧度量**：闪烁检测、键到绘制延迟、锚点稳定性分类，纳入 CI 预算。
9. **软重绘失效**：区分"真实脱同步需硬清屏"与"滚动重绘用哨兵失效"，避免中间清屏造成闪烁。
10. **图表/图像/包裹行映射**：按产品需要引入 mermaid/终端图像与 `WrappedLineMap` 式选择/复制映射。

## 七、本项目无需借鉴或领先之处

- 可注入测试时钟：jcode 全靠 `Instant::now()`，本项目 `tui-clock` 可确定性回放。
- Markdown 流式：本项目的已提交/流式边界 + 尾部增量解析是真实增量；jcode 的"Incremental"实为全量重渲染。
- 重绘判定：`decide_scope` 是纯函数，边界清晰、可单测；jcode 依赖大量运行期状态分支。
- 准备缓存职责划分：本项目 header/body 分离 + 行身份缓存 + 溢出降级，结构清晰；jcode 为进程级全局缓存，耦合更多运行期状态。

## 八、落地注意

- 保持既有分层与文件扁平命名、英文注释、无 `mod.rs`、不使用 `unwrap`。
- 局部重绘的改造应封装为单一提交边界（类似 `FrameTransport`），整帧路径与现在逐字节一致，避免快照回归。
- 引入高亮/数学/图表时，缓存键需把新增签名的输入纳入（对齐 jcode 的做法），否则会埋下"改了不刷新"的隐患。
